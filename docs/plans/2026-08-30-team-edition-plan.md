# ShuyoNote 团队版（自建协作，不接外部通讯 App）实现方案

> 目标：把 ShuyoNote 从「**单用户 · 多设备 · 本地优先**」演进为「**可自建的团队知识库**」——**不接入微信 / 企业微信 / 钉钉**，账号、通知、讨论、采集全部自建。核心是**两根柱子：多用户（账号/认证）与权限模型**；**实时协同编辑后置（P2）**。服务端设计以 **shuyonote-sync-server 仓库（私有，商业授权）** 为准，已实现到 S5。
> 关联：[多工作空间](2026-08-22-multi-workspace-plan.md)（空间隔离）、[每空间独立存储](2026-08-22-per-workspace-storage-plan.md)（M15）、[跨平台](2026-08-24-cross-platform-plan.md)（客户端形态）。服务端团队版设计见 sync-server 仓库 `docs/team-edition-*.md`。

> ⚠️ **定位说明**：这是**架构演进提议**。服务端（sync-server）已实现 S1–S5（认证 / 空间 / 成员 / 同步隔离）；本仓库聚焦**客户端侧**。现有个人版「无账号、本地优先」用法完全保留，团队能力是「可选开启」的增量。

---

## 1. 背景与动机

### 1.1 为什么「全自建」而不是接外部通讯 App

| 外部 IM 的痛点 | 全自建的对应收益 |
|---|---|
| 企微消息回调不含员工私聊，全量要靠付费「会话存档」 | 自建讨论/评论天然落库、实时、全量、可检索、可喂 AI |
| 身份/组织/触达依赖第三方平台，被规则与收费绑架 | 自建账号/空间/通知，数据与命运自持 |
| 个人微信无官方 API，灰色协议违规 | 无合规风险 |
| AGPL 下引入第三方 SDK 开源边界复杂 | 自建链路边界干净 |

### 1.2 团队版要解决的问题

- **多用户**：一个团队多人同时用，各自有账号、登录态、身份。
- **权限**：谁能看哪个空间，谁能改。
- **触达**：@ 提及、评论能通知到人。
- **采集与沉淀**：团队内容进得来，讨论存得住、查得到、喂给 AI。
- **（后置）协同**：多人同页实时编辑——**成本极高，P2 后置**，先做「共享 + 权限 + 评论」。

## 2. 现状盘点（代码已核实）

| 能力域 | 现状 | 团队版目标 | 缺口定性 |
|---|---|---|---|
| **身份/账号** | 无账号、无登录；sync-server 仅单一共享 token | 多用户 + 会话令牌 + Bearer | 🔨 sync-server 已做（S3） |
| **空间/成员** | 多工作空间 = 本机个人隔离 | 组织空间 + 成员 + 角色 | 🔨 sync-server 已做（S4） |
| **权限** | 无 `role/permission` 概念 | 空间级角色 + `require_space` | 🔨 sync-server 已做（S4/S5） |
| **审计** | 版本历史有，但无「谁改的」 | 操作审计 | 🧩 sync-server 已有 `audit_log` 表 |
| **协同编辑** | 页级 LWW、5 分钟轮询、同页覆盖 | 块级/实时 | ⏸ **后置（P2）** |
| **评论/@/通知** | 无 | 页面评论、@ 成员、通知中心 | 🔨 从零建（P1） |
| **采集入口** | 仅手动导入 | 网页剪藏、Email-in、REST API | 🔨 从零建（P2） |
| **移动端** | 未做 | 团队协作需移动端 | 🔨 从零建（P3） |

**一句话定性**：团队版 = 在「个人强大 + 可私有部署」之上补上**多用户、权限、审计、部署**这层组织能力；实时协同是「看起来该有、实际高成本低频」，后置。

## 3. 目标架构与仓库边界

```
┌─ 客户端 (桌面 Tauri / Web / 未来移动) ──────────────────────┐
│  现有编辑器 + 视图（不回归）                                  │
│  新增：登录态 · 空间绑定 · 成员/权限 UI · 评论/@ · 通知中心   │
└───────────────────────┬──────────────────────────────────────┘
                        │ HTTPS + Authorization: Bearer <token>
                        │ （个人空间 E2E；组织空间传输加密 + 服务端信任边界）
┌───────────────────────▼──────────────────────────────────────┐
│         sync-server（已有，S1–S5 已实现）                      │
│  认证 · 空间/成员/权限 · 同步隔离(space_id) · 审计             │
└───────────────────────┬──────────────────────────────────────┘
                        │
             SQLite（users / sessions / spaces
                    / space_members / audit_log / changes+space_id）
```

> **仓库边界（决策）**：团队版跨两个仓库——**客户端侧**（登录 UI、成员/权限 UI、评论/@/通知 UI、采集客户端）落地本仓库（AGPL-3.0）；**服务端侧**（认证、空间/成员/权限、同步隔离、审计、部署包）落地 **shuyonote-sync-server 仓库（商业授权）**，其设计见该仓库 `docs/team-edition-*.md`，**本仓库不重复维护服务端设计**。

**核心原则**：

1. **E2E 分空间**：个人空间保留客户端 E2E（零知识）；**组织空间放弃零知识**——传输加密 + 企业自托管信任边界，换取服务端协同/检索/AI。
2. **服务端只做协调**：延续 outbox 模型，服务端存变更日志 + 权限 + 元数据。
3. **个人版不回归**：单用户本地用法、E2E、备份能力不动；团队能力是可选增量。
4. **客户端零 SQL**：新增能力仍经 `platform.executor.invoke` 语义命令。

## 4. 能力自建清单（替代原先企微的角色）

| 原企微能力 | 全自建方案 | 承载 |
|---|---|---|
| 身份/SSO | 账号：邮箱 + 密码（argon2id）+ 会话令牌（Bearer） | sync-server（已做） |
| 组织架构 | 空间（space）+ 成员/角色（owner/admin/editor/viewer） | sync-server（已做） |
| 消息触达 | 站内通知中心 + 可选邮件/Webhook 外发 | 客户端 + 服务端（P1） |
| 内容采集 | 网页剪藏 / Email-in / REST API | 客户端 + 服务端（P2） |
| 会话归档 | 讨论/评论：天然落库、可检索、可喂 AI | 客户端 + 服务端（P1） |
| 团队协作 | 权限 + @ 提及 + 评论；**实时协同后置** | 两根柱子 + 后置 |

> 说明：「全自建」不等于自建完整 IM。团队知识库需要的「通信」是「通知 + 讨论 + @」，不是通用即时通讯（YAGNI）。

## 5. 两根柱子 + 后置项

### 5.1 账号 / 认证（柱子一，已实现）

- sync-server `auth.rs`：`/auth/register` `/auth/login` `/auth/logout`，argon2id 存密码，32B 随机 token 存 `sessions`（30 天），中间件解析 `Authorization: Bearer <token>`。
- 客户端侧（本仓库）：登录 UI + 存 token 到 `sync_state` + 所有同步请求带 Bearer 头。

### 5.2 权限模型（柱子二，已实现）

- 角色：`viewer / editor / admin / owner`（`ROLE_RANK` 优先级比较）。
- 主体：成员（挂在 space 上，`space_members`）。
- 客体：**空间**（space 即顶层组织单元，MVP 空间级权限；页面/文件夹级 ACL 为 P2 可选）。
- 校验：`require_space(user, space, min_role)` —— 读需 `viewer`、写需 `editor`、管理需 `owner/admin`。
- **红线**：权限遗漏一处 = 越权泄露，必须双账号 + 两空间交叉验证（sync-server S5 已做）。

### 5.3 E2E（✅ 决策 A：组织空间放弃零知识，个人空间保留 E2E）

- **决策：组织空间放弃零知识**——组织空间用「传输加密（TLS）+ 企业自托管信任边界」，服务端可见明文；**个人空间保留客户端 E2E（零知识）**。
- 换取的能力：**块级协同合并、团队内容服务端全文检索、AI 归档/知识库分析**（服务端需明文才能做）。
- ⚠️ 与 sync-server 现有红线「端到端加密必须守住」**冲突**：sync-server 当前实现是客户端加密、服务端只见密文；本决策要求**组织空间**改为服务端可见明文，需同步修订 sync-server 的组织空间加密路径（组织空间 / 个人空间分两条路）。

### 5.4 实时协同（后置 P2）

- 页级 LWW + 5 分钟轮询对「多人共享查看 + 少量编辑」够用；真正的块级/实时协同（CRDT/WebSocket）**成本极高、非团队购买点核心**，后置。
- 后置期间用「共享 + 权限 + 评论 + @」替代协作诉求。
- 注：组织空间放弃零知识（§5.3）已移除「服务端合并明文」的障碍，但协同仍后置——**成本/优先级独立于 E2E**，需时再评估块级 LWW → CRDT。

## 6. 数据模型（对齐 sync-server，已实现）

```sql
users(id, email UNIQUE, display, password /*argon2id*/, role, created_at, disabled_at)
sessions(token PRIMARY KEY, user_id, created_at, expires_at)
spaces(id, name, owner_id, created_at)
space_members(space_id, user_id, role DEFAULT 'editor', PRIMARY KEY(space_id,user_id))
audit_log(id, space_id, user_id, action, entity, entity_id, detail, at)
-- 现有 changes 加列 space_id + 组合索引 (space_id, seq)
```

> 说明：**空间（space）即顶层组织单元**，成员直接挂 space（`space_members`），**无租户/组/邀请表**（邀请 = 按 email 加 member）。早期头脑风暴的「tenants / groups / invitations」模型已**弃用**，对齐 sync-server 现有实现。

## 8. 测试与验收标准

- [ ] 客户端登录后，所有同步请求带 `Bearer`；token 过期/吊销后正确 401 并登出。
- [ ] 成员只能看到被授权空间；越权写（viewer push）被拒 403；双账号 + 两空间交叉验证无泄漏。
- [ ] 个人版存量数据（个人空间 + E2E + 备份/导出）**零回归**。
- [ ] 评论/@ 能触达目标用户；通知中心未读/已读正确。
- [ ] 审计日志完整记录「谁、何时、对什么、做了什么」。

## 9. 风险与取舍

- **E2E 分空间是取舍**：个人空间守零知识；组织空间放弃零知识（服务端见明文）——换取协同/检索/AI，代价是团队数据信任边界移到服务端（私有化部署下可接受）。
- **权限是安全底线**：越权泄漏是最高危，靠交叉验证 + 集成测试兜底。
- **协同后置的代价**：多人同页编辑会覆盖（页级 LWW），接受「共享 + 权限 + 评论」替代，直到 P2 再评估块级/CRDT。
- **自建账号的安全负担**：密码哈希（argon2id，sync-server 已做）、防爆破、找回流程是长期责任；TOTP 2FA / 防爆破 / 组 列为**可选增强**，后续按需提给 sync-server。
- **通知触达率不如 IM**：站内通知依赖打开客户端，用邮件/Webhook 补偿。

## 10. 决策记录（已拍板）

1. **部署形态**：✅ 私有化部署（企业自托管）为默认；SaaS 后置。
2. **E2E**：✅ **组织空间放弃零知识**（传输加密 + 服务端信任边界），**个人空间保留 E2E**（即「决策 A」，撤回上一轮「零知识守住」）。
3. **协同**：✅ **后置 P2**——先共享 + 权限 + 评论；实时协同单独评估（撤回早期「协同 P0」）。
4. **站内实时聊天**：✅ 本期不做（YAGNI）。

## 11. 结论

ShuyoNote 团队版「全自建、不接外部通讯 App」的**服务端已实现到 S5**（认证/空间/成员/同步隔离），设计以 sync-server 仓库为准；本仓库剩余工作聚焦**客户端侧**（登录 + Bearer + 空间绑定 + 成员 UI + 评论/通知）。两根柱子是**账号/认证**与**权限**；**实时协同后置 P2**，E2E **组织空间放弃零知识（决策 A）、个人空间保留 E2E**——需同步修订 sync-server 组织空间的加密路径。

配套取舍见[设计哲学](../design-philosophy.md)（本地优先 + 数据可移植）。
