# ShuyoNote 团队版（自建协作，不接外部通讯 App）实现方案

> 目标：把 ShuyoNote 从「**单用户 · 多设备 · 本地优先**」演进为「**可自建的团队知识库**」——**不接入微信 / 企业微信 / 钉钉等任何外部通讯 App**，账号、通知、讨论、采集、协作全部自建。核心是补齐三根柱子：**多用户（账号/租户）、权限模型、协同编辑**，其余能力围绕这三根柱子做。
> 关联方案：[本地优先方案](plans/2026-08-15-local-first-note-app-plan.md)（数据层）、[多工作空间](plans/2026-08-22-multi-workspace-plan.md)（空间隔离）、[每空间独立存储](plans/2026-08-22-per-workspace-storage-plan.md)（存储布局）、[跨平台](plans/2026-08-24-cross-platform-plan.md)（客户端形态）。由头脑风暴「企业微信 + ShuyoNote」收敛而来，结论为**弃用外部 IM，全自建**。

> ⚠️ **本方案定位说明**：这是**架构演进提议**，尚未进入实现。文中「里程碑 M1–M9」为规划，`docs/README.md` / `roadmap.md` 按「规划（待里程碑落地）」登记，**未标记 ✅**。现有 app 继续以单用户本地形态正常运行，个人版能力不回归。

---

## 1. 背景与动机

### 1.1 为什么「全自建」而不是接外部通讯 App

头脑风暴阶段评估了微信 / 企业微信 / 钉钉三类接入，结论是**放弃外部依赖**，理由：

| 外部 IM 的痛点 | 全自建的对应收益 |
|---|---|
| 企微消息回调**不含员工私聊**，全量要靠「会话存档」（认证+付费+员工知情同意+约 5 分钟延迟） | 自建讨论/评论天然落库，**实时、全量、可检索、可 AI 分析**，无需付费 |
| 身份/组织/触达依赖第三方平台，被平台规则和收费绑架 | 自建账号/租户/通知，**数据与命运自持**，契合「本地优先 + 可自建」定位 |
| 个人微信无官方 API，灰色协议违规 | 无合规风险 |
| 「服务端零知识」与「企微接入」冲突（桥接端要持密钥） | 自建后边界清晰，加密取舍由自己拍板 |
| AGPL 下引入第三方 SDK/服务，开源边界复杂 | 自建链路可整体 AGPL 开源，边界干净 |

### 1.2 团队版要解决的问题

个人版现在是「单用户、无账号、无权限、无实时协同」。团队版要补的是：

- **多用户**：一个团队多人同时用，各自有账号、登录态、身份。
- **权限**：谁能看哪个空间/页面，谁能改。
- **协同**：多人编辑同一页不互相覆盖，接近实时。
- **触达**：@ 提及、评论、待办提醒能通知到人。
- **采集与沉淀**：团队内容能进得来（网页/邮件/API），讨论能存得住、查得到、喂给 AI。

## 2. 现状盘点（代码已核实）

基于 `src-tauri/src/` 全量 grep + `docs/architecture.md`，现状与团队版目标的差距：

| 能力域 | 现状（已核实） | 团队版目标 | 缺口定性 |
|---|---|---|---|
| **身份/账号** | 无账号、无登录；sync-server 仅**单一共享 token**（`sync.rs` 的 `KEY_TOKEN`，`bearer_auth`） | 多用户账号 + 登录态 + 2FA | 🔨 从零建 |
| **租户/组织** | 多工作空间 = 本机个人物理隔离（`meta.db` + `spaces/<id>.db`） | 一团队 = 一租户，成员/组 | 🔨 从零建 |
| **权限** | 无 `role/permission/owner` 任何概念（grep 全无） | 空间/页面/角色/按成员授权 | 🔨 从零建 |
| **协同编辑** | 页级 LWW + 5 分钟轮询，**同页并发覆盖**（`architecture.md` §9 ADR 明写） | 块级/实时，不丢冲突 | 🧩 改同步内核 |
| **评论/@/通知** | 无 | 页面评论、@ 成员、通知中心 | 🔨 从零建 |
| **审计** | 版本历史已留快照（每页 50 份），但无「谁改的」 | 操作审计、版本关联用户 | 🧩 改造 |
| **采集入口** | 仅手动导入/粘贴 | 网页剪藏、Email-in、REST API | 🔨 从零建 |
| **部署/计费** | sync-server 单实例、单 token、无计费 | 多租户隔离、席位、用量 | 🔨 从零建 |
| **移动端** | 未做（README 路线图已标） | 团队协作需移动端 | 🔨 从零建 |

**一句话定性**：ShuyoNote 现在的架构是「**单用户、多设备、本地优先**」，团队版要补的三根柱子——**多用户、权限、协同**——全部是现有代码里没有的东西；企微能帮的「身份/组织/触达」现在也要自建，但自建后边界更干净。

## 3. 目标架构

把现有「sync-server（独立商业授权，Axum + SQLite）」**演进为自建团队服务端**，客户端保持桌面 + Web（未来移动）。分层如下：

```
┌─ 客户端 (桌面 Tauri / Web / 未来移动) ──────────────────────┐
│  现有编辑器 + 视图（不回归）                                   │
│  新增：登录态 · 权限感知 UI · 实时协同编辑 · 评论/@ · 通知中心  │
└───────────────────────┬──────────────────────────────────────┘
                        │ HTTPS + 块级同步协议（原「页级 LWW」升级）
                        │ + WebSocket（实时推送，替代 5 分钟轮询）
┌───────────────────────▼──────────────────────────────────────┐
│              自建团队服务端（sync-server 演进）                  │
│  账号/认证 · 租户 · 权限 · 块级同步 · 实时(WS)                 │
│  通知 · 审计 · 讨论/评论 · 采集入口(Email-in / REST API)        │
└───────────────────────┬──────────────────────────────────────┘
                        │
             SQLite（users / tenants / memberships / acl
                    / comments / audit / 块级变更日志）
```

**核心原则**：

1. **服务端只做「协调」不做「真相」**：内容仍以客户端为事实源（本地优先），服务端存变更日志 + 权限 + 元数据，延续现有 outbox 模型。
2. **自建替代企微的每一项能力**，对应关系见 §4，全部走自建、可整体开源、可私有化部署。
3. **个人版不回归**：单用户本地用法、E2E 加密、导出/备份能力保持不动；团队能力是「可选开启」的增量。
4. **客户端零 SQL 不变**：新增能力仍经 `platform.executor.invoke` 语义命令，前端不直接碰 SQL。

## 4. 能力自建清单（替代原先企微的角色）

| 原企微能力 | 全自建方案 | 承载位置 |
|---|---|---|
| 身份/SSO（扫码登录） | 账号体系：邮箱/用户名 + 密码 + **TOTP 2FA**（可选 Passkey） | 团队服务端 |
| 组织架构（通讯录） | 租户 + 成员 + **组**（自建部门等价物）+ 邀请/移除 | 团队服务端 |
| 消息触达 | **站内通知中心** + 可选外发：邮件 / 桌面推送 / **Webhook**（自建，非第三方 IM） | 客户端 + 服务端 |
| 内容采集 | 网页剪藏扩展 / **Email-in** / REST API / 未来移动端分享 | 客户端 + 服务端 |
| 会话归档 | **讨论/评论**：天然落库、实时、全量、可检索、可喂 AI（无需付费存档） | 客户端 + 服务端 |
| 团队协作 | 块级协同编辑 + 权限 + @ 提及（本就自建） | 三根柱子 |

> 说明：**「全自建」不等于自建一个完整 IM/聊天 App**。团队知识库需要的「通信」是「通知 + 讨论 + @」，不是通用即时通讯。若未来确需实时团队聊天，再单独评估——YAGNI，本期不做。

## 5. 三大硬骨头（逐项拆解）

### 5.1 协同编辑（最深，架构级）

- **现状**：outbox 变更粒度 = 页面（页级 LWW），5 分钟轮询，同页并发互相覆盖。
- **目标**：粒度降到**块级**，接近实时，冲突不静默丢数据。
- **路径**：
  - **块级 LWW**（最小改动）：outbox 变更从「页」降到「块」，服务端按块 `updated_at` 合并。仍会「同块并发覆盖」，但覆盖面缩小到单块。
  - **块级 CRDT**（Yjs/Automerge 思路，终局）：不丢冲突，但要改造 Lexical 节点↔块映射 + 变更编码 + 合并算法，触及编辑器/同步协议/schema 三层。
- **建议**：**先块级 LWW 跑通链路，再评估 CRDT**。这是整个团队版最大的坑，**必须先做 PoC 技术验证**，不能留到最后。

### 5.2 权限模型（从零到一）

- 角色：`owner / admin / editor / viewer`（commenter 可后置）。
- 主体：成员 / **组**（自建，承载「部门」语义）。
- 客体：空间 / 页面树 / 文件夹 / 单页。
- 继承：空间 → 页面树 → 子页，默认向下继承，子项可覆盖。
- 落地三层：**服务端鉴权**（每次变更校验）+ **同步下发过滤**（无权限的内容不下发）+ **客户端 UI**（隐藏/禁用无权限操作）。
- **红线**：权限遗漏一处 = 越权泄露，是团队版的安全底线，测试必须覆盖越权用例。

### 5.3 E2E 加密 vs 团队协作（产品级取舍，✅ 已拍板：选 A）

- **现状**：E2E 是「个人口令、每空间一密钥、锁定拒同步」（`security.rs` / `crypto.rs`）。
- **冲突**：团队共享空间时，服务端若拿不到明文，就做不了块级协同、服务端检索、AI 分析（明文只有客户端有）。
- **三条路**：
  - **A. 团队空间用「传输加密 + 企业自托管信任边界」，个人空间保留 E2E**（推荐默认）：私有化部署下服务端在信任边界内，可接受。
  - **B. 团队共享密钥（key-sharing）**：成员间分发空间密钥，仍零知识，但密钥分发/轮换/撤权复杂，且协同仍需客户端协作，服务端检索/AI 分析做不了。
  - **C. 坚持全量 E2E 零知识**：牺牲协同与 AI 分析，团队版价值大打折扣。
- **✅ 已拍板（决策 A）**：团队空间用「传输加密 + 企业自托管信任边界」，个人空间保留 E2E；B（共享密钥）列为远期可选，C（全量零知识）不做。

## 6. 数据模型与存储改造

### 6.1 团队服务端新增表（服务端 SQLite）

```sql
users(id, email, username, password_hash, totp_secret, created_at)
tenants(id, name, created_at)                       -- 团队 = 租户
memberships(tenant_id, user_id, role)               -- owner/admin/member
invitations(id, tenant_id, email, role, token, expires_at)
groups(id, tenant_id, name)                          -- 组（部门等价物）
group_members(group_id, user_id)
acl(tenant_id, subject_type, subject_id,             -- subject: user/group
    object_type, object_id, role)                    -- object: space/page/folder
comments(id, page_id, block_id, user_id, body, created_at)
notifications(id, user_id, type, payload, read_at)
audit_log(id, tenant_id, user_id, action, object, at)
-- 变更日志升级：outbox 增加 user_id + block 粒度
changes(... , user_id, entity_type, entity_id)       -- entity_type: page/block/…
```

### 6.2 客户端改动

- `meta.db` 增加本地登录态（token / 当前用户 / 当前租户），不存明文口令。
- 空间（workspace）增加「**本地个人空间** vs **团队共享空间**」区分：团队空间 = 服务端租户下发的空间，本地空间保持现状。
- 前端新增 Zustand：`auth`（登录态）、`members`（成员/组）、`comments`、`notifications`、`presence`（在线状态）。

### 6.3 迁移策略

- 现有单用户数据全部视为「**个人空间**」，不迁移、不回填，零风险。
- 团队能力是「新建团队空间」时才启用，不影响存量个人库。

## 7. 实施顺序（里程碑）

> 依赖驱动：先「身份/租户」地基，再「权限」「协同」，其余按需。每个里程碑独立可验证、可上线。

| 里程碑 | 内容 | 验收要点 | 优先级 |
|---|---|---|---|
| **M27.1 账号 + 租户** | 自建账号注册/登录/登出、TOTP 2FA、会话令牌、团队创建、邀请/移除成员、组 | 多用户登录隔离；邀请流程闭环；旧个人数据不受影响 | P0 |
| **M27.2 权限模型** | 角色 + ACL + 继承；服务端鉴权 + 下发过滤 + 前端 UI 三层 | 越权访问被拒；无权限内容不下发；UI 正确隐藏 | P0 |
| **M27.3 块级同步（协同 PoC）** | outbox 粒度页→块；服务端块级 LWW；冲突不静默丢 | 两人同页编辑不整页覆盖；块级合并正确 | P0 |
| **M27.4 实时推送** | WebSocket/SSE 替代 5 分钟轮询；在线状态 presence | 变更秒级触达；断线重连不丢 | P1 |
| **M27.5 评论/@/通知** | 页面/块评论、@ 成员、站内通知中心 + 邮件/Webhook 外发 | @ 触达；通知未读/已读；外发可选 | P1 |
| **M27.6 审计** | 变更日志加 user_id；操作审计查询；版本关联用户 | 「谁在何时改了什么」可追溯 | P1 |
| **M27.7 采集入口** | Email-in（IMAP 轮询）+ 网页剪藏 + REST API | 邮件/网页内容进指定团队空间 | P2 |
| **M27.8 部署/计费** | 多租户隔离、席位/用量统计、服务端商业化授权 | 多团队互不越权；用量可统计 | P2 |
| **M27.9 移动端** | 移动端壳（复用 M16 driver，Web 响应式兜底 → 原生） | 手机上可看/写/收通知 | P3 |

> **关键提醒**：M27.3（协同）和 M27.2（权限）才是团队版真正的工程量所在，M27.1 是地基。不要被「采集/通知」这类外围能力带偏节奏——**先定 M27.1–M27.3 三根柱子，外围能力随时能加**。

## 8. 测试与验收标准

- [ ] 多用户同页并发编辑，块级合并不丢数据、不整页覆盖（M27.3 核心）。
- [ ] 越权访问被服务端拒绝；无权限内容不下发、UI 不显示（M27.2 核心）。
- [ ] 账号注册/登录/2FA/邀请/移除成员全流程闭环；会话令牌过期/失效正确。
- [ ] 个人版存量数据（本地空间 + E2E + 备份/导出）**零回归**。
- [ ] @ 提及、评论能触达目标用户；通知中心未读/已读正确；邮件/Webhook 外发可选。
- [ ] 审计日志完整记录「谁、何时、对什么、做了什么」。
- [ ] Email-in / 剪藏 / API 采集内容正确落到指定团队空间。
- [ ] 多租户间数据与权限严格隔离，无跨租户泄漏。

## 9. 风险与取舍（诚实标注）

- **最大风险**：协同编辑（M27.3）触及编辑器 / 同步协议 / schema 三层，是纯成本、回报后置，**必须先 PoC 验证块级合并**，避免最后返工。
- **权限是安全底线**：任何一处鉴权遗漏即越权泄露，测试必须专门写越权用例。
- **E2E 取舍**：团队协同与「服务端零知识」二选一，需产品先拍板（§5.3），否则后续返工。
- **自建账号体系的安全负担**：密码哈希（Argon2id 已有原语可复用）、2FA、找回流程、防爆破/防撞库，都是长期安全责任，**不是写完就结束**。
- **通知触达率不如 IM**：没有「随时在线的 IM 入口」，站内通知依赖用户打开客户端，用邮件/Webhook/桌面推送补偿，接受触达率折损。
- **移动端工具链受限**：README 路线图已标「移动端未做」，M27.9 放最后，先用 Web 响应式兜底。
- **不做最优解**：协同先块级 LWW（可预测、易验收），CRDT 后置；团队空间加密先「传输加密 + 自托管信任边界」，不追求零知识。

---

## 10. 开放决策点（需拍板后落定）

1. **部署形态**：私有化部署（企业自托管）为默认假设；若要做 SaaS 云团队版，M27.8 需加计费/多租户强隔离。
2. **E2E 取舍**：✅ 已定 **A**（团队空间传输加密 + 自托管信任边界；个人空间保留 E2E）。
3. **协同终态**：块级 LWW 够用，还是目标 CRDT（建议先 LWW 跑通再评估）。
4. **是否要站内实时聊天**：本期不做（YAGNI），如需要另立方案。

---

## 11. 结论

ShuyoNote 团队版「全自建、不接外部通讯 App」是成立的：**把 sync-server 演进为自建团队服务端，补齐「账号/租户、权限、块级协同」三根柱子，用自建通知/讨论/采集替代企微的角色**，保持本地优先与可自建定位，边界比接企微更干净、更可控。最大工程量在**协同编辑（M27.3）**与**权限模型（M27.2）**，必须作为 P0 优先推进并先做 PoC；E2E 取舍已拍板（A）；剩余待拍板：协同终态（块级 LWW vs CRDT）与部署形态（私有化 vs SaaS）。

配套取舍见[设计哲学](../design-philosophy.md)（本地优先 + 数据可移植）与[架构](../architecture.md)。
