## 1. 两个前置条件（不确认就别开工）

### 1.1 国密：客户要哪一档？

**这是唯一决定工作量的问题。** 「用国密」在实践里有三个差别巨大的档位（详见 §3）：

- **档 1**：只要求**密钥管理**用国密（口令派生用 SM3 系）——3 人日量级；
- **档 2**：要求**外发数据**（附件、导出包、同步载荷）用国密加密——3–5 人日；
- **档 3**：要求**数据库静置密文**也是国密——2–4 周，且需要替换 SQLCipher 的加密层（§4.3）。

### 1.2 国密：是"用国密算法"还是"用**通过认证的**商用密码产品"？

这两句话的分量完全不同：

- 前者：自研实现 + 标准测试向量即可（本文方案覆盖的路径）；
- 后者：**自研实现不满足**。认证针对**产品/密码模块**，不是针对算法。此时应采购已认证的密码模块 SDK（或使用具备资质的国产密码库），工程路径完全不同。

> ⚠️ **这一条必须在写代码之前问清**，否则可能出现"按档 3 做了两周，客户要的其实是认证证书"的局面。
>
> ✅ **已确认（2026-09-16）：用国密算法**（不要求认证产品）⇒ 走 §3 路线 A / 落地方案 §3 路线 A，**不需要采购认证模块**。

### 1.3 PDFium：是"确定要做闭源商业授权版"吗？

- 只做 AGPL 分发 / 卖服务（实施、迁移、定制、支持） ⇒ **MuPDF 不用换**，工程省下 3–5 人日；
- 要交付闭源授权版 ⇒ 换 PDFium 或买 MuPDF 商业授权（后者是"花钱换时间"，适合项目马上签）。

## 2. 国密：现状（代码依据）

**加密面很小，且集中**——这是好消息：

| 位置 | 作用 | 依据 |
|---|---|---|
| `crypto.rs:40-46` | 口令 → 32 字节密钥（**Argon2id**） | `Argon2::default().hash_password_into(...)` |
| `crypto.rs:62-89` | 内容 AEAD（**XChaCha20-Poly1305**，`nonce(24)‖ct`） | 附件、导出包、同步载荷都走它 |
| `crypto.rs:49-53` | 16 字节随机 salt | `random_salt()` |
| `crypto.rs:57-59` | 32 字节密钥 → hex，供 SQLCipher 用 | `key_hex()` |
| `crypto.rs:13-19` | `sync_state` 里的 `encryption_enabled` / `_salt` / `_verify` / `_key` | 口令校验用 sentinel 密文 |
| `security.rs:126-128` | 空间库静置加密（**SQLCipher**，`PRAGMA key = "x'<hex>'"`） | `set_cipher_key()` |
| `security.rs:148-172` | 开/关加密的双向迁移 | 走 `sqlcipher_export('target')`（**不用**手动拷页） |
| `src/lib/vault.ts` | 会话锁定态（密钥不落盘） | —— |

**不在范围内（重要）**：

- **Web 版没有静置加密**：`src/lib/platform/web.ts:2916` 的 `encryption_status` 恒返回 `{enabled:false, locked:false}`，`set_encryption`/`lock`/`unlock`/`disable` 都是空实现（`web.ts:2917`），且 `web.ts:2007` 注释明确"blobStore 无 E1 加密"。⇒ **国密只需覆盖桌面端 + 导出/同步载荷**。
- **同步服务端**：载荷是客户端加解密后转发的（M2.2 起 push 加密 / pull 解密），服务端只需转发密文 ⇒ **无需改**。但服务端**自己的账号口令存储**是否也要国密，是**另一个仓库的范围**，需要单独确认。

## 3. 国密：三个档位

| | 档 1 · 密钥管理国密 | 档 2 · 外发数据国密 | 档 3 · 全链路国密 |
|---|---|---|---|
| **做法** | 口令 → **PBKDF2-HMAC-SM3** → 32B；密钥仍交给 SQLCipher 当 raw key | 档 1 + 附件/导出包/同步载荷改用 **SM4** 系列 AEAD | 档 2 + 空间库静置密文也换 SM4 |
| **数据库密文** | 仍是 SQLCipher 的 AES-256-CBC | 同左 | **必须换掉 SQLCipher 的加密层** |
| **改动面** | `crypto.rs::derive_key` ＋ 密文/密钥格式版本化 | 档 1 ＋ `encrypt`/`decrypt` ＋ 附件与导出路径 | 档 2 ＋ 自研/替换库级加密（最危险） |
| **能对外怎么说** | "**密钥派生**使用 SM3"（**不能说**"数据库用国密加密"） | "**外发数据**使用 SM4 加密" | "静置与外发均使用国密" |
| **估算** | **≈3 人日** | **≈3–5 人日** | **≈2–4 周**（含加密层自维护风险） |

> ⚠️ **SQLCipher 不支持 SM4**（它的 cipher 是 AES-256-CBC / ChaCha20）。档 3 不是"改个参数"，而是要替换库级加密实现——这也是为什么必须先把档位问清。

## 4. 国密：算法映射与五个坑

### 4.1 映射表

| 用途 | 现在 | 国密方案 | 备注 |
|---|---|---|---|
| 口令 KDF | Argon2id | **PBKDF2-HMAC-SM3**（GM/T 0004 的 SM3 作 PRF） | 国密**没有** Argon2 的对应物（无内存硬化）⇒ 迭代次数必须够（先定值并压测解锁耗时），口令强度策略要补 |
| 内容 AEAD | XChaCha20-Poly1305 | **SM4-GCM**（GM/T 0002 的 SM4 ＋ GCM），或 SM4-CBC ＋ HMAC-SM3（encrypt-then-MAC） | **nonce 从 24B 变 12B、tag 16B** ⇒ 密文格式必然变化（所以 §5.1 是前提） |
| 库级静置 | SQLCipher (AES-256-CBC) | 仅档 3 涉及 | 见 §4.3 |
| 更新包签名 | minisign (Ed25519) | 若要全链路：**SM2 签名**（GM/T 0003） | 只在客户明确要求"签名也要国密"时才做 |
| 传输层 | HTTPS（rustls/native-tls） | 若要全链路：**国密 TLS（GM/T 0024）** | 又是一整块；需先确认客户是否要求 |

### 4.2 坑一：附件内容寻址用的是 **SHA-256**，**不要换**

附件文件名就是内容 SHA-256（`src-tauri/src/attachments.rs:291-292`：「Content-addressed storage: filename = sha256 + ext inside a 2-char bucket dir」），邮件子部分同样按内容寻址（`email.rs:953-1006`），同步协议也以 hash 为标识。

**把 SHA-256 换成 SM3 = 所有附件改名 + 同步标识全变 + 需要全库重命名迁移。** 建议：**寻址继续用 SHA-256，只把"加密"这一层换成国密**；SHA-256 是公开摘要算法，通常不属于"密码合规"的审查重点。若客户明确要求"全链路含摘要算法"，这一条要单独立项讨论（成本与档 3 同级）。

### 4.3 坑二：SQLCipher 换不了 SM4（档 3 的真正难点）

SQLCipher 的 cipher 固定为 AES-256-CBC（部分构建带 ChaCha20），**没有 SM4**。档 3 的三条路：

1. **改 SQLCipher 源码加 SM4 cipher** —— 自己要维护一份加密库的实现，风险最高（密码实现的正确性维护是长期成本）；
2. **换支持国密的 SQLite 加密方案**（或应用层页级加密）—— 工程量大，且要重新验证 `sqlcipher_export` 那套迁移路径；
3. **只加密"密钥"而库仍由 SQLCipher 保护** —— 即**回落成档 1**，不满足"全链路"。

### 4.4 坑三：密文格式没有版本号（**必须先修，与档位无关**）

现在的密文是裸的 `nonce(24)‖ciphertext`（`crypto.rs:28,61`），**没有任何算法标识**。这意味着：一旦换算法，程序**无法判断一段密文是新算法还是旧算法**，也就无法"双读"。

**修法**：引入格式头（例如 `v1:` 前缀或 1 字节 magic ＋ 版本号），并让 `decrypt` 按版本分派。**这一条无论最终走哪档都要做**，也是唯一"现在做也绝不浪费"的改动。

### 4.5 坑四：`ENC_VERIFY` sentinel 的兼容

`crypto.rs:16` 的 `encryption_verify` 是一段用于**校验口令**的哨兵密文。换算法后旧哨兵解不开 ⇒ 必须支持"按版本用旧算法校验、随后用新算法重写"，否则老用户会在解锁这一步就被挡住。

### 4.6 坑五：自研 vs 复用国产密码库

| 选项 | 优点 | 代价 |
|---|---|---|
| **A. RustCrypto**（`sm3`/`sm4`/`sm2`）自组装 | 无新 C 依赖；纯 Rust 跨平台最省事 | SM4-GCM 是否有一等公民实现、是否经审计，需选型时核实；**"自研实现"在合规沟通里说服力最弱**；测试向量要自己钉 |
| **B. 复用国产密码库**（Tongsuo / GmSSL）＋ FFI | 合规说服力更强 | 引入 C 依赖；**但 Tongsuo 是 OpenSSL 分支**，与现有 vendored-openssl 构建链同源（见 `Cargo.toml:102-111`），风险可控 |
| **C. 采购已认证密码模块 SDK** | 唯一能满足"认证产品"要求的路 | 花钱、要集成、可能绑定平台 |

**建议**：若只是"用国密算法"，选 A 或 B；若客户要认证产品，直接走 C，别在 A/B 上花时间。

## 5. 国密：迁移与兼容（最危险的部分）

顺序不能颠倒：

1. **格式版本化**（§4.4）——必须先落地，单独一次改动、单独一次验收；
2. **双读**：`decrypt` 按版本分派，旧密文用旧算法；
3. **后台重写**（可中断、可恢复、有进度）：
   - 附件逐个重加密（`attachments/` 桶内文件）；
   - 导出包/备份 zip：新写的用新算法，旧的仍可读；
   - **空间库**：仅档 3 涉及，沿用 `sqlcipher_export` 那套双向迁移思路（`security.rs:148-172`），但跨 cipher 的导出需要先验证能否在一条连接里同时打开两种 cipher；
4. **回归 fixture**：用**当前版本生成的加密库/附件**做固定样本，断言"新版本仍能打开"——这是唯一能防"把老用户数据锁死"的手段；
5. **测试向量**：SM3 / SM4 必须用 **GM/T 标准测试向量**断言；再加一条**跨语言一致性**用例（Rust 加密 → 服务端/前端解密），防止两边实现漂移。

## 6. 国密：验收标准

- [ ] 新装用户：口令 → 加密 → 重启解锁 → 读写正常（桌面真机）
- [ ] **老用户回归**：用旧版生成的加密库与加密附件，新版能正常打开（fixture 钉住）
- [ ] 加密开关双向迁移（开→关、关→开）数据不丢
- [ ] 附件加密 + 导出包加密 + 同步载荷加密三条路径全覆盖（不漏一条）
- [ ] GM/T 标准测试向量通过；跨语言一致性通过
- [ ] 锁定态不读库（`vault.ts` 的既有约束不回退）
- [ ] 真机验收（桌面 + Android），不只看单测

## 7. PDFium：范围与步骤

**范围只有一件事**：把桌面端的光栅化从 MuPDF 换成 PDFium。依据是现状分层——

```ts
// src/components/PdfReader.tsx:122,136,651 —— 桌面：native 出页位图
if (attachmentId && platform.pdfRender.nativeAvailable()) {
  const { bytes, width, height } = await platform.pdfRender.renderPdfPage(...);
}
// 文本层 / 坐标 / 页数 / 目录 —— 全部来自 createPdfjsEngine()（pdf.js）
// src/lib/platform/web.ts:3605 —— Web：nativeAvailable() === false
```

⇒ **坐标语义不经 native 引擎**，所以换引擎**不需要两引擎坐标对拍**，`parseNativePageResponse`（`src/lib/pdfNativePage.ts:112`）与前端契约**一行不改**。

步骤：

1. **选型**：`pdfium-render`（动态加载 / `static` feature）或直接 FFI —— 需确认所钉 PDFium 版本的位图格式枚举与 API；
2. **库获取策略**：商用交付**建议自己构建**并固定版本与校验和（社区预编译包只作开发期便利）；
3. **Windows 先行**：`pdfium.dll` 随 Tauri bundle 分发，跑通渲染 + 打包；
4. **对拍**：同一批真实 PDF（含**扫描件、中文、旋转页、超大文件**）对比 MuPDF 与 PDFium 的渲染结果（容差内像素一致 / 目视）＋单页耗时；**不做对拍不算完成**；
5. **多平台打包**（独立任务，别混进同一次提交）：macOS bundle ＋ 公证、Linux rpath、Android `jniLibs`；
6. **灰度与回滚**：保留 MuPDF 路径一个发布周期（Cargo feature 或运行时开关），出问题一键切回。

**代码要点**：

- `fz_context` 那套「进程全局 init 一次 ＋ 渲染全程持锁」（`pdf_native.rs:38-52`）**可以 1:1 搬到 PDFium**（`FPDF_InitLibrary` 一次 ＋ `Mutex`）⇒ 两个最阴的坑（base context 反复重建、非线程安全）不会重踩；
- **位图通道顺序**：PDFium 常用档是 **BGRA/BGRx/GRAY**（按所钉版本核对枚举），**没有 RGBA** ⇒ 必须在 Rust 侧换成 RGBA，**保持前端契约不变**（与 `pdf_native.rs:233` `compact_rgba` 同一条原则：差异在本侧消化）；
- **stride 反而更简单**：PDFium 的位图缓冲由调用方分配 ⇒ **行对齐填充问题消失**，`compact_rgba` 可退化为"无需处理"。
