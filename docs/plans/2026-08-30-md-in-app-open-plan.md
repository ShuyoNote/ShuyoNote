# 「文件夹内 MD 文档直接应用内打开」利弊分析

> 目标：评估在**文件管理器（文件夹 = 网盘）里点击 `.md` 文件**，能否且在**应用内**直接打开（内嵌渲染/预览），而非跳外部应用。属于 [文件夹 = 网盘](2026-08-22-folder-netdisk-plan.md) 的在线预览子项，落脚在「文档类文件在 app 内闭环查看」。
> **状态**：利/弊分析 + 建议。未实装。
> 关联：[文件夹=网盘](2026-08-22-folder-netdisk-plan.md) / [设计哲学](../design-philosophy.md)（文件是一等公民）/ [Markdown 导入](../plans/2026-08-15-local-first-note-app-plan.md)。

## 1. 现状（代码已核实）

- 文件管理器预览按 `mime` 分流：图片/视频/音频/PDF 均可内嵌预览；`text/markdown`（.md）落 `startsWith("text/")` 分支，显示「**文本文件：请在文件夹中打开查看**」→ 只能调起外部应用。
- app 已具备做这件事的完整链路：
  - `api.readTextFile(path)` 读 md 文本（Markdown 导入已用）✅
  - `parseMarkdown` / `$convertFromMarkdownString` + `SHUYONOTE_TRANSFORMERS` + `mdToHtml` 把 md 转块 ✅
  - asset 协议可为 appdata 内附件提供本地 URL ✅
- **已有先例**：PDF 在文件管理器里已「应用内打开」（`fm-preview-read` → `usePdfReader.openPdf`）。md 补上后交互范式一致。

## 2. 利（为什么值得做）

1. **用户价值高**：不用跳外部编辑器，在 app 里直接看 md，闭环顺手。
2. **产品一致性**：PDF 已如此；md 补上后「文档类文件都能在 app 里看」，体验统一。
3. **可进知识体系（若叠加"转页面"）**：md 内容可渲染后，复用 `MarkdownImportDialog` 很容易「导入成笔记页面」→ 可检索/双链/引用/编辑。这是**真正高价值**（不只"看"）。
4. **成本低**：链路全是现成的，几乎零新解析逻辑。
5. **契合定位**：与「文档/知识库」「文件夹=网盘+页面可引用」方向一致，md 是知识工作者常用格式。

## 3. 弊 / 风险

1. **角色歧义（最大风险）**：点 md 是「**看**」还是「**导入成笔记**」？若一键打开自动变页面，用户会困惑（"我只是想看这篇，怎么建了个页面进版本历史/关系图"）——**心智模型冲突**。
2. **"文件"与"页面"界限模糊**：文件管理器里 md 是附件/文件；转页面后是笔记，二者数据模型/生命周期（版本/回收站/关系图）不同。默认自动转化会破坏「文件 = 网盘」定位。
3. **编辑语义未定**：只读渲染没问题；但"应用内打开"若暗示**可编辑**，要决定是「编辑文件本身（写回 .md，改内容寻址源）」还是「转页面再编辑（不复写文件）」。前者危险（动源文件），后者又回到"转页面"。
4. **md 多样性**：严格 md 无图/链接/样式定义；实际 md 常混 HTML、相对图片路径、目录树（`[[ ]]`、`<img>`、mermaid、md 内的相对资源）。渲染需处理边界，否则显示难看/错误。
5. **性能/大文件**：超大 md 一次性读 + 渲染，要限流/虚拟滚动。
6. **商业化边界**：md 若是用户已有文件，一键"收编"进知识库可能被质疑"我为什么要传进去才叫笔记"——依赖产品叙事（"导入并整理"而非"被迫收编"）。

## 4. 建议：应用内打开 = 只读渲染 + 明显的「转为笔记」第二动作

不要默认自动转页面，分层给用户选择：

| 动作 | 行为 | 何时 |
|------|------|------|
| **打开（内嵌预览）** | 应用内渲染 md 为**只读视图**（标题/列表/代码/表格/图片），不落库 | 默认点文件 → 看内容 |
| **转为笔记** | 点明确的「导入到笔记」按钮 → 复用 `MarkdownImportDialog` → 生成页面（可检索/双链/编辑） | 用户主动选择 |

这样：
- **"看"零副作用**、无需确认，体验顺畅；
- **"收进知识库"**是明确动作，用户心智清晰，不会误建页面；
- 复用现有 `MarkdownImportDialog`，几乎零新逻辑。

**不推荐**的两个极端：
- ❌ 维持现状（只在外部打开）：价值太低。
- ❌ 一键打开即转页面：破坏"文件=网盘"心智，且可能误生成大量页面。

## 5. 待拍板点

1. **只读渲染用哪种**：直接用 `mdToHtml`（复用 MarkdownImportDialog 转换）还是先 `parseMarkdown` 再走 Lexical 块渲染？建议前者（`mdToHtml` + 样式表），简单够用。
2. **"转为笔记"落点**：导入到**当前文件夹**下新建页面，还是打开现成 `MarkdownImportDialog` 让用户选？建议后者（与现有导入一致、更安全）。
3. **是否支持编辑**：建议暂不做"编辑文件"；「转页面」才是"可编辑"的正路，避免动源文件。

## 6. 结论

**值得做，建议"应用内只读渲染 + 一键转笔记页面"两手给**；但别把"应用内打开"默认成自动转页面。收益高、成本低、有先例；风险集中在"看 vs 转"的心智歧义，靠分层动作化解。
