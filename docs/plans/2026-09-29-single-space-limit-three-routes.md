# 提高「单空间设备上限」的三条现实路线 —— 深入对比

> 上游：[容量压测报告](2026-09-29-server-capacity-loadtest.md)（实测 M1≈10／M2≈100／M3≈200 台）
> 起因：owner「增加服务器可以吗？」→「讨论提高单空间上限的路线」→「1、2、3 三条深入研究对比」
> ⚠️ 本文的结论**与直觉相反**（见 §5）：看起来最"根本"的换存储，对这一项帮助**最小**。

---

## 0. 先立一条总原则
```text
扇出是 **N²** ⇒
  · 优化【常数】（读池、索引、SQL）⇒ 20%~2 倍
  · 改变【形状】（少拉、改扇出阶）⇒ 10 倍以上
  · 换【底座】（存储）⇒ **不改扇出** ⇒ 对这一项帮助最小（见 §4）
```

## 1. 路线一：**少拉**（只读设备不订阅通知）
### 1.1 机制
```text
扇出 = 写次数 × **订阅者数**
⇒ 只让写者订阅 ⇒ 订阅者数从 N 降到 α·N（α = 正在写的比例）
⇒ 读/秒 从 `α·r·N²` 降到 **`α²·r·N²`** ⇒ 幅度 = **1/α**
⇒ α=0.1（owner 问的"10% 实时协同"）⇒ **10 倍** —— 且**实测 9.92 倍**（算术 9.94）
```
### 1.2 成本：**最小**（三项零改动）
```text
客户端：按"我最近编辑过这个空间吗／是不是正在看这一页"决定订不订阅
服务端：**零改动** ✅   协议：**零改动** ✅   存储：**零改动** ✅
```
### 1.3 ⚠️ 真代价在"只读者的可见延迟"
```text
只读者从"**通知即拉**"（实测 16ms + 往返）退化成"**按间隔拉**"
⇒ 他看到新内容的时间：从 ~1 秒 变成 **最长一个拉取间隔**
  （服务端档兜底 5 分钟／局域网档用户选的 5 秒）
⇒ ⇒ **这是产品取舍，不是技术问题** —— 取决于"只读的用户能不能忍"
```
### 1.4 ⚠️⚠️ 而最大的风险是**判定判错**（代价不对称）
```text
"谁算只读者"三种判法，都有误判面：
  · 按"最近 N 分钟有没有编辑过" ⇒ 简单，但**刚编辑完的人**会被判成只读
  · 按"当前有没有打开编辑器"    ⇒ 更准，但"没打开的这一刻"别人改了他也看不到
  · 按"在不在看这一页"          ⇒ 最准，但要 presence（已有雏形）

⇒ ⚠️ **判错的两个方向代价极不对称**：
   · 把写者误判成**只读** ⇒ **他的改动要等一个节拍才出去**
     ⇒ ⇒ 这会把**刚修好的"上传侧触发"（`dfa79e1a`）打回原形**！
   · 把只读者误判成**写者** ⇒ 只是没省下扇出，无害
⇒ ⇒ **判定必须保守：宁订阅、勿退订。** 并在规格里写死这条偏置。
```
### 1.5 验收
```text
可测：订阅者数的分布（写者比例 α）＋ 读/秒曲线（应见 α² 形状）
可测：只读设备的"内容可见延迟"分布（这是它的代价，要量化）
⚠️ 必须单独测：**判定准确率**（尤其"写者被误判为只读"的比率 → 必须为 0 或极小）
```

## 2. 路线二：**转发增量**（服务端把变更内容推给订阅者）
### 2.1 机制
```text
今天：1 次写 ⇒ N 个通知 ⇒ **N 次 pull**（每次一次 HTTP ＋ **两条** SQLite 查询）
L4  ：1 次写 ⇒ **1 次 broadcast（帧里带 payload）** ⇒ N 个订阅者直接收
⇒ 扇出 **O(N²) → O(N)**
⇒ 按实测折算：M2 N=200 的 9999 读/秒 ⇒ L4 下变成约 **200 帧/秒** ⇒ **约 50 倍**
⇒ ⇒ **这是唯一能把单空间抬到四位数的路线。**
```
### 2.2 成本：**大**（要动服务端私有商业仓 ⇒ 要发版）
```text
服务端：SSE 帧带 payload ＋ 按 seq/页 组织
客户端：从"收到就拉"改成"收到就应用"
  ⚠️ 正确形状：**帧里带 `seq`，客户端仍走【既有应用路径】**
     —— 变的只是"数据来源"（pull → push），**不是新造第二条合并路**
     （本仓最忌"同一件事两处实现"＝第二份真相）
协议：帧变大 ⇒ 要定"多大算太大"
存储：零改动 ✅
```
### 2.3 ⚠️ 最大的技术陷阱：**payload 大小**
```text
`broadcast::channel(64)` 是**每接收者 64 条环形缓冲** ⇒ 每空间常驻内存 ≈ 64 × payload
  · payload 小（Yjs 增量，通常几 KB 以内）⇒ 常驻可接受 ✅
  · ⚠️ payload 是**整页 CRDT state**（可能几十 KB ~ 几 MB）⇒ **内存爆炸** ❌
⇒ ⇒ **L4 必须"只转发增量"，不能转发整页状态。**
   ⚠️ 而今天的 outbox 记录带的**正是整页 state**（S4b-1a「带上状态」）——
      ⇒ ⇒ **L4 与"搬整块还是增量"是同一个问题，必须一起解决。**
      这是 L4 的前置条件，不是它可以绕开的东西。
```
### 2.4 与既有口径的冲突（要 owner 拍）
```text
那条流的设计稿把这两条列为**明文非目标**：
  · 「**拉取语义一行不改**（仍是 pull by seq ＋ 既有的合并/落盘）」
  · 「**别把长连接当同步引擎**」
⇒ L4 与它们直接冲突 ⇒ 不是"工程做不到"，是"**要推翻一条既有非目标**"。
```
### 2.5 ⭐ 一个反直觉的好消息：**它不必然破 E2E**
```text
个人空间的内容本来就是**密文** —— 服务端**转发密文**不需要看懂内容。
团队空间明文 ⇒ 更没问题。
⇒ ⇒ 与"许可边界"（`INV-LIC-no-server-in-client`：不许把服务端实现搬进客户端）**不冲突**：
   **转发 ≠ 实现。** 服务端仍然"哑且盲"，只是从"只发通知"变成"也转发字节"。
```
### 2.6 必须做对的三件
```text
① **断线重连能补**：帧带 `seq` ⇒ 客户端发现**跳号就回退去 pull**
   ⇒ 既有拉取路径仍在 ⇒ 它是**兜底**，不是替代（这条让"拉取语义不改"其实仍成立！）
② **慢订阅者**：channel 满了仍 `Lagged` ⇒ 沿用今天"lagged ⇒ 立刻拉"的兜底
   ⚠️ 但要**限频**（今天 ping 触发"立刻拉"是正反馈：负载高 ⇒ ping 多 ⇒ 拉更多）
③ **内存**：见 §2.3 ⇒ 只转发增量
```
### 2.7 验收
```text
可测：**帧/秒 vs 读/秒**（pull 次数应断崖式下降）
可测：端到端延迟（应比"通知+拉"少一跳）
⚠️ 必须测：**内存**（channel 常驻 × 空间数）；**大页面**行为
⚠️ 必须测：**跳号回退**（人为丢帧 ⇒ 客户端能否回退到 pull 且不漏）
⚠️ 必须测：**payload 到底是增量还是整页**（这决定它成不成立）
```

## 3. 路线三：**换存储**（分布式 / Postgres）
### 3.1 机制
```text
把"每空间一个 SQLite ＋ 单写者 ＋ **表级 AUTOINCREMENT seq**"换成
  · 关系库（Postgres）⇒ 真并发写、行级锁、更大数据量
  · 或分布式（分片 ＋ 共识）
⇒ 突破"**单空间 = 单机单元**"这个结构性约束
```
### 3.2 成本：**极大**
```text
· ⚠️ **服务端存储层整体重写**（事务模型 ＋ **seq 分配**）
  ⇒ 注意：`seq INTEGER PRIMARY KEY AUTOINCREMENT`（`db.rs:19`）是**表级全局单调**，
     而客户端拿它当**空间水位**（`last_pulled_seq` per ws_id）
     ⇒ 要支持多机，得先把它改成**空间级**（`MAX(seq)+1 WHERE space_id=?`）
     ⇒ 而那会引入"**同空间并发写抢序列**"⇒ 与"单写者"的简化假设正面冲突
· **部署复杂度上升**：客户要跑一个 DB 服务（而今天是**一个文件**）
· **迁移**：现有 SQLite 数据要迁
```
### 3.3 ⚠️ 而它会破掉一个**产品定位**
```text
"SQLite 单文件"是这个产品的一个卖点：**自建、零依赖、易备份**。
⇒ 换 Postgres ⇒ 运维成本**转移给自建客户** ⇒ **这是产品决定，不是技术决定**。
```
### 3.4 ⚠️⚠️ 最关键：**它并不解决扇出**
```text
换成 Postgres 之后：1 次写 **仍然是** N 次 pull（今天那条"通知＋拉"的形状没变）
⇒ 只是**每次 pull 更快了**（常数变小）
⇒ ⇒ **L6 对"单空间设备上限"的贡献，可能还不如 L4** —— 而且成本高一个量级。
```
### 3.5 那它解决什么（它真正的用途）
```text
· **多空间 / 大团队下的写并发**（今天单写者 `Arc<Mutex<Connection>>`）
· **数据量**（SQLite 单文件的上限、备份窗口）
· **高可用 / 复制 / 审计**（企业功能的地基）
⇒ 也就是说：**L6 是"平台级"的决定，不该为了"单空间设备数"去做。**
```

## 4. 三者对比（一张表）
| | 路线一 少拉 | 路线二 转发增量 | 路线三 换存储 |
|---|---|---|---|
| **改的是什么** | 扇出的**系数**（1/α） | 扇出的**阶**（N²→N） | **不是扇出**（每次的成本 ＋ 写并发） |
| **幅度（对单空间上限）** | **10 倍**（实测 9.92） | **约 50 倍**（推算） | **小**（只降常数） |
| **能否到四位数** | ❌（α 有下限） | ✅ **唯一能** | ❌ |
| **客户端改动** | 中（判定逻辑） | 大（改数据来源） | 无 |
| **服务端改动** | **零** ✅ | 大（要发版） | **整体重写** |
| **协议改动** | **零** ✅ | 中（帧带 payload ＋ seq） | 中（seq 空间级） |
| **存储改动** | **零** ✅ | **零** ✅ | 换掉 |
| **部署影响** | 无 | 无 | ⚠️ 客户要装 DB |
| **破 E2E?** | 否 | **否**（转发密文） | 否 |
| **撞既有非目标?** | 否 | ⚠️ **是**（"拉取语义一行不改"） | 否（但撞产品定位） |
| **前置条件** | 判定偏置要写死 | **payload 必须是增量**（见 §2.3） | seq 要改空间级 |
| **主风险** | 判错 ⇒ 把写者当只读（打回上传侧） | 内存爆炸（若转发整页） | 成本与定位 |
| **何时做** | 真实拐点 < 需要时 | 需要"真·实时"或四位数时 | **平台级需求**出现时（不是为这一项） |

## 5. ⭐ 结论（与直觉相反）
```text
按"对【单空间设备上限】的贡献 ÷ 成本"排：
  🥇 **路线一（少拉）**      —— 10 倍 / 成本极小（**只改客户端**）⇒ 最高性价比
  🥈 **路线二（转发增量）**   —— 约 50 倍 / 成本大，但**唯一能到四位数**
  🥉 **路线三（换存储）**     —— 对这一项**帮助最小** / 成本最大
     ⇒ 它看起来最"根本"，其实**不碰扇出** ⇒ 不该为了设备数去做它。

⇒ 一句话：**要提单空间上限，先"少拉"（便宜），不够再"改扇出阶"（根本），
   而"换存储"是另一件事（平台级），别拿它当解药。**
```

## 6. ⚠️ 而第一步不是选路线，是**把真实上限测准**
```text
压测给的 N² 是【**上界**】：真客户端有 `busy` 防重入（同时只 1 个 pull 在飞）
⇒ 实测 M2 N=100 只发出 **32%** 的读、N=200 只 **13.5%** ⇒ pull P95 214ms → **22.8ms**
⇒ ⇒ **M2 的真实上限可能明显高于 100 台**，而 `--guard fidelity` 只跑了 N=100/200 两格
⇒ 顺序：**先跑完整栅格（找到真实拐点）⇒ 再决定要不要动路线一**
   ⚠️ 否则可能在"上限其实够用"的情况下白做优化。
```

## 7. 各路线要补的"研究件"
```text
路线一：① 判定偏置的规格（写死"宁订阅勿退订"）② 只读延迟的量化
路线二：① **payload 是增量还是整页**（前置！）② 帧形状（带 seq）
       ③ 跳号回退的判据 ④ 内存模型（64 × payload × 空间数）
       ⑤ **那条非目标该怎么处置**（要 owner 拍）
路线三：① seq 改空间级的迁移方案 ② 自建客户的部署成本评估
       ③ 它到底为哪一条平台需求服务（不是为设备数）
```
