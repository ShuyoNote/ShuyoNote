# yrs 对拍尖刺：结论（JS `yjs` ↔ Rust `yrs`，2026-09-23）

> 上位：[全上线冲刺](2026-09-23-crdt-full-launch-sprint.md) 的缺口 §10.3-6 / §9.2-4；
> 边界决策见 [平面边界决策](2026-09-23-crdt-plane-boundary-decision.md) §6（已拍 = **服务端合并**）。
>
> 一句话：**格式层可行** —— 同一批 fixtures（同血统两分支 → 合并 → 投影）在 JS 与 Rust 两侧
> 得到**逐字节相同**的投影；阶段 2 剩下的不是"能不能互操作"，而是**隐私口径、状态体积、
> 并发口径**这三件。

## 1. 这一片回答什么 / 不回答什么

**回答**：Rust 的 `yrs` 能不能收下 JS `yjs` 产生的 update、把它与另一端的 update 合并、
再把合并结果吐回去让 JS 认。

**不回答**（别读成已验证）：
- 服务端要不要合并（那是产品决策，且隐私口径要重定义 —— 服务端从此**看得懂内容**）；
- 状态体积 / 每页状态随编辑增长的读数（本次 fixtures 只有 4 个块）；
- 投影本身：**Rust 侧刻意不实现投影**（那要 `@lexical/yjs` 的编辑器语义，复刻它就是本仓最忌的
  "第二份派生实现"）。分工是"Rust 只搬字节，JS 用**应用自己那份**实现投影来验"。

## 2. 造了什么（可复核、可重跑）

| 件 | 位置 | 说明 |
|---|---|---|
| Rust 尖刺二进制 | `spikes/yrs-interop/`（**独立 crate**，不进 `src-tauri` 依赖树） | 子命令 `merge`（收 update → 合并 → 吐 update）／`inspect`（根节点树 ＋ state vector 读数）／`threads`（并发/事务失败形态） |

```powershell
cd ..\.. ; pnpm vitest run src/lib/crdt/yrsInterop.spike.test.ts
```

依赖版本（写下来，免得下次对不上）：**`yrs` 0.23.5** ↔ **`yjs` 13.6.32**（应用钉死的版本）。

## 3. 读数（本机实跑，2026-09-23）

### 3.1 ★ 互操作成立：两侧合并 ⇒ **同一份投影**

fixtures 与 S2a 的承重判据同形：基线两段（`blk-1`/`blk-2`）→ 同一条血统 → 两台各加一块
（`blk-A`／`blk-B`）。

```
【实测】JS 投影   = ["blk-1","blk-2","blk-A","blk-B"]
【实测】Rust 投影 = ["blk-1","blk-2","blk-A","blk-B"]
⇒ projectStateToJson(JS 合并的状态) === projectStateToJson(Rust 合并的状态)   ← 逐字节相同
```

**反方向也成立**：把 JS 合并出来的状态交给 Rust 收下再吐出来，JS 投影出来仍是同一份。

Rust 侧的结构读数（`inspect`）表明它**认得出真实的 doc 形状**（不是只当二进制搬运）：

```
state_vector=1534941270:7,264498149:19      ← 两个 client，与"两条血统分支合起来"一致
root_children=4                              ← 与 JS 侧 XmlElement.length 相等（同一门断言）
  [0] <shuyo-paragraph __blockId=blk-1>
    [0] #text "第一段"
  [1] <shuyo-paragraph __blockId=blk-2>
    [0] #text "第二段"
  [2] <shuyo-paragraph __blockId=blk-A>
    [0] #text "A 加的"
  [3] <shuyo-paragraph __blockId=blk-B>
    [0] #text "B 加的"
```

⇒ **结论**：`yrs` 与 `yjs` 在**本应用真实的 doc 形状**（`root-v2` 根 ＋ `shuyo-paragraph` 元素 ＋
`__blockId` 属性）上互操作成立。

### 3.2 ★ 失败形态：**卡死**，不是报错（服务端要防的就是这个）

```
读事务还活着时再调 get_or_insert（失败形态）: ★ 2 秒内没有结束（卡住）
共享一个 Doc ＋ 两线程各自 get_or_insert 并写: 线程 A 没有 panic／线程 B 没有 panic
各用一个 Doc（我们打算用的形状）: A=Ok(clients=1 text="A") B=Ok(clients=1 text="B")
```

两条读数都要读全（**第一条是踩出来的，第二条是纠正**）：

1. **读事务还活着时再调 `get_or_insert_*`（它内部开写事务）⇒ 卡住**。
   这是真的踩到的：本尖刺第一版 `structure()` 就是"先 `doc.transact()`，再去
   `doc.get_or_insert_xml_fragment(...)`"，`inspect` **挂住 ≥45s 无输出**；另一次整条命令
   卡到 **120s 超时**。**单线程就能复现**，不是并发问题。
   ⇒ 对服务端的约束：**根句柄必须在读事务之前取好**；任何"事务里顺手 get_or_insert"都会变成
   **不返回**（比 panic 危险得多：连接不返回、线程池会被吃光）。
2. **并发共享一个 Doc（两个线程各自 `get_or_insert` ＋ 写）没有复现失败**。
   ⚠️ 我第一版把它读成了"共享 Doc 就会卡"—— 那是**错的**（当时的卡死是自己 ① 那种写法造成的）。
   如实记下来：本地这台机上，共享 Doc 的并发写**没有**失败证据。
   ⇒ 但**不因此推荐共享**：① 说明"事务套事务"会卡死，"每页独立、请求内短命 Doc"这条设计
   （S5-0 已定）仍然是最省心的口径，尖刺既没有推翻它、也没有给它加新证据。

## 4. 对 S5 阶段 2 的影响

| 问题 | 尖刺后的答案 |
|---|---|
| 格式层能不能互操作？ | ✅ **能**（§3.1，两侧投影逐字节相同） |
| 阶段 2 的成本还是"Rust 侧要有一份 Yjs 实现"吗？ | **不再**是"从零写一份"：`yrs` 现成可用（本尖刺就是证据），成本降到"接依赖 ＋ 写合并/存储 ＋ 判据" |
| 阶段 2 现在就能上吗？ | ❌ 还有前置：**隐私口径**（服务端从此看得懂内容 ⇒ 面 5 E2EE 快照必须先答）、**状态体积**（每页状态随编辑增长，没有读数）、**并发/卡死口径**（一页一 Doc、根句柄先取好、绝不共享 Doc） |
| 尖刺证明了"服务端合并没有必要"吗？ | ❌ 没有。它只证明"**做得到**"，没证明"**值得做**" |

## 5. 这一片的边界（别读强）

- 判据是**尖刺**，不是门禁：没有那个二进制就自报跳过 ⇒ 它绿不等于"生产没有回归"；
- 只覆盖 4 个块的 fixtures（体积/性能无读数）；
- 只覆盖"合并"这一件事：**投影、加密、传输格式版本（v1 wire 标记）都不在本次射程内**；
- 本地一处环境（Windows）的读数，没有跨平台矩阵。
