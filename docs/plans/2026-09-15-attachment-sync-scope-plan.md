# 附件同步「范围与刹车」方案（手机端 × 海量视频空间）

> **依据**：2026-09-15 对 `sync_attachments` 的**代码级取证**（起因是一句追问："手机被设置和
> 海量视频空间同步，结果如何？"）。结论是**当前附件同步的语义 = 把整个空间在设备上做一份完整副本**，
> 而不是"按需取用"；这条语义在桌面上是合理的，**换到手机上同时缺三样东西：体积预算、磁盘余量、网络闸门**。
> **目标**：让"手机 × 大空间"**不会在用户不知情的情况下**把设备填满或被系统杀掉；
> 并让"同步了什么、还剩多少、为什么停下"对用户可见。
> **状态**：方案，**未实施**。执行顺序见 **§4.1 建议的执行批次**：
> **第一批（现在就做）**＝ B1 口径修正 / B2 补 `end()` / **B3 ＝ P2a** 导出改真流式 / B4 先实测重复行
> ——**四件都不改同步语义**；**第二批（Android 上架前）**＝ C1 预算刹车（P3）+ C2 网络闸门（P5）。
> **P2b** 目标明确但**全方案风险最高**（牵动加密格式与存量兼容）⇒ **先真机实测，没实测不动格式**；
> **P4 建议不做**（用"每空间开关"替代）；**P6 下一轮**。
> **本方案不改变"同步仍会拉附件"这一事实**（那是 P6）。
> **范围**：`src-tauri/src/sync.rs`、`src-tauri/src/security.rs`、`src/lib/platform/web.ts`、
> `src/hooks/useAutoSync.ts`、`src/store/syncStatus.ts`、`src/components/SyncPanel.tsx`、
> `docs/MOBILE.md`、`src/App.css`（注释）；跨仓一处：社区仓 `shuyo-community` 的事实核对表 **#40**。
> ⚠️ **本方案的证据全部来自读代码，未在真机 / 真服务端上跑过大文件同步**——见 §七 未验证清单。
> **执行方式**：按 **§4.1 的批次**做，**不是**按 §五 的档位编号顺序做。**B1 可立刻单独发**（零风险）。

## 一、结论（先给判断）

现状是**有意设计**，不是疏忽——`docs/SYNC.md:34` 已经把行为写成文档：
"本地有而远端没有的就上传，远端有而本地没有的就**下载到本地字节库**"。
问题不在"它会下载附件"，而在**它没有任何刹车**，且这条设计**默认了桌面环境**：

| 桌面假设 | 手机上的现实 |
|---|---|
| 盘大（几百 GB 起） | 盘小，且与系统共享 |
| 常插电、常宽带 | 电池 + 计量流量 |
| 内存宽裕 | 单个大文件就能触发 OOM |
| 用户坐在机器前 | 后台自动同步，用户不知情 |

**三条真正会伤到用户的，按严重度排**：

1. **无大小上限、无数量上限、无磁盘余量检查** —— 一直下到写不进去为止。
   填满设备不只是"同步失败"：**同一个分区上还躺着 SQLite 库**，写满会牵连数据库写入。
2. **有四条路径会把整个附件读进内存** —— 但**触发条件不同，而这个差别决定先修哪个**（穷举见 **§2.6（2）**）：
   **导出 / 另存为是"无条件"的**（`attachments.rs:378` 的 `std::fs::read` 与是否加密无关）；
   而**导入、同步上传、同步下载只在"用户开了静态加密"时**才整块读（未加密本来就是流式）。
   ⇒ 两个结论：**默认配置下手机同步大文件不会 OOM，它会安静地把设备填满**；
   而"把传进去的视频再下载出来"这条**任何人都踩得到**，且**不需要同步参与**。
3. **自动同步无网络与体积判断** —— 间隔 5 分钟、启动后 3 秒触发、**无条件调用**，
   移动数据下后台拉视频；而且**桌面/安卓侧完全没有附件进度上报**，用户看不见任何东西。

**外加一个必须排在前面修的地基问题**：`useSyncStatus` 的 `end()` **只在 Web 侧被调用**，
桌面/安卓手动同步后状态永远停在"正在同步…"（§二 #19）。**进度上报要建在这上面，所以先修它。**

### 2.6 补充盘点（2026-09-15 补：两类上传路径 + "整块进内存"的真实范围 + 一个待实测的副作用）

> 本节是三问之后的追加取证：「**文件夹上传的文件和页面上传的附件有何区别？**」
> 结论是**几乎没有区别**——而这恰好把 §2.1 的范围和 §五 的施工面（**P2a / P2b**）**都放大了**。

**（1）"页面附件"与"文件夹里的文件"是同一个东西，区别只在挂在谁下面**

| 上传位置 | `page_id` 指向 | 前端入口 |
|---|---|---|
| 页面上传的附件 | **那一页**的 id | `AttachmentPanel.tsx:93` |
| **文件夹里上传的文件** | **那个文件夹的 id**（文件夹本身是 `kind='folder'` 的 **page**） | `FileManagerView.tsx:194`、`PageTree.tsx:127`；`commands.rs:133` |
| 画布图片 / 封面 | **`NULL`** —— UI 语义是「**空间根下的未整理文件**」 | `DrawingEditorModal.tsx:279`、`CoverPicker.tsx:72`；`attachments.rs:612` 注释 |

- **共同**：同一张表（`db.rs:606-616`，只有 `id / page_id / name / hash / mime / size / created_at`）、
  同一个命令、**同一套内容寻址**（字节层同内容只存一份，`attachments.rs:561-564`）、**同一条同步通道**；
  连"搬家"都只是改 `page_id`（`attachments.rs:748-771`）。
- **行不去重**：每次导入都 `INSERT` 一行新 uuid（`attachments.rs:578-584`）⇒
  **同内容挂在 N 处就有 N 行、磁盘上仍只有 1 份字节**（即社区仓核对表 #8 那个 ⚠️ 的由来）。
- **「同名文件历史版本」是前端视图，不是存储特性**：`FileManagerView.tsx:314-324` 按 `name` 分组
  （注释原话 "implicitly content-addressed historical versions"）、`:551` 恢复、`:526` 本地名子串搜索。
  ⇒ 三点要记住：① **页面附件面板没有版本入口**（`AttachmentPanel.tsx` 里搜不到任何 `版本`/`version`）；
  ② 它按 **name** 分组，**改过名的同内容文件不算同一文件、同名的不同文件却算**；
  ③ 附件**不进全文检索**（`search.rs` 无 `attachment`；`db.rs:606-616` 只有两个**普通**索引，**无 FTS、无触发器**）。

**（2）"整块进出内存"的真实站点范围：⚠️ 一条无条件 + 三条随加密**

`encrypt_attachment_bytes` / `decrypt_attachment_bytes` 共 8 处调用（另 6 处在测试里），
其中**会读写整个文件**的是这四条 —— **关键是它们的触发条件并不相同**（初版把这四条写成"同病"，不准确）：

| # | 路径 | 位置 | **触发条件** | 形态 |
|---|---|---|---|---|
| a | **导入**（文件夹 / 页面 / 画布**都走它**） | `attachments.rs:568-575` | **仅当开了加密**（`else if key.is_some()`） | 流式写**明文** tmp → rename → **整文件读进内存** → 加密 → 写回 |
| b | **同步下载** | `sync.rs:1654-1677` | **仅当开了加密**（`:1670` `if let Some(k)`) | 分块落盘后**整块读回**再加密写回 |
| c | **同步上传** | `sync.rs:1590-1599` | **仅当开了加密** | 加密时 `tokio::fs::read` 整块读 → 解密 → 发送；**未加密是流式**（`:1597-1599`） |
| d | **导出 / 另存为** | `attachments.rs:374-386` | 🔴 **无条件**（与是否加密无关） | `std::fs::read` 整块读 → 解密 → `std::fs::write` 整块写 |

- **最重要的推论**：**静态加密是用户主动开启的**（`security.rs:35` 从 meta.db 读，默认关）⇒
  **默认配置下只有 d 会咬人**；a/b/c 要等用户开了加密才出现。
  ⇒ **d 应当从 P2 里拆出来独立做**（见 §四 的 **P2a**）：它零风险、**不改加密格式**、改完就是真流式。
- **d 为什么"无条件"也整块**：`copy_attachment` 先 `std::fs::read`，再 `decrypt_attachment_bytes(key, &raw)`——
  而 key 为 `None` 时该函数**原样返回**（`security.rs` 里 `encrypt/decrypt(None, ..)` 的测试）⇒
  **未加密时这一读一写纯属白费**，可以直接 `std::fs::copy`。
  这条路正是文件管理器的「下载」（`FileManagerView.tsx:538`）⇒
  **手机上"把传进去的视频下载出来"当场 OOM 的就是它，且不需要同步参与。**
- a 与 d 是**本地操作**、与同步无关；**只有 b/c 在同步链路上**。
- 另有第 5 类 `attachments.rs:431-439`（`attachment_bytes`）会把**整个附件**解密后交给前端；
  但它是否落在**大媒体预览**的热路径上**本次未核实**（大媒体很可能走 `attachment_path` + 资源协议，
  那样就不进内存）⇒ **要动它之前先确认这一点**。

**（3）一个代码推断的副作用：第二台设备会多出重复行（❓ 待实测，不得当已证）**

- 经 `changes` 进来的附件行带**正确的 `page_id`**（`sync.rs:1297-1313` 的 upsert）；
- 字节下载路径**又插一行** `page_id = NULL`（`sync.rs:1681-1687`：**新 uuid** + `INSERT OR IGNORE`，
  而 `INSERT OR IGNORE` 只对**主键** `id` 冲突生效 ⇒ **永不冲突**）⇒ 同一 hash **两行、两个 id**。
- ⇒ 在第二台设备上，**本应归在文件夹里的文件，会在「未整理」（根目录）多出一份以 `hash.ext` 命名的副本**
  （`page_id IS NULL` 的语义见 `attachments.rs:612`；根目录视图见 `FileManagerView.tsx:150` 传 `null`）。

⚠️ **这条只有代码依据，我没实测。** 验证手段是现成的：`scripts/sync-regression.mjs`（两设备收敛回归）
或 `docs/sync-multidevice-test.md`（Windows ⇄ Mac）。**实测确认之前，不得写进任何对外结论。**

## 三、根因（三层）

### 3.1 「差集对齐」这个语义被直接复用到了手机上
`sync_attachments` 是同**一个函数**同时服务桌面与 Android（`sync.rs:1360` 被 `sync_workspace_only` 调用，
后者被 `sync_now:1379` 与 `sync_workspace:1423` 调用）。**没有任何平台分叉**。
桌面上的合理语义，在手机上就是"把 NAS 搬进来"。

### 3.2 全文没有「预算」这个概念
没有体积预算、没有磁盘余量预算、没有流量预算、没有内存预算。
唯一的限制来自**操作系统在失败那一刻的报错**（#6、#10）。

### 3.3 可见性缺口让前两层无法被发现
#16–#20：桌面/安卓既没有附件进度，**连结束态都没有**。
所以"后台默默下了 8 GB"这件事**在 UI 上是一片空白**——用户不可能自己发现，也就不会有人来报。

### 4.1 建议的执行批次（本方案的实际推荐）

1. **真凶不是 OOM，是"没有刹车"。** §2.6（2）分清了触发条件 ⇒

### P2a 导出 / 另存为改真流式（第一批 B3，**先做这个**）

**文件**：`src-tauri/src/attachments.rs`（Modify: `copy_attachment` `:374-386`）

现在**无论是否加密**都是 `std::fs::read` 整块读 → `decrypt_attachment_bytes` → `std::fs::write` 整块写；
而 key 为 `None` 时 `decrypt_attachment_bytes` **原样返回**（`security.rs` 里 `encrypt/decrypt(None, ..)` 的测试）
⇒ **未加密时这一读一写纯属白费**，可以直接按文件复制：

```rust
let target = crate::save_target::SaveTarget::new(&app, &dest_path, "shuyonote-att")?;
match key {
    // 未加密：磁盘上就是明文 ⇒ 直接文件级复制，内存与文件大小无关
    None => { std::fs::copy(&p, target.write_path()).map_err(|e| format!("复制失败: {e}"))?; }
    // 加密：仍是整块解密（要真流式得改加密格式，见 P2b）
    Some(k) => {
        let raw = std::fs::read(&p).map_err(|e| e.to_string())?;
        let plain = crate::security::decrypt_attachment_bytes(Some(&k), &raw)?;
        std::fs::write(target.write_path(), &plain).map_err(|e| format!("复制失败: {e}"))?;
    }
}
target.commit()
```

- **为什么独立成档**：它是**唯一无条件**发生的一条（§2.6（2）d），而修复**不碰加密格式** ⇒
  风险与 P2b 差一个量级，不该被"P2b 风险最高"这个标签拖住。
- **判据**：走 `FileManagerView.tsx:538` 的「下载」，未加密时导出 2 GB 文件 ⇒ **RSS 不随文件大小增长**。
- ⚠️ 动工前确认 `SaveTarget.write_path()` 在桌面与 Android（`content://`）两侧都能作为 `fs::copy` 的目标
  ——桌面是普通路径、Android 是先写缓存再整份搬（`attachments.rs:381-385` 的注释），语义一致。

### P2b 加密开启时的流式化（**先实测，暂不动格式**）

**文件**（真要做时）：`src-tauri/src/attachments.rs`（**导入** `:568-575`）、
`src-tauri/src/sync.rs`（下载 `:1654-1677`、上传 `:1590-1600`）、
`src-tauri/src/security.rs`（分块 AEAD + 兼容读）

> ⚠️ **触发条件**：这三条**只在用户开了静态加密时**才整块读（§2.6（2）a/b/c）。
> 未加密时导入走 `copy_and_hash` 流式、上传走 `:1597-1599` 流式、下载分块落盘 ⇒ **本来就是对的**。
>
> ⚠️ **为什么先实测**：流式**静态**加密的前提是**分块 AEAD**，而现有是整块 ⇒ 改格式 =
> **存量附件兼容**（读路径要同时认两种，否则老用户附件全部解不开）。
> **判据：真机 + 开加密 + 1–2 GB 文件，先看是否真的 OOM。没实测就不动格式。**
>
> 另需先确认 `attachments.rs:431-439`（整份交给前端）**是否在大媒体预览的热路径上**。

**下载侧**：现在是「明文书 `.part` → rename → 整块读 → 加密 → 写回」（#10、#11）。
改为**边收边加密写 `.part`**，全部成功后再 `rename` ⇒ **明文从不落盘、内存恒定**：

```rust
// 伪代码：分块读取 → 分块加密 → 直接写 .part
let mut file = tokio::fs::File::create(&tmp).await?;
let mut enc = match &session_key { Some(k) => Some(StreamEncryptor::new(k)?), None => None };
while let Some(chunk) = stream.next().await {
    let chunk = chunk.map_err(|e| e.to_string())?;
    size += chunk.len() as i64;
    let out = match &mut enc { Some(e) => e.push(&chunk)?, None => chunk.to_vec() };
    file.write_all(&out).await?;
}
if let Some(e) = enc { file.write_all(&e.finish()?).await?; }   // 收尾（AEAD tag）
std::fs::rename(&tmp, &path)?;                                   // 只有完整才改名
```

**⚠️ 这条有两个必须处理的约束（否则是数据损坏级的 bug）**：
1. **必须确认现有 `encrypt_attachment_bytes` / `decrypt_attachment_bytes` 的格式是"整块 AEAD"还是
   "分块可拼接"**（`nonce||ct`）。若是整块 AEAD，**不能**简单分块加密拼起来——
   要么改成**分块 AEAD（每块独立 nonce + tag）并同时升级读路径**。
   ⚠️ 注意「流式读 → 整块加密 → 流式写」**解决不了问题**：整块加密必然要求整个明文同时在内存里，
   所以它**不降低峰值内存**，只是把"读回"换了个说法——**别做这种看起来流式的假优化**。
2. **改格式 = 存量数据兼容问题**：已有附件是按旧格式存的，读路径必须**同时支持两种**
   （按长度 / 魔数判别），否则老用户的附件全部解不开。
   **这是本方案里风险最高的一步，必须单独一个提交 + 单独的回归证据。**

> **因此 P2b 的诚实结论**：**要么改格式（并做存量兼容），要么就先不做。**
> 动工前的第一件事是确认 `security.rs` 的实际格式（本次**未读**，见 §七）。
> 若格式是整块 AEAD 而不愿承担兼容成本，**P2b 就降级为"只记录、不实施"**——

### P3 同步预算刹车

**文件**：`src-tauri/src/sync.rs`（Modify: `sync_attachments`）、`src/lib/platform/web.ts`（同构修改）、
设置项落在同步 profile 或全局设置

**三档刹车，全部要"优雅停止 + 报告"，不是抛错**：

| 刹车 | 触发条件 | 行为 |
|---|---|---|
| **磁盘余量**（硬性，不可关） | 剩余空间 < 阈值（默认建议 1 GB，待拍板） | **立即停止下载**，保留已下部分，报告"因磁盘余量不足停止" |
| **本次下载总量** | 本轮已下载字节 > 上限（默认值待拍板） | 停止，报告"已达本次上限，可再次同步继续" |
| **单文件大小** | 单文件 > 阈值 | 跳过该文件，计入报告（**这就是 P4 的雏形，但先不引入"未下载"状态**） |

**实现要点**：
- **幂等可续**：因为按内容寻址、且 `local_set` 每轮重算，**停止后再同步会自然接着下** ⇒
  不需要断点续传协议，这是现有设计的免费红利。
- **必须让 #12 的错误处理对称**：把 `:1660` 的 `?` 改成与 `:1646` 一致的「记一笔、跳过、继续」，
  否则一次网络抖动会炸掉整轮（也就无法"优雅停止"）。
- **报告走 P1-b 的通道**，并在 `SyncPanel` 的结果文案里带上"跳过 N 个附件（原因）"。

**验收**：
```bash
# 1) 正常空间不受影响
pnpm test && pnpm release:preflight --skip-remote
# 2) 用一个小配额磁盘/目录模拟余量不足 → 同步应「停止并报告」，而不是报错崩溃
# 3) 连续两次同步 → 第二次接着下，不重复下载已完成的部分（幂等）
```
**期望**：停止后再次同步可继续；`attachments` 表不出现重复行；应用不崩。

## 七、边界与不做的事 / 未验证清单

**不做**：
- **不改"同步会拉附件"这个语义**（那是 P6，需拍板）。本方案只加刹车与可见性。
- **不给 Web 版"加上同步"或"去掉同步"**——它**本来就有实现**，本方案只修口径（P0）+ 保持置灰。
- **不引入"未下载"状态**（P4 之前的任何步骤都不该偷偷引入一个半成品状态）。
- **不动服务端的 2 TB 默认上限**（#23）——那是"本地优先、不武断设限"的既定选择；
  要改也应该是**客户端刹车**，而不是服务端挡人（自建用户的磁盘他自己说了算）。
- **不用 `--skip-remote` 之类绕过**来"验证"P3；余量不足必须真的用小配额环境测。

**未验证（别当已证）**：
1. **没有在真机 / 真服务端上跑过大文件同步**——全部结论来自读代码。要坐实至少两件事：
   ① **默认配置（未开加密）下"填满设备"会做到什么程度**——这是**主要**风险；
   ② **开了加密之后，大文件是否真的 OOM**——这是 **P2b** 的判据（见第 2 条）。
2. **`security.rs` 的附件加密格式本次未读**（`encrypt_attachment_bytes` / `decrypt_attachment_bytes`）——
   只从**调用点与测试**推断出"key 为 `None` 时原样返回"。
   **这是 P2b 的动工前置，但不是 P2a 的**（P2a 不碰格式，可以直接做）。
3. **附件字节缺失时的读路径行为未查**（P4 的前置问题 1、2）。
4. **Android 系统级限制未查**：应用私有目录配额、后台限制、Doze 对 5 分钟定时器的影响。
5. **浏览器配额上限未测**（P0 提到的那条 Web 路径）。
6. **`docs/SYNC.md` 未通读**（只精读了附件那一节），不排除别处已讨论过"选择性同步"。
7. **§2.6（3）那个"第二台设备多出重复行"没有实测**——只有代码依据
   （`sync.rs:1297-1313` 插一行带 `page_id` 的、`sync.rs:1681-1687` 又插一行 `page_id = NULL` 的新 uuid）。
   **必须用 `scripts/sync-regression.mjs` 或 `docs/sync-multidevice-test.md` 验一次**，
   因为如果成立，它是**用户可见的脏数据**（根目录冒出 `hash.ext` 命名的文件），够单独立项。
8. **`attachment_bytes`（`attachments.rs:431-439`）是否在大媒体预览的热路径上未核实**——
   若在，则"打开一个大视频"也会整份进内存；若走 `attachment_path` + 资源协议则不会。**这是 P2b 的前置问题之一。**
