# 附件同步「范围与刹车」方案（手机端 × 海量视频空间）

> **依据**：2026-09-15 对 `sync_attachments` 的**代码级取证**（起因是一句追问："手机被设置和
> 海量视频空间同步，结果如何？"）。结论是**当前附件同步的语义 = 把整个空间在设备上做一份完整副本**，
> 而不是"按需取用"；这条语义在桌面上是合理的，**换到手机上同时缺三样东西：体积预算、磁盘余量、网络闸门**。
> **目标**：让"手机 × 大空间"**不会在用户不知情的情况下**把设备填满或被系统杀掉；
> 并让"同步了什么、还剩多少、为什么停下"对用户可见。
> **状态**：方案，**未实施**。P0 为零风险文档修正；P1–P3 是"不改语义、只加刹车与地基"；
> P4 引入新状态；P5/P6 需拍板。**本方案不改变"同步仍会拉附件"这一事实**（那是 P6）。
> **范围**：`src-tauri/src/sync.rs`、`src-tauri/src/security.rs`、`src/lib/platform/web.ts`、
> `src/hooks/useAutoSync.ts`、`src/store/syncStatus.ts`、`src/components/SyncPanel.tsx`、
> `docs/MOBILE.md`、`src/App.css`（注释）；跨仓一处：社区仓 `shuyo-community` 的事实核对表 **#40**。
> ⚠️ **本方案的证据全部来自读代码，未在真机 / 真服务端上跑过大文件同步**——见 §七 未验证清单。
> **执行方式**：按 §五 顺序做，**P0 可立刻单独发**（零风险），P1–P3 一批，P4 一批。

## 一、结论（先给判断）

现状是**有意设计**，不是疏忽——`docs/SYNC.md:34` 已经把行为写成文档：
"本地有而远端没有的就上传，远端有而本地没有的就**下载到本地字节库**"。
问题不在"它会下载附件"，而在**它没有任何刹车**，且这条设计**默认了桌面环境**：

| 桌面假设 | 手机上的现实 |
|---|---|
| 盘大（几百 GB 起） | 盘小，且与系统共享 |
| 常插电、常宽带 | 电池 + 计量流量 |
| 内存宽裕 | 单个大文件就能触发 OOM |
| 用户坐在机器前 | 后台自动同步，用户不知情 |

**三条真正会伤到用户的，按严重度排**：

1. **无大小上限、无数量上限、无磁盘余量检查** —— 一直下到写不进去为止。
   填满设备不只是"同步失败"：**同一个分区上还躺着 SQLite 库**，写满会牵连数据库写入。
2. **加密开启时，每个文件下完会整块读进内存**再加密写回 —— 手机上很可能**先 OOM，而不是先满盘**。
3. **自动同步无网络与体积判断** —— 间隔 5 分钟、启动后 3 秒触发、**无条件调用**，
   移动数据下后台拉视频；而且**桌面/安卓侧完全没有附件进度上报**，用户看不见任何东西。

**外加一个必须排在前面修的地基问题**：`useSyncStatus` 的 `end()` **只在 Web 侧被调用**，
桌面/安卓手动同步后状态永远停在"正在同步…"（§二 #19）。**进度上报要建在这上面，所以先修它。**

## 三、根因（三层）

### 3.1 「差集对齐」这个语义被直接复用到了手机上
`sync_attachments` 是同**一个函数**同时服务桌面与 Android（`sync.rs:1360` 被 `sync_workspace_only` 调用，
后者被 `sync_now:1379` 与 `sync_workspace:1423` 调用）。**没有任何平台分叉**。
桌面上的合理语义，在手机上就是"把 NAS 搬进来"。

### 3.2 全文没有「预算」这个概念
没有体积预算、没有磁盘余量预算、没有流量预算、没有内存预算。
唯一的限制来自**操作系统在失败那一刻的报错**（#6、#10）。

### 3.3 可见性缺口让前两层无法被发现
#16–#20：桌面/安卓既没有附件进度，**连结束态都没有**。
所以"后台默默下了 8 GB"这件事**在 UI 上是一片空白**——用户不可能自己发现，也就不会有人来报。

## 四、方案取舍

| 档 | 做法 | 判据 / 代价 | 结论 |
|---|---|---|---|
| **P0** | **修文档口径**（#24 三处） | 零风险、零行为变化；不修就是"下一个离线 OCR"（纪律第 9 条） | ✅ **立刻做** |
| **P1** | **补结束态 + 附件进度上报**（先修 #19 的地基，再让 Rust 侧上报 `attCurrent/attTotal`） | 不改语义；是 P3「刹车触发要能报告」的前置 | ✅ **做（地基）** |
| **P2** | **下载/上传改为「边流边加密」** | 一次同时修 #10（内存）与 #11（明文窗口）；**没有取舍**——纯技术改进 | ✅ **做** |
| **P3** | **同步预算刹车**：本次下载总量上限 + 磁盘余量下限（硬性），触发即**优雅停止并报告** | 不改语义、不改数据模型；默认值需拍板 | ✅ **做（最小闭环）** |
| **P4** | **大附件不自动下载 + 「未下载」状态** | 价值最高，但**引入新状态**：需要读路径/UI 配合，否则文件看起来"坏了" | ⏸ **第二批** |
| **P5** | **网络与时机闸门**（仅 Wi-Fi / 仅充电 / 仅手动） | 需要**新能力**（#9，可行性未评估） | ⏸ **待评估** |
| **P6** | **按需取字节 / 每空间开关** | 真解法（这才是"桌面 vs 手机"的正确语义），但改动最大：新状态 + 读路径 + UI + 可能的元数据/字节分离 | 🔴 **待拍板** |
| **P7** | **只修文档，行为一律不动** | 最低成本，但 #1/#2/#3 三条伤害照旧 | ❌ 不推荐 |

**为什么 P1–P3 是"最小闭环"**：它们**都不改变"同步会拉附件"这件事**，只是加了刹车与可见性。
所以不需要产品决策就能做，而收益（不会静默填满设备 / 不会 OOM / 用户看得见）**已经覆盖了最严重的三条**。

**为什么 P4/P6 要分开**：一旦引入"未下载"，就必须回答一串新问题——
打开一页时图片没下载怎么办（占位？自动取？）、导出时缺字节怎么办、`cleanup_orphan_attachments`
会不会把"未下载"的元数据当孤儿清掉、跨设备如何表达"这台机器上有、那台没有"。
**这些是数据模型层面的问题，不该塞进第一批。**

### P2 改为「边流边加密」（同时修内存与明文窗口）

**文件**：`src-tauri/src/sync.rs`（Modify: 下载 `:1654-1677`、上传 `:1590-1600`）、
`src-tauri/src/security.rs`（可能新增流式加解密辅助）

**下载侧**：现在是「明文书 `.part` → rename → 整块读 → 加密 → 写回」（#10、#11）。
改为**边收边加密写 `.part`**，全部成功后再 `rename` ⇒ **明文从不落盘、内存恒定**：

```rust
// 伪代码：分块读取 → 分块加密 → 直接写 .part
let mut file = tokio::fs::File::create(&tmp).await?;
let mut enc = match &session_key { Some(k) => Some(StreamEncryptor::new(k)?), None => None };
while let Some(chunk) = stream.next().await {
    let chunk = chunk.map_err(|e| e.to_string())?;
    size += chunk.len() as i64;
    let out = match &mut enc { Some(e) => e.push(&chunk)?, None => chunk.to_vec() };
    file.write_all(&out).await?;
}
if let Some(e) = enc { file.write_all(&e.finish()?).await?; }   // 收尾（AEAD tag）
std::fs::rename(&tmp, &path)?;                                   // 只有完整才改名
```

**⚠️ 这条有两个必须处理的约束（否则是数据损坏级的 bug）**：
1. **必须确认现有 `encrypt_attachment_bytes` / `decrypt_attachment_bytes` 的格式是"整块 AEAD"还是
   "分块可拼接"**（`nonce||ct`）。若是整块 AEAD，**不能**简单分块加密拼起来——
   要么改成**分块 AEAD（每块独立 nonce + tag）并同时升级读路径**，要么退一步只做
   **"流式读 → 整块加密 → 流式写"**（内存仍是 O(1) 于块大小，但需要一份临时明文内存？
   不——整块加密必然要整块在内存，所以**必须改成分块格式**）。
2. **改格式 = 存量数据兼容问题**：已有附件是按旧格式存的，读路径必须**同时支持两种**（按长度/魔数判别），
   否则老用户的附件全部解不开。**这是本方案里风险最高的一步，必须单独一个提交 + 单独的回归证据。**

> **因此 P2 的诚实排序**：如果不想动加密格式，**P2 可以只做"下载侧不再整块读回"这一半**——
> 即保持"明文 `.part` → rename → 整块加密写回"，但用**流式读 + 流式写**配合整块加密是做不到的。
> **结论：P2 要么改格式（并做兼容），要么就先不做**，不要做一个"看起来流式、实际仍整块"的假优化。
> **这条建议在动工前先确认 `security.rs` 的实际格式**（本次未读，见 §七）。

### P3 同步预算刹车

**文件**：`src-tauri/src/sync.rs`（Modify: `sync_attachments`）、`src/lib/platform/web.ts`（同构修改）、
设置项落在同步 profile 或全局设置

**三档刹车，全部要"优雅停止 + 报告"，不是抛错**：

| 刹车 | 触发条件 | 行为 |
|---|---|---|
| **磁盘余量**（硬性，不可关） | 剩余空间 < 阈值（默认建议 1 GB，待拍板） | **立即停止下载**，保留已下部分，报告"因磁盘余量不足停止" |
| **本次下载总量** | 本轮已下载字节 > 上限（默认值待拍板） | 停止，报告"已达本次上限，可再次同步继续" |
| **单文件大小** | 单文件 > 阈值 | 跳过该文件，计入报告（**这就是 P4 的雏形，但先不引入"未下载"状态**） |

**实现要点**：
- **幂等可续**：因为按内容寻址、且 `local_set` 每轮重算，**停止后再同步会自然接着下** ⇒
  不需要断点续传协议，这是现有设计的免费红利。
- **必须让 #12 的错误处理对称**：把 `:1660` 的 `?` 改成与 `:1646` 一致的「记一笔、跳过、继续」，
  否则一次网络抖动会炸掉整轮（也就无法"优雅停止"）。
- **报告走 P1-b 的通道**，并在 `SyncPanel` 的结果文案里带上"跳过 N 个附件（原因）"。

**验收**：
```bash
# 1) 正常空间不受影响
pnpm test && pnpm release:preflight --skip-remote
# 2) 用一个小配额磁盘/目录模拟余量不足 → 同步应「停止并报告」，而不是报错崩溃
# 3) 连续两次同步 → 第二次接着下，不重复下载已完成的部分（幂等）
```
**期望**：停止后再次同步可继续；`attachments` 表不出现重复行；应用不崩。
