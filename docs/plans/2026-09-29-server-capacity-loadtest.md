## 7. 与你转述不一致的地方（逐条）

1. **读连接池只有 4 条**（`src/main.rs:280` `open_read_pool(&db_path, 4)`，硬编码，无配置）。
   你的背景里没提这条 —— 它意味着**最多 4 个 pull 真正并行**，第 5 个起在 4 个互斥量上排队。
2. **"每个订阅者各拉 1 次"只在你给的模型里成立，真客户端不这么做**：
   `src/hooks/useSyncStream.ts:51,55` 有 `busy` **防重入**（同时最多 1 个 pull 在飞），
   桌面路还多一层 `PULL_DEBOUNCE_MS = 300` 去抖（`ping` 走立刻拉、不去抖）。
   ⇒ N² 是**上界**。实测（我照真语义加严实现 `--guard busy`）：
   M2 N=100 只发出 **806/2501 = 32%** 的读；N=200 只发出 **1350/9999 = 13.5%**，pull P95 从 214ms 掉到 22.8ms。
3. **web 路收到 `ping` 也会拉**（`useSyncStream.ts:140` 只判 `frame.includes("data:")`，ping 帧同样是 data 帧）。
   所以"落后 ⇒ ping"在客户端不会降载，反而再触发一次 pull。
4. **广播是在持有写锁时发的**：`sync.rs:225` 的 `publish_space_change` 在 `conn`（写锁 MutexGuard）**仍未释放**时调用。
   `broadcast::Sender::send` 本身不阻塞（旧槽位直接被覆盖），所以不是死锁，但"写路径上不带广播"这句话不成立。
5. **每次 pull 是两条查询**：`require_space`（查 `space_members`）＋ 变更查询（`sync.rs:248-249`）。你的描述只算了索引扫描。
6. **`idx_changes_seq` 只索引 `seq` 一列**（`db.rs:29`），查询却按 `space_id` 过滤 + `seq` 排序。
7. 你说的"没有任何设备数/连接数/限流上限"——**核实为真**（grep `MAX_|rate_limit|quota|semaphore` 在 `src/` 下为空）。
8. `pull` 用只读池、`idx_changes_seq`、`limit` 默认 500/clamp 1000、`Arc<Mutex<Connection>>` 单写锁、
   `broadcast::channel(64)` 每空间一个、64 是**每接收者的缓冲深度**而非订阅者上限、
   端点 `GET /spaces/{id}/changes-stream`、落后发 `{"type":"ping"}`、
   推送帧 `{"type":"push","space_id","accepted"}` **无 page_id** —— **全部核实为真**。

## 8. 没做成 / 拿不准 / 环境不具备

- ⚠️ **发生器与服务端同机 16 核**：高 N 时客户端 CPU（M2 N=500 达 5.07 核）与服务端抢核，
  **高 N 的延迟读数是悲观的**（含 CPU 饥饿，不只是服务端代码）。要干净的服务端容量数需要**另一台机器**跑发生器。
- ⚠️ **M1 从 N=50 起发生器先饱和**（丢帧比例 10% / 49% / 64% / 98%），
  **M1 N≥50 的读数主要反映"发生器拉不过来"**，不能读成"服务端只能扛这些"。
- ⚠️ M1 N=500 / M2 N=500 出现错误（push 5391 / pull 39098；push 29 / pull 15291），该两格是**崩溃态**读数。
- ⚠️ 每格 pull 用 `since=0&limit=500`（**恒定 500 行**）—— 比真客户端"拉到新增几行"重，
  是为可比性故意选的**保守**口径。
- ❌ **没测**：>500 台（M3 的上限只到 500，未找到其真实拐点）；多空间并发（本压测只用 1 个空间、1 个 broadcast channel）；
  内存长跑泄漏（每格只有 60s）；附件/大 payload 路径。
- ❌ **没测** guard=fidelity 的完整栅格（只补了 M2 N=100/200 两格）。
