## 7. 与你转述不一致的地方（逐条）

1. **读连接池只有 4 条**（`src/main.rs:280` `open_read_pool(&db_path, 4)`，硬编码，无配置）。
   你的背景里没提这条 —— 它意味着**最多 4 个 pull 真正并行**，第 5 个起在 4 个互斥量上排队。
2. **"每个订阅者各拉 1 次"只在你给的模型里成立，真客户端不这么做**：
   `src/hooks/useSyncStream.ts:51,55` 有 `busy` **防重入**（同时最多 1 个 pull 在飞），
   桌面路还多一层 `PULL_DEBOUNCE_MS = 300` 去抖（`ping` 走立刻拉、不去抖）。
   ⇒ N² 是**上界**。实测（我照真语义加严实现 `--guard busy`）：
   M2 N=100 只发出 **806/2501 = 32%** 的读；N=200 只发出 **1350/9999 = 13.5%**，pull P95 从 214ms 掉到 22.8ms。
3. **web 路收到 `ping` 也会拉**（`useSyncStream.ts:140` 只判 `frame.includes("data:")`，ping 帧同样是 data 帧）。
   所以"落后 ⇒ ping"在客户端不会降载，反而再触发一次 pull。
4. **广播是在持有写锁时发的**：`sync.rs:225` 的 `publish_space_change` 在 `conn`（写锁 MutexGuard）**仍未释放**时调用。
   `broadcast::Sender::send` 本身不阻塞（旧槽位直接被覆盖），所以不是死锁，但"写路径上不带广播"这句话不成立。
5. **每次 pull 是两条查询**：`require_space`（查 `space_members`）＋ 变更查询（`sync.rs:248-249`）。你的描述只算了索引扫描。
6. **`idx_changes_seq` 只索引 `seq` 一列**（`db.rs:29`），查询却按 `space_id` 过滤 + `seq` 排序。
7. 你说的"没有任何设备数/连接数/限流上限"——**核实为真**（grep `MAX_|rate_limit|quota|semaphore` 在 `src/` 下为空）。
8. `pull` 用只读池、`idx_changes_seq`、`limit` 默认 500/clamp 1000、`Arc<Mutex<Connection>>` 单写锁、
   `broadcast::channel(64)` 每空间一个、64 是**每接收者的缓冲深度**而非订阅者上限、
   端点 `GET /spaces/{id}/changes-stream`、落后发 `{"type":"ping"}`、
   推送帧 `{"type":"push","space_id","accepted"}` **无 page_id** —— **全部核实为真**。

# 附二：**两个"上限"的区别 —— 加服务器能不能解？**

> 起因：owner 问「这个设备上限可有提高的可能？」→「增加服务器可以吗？」
> ⚠️ 先分清两个不同的"上限"，否则会拿错的药治错的病。

## 1. 两个上限
```text
① **总容量**：平台能装多少空间 / 多少团队
② **单空间上限**：**一个**空间能挂多少台设备（＝本报告测的那个，M2≈100 台）
⇒ **加服务器对 ① 有效，对 ② 基本无效。**
```

## 2. ① 总容量 ⇒ ✅ **可以，而且今天就能做，零代码改动**
```text
证据：
· `sync_profiles` 的行形状 = `ws_id, server_url, token, space_id, last_pushed_seq, last_pulled_seq`
  （`src-tauri/src/sync.rs:720` / `:780`）⇒ **每个本地空间（ws_id）各自绑一台服务器**
· 服务端每个空间是独立的（各自的 members／各自的 channel／各自的数据）
⇒ ⇒ **按空间分片**：一台服务器管一批空间，客户端把不同空间指到不同服务器 ⇒ **线性扩展**
⇒ 这就是"加服务器"在这套架构里的**正确用法**。
```

## 3. ② 单空间上限 ⇒ ⚠️ **不能靠加服务器**（障碍很具体）
```text
★ 关键：`seq INTEGER PRIMARY KEY AUTOINCREMENT`（`src/db.rs:19`）
  ⇒ **seq 是【表级全局单调】，不是空间级**
  ⇒ 而客户端把它当"**空间水位**"用（`last_pulled_seq` 存在 `sync_profiles` 里，per ws_id）
  ⇒ ⇒ **同一个空间的数据必须在一张表里** —— 否则两台机器各自 AUTOINCREMENT 会给出
     两套**不可比**的 seq，客户端那个唯一的水位就失去意义。

叠加的三条障碍：
  · **写是单写者**（`Arc<Mutex<Connection>>`）
  · **SSE channel 在内存里** ⇒ 每台只知道自己收到的写 ⇒ 另一台上的订阅者收不到推送
  · **`pull?since=<seq>` 的语义**依赖那个单调序列

⇒ ⇒ 要真把单空间分片，得先：
   ① 把 seq 改成**空间级**（`MAX(seq)+1 WHERE space_id=?`）⇒ 那引入"同空间并发写抢序列"
   ② 让广播跨机（外部队列之类）
   ③ 处理"副本滞后 ⇒ 订阅者读到旧水位"
   ⇒ **成本：一个台阶**（协议 ＋ 一致性），且会动服务端私有仓。
```

## 4. ⭐ 结论
```text
**可以加服务器 —— 但它扩展的是"能装多少个空间"，不是"一个空间能挂多少台设备"。**

· 想多接团队/多接空间 ⇒ ✅ 按空间分片，今天就通（客户端每空间各绑一台，架构本来就支持）
· 想让【一个】空间挂更多设备 ⇒ ⚠️ 加服务器帮不上；该做的是【**少拉**】（见附三），不是【多机】
```

# 附三：**提高「单空间上限」的路线**（按性价比，含实测依据）

> ⚠️ 总原则：**扇出是 N² ⇒ 优化常数只能提 20%~2 倍，改变形状才能提 10 倍以上。**
> 所以下面按"改变形状"的力度排，而不是按"工程难度"排。

## L0 · 今天（M2 形状）≈ **100 台**
```text
1 次写 ⇒ N 个通知 ⇒ **N 次 pull，每次拉整个空间** ⇒ 读/秒 = 0.25·N²（实测四点误差 <0.1%）
```

## L1 · ⭐ **让只读设备不订阅通知** —— 实测 **10 倍**（**只改客户端，不动服务端**）
```text
实测：M2 ≈ 100 台 → M3 ≈ 200 台，读/秒差 **9.92 倍**（算术 9.94，误差 <0.5%）
做法：按"这个空间我最近编辑过吗／是不是正在看这一页"决定订不订阅（presence 已有雏形）
代价（如实）：只读者从"**通知即拉**"退化成"**按间隔拉**"
⇒ **性价比最高：一步 10 倍、不动服务端、不改协议。**
```

## L2 · **`push` 帧带页级定位** ⇒ 降**每次** pull 的成本
```text
今天：帧只有 `{"type":"push","space_id":…,"accepted":count}` ⇒ 客户端只能拉整个空间
改后：带上"改了哪几页" ⇒ 客户端只处理那一页（服务端再支持按页拉后，只拉那一页）
⇒ 它降的是【每次成本】，不是【次数】⇒ 与 L1 叠加最好
成本：中（要动服务端私有仓 ⇒ 要 owner 点头）
```

## L3 · **服务端优化常数** ⇒ 20%~2 倍
```text
· **读池 4 → 16/32**：`main.rs:280 open_read_pool(&db_path, 4)` 硬编码 ⇒ 第 5 个 pull 起排队
  ⚠️ 但实测 M2 N=200 时 CPU 已 4.33 核 ⇒ **CPU 才是瓶颈**，加读者未必立刻有用
· **清冗余索引**：`db.rs:29 idx_changes_seq(seq)` 与 `db.rs:724 idx_changes_space_seq(space_id, seq)`
  并存；而查询是 `WHERE space_id=? AND seq>? ORDER BY seq` ⇒ 复合索引才对，
  那条只有 seq 的**每写一行都要维护**（压测说的"索引与查询不匹配"**不准确** —— 真问题是**冗余**）
· **合并 pull 的两条查询**：`require_space`（查 `space_members`）＋ 变更查询
· ⚠️ **`ping` 限频**：`ping` 触发"立刻拉"是**设计如此**（代码注释明写），
  但它构成**正反馈**（负载高 ⇒ Lagged 多 ⇒ ping 多 ⇒ 拉更多）⇒ 该限频（例如 1 秒内多个 ping 只拉一次）
```

## L4 · ⭐⭐ **改变形状：从"通知＋全量拉"改成"服务端转发增量"**
```text
今天：1 次写 ⇒ N 个通知 ⇒ **N 次 pull**（O(N²)）
L4  ：1 次写 ⇒ 服务端把【那一条变更】直接推给 N 个订阅者（SSE 帧里带 payload）
      ⇒ 扇出 **O(N²) → O(N)**，且省掉 N 次 HTTP 往返 ＋ N 次 SQLite 查询
      ⇒ **这才是"真正的实时"（腾讯/WPS 的形状）**，且单机可以上千台

⚠️ 而它**不必然破 E2E**：个人空间的内容本来就是密文，服务端【转发密文】不需要看懂内容。
   ⇒ 团队空间明文 ⇒ 更没问题。

⚠️ 但代价（且与既有口径冲突）：
   ① 帧要带 payload ⇒ broadcast channel 内存 = 64 × payload × 空间数
   ② 客户端要从"收到就拉"改成"收到就应用" ⇒ **绕过既有 outbox/水位路径**
      ⚠️ 而「拉取语义一行不改」是那条流的设计稿**明文非目标**
   ③ 断线重连要能补（不能只靠最后一条）⇒ 需要"增量 ＋ 水位"双轨：
      帧里带 `seq` ⇒ 客户端发现跳号就回退去拉（既有路径仍在 ⇒ 是**兜底**不是替代）
⇒ ⇒ **可行，但它是"另一片"，且要 owner 拍（因为撞既有非目标）。**
```

## L5 · **单写多读副本** ⇒ 被 `seq` 挡住
```text
一台主写 ＋ N 台只读副本：读能横向扩，但
  · **seq 是表级 AUTOINCREMENT** ⇒ 副本要么共享序列（协商/慢），要么分段（水位不可比）
  ⇒ 要先做"seq 改空间级"那一大步 ⇒ 排在 L4 之后
```

## L6 · **换存储模型**（分布式/Postgres）⇒ 另一个量级
```text
SQLite 单写者 ＋ 表级 seq ⇒ **"单空间"天然是"单机单元"**
⇒ 突破它等于换掉这套存储模型 ⇒ 不是"加台服务器"那种决定。
```

## ⭐ 而**第一步其实不是优化，是"把真实上限测准"**
```text
本报告给的 N² 是【上界】：真客户端有 `busy` 防重入（`useSyncStream.ts:51,55`），
同时只允许 1 个 pull 在飞 ⇒ 实测 M2 N=100 只发出 **32%** 的读、N=200 只 **13.5%**
  ⇒ pull P95 从 214ms 掉到 **22.8ms**
⇒ ⇒ **M2 的真实上限可能明显高于 100 台** —— 而 `--guard fidelity` 只跑了 M2 的 N=100/200 两格。
⇒ 建议先补这一格（把 guard=fidelity 跑完整栅格），再决定要不要动 L1。
   否则可能在"上限其实够用"的情况下白做优化。
```
