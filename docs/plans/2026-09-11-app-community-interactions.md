# ShuyoNote × 数友社区：互动方案（优先级 + 分阶段）

> 2026-09-11 · **状态：方案，未实施** · 本轮只有这份文档，没有代码改动。

---

## 一、先定一条底线

**数据主权：任何"自动上传"默认关闭；上传前必须给出清单，并由人手动确认。**

诊断包、笔记片段、插件包、草稿——一律如此。这个产品的一切建立在"数据在自己手里"上，
而**互动功能最容易在这里背叛它**：一个"顺手帮你同步"的开关，就足以把前面所有主张作废。
下面每一条都服从这条底线，需要例外的地方会单独写明。

---

## 二、现状：两边已经有什么

判断"接通"还是"新建"，只看已有的东西。

| ShuyoNote（应用） | 数友社区（站点） |
|---|---|
| 本地优先、SQLCipher 加密库 | 帖子 / 评论 / 标签 / 专题 / 板块 |
| 附件**内容寻址**（`/attachments/<sha256>`） | 评论**已支持贴图**（2026-09-11 起） |
| **插件系统**：JS 运行时 + 权限 + 视图（`rail` / `overlay`）+ 触发器 / 事件 | **插件配方**（12 个成品）+ **插件 API 教程** + 「给插件作者」专题 |
| **插件索引：发布者密钥 + 包签名校验 + 撤销名单 + 来源白名单（仅 https / 回环）+ 解压防 zip-slip + sha256 先校验后解压** | 全文检索（FTS）+ 通知流（SSE）+ 关注 / 私信 |
| 邮件转笔记、备份、PDF 阅读与批注 | 公告（置顶）、**「更新日志」板块**、后台（含新增的删帖） |

**结论**：**分发的信任基础在应用侧已经建好了**（签名、撤销、来源限制、完整性）；
社区侧缺的不是"能发内容"，而是**与应用之间的通道**。所以第一优先级不是"做新功能"，
而是**定义通道**。

## 四、分阶段

### P0：最小闭环 —— `shuyonote://` 协议

**做三件事**：社区帖子可"存进笔记"；帖子里的配方可"导入"；应用里可"分享一段到社区"。

- 协议形态：`shuyonote://save?url=…`、`shuyonote://import?url=…`、`shuyonote://compose?title=…&body=…`；
- **导入一律先给清单再执行**（装什么、要什么权限、来源是谁），与插件权限模型一致；
- **分享默认只带摘要 + 原帖链接**，全文要不要发由人点。

**验收**：社区帖子页出现"存进笔记"入口；应用收到链接后弹出确认框并成功落库；
分享后的帖子带着来源标注。**不做**：自动同步、静默导入、后台轮询。

### P1：身份、讨论与更新（把两边"看成同一个产品"）

- 应用内显示"我的帖子 / 我的插件"（复用登录令牌）；
- 插件详情页显示社区里关于它的讨论（一次检索）；
- **应用检查更新直接读社区的「更新日志」板块**，不再两边各写一遍；
- 问题反馈生成**脱敏诊断包**（版本、插件清单、日志片段，**绝不含笔记内容**），
  弹预览让人删减后再发。

### P2：内容与分发

- **社区精选离线读**：精华帖同步进应用，可离线读——本地优先的社区版；
- **社区作为插件索引来源**：应用"发现插件"能列出社区上架的插件；帖子携带可校验的包
  （sha256 + 发布者签名），应用侧沿用已有的签名/撤销/来源校验，**不新增信任假设**。

## 五、明确不做（附理由）

| 不做 | 理由 |
|---|---|
| 笔记库整体同步到社区 | 与"本地优先"直接冲突；社区不是备份服务 |
| 静默上传（含静默遥测） | 底线条款 |
| 自动安装社区里的插件 | 安装必须由人确认；签名只保证"来源可信"，不保证"你想要" |
| 应用内嵌社区网页 | 维护两套 UI；协议跳转足够 |
| 社区侧存笔记正文副本 | 数据主权主张不允许；只存人主动发布的内容 |

---

## 六、建议的执行顺序

**P0（1 天量级）→ P1 中的"更新日志单一来源"与"讨论串"（各半天）→ 再评估 P1 其余与 P2。**

理由：P0 全部是"接通"（不改数据模型、不动信任链），能立刻用上；
P2 的插件分发虽然最有产品价值，但它会**改动分发链路**，应当在前面几条把
"应用 ↔ 社区"的通道跑顺之后再动。
