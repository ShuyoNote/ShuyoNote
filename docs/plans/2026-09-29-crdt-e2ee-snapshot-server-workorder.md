## 1. 为什么现在做它（不是"防患于未然"）

```text
尖刺已证【E2EE 之下 CRDT 可行，服务端可以继续"哑且盲"】✓（13 通过 / 0 失败）——
  它在 Node 里用真 `yjs` ＋ 真 `@lexical/yjs` ＋ `node:crypto` 的 AES-256-GCM 代指内容层加密跑通 ✓
体积读数（同步预算要用 ✓）：单条增量 **明文 ~112 B → 密文 140 B**（+28 B = GCM 的 iv+tag ✓）
收敛读数：客户端产**加密快照** ⇒ 服务端**丢掉全部旧 blob** ⇒ 新设备只用「快照 + 之后的增量」⇒ 收敛 ✓；
  服务端占用 **249 B → 175 B** ✓
⇒ 协议可行性与客户端那一半**都已验** ✓；缺口只剩【**服务端接口改动**】与【**真机多设备**】✗
```

## 2. 要改什么（服务端那一半；本仓只写接口契约，实现落在 `shuyonote-sync-server`）

```text
① 上传：`PUT /spaces/:id/snapshot` —— 收**一个不透明密文 blob** ＋ `snapshotSeq`（它覆盖到哪一条）
     服务端**不许**解析、不许看字段、不许记密钥 ✓（"哑且盲"就是判据 ✓）
② 下载：`GET /spaces/:id/snapshot` ⇒ 老设备/新设备拿到同一份密文 ✓（幂等 ✓）
③ 退役：服务端在**确认快照已收妥**后，丢掉 `seq <= snapshotSeq` 的旧增量 blob ✓
     ⚠️ 顺序必须是"先落快照、再丢旧的"✗ 反了就是**不可逆的数据丢失** ✓
④ 权限：与现有空间鉴权同一套 ✓；**不引入**任何"服务端可解密"的分支 ✓
```

