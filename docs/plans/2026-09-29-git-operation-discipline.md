# git 操作纪律 —— **从 2026-09-29 的四次失误里收出来的**

> 由来：owner 2026-09-29「持续自主工作」；而我在这一天里**犯了四次 git 失误**。
> ⇒ 本文件把教训**收成一条条可执行的规则** —— 因为它们的共同点是
> **"看起来没问题、事后才发现在别处留了痕"**，且**没有任何判据会替我拦住**。

---

## 1. 四次失误（**都真实发生过，都留了痕**）
### ① `git add -A` 把别人的临时文件带进 HEAD
```text
当时：我 `git add -A` 提交自己的一批文档，而**另一位执行者**在树里放了一个临时文件
      （`scripts/frames-node-gen.test.mjs`）⇒ **被我一起提交进 HEAD**。
后果：那个不该进仓的文件进了 HEAD（后来单独提交了它的删除 `154dc8f9`；**没有改历史**）。
⇒ ⚠️ 根因：`-A` 的语义是"**整个工作树**"，而工作树**不是只有我的东西**。
```

### ② `git commit -m "…"` 里的反引号被 shell 吃掉（**一天里 3 次**）
```text
当时：在 `-m "…"` 里写 `` `code` `` ⇒ **shell 先做命令替换** ⇒ 内容被替换成命令输出（或空）
后果：提交信息**静默变形**（内容少了一块，而 commit 照样成功 ⇒ **不会报错**）。
⇒ ⚠️ 根因：**双引号里反引号仍会展开**。
```

### ③ `git commit`（**不带 pathspec**）带走了别人暂存的 `git rm`
```text
当时：我只 `git add` 了**我自己那一个文件**，然后 `git commit`（**不带 `-- <files>`**）
      ⇒ 而**另一位执行者当时 `git rm --cached` 暂存了一个删除**（312 行）
      ⇒ **它被我的提交一起带走了** ⇒ 那个删除进了**我那一笔**的 diff。
后果：一笔"文档提交"里混进了 312 行代码删除 ⇒ **提交的语义被污染**（后人看 log 会误判）。
⇒ ⚠️ 根因：**`git commit` 提交的是【整个暂存区】**，不是"我刚 add 的那些"。
```

### ④ `--no-verify` 未写理由（**一次**）
```text
当时：信箱仓的 `pre-push`/`pre-commit` 被**四条既存红**拦着，我直接 `--no-verify` 推了。
问题：本仓 K11 的规矩是「**never `--no-verify` except with a written reason**」
      ⇒ 我第一次**没写理由**就绕了（后来补写了，并把四条红的清单写进提交信息）。
⇒ ⚠️ 根因：把"**绕门禁**"当成了"**让路**"—— 而它们的区别就是**有没有留下理由**。
```

## 2. ⇒ 收成的规则（**六条，按发生概率排**）
```text
**R1 · 提交一律带显式文件清单**
   `git commit -m … -- <file1> <file2>`
   ✅ 好处：**pathspec 会覆盖"整个暂存区"的语义** ⇒ 别人暂存的东西带不走（防 ① ③）
   ⚠️ 或退一步：提交前 `git status` **看一眼暂存区是不是只有自己的东西**

**R2 · 提交信息一律用 `-F <file>` 或 heredoc，绝不用 `-m "…"` 写反引号**
   ✅ 防 ②（shell 命令替换）

**R3 · `git add` 一律列显式路径，禁用 `-A` / `-u` / 通配**
   ✅ 防 ①（把别人的临时文件带进仓）

**R4 · 用 `--no-verify` 时必须**在同一笔提交信息里写清理由**（含"哪几条红、为什么与本笔无关"）
   ✅ 满足 K11 的"with a written reason"（防 ④）
   ⚠️ 而 **push 的 `--no-verify` 无处写理由** ⇒ 理由要写在**被推的那笔提交**里（可追溯）

**R5 · 多执行者在同一树里时，提交前先核"暂存区里有没有不是我的路径"**
   `git diff --cached --name-only` ⇒ **逐个认领**（防 ③）

**R6 · 提交后立刻 `git show --stat` 核一眼**（确认改动数与预期一致）
   ✅ 这是唯一能发现"带走了别人的东西"的动作（防 ③）
```

## 3. ⚠️ 而它们的共同点（为什么值得单独记一份）
```text
**四次都满足"看起来成功 + 没有任何判据变红"：**
  · ① 提交成功，门禁绿（那个临时文件本身合法）
  · ② 提交成功，信息只是**少了一块**（没人比对）
  · ③ 提交成功，diff 里多了 312 行（**而它恰好是"合理"的删除** ⇒ 不显眼）
  · ④ 推送成功（门禁本来就红，绕与不绕都红）
⇒ ⇒ **它们全靠"人回头看"才发现** —— 这正是本仓反复强调的那类问题：
   **"写在文档里的规矩会在顺手时消失，而消失时没有信号"**（`knowledge-base-ai-coverage-plan:614` 同义）。
⇒ ⇒ ⇒ 所以本文的价值不在"记下规矩"（规矩本来就有），而在
   **把"什么信号能证明我违规了"写下来**（R1–R6 每条都配一个可查的动作）。
```

## 4. 一句话
```text
**四次失误的共同形状是"提交成功、判据全绿、痕迹在别处"。**
⇒ 六条规则里最要紧的是 **R1（提交一律带显式文件清单）** 与 **R6（提交后 `git show --stat` 核一眼）**：
   前者**事前**防"带走别人的"，后者**事后**能发现。
⇒ ⚠️ 而 `--no-verify` 不是不能用 —— 是**必须写理由**（否则它就从"让路"变成"关掉门禁"）。
```
