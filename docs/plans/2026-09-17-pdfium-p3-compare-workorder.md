# PDFium P3 · 对拍施工单（**不做对拍不算完成** —— 方案 §4 验收第 1、2 条）

> 状态：**施工单**（2026-09-17）。方案见 [PDFium 替换方案](2026-09-16-pdfium-engine-plan.md) §4/§2-P3。
> 前置：**P2 已落地**（`feat/pdfium-engine @ 6caa4e0`：`SHUYONOTE_PDF_ENGINE=pdfium` 走 PDFium，缺省仍 MuPDF）
> ⇒ **两引擎已可切换，对拍的前提具备**。

---

## 0. 为什么必须先说清"谁跑"

**Windows 本机跑不了 `cargo test`**（`0xC0000139`）⇒ 对拍**不可能在 Windows 上执行**。
所以形态固定为：**Windows 写 harness 与样本生成脚本 → AMD(WSL2) 或 Mac 执行并出报告**。
（谁执行无所谓，但**报告必须写清"在哪台机、什么 commit"**，见 `development.md` §10.5。）

## 1. 放哪里：**crate 内的 `#[cfg(test)]`，不是 integration test**

`pdf_native` / `pdfium_native` 都是**私有模块**（`lib.rs` 里 `mod pdf_native;`）
⇒ `src-tauri/tests/*.rs` 这种集成测试**够不到它们**。
⇒ 落点：`src-tauri/src/pdf_engine_compare.rs`，模块内 `#[cfg(test)] mod tests`，
`lib.rs` 加一行 `#[cfg(test)] mod pdf_engine_compare;`。

## 2. 缺什么依赖（仓库现状：**没有**任何图像/比对工具）

| 需要 | 现状 |
|---|---|
| 图像编解码（落盘 PNG 给人目视） | ❌ `image`/`png` **都不在 `Cargo.toml`**（`image 0.25` 只是 `pdfium-render` 的**传递**依赖，用不了） |
| 像素比对 | ❌ 无（`dssim`/`pixel` 都没有） |

⇒ **结论（2026-09-17 改）：Rust 侧零新依赖。**

- **比对在 Rust 里做**：两个引擎的输出**本来就都是裸 RGBA**，`std` 足够算「最大通道差 / 超阈占比」；
- **落盘也写裸 RGBA**（`<样本>-<页>-<引擎>.rgba`），**PNG 编码交给 Node 侧**：
  `node tmp/fixture/rgba-to-png.mjs <in.rgba> <w> <h> <out.png>`（只用 `node:zlib`，标准库）
  —— **已在本机验证**：4×3 常量图 → PNG 71 字节，读回 PNG 头 `89504e47…` ＋ IHDR 宽高均正确。
  ⇒ **不必给 Rust 加 `image`**（原方案那笔省掉），而且**编码这一步在 Windows 上就能验**。
- **不要**引 `dssim` 之类的感知指标——第一轮只要"能看 + 有数字"，别把判据复杂化。

## 3. 判据（**可量化 + 必须人工目视**）

方案 §4 的原话是「目视一致，像素差异在约定容差内」。落成三条：

| # | 判据 | 阈值（第一版） |
|---|---|---|
| 1 | **尺寸必须完全相等** | `w/h` 逐引擎一致（不等直接 FAIL，不进像素比对） |
| 2 | **逐像素最大通道差** | ≤ **8**/255 |
| 3 | **超阈像素占比** | ≤ **0.5%** |

⚠️ **两条纪律**：
- **不许用自动判据替人签字**：即使三条全过，也**必须把两张 PNG 落盘**（`tmp/pdf-compare/<样本>-<页>-<引擎>.png`）**由人看一眼**——
  「能显示但不对」（颜色错乱、字体替换、透明底变黑）恰恰是阈值抓不住的那类；
- **阈值是约定不是真理**：PDFium 与 MuPDF 的字形栅格化/抗锯齿本来就不同，
  「像素完全一致」不现实 ⇒ 阈值要写进报告，**改了阈值也要写**。

## 4. 样本集（方案 §0.2-H：**写生成脚本 ＋ 少量产物入库**）

自制样本，**无版权风险**，且结论可复现。至少覆盖方案点名的六类：

| # | 样本 | 为什么必须有 |
|---|---|---|
| 1 | 印刷体正文（多字体） | 基线 |
| 2 | **中文** | 字体回退/子集化是最容易不一致的地方 |
| 3 | **扫描件**（整页位图） | 走的是图像解码路径，与矢量完全不同 |
| 4 | **旋转页**（90/180/270） | 旋转语义两引擎历史上就易错 |
| 5 | **超大页**（或高倍率） | 触发 `MAX_PAGE_PIXELS` 与内存路径 |
| 6 | **透明底** | 暗色主题下最容易"能显示但不对" |

**生成脚本**：`scripts/make-pdf-fixtures.mjs`（自写最小 PDF 字节，不引第三方库——它们是**测试夹具**，
引依赖等于给夹具加供应链）。产物落到 `src-tauri/tests/fixtures/pdf/`（**少量、小体积**，入库）。

## 5. 报告格式（贴在信箱 + 落一份文档）

| 样本 | 页 | 引擎 | 尺寸 | 最大通道差 | 超阈占比 | 单页耗时 | 目视 |
|---|---|---|---|---|---|---|---|
| 中文 | 1 | MuPDF / PDFium | 相等? | n / n | x% / x% | ms / ms | 一致? |

外加：**执行环境**（`uname -a` / `rustc -V`）、**被验 commit**、**PDFium 版本**（build 7881）、
**是否 `no-asm`**（若自建）。最后一行给**结论**：可切默认 / 需修 / 需重定阈值。

## 6. 顺序与分工

1. **Windows**：写 `pdf_engine_compare.rs` ＋ `make-pdf-fixtures.mjs`，并保证 `cargo check --tests` 过（**能编不等于能跑**）；
2. **AMD(WSL2)/Mac**：`fetch-pdfium.mjs` 取库 → `cargo test pdf_engine_compare -- --nocapture` → 交报告 + PNG；
3. **Windows**：把报告收进文档，再决定是否把默认引擎切到 PDFium（方案 P5 灰度那步）。

**未做前，PDFium 一律不切默认**（缺省仍是 MuPDF）——这是回滚能力的保证。
