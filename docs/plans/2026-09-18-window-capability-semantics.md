# 窗口类能力的口径（草案 · v1）

> 2026-09-18，macOS 侧。**这是一份草案**：内容是`pages.get` / `files.read` / `blocks.list` /
> `pages.search` / `files.search` 这五条"会返回一段窗口或一页结果"的能力**已经落地并有判据**的口径，
> 目的是让**下一个**窗口类能力有现成规范、不必每次重新吵一遍。
> 请 Windows 裁定后把它转成契约正文（`docs/plans/2026-09-17-knowledge-base-ai-coverage-plan.md` §15 那一节旁边）。

## 0. 一句话

**"成功"不等于"读全了"** —— 只要返回的是一个窗口/一页，就必须让调用方能算出"还有没有、从哪继续"，
否则模型会把窗口当整页、然后自信地总结一个片段（与抽取层 `ExtractCoverage` 同一条原则，方案 §15.10）。

## 1. 三条硬口径

### 1.1 计数与切片按 **Unicode 标量（码点）**，不是码元、不是字节

- Rust 侧 `chars()`，TS 侧 `Array.from` —— **两侧同一个口径**；
- 为什么：emoji / 部分生僻字是代理对，`slice` 会切出孤立代理（解码方通常换成 U+FFFD），
  而 `"😀".length === 2` 会让 `chars_total` 直接算错；
- 判据：`tests/pages-get-window-parity.json` 的 emoji 用例（100 码点 / 200 码元）。
  **两侧读同一份夹具、逐字比对**，任一侧换成 `slice` 都会红。

### 1.2 越界**不是错误**

- `offset` 超过总长 ⇒ **空串 + 真实的 `chars_total`**（不是报错、不是 `null`）；
- 为什么：调用方要能区分"我翻过头了"与"这页是空的" —— 后者是内容问题，不该被当成翻页结束；
- 判据：夹具的 `offset 远超过总长` 用例 + `pagesGet.test.ts`。

### 1.3 `truncated` 的含义是「**还没读完**」

- 即"窗口没够到末尾"（`offset + returned < total`），**不是**"这页太长"；
- 为什么：等价于"太长"时，翻到最后一页它仍是 `true` ⇒ 模型以为还有内容、无限往下翻；
- 判据：夹具的 `翻到最后一页` / `恰好整除` 两个用例。

## 2. 参数口径（与 Rust `arg_i64` 逐值一致）

数值参数统一走**一个实现**：TS `intArg(args, 名, 默认, 最小, 最大)` ↔ Rust
`arg_i64(名, 默认)` + `clamp(最小, 最大)`。语义（`tests/numeric-arg-parity.json`，21 例）：

| 输入 | 取值 |
|---|---|
| 整数 `3` | 3 |
| 整数字符串 `"3"` / `"+7"` | 3 / 7 |
| **整数值浮点 `2.0`** | 2（JS 的 `JSON.parse` 会把它折成 2，所以只有 Rust 侧让步才对齐） |
| 非整数浮点 `2.5` | **回落默认值**（不取地板 —— 取地板会让两端得到 2 与 6000） |
| `0` / 负数 | **合法值**，再由 `clamp` 夹到下界（`pages.get` ⇒ 1；`offset` ⇒ 0） |
| `null` / 布尔 / 数组 / 对象 / 非数字字符串 / `" 7 "` | 回落默认值（**不做 trim、不做 JS 强制转换**） |
| 超上限 | 夹到上限 |

⚠️ **`0` 不是"没传"**：写 `args.limit || 默认` 或 `limit > 0 ? limit : 默认` 会让 `0` 走默认值，
而 Rust 是 `clamp(1, ·)` ⇒ 两端差 6000 倍。这一天里这个坑在**四个适配器**上各犯了一遍。

## 3. 返回形状

窗口类能力必须给出**至少三个读数**：

```
content_text / segments ...   ← 窗口本身（**忠实原文的窗口**，不改写、不补省略号）
chars_total / total           ← 总数（按 1.1 的口径计数）
offset / limit                ← 本次窗口的坐标（便于调用方算出下一步）
truncated                     ← 是否还没读完（按 1.3）
```

- **不补 `…`**：原文可能本身就以省略号结尾，模型分不清哪个是我们加的；
- "截断"要靠**显式字段**说，不靠文案；并在 `note` 里给出**下一步可执行的** `offset`。

### 已知缺口（等 Windows 裁定，本草案不拍板）

1. `blocks.list` 返回的是**数组**，`limit` 截断后**没有任何信号** ⇒ 三个选项：
   (a) 数组 + 文档写明（现状）；(b) 加姊妹能力 `blocks.count`；(c) 改返回形状（会破坏既有插件）。
2. `files.read` 的窗口单位是**段落（segment）行**，`pages.get` 是**码点** ——
   两者都叫 `offset`/`limit`。是否要求在 `desc` 里显式写单位？（本草案倾向：**必须写**。）

## 4. 描述必须说清"单位"与"面"

同一条能力可能有两个**行为不同**的面（`pages.search`：插件面是子串 `LIKE`；应用内 AI 检索是
词频排序 + 本地嵌入语义加分）。这类差异**必须在注册表的 `desc` / `returns.desc` 里写明**，
否则同一个 `desc` 会同时骗到插件作者与模型（`e5d19436` 就是修这个）。

## 5. 判据清单（新加窗口类能力时照抄这几条）

1. **跨语言夹具**登进 `tests/*-parity.json`（两侧读同一份、逐字/逐值比），
   至少含：中段窗口、头部窗口、最后一页、恰好整除、越界、emoji、`limit=0`、超上限；
2. **参数口径**用例（走 `numeric-arg-parity.json` 那张表的语义）；
3. **机器判据**：`check-capabilities` 会比对注册表 ⟷ Rust dispatch 的参数/默认值，
   以及注册表 ⟷ TS 适配器的参数覆盖 —— 新能力不改脚本就能被覆盖；
4. **变异验证**：把两侧任一处改成"差不多但不一致"的写法，判据必须红（当天四个分歧全是这么证的）。
