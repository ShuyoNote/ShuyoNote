## 1. 我选的喂帧路径（＋为什么它是"真实路径"）

### 1.1 先说清"桌面今天到底怎么应用远端帧"（读代码得到的，不是猜的）

```text
Rust pull 收到带 `crdt_state` 的页载荷
  ⇒ src-tauri/src/sync.rs:284 `page_crdt::put_pending_state(...)`   ← **只收字节，不合并**
  ⇒ 唯一的"应用"落地：src/lib/crdt/pageBinding.ts:371 `session.merge(p.state)`
     （在 `bindPageToEditorViaPort` 的待并循环里，**打开页面时**逐条合并，每页上限 24 条）
Web 平台不同：src/lib/platform/web.ts:885 `applyRemoteCrdtState(...)`
  ⇒ src/main.tsx:36 `mergeRemotePageState(db, pageId, state, Date.now())`（当场合并）
⇒ ⇒ **桌面今天没有"帧到了就应用"那条路** —— 帧先躺在 `page_crdt_pending` 里。
```

⇒ 本压测就喂这两个**真实应用点**：

| 档 | 喂的函数 | 对应生产的哪一处 |
|---|---|---|
| **A**（主档） | `pageBinding` → `yDocBridge` 的 `session.merge(remote)`，会话挂在**页面里那个真编辑器**上 | 桌面 `pageBinding.ts:371` 的待并循环（逐帧） |
| **B**（对照） | `pageBinding.mergeRemotePageState(db, ...)`，`db` 用假 `ContentSql` | Web / 将来 L4 的"收到就应用"那条路（`main.tsx:36`） |

### 1.3 帧是怎么造的（真字节，不手搓）

```text
① 用真 `openPageSession({ json: seed })` 建基线血统；
② 另开一个 `Y.Doc`，`Y.applyUpdate(doc, baseline)` 到**同一条血统**（＝"另一台设备"）；
③ `doc.on("update", u => frames.push(u))` ⇒ 每次 mutate 由 **Yjs 自己**编出真增量字节；
④ 每一帧就是那一笔增量（与生产 `page_crdt_pending` 一行一条的状态同一形状）。
```

这条生成器被**单独钉住**了（vitest，**本机能跑**，见 §7）：`/tmp/frames/frames-node-gen.test.mjs`
那份判据证明"200 帧 ⇒ 编辑器正文恰好长 200 字、逐帧可合、重放幂等"。
（⚠️ 它曾被并行的一笔 `git add -A` 带进仓内 `scripts/` 一次 ⇒ 已按 §9 末尾那条处置移除。）

### 1.4 这一场**不**包含什么（写在明处）

```text
· 不含跨进程投递（WebView postMessage / IPC / 网络）—— 那是"帧怎么到"，不是"应用一帧"；
· 不含**真**落盘：桩的 `save_page_state` 是空转（真桌面那一次 IPC ＋ SQLite BLOB 写**更大**）；
· A 档的合并对象是**真编辑器**（DOM 照常 reconcile），输入延迟/FPS/长任务量的是**整个主线程**；
· 帧形状 = **单字符插入**（19–20 字节/帧）。大帧（粘贴、块级重构）没测（见 §8）。
```

## 2. 判据（我自己定的，写在明处）

任一**成立**即算"可观测劣化"：

```text
① 主线程阻塞：`PerformanceObserver('longtask')` 里 duration>50ms 的次数 ≥ **1 次/秒**；
② 输入延迟：端到端"按键 → 编辑器正文里真的多出这个字"的 **P95 > 100ms**；
③ 掉帧：rAF 计数算出的 **FPS < 50**；
④ 定时器漂移：50ms 绝对排程探针的 **P95 > 100ms**（独立于①，能抓住"没到 50ms 但一直在拖"）。
```

另外记一条**辅助读数**：单帧同步耗时（`session.merge` 调用的 p50/p95/max）。
它不参与判劣化（否则等于用"我自己的实现"当判据），但它是"帧率上限"的分子。

## 6. ⚠️ 外推（标明是外推）

```text
按 α=0.1、r=2.5 ⇒ fps = 0.25 · N ⇒ N = fps / 0.25
  · 250 帧/秒（本压测里最舒服的一档）  ⇒ N ≈ 1000
  · 500 帧/秒（舒适上限）              ⇒ N ≈ 2000
  · 600 帧/秒（劣化开始）              ⇒ N ≈ 2400
  · 900 帧/秒（吞吐天花板）            ⇒ N ≈ 3600
⇒ 在 L4 的这条模型下，**客户端不是那个先撞墙的**：一台客户端要吃满 250 帧/秒
  要等到单空间 1000 台；它能吃到 2000 台那一档才开始劣化。
  ⚠️ 这是**外推**（帧形状＝1 字符插入、单页、无加密、本机无其它负载）。
```

## 7. 与你转述不一致的地方（逐条）

1. **桌面今天没有"帧到了就应用"那条路。** pull 只把字节收进 `page_crdt_pending`
   （`sync.rs:284`），唯一的落地是**打开页面**时 `pageBinding.ts:371` 的待并循环；
   而那条循环前面还有 `put_pending_state` 的硬上限 **`MAX_PENDING_PER_PAGE = 24`**
   （`src-tauri/src/page_crdt.rs:82`，超了丢最旧的并 `eprintln` 留痕）。
   ⇒ "从'收到就拉'改成'收到就应用'"（L4 报告 §241）在桌面上**不是改调用点，是要新建一条路**。
2. **每个客户端每秒收到的帧数不是 α·r·N，而是 α·r·N（每人一份）× ……**：按"每笔增量都转发给所有订阅者"
   去算，一台客户端收到的帧/秒 = **写者数 × 每写者帧率 = α·N·r**（N=1000、α=0.1、r=2.5 ⇒ 250）。
   你给的式子 `fps = 0.25·N` 数值上对得上；但要注意它**与"按写批帧"的口径差 N 倍**：
   若服务端按"一次写一个帧"批量发，则每客户端只有 α·r = **0.25 帧/秒**，与 N 无关。
   ⇒ 这个 N 倍的口径差直接决定"客户端是不是瓶颈"，本报告是按**你那个（每增量一帧）**口径答的。
3. **`push` 帧仍然没有 `page_id`**（L4 报告 §99 核实过）⇒ L4 若照这个形状推，客户端拿到一帧
   不知道是哪一页；而"按页合"是这条路的全部意义。
4. **每应用一帧，应用自己那套绑定会触发一次全量状态保存。** 实测：`save_page_state` 次数 ≈ 帧数
   （250 帧/秒 × 30 秒 ⇒ 8183 次；A 档 12 档全部如此，系数 1.02–1.5）。
   机制：帧落回编辑器 ⇒ `yDocBridge` 的 update 监听里 `onLocalEdit` 报一次
   （`Editor.tsx:572` 订阅）⇒ `persist()` ⇒ `port.save` ⇒ `save_page_state(session.exportState())`。
   ⇒ **L4 的每帧成本 = 合并 ＋ 一次全量状态序列化（＋桌面侧 IPC/SQLite 写）**，
   我量到了前两项、没量到后两项。
5. **B 档的成本大头是"每帧两次整页投影"而不是合并**：`mergeRemotePageState` 逐帧调
   `projectStateToJson(mine)` 与 `projectStateToJson(merged)`（`pageBinding.ts:234`）各一次，
   而 `yDocToContentJson` **每次新建一个 `Y.Doc` ＋ 一个 headless Lexical editor**
   （`yDocBridge.ts:163-168`）⇒ p50 从 0.6ms 抬到 2.4ms、FPS 在 250 帧/秒掉到 49.5。
   ⇒ "增量转发"要把**投影也做成增量**，否则瓶颈会从网络移到这一层。
6. **上一场压测那句"客户端（发生器）CPU 5.07 核（M2 N=500）"不能直接读成"客户端的合并成本"**：
   那 5.07 核是**发生器**（假设备只打 HTTP、不做 CRDT）＋ 该格已过载（达成率 13%）。
   本场量到的是**应用一帧**本身：**0.6–0.8ms/帧 ⇒ 250 帧/秒 ≈ 0.15–0.2 核**。
   两个数不是一回事（**"拉一次"与"应用一帧"是两笔成本**）。
7. **`vitest` 本机能跑**（另一笔说跑不通）：`node node_modules/vitest/vitest.mjs run src/lib/crdt/yDocBridge.test.ts`
   ⇒ **8 tests passed**（525ms）。我用它钉住了帧生成器（200 帧 = 200 字符、可合、幂等）。
8. **`getRootElement().getTextContent()` 在 lexical 0.50 上不存在** —— 我第一版用它测"帧有没有落到编辑器"，
   被 try/catch 吞成 `""` ⇒ `editor_text_gained` 恒 0 的**假读数**（差点当成"帧没落进编辑器"）。

## 8. 没做成 / 拿不准 / 环境不具备（如实）

1. **真 Tauri IPC ＋ SQLite 写没量到**：桩的 `save_page_state` 是空转 ⇒ 桌面那一次
   "全量状态过 IPC ＋ BLOB 事务"的耗时**不在读数里**。只量到了 JS 那一半（<0.03ms + ≈1 B/字）。
2. **帧形状单一**：只测了"1 字符插入"（19–20 字节/帧）。**没测**大帧（粘贴、块级重构、格式变更）、
   **没测**多页并发、**没测**加密空间与数据库页。
3. **堆增长的成因没有定论**：A 档 500 帧/秒跑 30 秒后堆 246MB（起点 88MB），
   线性约 **10KB/帧**，而同期文档本身只有 21KB ⇒ 数字对不上"文档变大"。
   30 秒窗口分不清"没回收的垃圾"与"真泄漏"；**没有做堆快照/分配采样** ⇒ 我只能报读数，
   不解释成因。按线性外推 500 帧/秒 ≈ **5MB/秒**，值得单独查（长跑 + heap snapshot）。
   而 B 档在 250/500 帧/秒出现 **1.7–2.7 秒的单次卡死**，我怀疑是 GC（未证实）。
4. **输入延迟这一维偏乐观**：`execCommand('insertText')` 的"按键→DOM"是同步路径、亚毫秒；
   它**没有**覆盖"连续打字时编辑器积压"（真用户是连续敲）。判据②因此形同虚设 ⇒ 我主要靠 ①③④ 判。
5. **A 档与"真生产"有一处结构性差异**：页面里那个真编辑器上同时挂着**应用自己的会话**与
   我的压测会话，两者各自持一份 Y.Doc，编辑器看到的是"谁最后合并谁赢"。
