# 附件同步「按需取字节」立项（P6）—— 第一步：每空间开关

> **依据**：`docs/plans/2026-09-15-attachment-sync-scope-plan.md` 的 **P6**；2026-09-15 **发布者裁定立项**，
> 并按该方案 §九 的建议**先只做「每空间开关」那一半**（成本低、立刻可用、不引入"未下载"状态）。
> **一句话目标**：让"这个空间的附件要不要同步"成为**显式选择**，而不是只能全量接受。
> **状态**：**已立项，未实施**。本文是 P6 的立项书 + **P6.1 的可执行施工单**。
> **范围**：客户端为主（`src-tauri/src/{db,sync,attachments}.rs`、`src/lib/platform/{commands,web}.ts`、
> `src/components/SyncPanel.tsx`）；**不改服务端**（服务端已有按 hash 取单件的接口）。
> **执行方式**：按 §四 的文件清单逐条做，每步带判据；§五 的设计决定**先拍板再动代码**。
> ⚠️ **前置依赖**：**必须先在 `SyncPanel` 补 `useSyncStatus.end()`（＝上游方案的 B2）**——

## 一、为什么立项，以及为什么只做这一半

来自 `attachment-sync-scope-plan` 的结论：附件同步的语义是**把整个空间在设备上做一份完整副本**
（`sync.rs:1496` 的双向全集差集），桌面上合理，**手机上同时缺体积预算、磁盘余量、网络闸门**。

那个方案给了两道防线，**它们是互补的，不互相替代**：

| | 作用 | 状态 |
|---|---|---|
| **C1 预算刹车** | **保险**：本次最多下多少、磁盘留多少 ⇒ 防"一次拉爆" | 待做（Android 上架前） |
| **P6（本文）** | **选择**：这个空间的附件**根本要不要拉** ⇒ 防"本来就不该拉" | **本次立项** |

⇒ **"刹车"是兜底，"开关"是意愿**。两者都要，但开关更早可用、风险更低。

## 二、一个决定范围的发现：「行有、字节没有」**已经是代码预期的状态**

这是本次立项**最重要的一条**，它把 P6 主体从"要引入新状态"降级为"复用已有语义"。

`attachments.rs:434-436` 的注释原文：

> 找不到文件时说清是"**文件不在盘上**"：这一条最常见的成因是外部把文件删了/移走了，
> **而数据库里那行还在**——笼统的"附件不存在"会让人以为是数据库的问题。

⇒ 也就是说，**「附件行存在、字节不在本机」早就被代码明确预期并给了专门文案**。
而这恰好就是"按需取字节"需要的那个状态。

再叠加两条已有机制：

- **元数据**：附件行随 `changes` 的 `attachment` 实体同步（写入 `attachments.rs:587-588`，
  应用 `sync.rs:1297-1313`）⇒ **不依赖字节同步**；
- **字节**：只有 `sync_attachments` 在管（`sync.rs:1531-1690`）。

⇒ **"只同步元数据、字节按需"= 把 `sync_attachments` 的第 3 步（上传）与第 4 步（下载）关掉**，
而**对端仍然能在文件管理器里看到这些文件**（行在），点开时才提示未下载。

**结论：不需要新的数据库状态、不需要数据模型改动、不需要协议改动。**
本立项因此可以小步走：先用一个开关把这个语义**暴露出来并可用**，再逐步补 UX。

## 五、必须先拍板的设计决定

| # | 问题 | 我的建议 | 理由 |
|---|---|---|---|
| 1 | 开关**控制什么**？ | **只控制"字节"，不控制"元数据"** | 元数据走 `changes`、与字节无关；只控字节 ⇒ 对端**看得见但打不开**，比"整个文件消失"更可解释（§二） |
| 2 | 关掉后，**本机已有字节**怎么办？ | **保留，不删** | 否则"改个开关就把文件删了"——这是最容易被骂的行为。要释放空间应走既有的存储面板/清理命令，是**另一件事** |
| 3 | 关掉后**还上传**本机附件吗？ | **不上传**，并在面板显示"N 个附件未上传" | 否则"关掉"名不副实（流量照走）；而静默不上传又会让用户以为已同步 ⇒ 必须可见 |
| 4 | **默认值**？ | **开**（`DEFAULT 1`） | 升级后行为不变；"按需"是**用户主动选择**，不是我们替他改默认 |
| 5 | 粒度？ | **每 `ws_id`（= 每空间）** | 与 `sync_profiles` 主键天然一致，且用户的心智单位就是"这个空间" |
| 6 | 要不要**同时做 P6.2 的最小版**？ | **建议不做**，先把开关落地 | 见 §三 的理由；P6.2 单独一轮，避免把"开关"和"读取路径改造"混在一个提交里 |
| 7 | **开关的生效时机**？ | **允许同步中途关闭，且"中途生效"**：在下载/上传循环的**每次迭代之间**重读开关，命中即**优雅停止 + 报告原因**（详见下方） | 用户中途关掉的**意图就是"别再拉了"**；而循环里**本来**每件都要 `db.0.lock()` 做 INSERT（`:1679-1687`），再加一次 PK 查询可忽略；同一个 mutex 已有此用法 ⇒ **不引入新锁风险** |

| 8 | **翻转开关用哪个命令**？ | **新增一个窄命令**（如 `set_sync_attachments(ws_id, enabled)`），**不复用 `set_sync_profile`** | ⚠️ **复用会清空凭证**——见下方"两个陷阱" |

> ⚠️ **陷阱 A（会清空用户凭证，必须在实现前知道）**：`set_sync_profile` 对**未传的字段是"清空"**语义——
> Rust 侧 `token.as_deref().unwrap_or("")`（`sync.rs:429`）、Web 侧 `web.ts:2546` 的注释明写
> 「未传 token/space_id 时清空（与桌面一致：Option 缺省 → `""`）」。
> 而 `SyncPanel` 里**已经有 5 处**在用这种"部分传参"的调用（`:250`、`:262`、`:405` 登出、`:422`、`:450`）
> ——它们**故意**只传部分字段。
> ⇒ **若为了翻转开关而复用 `set_sync_profile` 并省略 token/space_id，会把该空间的凭证清掉。**
> ⇒ 所以：**新字段用 `None = 保持不变`**（不是清空），且**翻转走一个专门的窄命令**，天然碰不到凭证。
>
> ⚠️ **陷阱 B（UI 侧）**：`SyncPanel` 的 `update()` 签名是 **`value: string`**（`:236`），
> 布尔开关塞不进去 ⇒ 需要单独的 setter；并且因为 §五.7 要求**中途生效**，
> 开关**必须在切换的那一刻就落库**（不能只在点「保存」时才提交），否则"中途关掉"永远到不了 DB。
>
> **为什么"中途生效"必须显式做（代码事实）**：`sync_now` 在 `sync.rs:1369-1372` **一次性快照**全部 profile，
> 之后 `sync_workspace_only(&app, &db, &profile)`（`:1379`）与 `sync_attachments(app, db, profile)`
> （`:1360`，参数是 **`&SyncProfile`**）**全程只用那份不可变快照** ⇒
> **若只在入口读一次，中途关掉不会生效，会一直下完**——而那正是开关最该起作用的时刻。
> 而 UI 侧**同步中并不禁用这些控件**（`SyncPanel.tsx:766` 只把**同步按钮**设成 `disabled={syncing}`，
> 其余 `disabled` 都是权限/登录态）⇒ 用户确实点得到。
>
> **检查粒度 = 文件级**（每次迭代之间）⇒ **最坏等待 = 当前这个文件的传输时间**。
> 要在单个大文件传输中途也停，得在**流内**也检查；那会留下 `.part`
> ——**无害**：`local_set` 构建时已排除 `.part`（`sync.rs:1541`、`:1556`），下轮 `File::create` 会截断复用。
>
> **停止语义**：不报错、**不回滚已下载的字节**（已完成的就是完成了）、
> 并**报告"因开关关闭而停止"**——否则面板会显示成"同步完成"，用户以为全下完了。
> ⚠️ **这正是 B2 成为前置的原因**：**`end()` 缺口不修，"停止"根本没有地方显示**
> ⇒ **先补 `end()`（§四 步骤 0），再动本项**。
>
> 🚫 **不要**做成"下次同步才生效"——用户关掉后什么都没发生，只会认为开关坏了。
> ⚠️ **UI 上不要禁用开关**（那会正好在最需要它的时刻把它锁住）；但要在 1–2 秒内给出
> "正在停止… / 已停止（开关已关闭）"的反馈。
> ✅ **每空间独立**：`sync_now` 遍历全部 profile（`:1374`），每个 profile 各读自己的开关 ⇒
> **关掉空间 A 只停 A，B 照常继续**。

## 七、边界与不做的事

- **不改**"全量对齐"这个默认语义——默认仍是开，P6.1 只**提供一个关掉它的开关**；
- **不引入**新的数据库状态（不加"未下载"列、不加 pending 表）——§二 已说明为什么不需要；
- **不动**加密格式（那是 P2b，且要先真机实测）；
- **不删**用户已下载的字节（§五.2）；
- **不改服务端**：按 hash 取单件的接口已经存在（`GET {att_base}/attachments/{hash}`，`sync.rs:1641`）；
- **不复制**第二份下载实现（P6.3 必须抽函数）；
- **不做**"按大小阈值自动跳过"（那是 P6.4，且要先有 P6.2 的 UX 才能告诉用户"为什么没下"）。

### 2. 施工单收紧一处：闸门放在"两份清单"之后（**这是 §六 #4 能成立的前提**）

§四 步骤 5 原话是"入口处读开关 ⇒ 整个跳过第 3/4 步"。落地时**闸门下沉到第 1/2 步之后**，
**只挡第 3/4 步的字节传输**——理由是代码里步骤编号本来就是
`1. List remote hashes / 2. Local hashes / 3. Upload / 4. Download`（`web.ts` 与 `sync.rs` 同号），
"跳过第 3/4 步"= 只跳这两段循环；而两份 hash 清单的**差集正好就是**
"未上传 N 个 / 未下载 M 个"（§六 **验收 #4** 要求面板显示这个数）。

**代价与取舍**：开关关着时**仍会发一次 `GET /attachments`**（只拉 hash+mime 清单，K 级）。
换取的是"关掉后用户知道差多少件"，以及 P6.2 需要的现成数据。
⚠️ 为守住"关掉不该让同步更容易失败"这条底线：**开关关着时清单拉不到 ⇒ 不报错**（按 0 件返回），
开关开着时保持原样（拉不到就是失败）——两侧（`fetch_remote_attachments` / `syncFetch`）语义一致。

**`attachments_paused` 与 `attachments_skipped_*` 的分工**（别混）：

| 字段 | 何时为非零 | 面板文案 |
|---|---|---|
| `attachments_paused = true` | **途中**被关掉（入口是开的） | "**同步已停止**：途中关闭了附件同步…"（**不许出现"同步完成"**，验收 #8） |
| `attachments_skipped_upload/download` | 被开关**挡下**的件数（入口关 = 全部；途中关 = 剩余） | "（附件 未上传 N 个 / 未下载 M 个）" |

⇒ 稳态关掉**不算 `paused`**（用户主动选的，不是"停止"），但件数照报。

### 6. P6.2 + P6.3 落地（2026-09-15）

| 层 | 位置 | 内容 |
|---|---|---|
| 引擎 | `sync.rs::download_one_attachment` | **C1 那轮就抽好了**（当时是为了"一件失败不炸整轮"）；P6.3 直接复用它 ⇒ **全仓仍然只有一份下载实现** |
| 命令 | `sync.rs::download_attachment(ws_id, hash)` | 校验 hash（进文件路径 ⇒ 当不可信输入）、取该 hash 的 mime（决定落盘扩展名）、拼 URL、解密密钥按当前加密状态取，然后交给同一个 `download_one_attachment` |
| 契约 | `commands.ts` / `api.ts` / `web.ts` | `download_attachment: { wsId, hash } -> number`（落盘字节数）；Web 侧落在 `blobStore`（浏览器没有"盘"，blob store 就是它的字节层） |
| 去重 | `sync.rs::attachment_base` | **同步下载与按需下载的 URL 拼装统一到一处**（绑空间 ⇒ space 作用域；否则旧的全局路径），并顺手 `trim_end_matches('/')`。抽之前这两段是复制关系——正是"改一处忘另一处"的温床 |
| UI | `FileManagerView.tsx` + `App.css` | 行上按**盘上真实有的 hash**（`list_attachment_hashes`，走附件目录而不是数据库）标「未下载」；该行的 ⬇ 与右键菜单项都换成「从服务器下载」，成功后这一行立刻恢复正常 |

**两个刻意的决定**（都写进了代码注释）：

1. **按需下载不受 C1 预算闸门约束**（单文件阈值 / 本轮总量 / 磁盘余量都不拦）。C1 管的是
   "**自动**拉取别在用户不知情时把设备填满"，而这是用户明确点了"下载这一件"——
   与"手动点同步不受 C2 仅 Wi-Fi 限制"同一条原则：**显式操作照做**。
2. **判据用"盘上有没有字节"，不是"数据库有没有行"**：`list_attachment_hashes` 走附件目录，
   所以"行在、字节不在"能被如实标出来 —— 这恰恰是 P6.1 关掉开关之后、以及预算刹车跳过之后的
   既有状态（`attachments.rs` 那两句"附件文件不存在（可能被移动或删除）"本来就是为它准备的文案，
   但它把人往"文件坏了"的方向误导）。
