# 插件宿主子进程化 + OS 级资源限制（M11.13）方案

> **状态：规划（待拍板）**｜日期：2026-09-10｜前置：M11.5（分配预算）/ M11.6（ABI v1 + 能力注册表）/ M11.7（能力面）均已落地
> 关联：[插件体系进化方案](2026-09-10-plugin-evolution-plan.md)（§3.11 结论四/五、M11.13 验收）、[插件分发策略](2026-09-10-plugin-distribution-strategy.md)（本文是 M11.11a 的硬前置）、`docs/plugin-api.md`（ABI 不变）
> **一句话**：把 Boa 与沙箱挪进**独立子进程**，插件宿主变成"纯解释器"——**没有数据库、没有密钥、没有文件系统、没有路径**；能力调用全部 RPC 回主进程校验。超时与取消从"放弃等待"变成**真的把进程杀掉**。

---

## 1. 结论先行

三件事一起做，缺一件都不算完成：

1. **崩溃隔离**：Boa（含 unsafe）跑在子进程里。段错误 / UB / OS OOM-killer 只终结**那一次调用**，主进程存活并给出可见错误。
2. **可中止**：墙钟超时与用户点「取消」都变成 **kill 子进程**。这顺带关掉 M11.5 遗留的"超时只是遗弃线程"——今天被遗弃的线程会一直空转烧 CPU 到进程结束。
3. **OS 级账目**：内存/CPU 上限在操作系统层真实生效，并且**可观测**（能在一个测试里断言"这个插件宿主进程的内存被限制在 X MiB 内"）。

**而下面这条是本文最重要的发现（代码已核实，见 §2.3），它决定了整个协议形状**：

> 今天插件的**能力调用就在插件线程里直接开 SQLCipher 连接**（`with_read_conn` → `open_space_conn` → `security::key_space_conn`，密钥来自进程级 `SESSION_KEY`）。也就是说**解密密钥与不可信代码在同一个进程里**，只靠"Boa 没有 FFI"这一层挡着。
>
> 所以子进程化**不能**走那条看起来更省事的路（"子进程已经有 app data 路径了，让它自己开库"）——那等于把密钥搬进一个专门运行不可信代码的进程。正确做法是：**子进程一个数据库都不碰、一个字节密钥都拿不到，所有能力调用 RPC 回主进程**。这样进程边界同时买到两样东西：崩溃隔离 + **不可信进程里没有任何秘密**。

## 2. 现状盘点（代码已核实）

### 2.1 一次调用现在长什么样

```
前端 run_plugin_command
  └─ Tauri 命令（async，运行在 Tauri 的异步运行时线程上）
       ├─ 校验：id 安全 / 启用 / 授权快照 / 参数体积
       ├─ 在主线程取数据：page_count、current_page_json、read_space   ← 持有全局 DB 锁，取完即释放
       ├─ resolve_permissions / setting_scopes
       └─ run_command_timeout(5s)
            └─ std::thread::spawn("plugin-run")          ← 插件线程
                 ├─ with_budget(64 MiB)：分配器超预算 → panic → catch_unwind → 干净错误
                 ├─ Boa Context：eval 插件源码 → __run(id, args)
                 │    └─ api.* → __cap(method, argsJson) → dispatch_capability
                 │         ├─ 权限逐次校验 + 审计（进程级环形缓冲）
                 │         └─ 能力实现：with_read_conn / with_meta_conn
                 │              └─ **在插件线程里 open_space_conn**（SQLCipher，用 SESSION_KEY 解密）
                 └─ 结果：message + insert/toasts/drafts/exports  ← 全在 thread_local RUN_STATE 里
       主线程 recv_timeout(5s) → 超时就 return Err，**丢弃 JoinHandle**（线程继续跑）
```

### 2.2 事实与出处

| 事实 | 出处 |
|---|---|
| 超时只是"不再等"，线程停不下来 | `plugins.rs` `with_timeout`（`recv_timeout` 后丢弃 JoinHandle） |
| 分配炸弹已在进程内闭合（超预算 panic + `catch_unwind`） | `plugin_budget.rs`、`with_timeout` 内注释 |
| 插件线程**自己开库**（且是加密库） | `plugins.rs:1274` `with_read_conn` → `db.rs:132` `open_space_conn_at` → `security::key_space_conn` |
| 解密密钥是**进程级**的 | `security.rs:17` `static SESSION_KEY: Mutex<Option<[u8;32]>>` |
| 插件产物（drafts/exports/toasts/insert）都在 `thread_local` | `plugins.rs` `RUN_STATE` |
| `main.rs` 只有 4 行，转调 `shuyonote_lib::run()` | `src-tauri/src/main.rs` |
| 事件派发也走同一个 `with_timeout`（2s），且逐插件串行 | `plugins.rs` `run_event_timeout`、`emit_plugin_event` |

### 2.3 与"现在到底有多不安全"的诚实对照

不是"什么都挡不住"，也不是"已经安全"：

- **已经挡住的**：能力缺席（无 fs/net/命令）、权限逐次校验、写中介（草稿）、分配炸弹、无限循环（有循环预算）、超时（主线程不卡）。
- **挡不住的**：Boa 原生崩溃（段错误/UB 会带走整个应用）；OS OOM-killer（`handle_alloc_error` 在 stable Rust 是 abort，进程内无解）；CPU 被遗弃线程持续占用；**以及上面那条：密钥与不可信代码同进程**。
- **所以这一档的定位是**：把"应用会被插件弄崩"和"密钥与不可信代码同居"这两件事一起关掉，**不是**做 OS 沙箱（见 §3.9 非目标）。

## 3. 设计

### 3.1 边界：子进程是"纯解释器"

子进程**只有一个职责**：跑一段 JS，把 `api.*` 变成"发给父进程的请求"。它的输入与能力被严格限制到手能数清的程度：

**子进程拿到的全部东西**（握手帧，一次）：

| 字段 | 为什么需要 |
|---|---|
| `source` | 要 eval 的插件源码（父进程已经读过，子进程不需要任何文件访问） |
| `commandId` / `argsJson` | 这次要跑哪个命令、参数 |
| `limits` | 循环预算、墙钟预算（让它自己也能尽早失败，父进程仍是最终裁决） |

**子进程拿不到的东西**（全部留在父进程）：

- **数据库连接与解密密钥**（`SESSION_KEY` 永不进子进程）；
- **任何路径**（app data dir、空间库路径、插件目录一律不传）；
- 权限列表（权限是父进程的判定，子进程连"我有什么权限"都不知道 → 连自我授权的余地都没有）；
- 其它插件的任何信息。

**它在一次调用里能做的对外动作**：只往 pipe 里写 `{method, argsJson}` 并等回复。

> 这条边界的副作用要写清楚：**将来若有"读文件字节"这类能力，也必须是父进程读、把结果回给子进程**。子进程永远不成为新的信任主体。

### 3.2 IPC：同二进制 re-exec + 长度前缀 JSON

| 备选 | 取舍 |
|---|---|
| **同二进制 re-exec**（`ShuyoNote --plugin-host`）+ stdin/stdout 上跑长度前缀 JSON | ✅ 不新增二进制（**macOS 签名/公证、Windows 安装包、Linux 打包全不用改**）、不开端口/套接字（Windows 不弹防火墙）、父子生命周期天然绑定（父进程死 → stdin EOF → 子进程自己退出）。❌ 需要在 `main.rs` 最早期分流（不能初始化 Tauri/窗口）。 |
| 单独的 helper 二进制 | ✅ 语义最干净。❌ 三平台打包/签名/公证/更新全要多带一个文件，且要处理"helper 与主程序版本不一致"。 |
| 本地套接字 / 命名管道 | ✅ 双向、易调试。❌ Windows 防火墙/权限、路径长度、跨平台差异；还要处理端点抢占。 |

**选第一个**。协议细节：

- 帧 = `u32` 小端长度 + JSON（子进程 → 父进程 / 父进程 → 子进程同一套），单帧上限 8 MiB（超过即协议错误 → 直接 kill）；
- **stdout 只跑协议**，诊断一律 stderr（父进程把 stderr 收进插件日志，前缀 `[host]`）；
- 请求/回复一一对应、同步阻塞（子树里不引入回调式并发——Boa 是单线程解释，没有必要）。

### 3.3 生命周期：一次调用一个子进程；超时/取消 = 杀

- **一次调用一个子进程**：保留"一次性执行不变式"（方案 §3.6 明确拒绝常驻实例/后台任务）。代价是每次调用约 5–20 ms 的进程启动开销——先接受，用 §6 的基准量一下再决定要不要优化（见 §5 阶段 4）。
- **墙钟**：父进程 `wait_timeout`，超时 → `kill()` → 返回 `plugin_timeout: 插件执行超时（5s），已强制终止`。
- **取消（前端「取消」按钮）**：语义**变了**，而且是变好：从"放弃等待（结果丢弃，插件线程还在跑）"变成"**真的终止**"。前端文案要跟着改（`store/plugins.ts` 里那句"已取消等待；插件代码可能仍在后台跑完"要删掉）。
- **父进程退出**：子进程读到 stdin EOF 自行退出（不依赖平台特有的 PDEATHSIG）；Windows 侧再加 Job Object 的 `KILL_ON_JOB_CLOSE` 兜底。

### 3.4 失败语义（都要可见）

| 情况 | 父进程行为 | 用户看到 |
|---|---|---|
| 子进程启动失败 | 错误，记日志 | `plugin_host_failed: 无法启动插件宿主（…）` |
| 子进程中途死（段错误/abort） | 收成"宿主异常退出（code=…，信号=…）"，记日志 + 审计 | 明确的失败提示，**应用照常运行** |
| 子进程 panic（Rust 侧） | 同上（panic 信息在 stderr 里，进插件日志） | 同上 |
| 内存/CPU 触到上限 | 如果是 OS 杀的 → 同上；如果是自设看门狗 → `plugin_oom: 插件超出内存上限（X MiB）` | 明确说清是超限而不是"崩了" |
| 协议错误 / 帧过大 | kill + 清晰错误 | `plugin_protocol: 插件宿主通信异常` |
| 超时 | kill | `plugin_timeout` |
| 插件自身抛错 | **照旧**（`__run` 里 catch，返回 `__plugin: 执行出错 …`），不是进程级失败 | 与今天一致 |

**不做自动重试**：崩溃循环的插件不该被父进程反复拉起。

### 3.5 OS 级资源上限（分平台 + 可观测看门狗）

| 平台 | 机制 | 说明 |
|---|---|---|
| Linux | `setrlimit(RLIMIT_AS, RLIMIT_CPU)`（`CommandExt::pre_exec`） | 可靠、够用；分配失败 → Rust abort → 进程退出 → 父进程给干净错误 |
| Windows | **Job Object**：`JOB_OBJECT_LIMIT_PROCESS_MEMORY` + `JOB_OBJECT_LIMIT_JOB_MEMORY` + `ActiveProcessLimit=1` + `KILL_ON_JOB_CLOSE` | 这是 Windows 上唯一真能"按进程记账并强杀"的机制 |
| macOS | `setrlimit` **加上**父进程侧看门狗 | macOS 上 `RLIMIT_AS` 在实践中不完全可靠（部分映射不计入），所以**不以它为准** |

**统一的父进程侧看门狗**（三平台都开，也是"可观测"那条验收的载体）：一个轻量采样线程每 200 ms 读子进程 RSS（Linux `/proc/<pid>/statm`、macOS `proc_pidinfo`/`task_info`、Windows `GetProcessMemoryInfo`），超过上限（默认 **256 MiB**，可配）立刻 kill 并返回 `plugin_oom`；同时把峰值 RSS 记进审计，供"这个插件平时吃多少内存"的可观测性用。

> 为什么默认 256 MiB 而不是 64 MiB：64 MiB 是**分配预算**（进程内、精确、防分配炸弹）；256 MiB 是**OS 上限**（粗、兜底、允许引擎自身的正常开销）。两层并存，不互相替代。

### 3.6 并发

- 子进程数上限 **2**（一次命令执行 + 一次事件派发），超出排队；**每次调用仍是独立进程**（不池化）。
- 事件派发保持逐插件串行（今天是串行），但每个插件一次独立调用。
- **绝不重入**：一个插件的两次调用不共享任何进程状态（今天靠 thread_local 保证，改成进程边界后由进程本身保证）。

### 3.7 子进程环境（默认全不给）

- `env_clear()` + 只给 `PATH`（Rust/系统需要的最小集）；**不传任何含密钥/令牌的变量**（今天子进程会继承父进程 env，等于白送）；
- 当前工作目录设为临时目录（不给 app data 目录当 cwd）；
- 除 stdin/stdout/stderr 三个 pipe 外不继承任何 fd（Rust 默认 CLOEXEC，显式确认一次）；
- macOS：**不初始化任何 GUI**（`main.rs` 在 `run()` 之前分流，避免第二个 Dock 图标/激活策略问题）；
- 单实例插件（`tauri-plugin-single-instance`）不得干涉子进程：分流必须发生在它注册之前。

### 3.8 与现有不变式的关系（逐条保号）

| 不变式 | 子进程化之后 |
|---|---|
| ABI v1 冻结（`api.*` 不变） | ✅ 插件零改动；协议是宿主内部实现 |
| 权限逐次校验在后端 | ✅ 位置从"插件线程"变成"父进程"，判定逻辑与测试全部不变 |
| 写中介（草稿/导出确认） | ✅ 产物由子进程回传，父进程照旧交给前端确认；**写盘与落库仍然只发生在父进程/前端** |
| 一次性执行（无常驻/无定时器） | ✅ 一次调用一个进程 |
| 审计与插件日志 | ✅ 能力调用发生在父进程 → 审计天然完整；子进程 stderr 并入插件日志 |
| 分配预算（M11.5） | ✅ 保留（进程内精确），新增 OS 层兜底 |
| E2EE 边界 | ✅ **变强**：密钥不进不可信进程 |

### 3.9 非目标（明确不做，避免被反复提）

- **不做 OS 沙箱**（macOS seatbelt / Linux seccomp+landlock / Windows AppContainer）。那是**再下一档**：它能挡住"Boa 逃逸后读用户文件"，但每次放宽规则都是一次新决策（模板目录？附件目录？），而且三平台三套规则。本文只买"崩溃隔离 + 可中止 + 资源账目 + 密钥不进门"，这四条已经能兑现验收。
- 不做常驻宿主 / 进程池 / 热重载复用进程（破坏一次性执行不变式；启动开销先量再说）。
- 不把插件宿主做成可选后端（**没有"退回进程内"这个开关**：安全边界一旦可选，就等于没有）。
- 不改 ABI、不加能力。

## 4. 不可逆决策与代价

| # | 决策 | 代价（现在就要认） | 什么时候会后悔 |
|---|---|---|---|
| D1 | 子进程不碰 DB、不拿密钥；能力全部 RPC | 每次能力调用一次 IPC 往返（本地 pipe，微秒级；`orphan-pages` 那种 200 次逐页调用也在毫秒量级）；未来"读文件字节"这类能力也必须父进程代读 | 若将来想让插件直连数据（如"给插件一个只读 SQL 视图"）——那与密钥边界冲突，届时只能拒绝 |
| D2 | 同二进制 re-exec + stdin/stdout JSON | 打包/签名不用动，但 `main.rs` 必须先分流；stdout 被协议占用（插件里的任何"打印"都不能走 stdout） | 若将来要双向流式/多路复用（同一进程跑多个插件）——要换协议 |
| D3 | 一次调用一个进程 | 每次 5–20 ms 启动开销；save 事件频繁时按插件个数累乘 | 若事件钩子变成高频（每次输入都发）——那时才需要池化，但池化与一次性不变式冲突，要重新拍板 |
| D4 | 取消 = 杀进程 | 取消语义变化（前端文案要改）；杀掉意味着"连草稿都不产出" | 几乎不会——这与"取消 = 无半途写入"更一致 |
| D5 | 崩溃不重试 | 崩溃的插件会持续失败（靠日志可见） | 若出现"偶发崩溃但重试就好"的真实案例 |
| D6 | 内存上限默认 256 MiB + 三平台看门狗 | 多一个采样线程 + 平台分支代码；偶发误杀（阈值可配） | 若有插件合法需要更多内存（例如导出大文档）——把上限做成可配置常量即可 |
| D7 | 不保留进程内后端 | 现有 165 个测试里直接调 `run_command_timeout` 的那批要重写成"起真子进程"的集成测试（见 §6） | 不会——留一个"进程内模式"才是真正会后悔的事 |

## 5. 迁移路径（每阶段独立可合、且任何一阶段停下都不留半残）

| 阶段 | 内容 | 完成标志 | 估时 |
|---|---|---|---|
| **0. 前置** | 把 `cargo test` 加进 CI（现在不跑）；`ci.yml` 三平台都要有 Linux 侧的 OS 上限测试入口 | CI 上能看到 Rust 测试结果 | 0.5 天 |
| **1. 协议与子进程骨架** | `--plugin-host` 分流、帧编解码、握手、纯假能力（echo）跑通；父进程 `HostClient` 封装 | 集成测试：起子进程跑一段 JS，拿到结果 | 2 天 |
| **2. 能力 RPC 上移** | `dispatch_capability` 及其数据访问留在父进程；子进程侧 `__cap` 变成 pipe 调用；权限/审计/写中介链路不动 | 现有能力测试全部改成"经子进程"仍绿；`orphan-pages` 等 11 个示例插件行为不变 | 2–3 天 |
| **3. 生命周期与上限** | wait_timeout + kill、取消改为终止、崩溃/协议错误语义、三平台 rlimit/Job Object + RSS 看门狗、env 清空 | §7 三条验收的自动化测试 | 3 天 |
| **4. 收口与观测** | 启动开销基准（命令 + 事件两条路径）；峰值 RSS 进审计；文档与 CHANGELOG；前端取消文案 | 基准数据 + 文档 | 1 天 |
| **合计** | | | **约 9–10 天** |

> 阶段 2 结束时应用就已经跑在子进程上了（功能等价、无上限）；阶段 3 才是"真正的 M11.13"。这样即便中途停下，也没有"两套后端"的历史债——**任何时刻只有一个后端**。

## 6. 测试与验收

### 6.1 对齐方案原文的三条验收

| 验收 | 怎么测（自动化） |
|---|---|
| 无限分配内存的插件不让应用崩溃（应用存活 + 明确错误提示） | 插件里 `while(true) arr.push(new Array(10000))`；断言：调用返回 `plugin_oom`（或 `plugin_budget`），**父进程仍在**（同一测试进程继续跑后续断言），插件日志里有记录 |
| panic 的插件不带走主进程 | 插件触发 Boa 内部 panic / 或 `rust` 侧 abort 路径（用一个 `#[cfg(test)]` 的"宿主强制 abort"开关）；断言主进程存活 + 错误可见 |
| 资源上限在 OS 层真实生效（可观测） | 起一个宿主子进程，分配 ~1 GiB；断言：进程被杀、峰值 RSS 被记录且 ≤ 上限（读 `/proc`/`task_info` 实测），错误码为 `plugin_oom` |

### 6.2 现有 165 个测试怎么办

- **留在单测里的**：纯函数与判定逻辑（`approval_snapshot`/`approval_drift`、`sanitize_export_file_name`、`normalize_extension`、`validate_setting_value`、`is_safe_plugin_id`、`plugin_validate` 全量、`plugin_budget`）——它们与"跑在哪"无关。
- **要改成集成测试的**：凡是直接调 `run_command_timeout` / `dispatch_capability` 的（命令执行、能力、草稿、预算、审计、事件）。放 `src-tauri/tests/plugin_host.rs`，用 `env!("CARGO_BIN_EXE_shuyonote")` 拿到宿主二进制，**用真子进程跑真插件**——这批测试的价值也因此变高（它们同时是"进程边界可用"的回归）。
- 不允许出现"测试走进程内、生产走子进程"的分叉：宁可测试慢一点。

### 6.3 手工验收（三平台各一遍）

用打包后的应用（不是 dev）：装一个恶意插件（无限分配 / 死循环 / 触发 panic）→ 应用不崩、错误可见、内存曲线在监视器里封顶；退出应用后 `ps` 里没有遗留宿主进程（三平台都要看）。

## 7. 风险与缓解

| 风险 | 说明 | 缓解 |
|---|---|---|
| macOS 上 re-exec 主二进制引发 GUI/单实例问题 | 第二 Dock 图标、单实例插件把子进程当"第二个实例" | 分流必须在 `run()` 与 single-instance 注册**之前**；阶段 1 就在打包产物上验证（不只 dev） |
| 父进程持锁等子进程 → 能力 RPC 死锁 | 今天已踩过"插件线程持锁"，改成 IPC 会**换个形式重现**（父进程等子进程、子进程回头要父进程开库） | 铁律：**父进程绝不在持 DB 锁时等子进程**；能力 RPC 由独立线程处理，锁只在单次查询内持有（沿用现有 `with_read_conn` + busy_timeout 500ms）；阶段 2 加一个"能力调用发生在等待期间"的专项测试 |
| 事件路径延迟变高（每次保存 × 插件数 × 进程启动） | 用户可感知的卡顿 | 阶段 4 基准；必要时把"一次事件派发内同一插件的多次调用"合并，或对事件路径放宽到"可延迟执行"（另案） |
| 打包/公证/安装包回归 | 新增进程启动路径，杀软/沙箱可能拦 | 同二进制 re-exec 把风险降到最低；三平台打包验证纳入阶段 3 的完成标志 |
| 取消语义变化引起用户困惑 | "取消了但文件已经导出"之类 | 取消发生在写盘/落库之前（草稿与导出都在返回后才处理），所以"取消 = 无半途写入"仍然成立；文案改成"已终止插件" |
| Windows Job Object 与 Tauri 进程树的关系 | 子进程再启动孙进程（当前不可能，但将来能力可能） | `ActiveProcessLimit=1`：**明确不允许**宿主再起进程；违反即被 OS 拦 |

### 8.1 已拍板（2026-09-10，逐条采纳上面的建议）

| 问题 | 结论 | 一句话理由 |

| 5. D7：不保留进程内后端 | **同意** | 阶段 2 结束时应用就跑在子进程上。留一条"进程内"分支等于留一条**没人在跑的代码路径**：它会慢慢腐坏，而腐坏的表现是"插件功能整个不动"。测试也走子进程（宁可慢）。 |

**为什么 2a 与 2b 分开做**：2b 一动就是"应用整体换执行方式"——命令与事件两条路都要切，而且按 D7
不留进程内后端，于是那 8 个直接调 `run_command_timeout` 的测试**必须一次性迁完**（它们要真子进程 +
真父进程 + 真库，而集成测试只能看到 `pub` 面，还得先把测试钩子做成公开 API）。半切的状态最坏：
一条路走进程内、一条走子进程，能力语义一旦有差异，测试恰好两边都测不到。所以先把**通道**打通并测住

**阶段 1/2a 的已知限制**（如实记着，阶段 2b/3 会消掉）：

- 子进程里的能力调用是**假应答**（`{"stub":true,…}`）：能证明"通道通"，不能证明"数据对"。
  所以阶段 1 **没有任何调用点**——父进程仍然走进程内那条路，功能零变化。
- 没有墙钟超时与 OS 上限（`HostClient` 的读是阻塞的，只有 `Drop` 保证不留孤儿）；
  这两条属于阶段 3，2b 会把超时接上（否则子进程卡住就是父进程卡住）。
- **应用还没有走子进程**（2a 只把通道打通并测住）：`CapMode::Stub` 仍是默认，两条执行路径
  只存在于测试里——生产路径一行没变。
