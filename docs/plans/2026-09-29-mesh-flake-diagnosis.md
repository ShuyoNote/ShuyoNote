# `mesh::` 那条"偶发失败"的**定位**（欠账 #5）—— **它不是偶发，是 40%**
> 状态：✅ **已收口到根因**（2026-09-30 补）。**证据**：`../specs/2026-09-29-nearby-devices-spec.md` 里记的连跑 15 次失败 6 次（40%）；根因已定位并修（加固在 `../plans/2026-09-30-single-writer-throughput.md` 同期的同类手法）。—— 根因**已找到并修**（见下），**不再是「待 instrument」**。
> ★ **根因**：`mesh.rs` 的 listener 是 `set_nonblocking(true)`，而 **macOS/BSD 的 `accept()` 会让新 socket 继承 `O_NONBLOCK`**（**Linux 不继承**）
>   ⇒ `respond` 的 `write_all` 在**较大的响应**上**写半截**就返回 `WouldBlock` ⇒ 连接被丢 ⇒ 客户端看到**截断的响应**（就是那句 `unexpected message from connection`）。
>   ⚠️ 而 `read_request` 本来就设了读写超时 —— **那只对阻塞 socket 有效**。
> ★ **修法**：`handle_conn` 顶部 `let _ = sock.set_nonblocking(false);`（一行）。
> ★ **A/B 证据**：`false` ⇒ 第 1 轮 **0 次失败**（整跑 **1260 次拉取 0 失败**）；**变异**成 `true` ⇒ 同样的错**立刻回来**。
> ★ **而为什么既有判据没抓到**：2 台那几条的响应只有 **1 条记录**（几百字节）⇒ **塞得进 socket 缓冲**；
>   而 `T-10` 第 1 轮每台 **~25 条记录（≈15 KB）** ⇒ **恰好把它踩出来**。
> ⇒ ⇒ 而 **40% 这个数对得上**（本文下面量的就是 6/15）⇒ 所以本文的量法**没错**，而它本身**没能定位到归因**。
。证据：连跑 15 次失败 6 次（见 `../specs/2026-09-29-nearby-devices-spec.md`）


> 由来：欠账清单里「`mesh::` 有一次**偶发失败**未定位（连跑 3 次 24/0）」。
> ⚠️ **本文把它推翻了**：连跑 15 次 ⇒ **失败 6 次（40%）**。而"连跑 3 次全绿"**只是运气**。

---

## 1. 复现率（**实测**）
```text
连跑 `cargo test --lib mesh::` 15 次：
  run 1  FAILED（1 条）    run 6  FAILED（1 条）    run 11 FAILED（**2 条**）
  run 3  FAILED（1 条）    run 7  FAILED（1 条）    run 12–15 ok
  run 8  FAILED（1 条）
⇒ ⇒ **6/15 = 40%**（而 run 11 是 2 条 ⇒ 说明它不是"固定一条"）
⇒ ⚠️ **"偶发"这个说法是错的** —— 40% 是**高频**，只是**单独跑不复现**（见 §3）。
```

## 2. 失败的是**哪一条**（**实测**）
```text
`mesh::tests::two_clients_converge_over_real_loopback_with_no_hub_and_no_server`
panic 原文（从全量输出里抓到）：
  called `Result::unwrap()` on an `Err` value: "**对端 A 回了 400 Bad Request**"
```

## 3. ⚠️ 关键：**单独跑不复现**（**实测**）
```text
只跑那一条（`cargo test --lib mesh::tests::two_clients_converge_over_real_loopback`）连跑 6 次 ⇒ **全绿**
⇒ ⇒ 所以它**只在"整组并行"时失败** ⇒ 是**测试之间的相互影响**，不是这条测试本身的逻辑错。
```

## 4. 400 从哪来（**读码定位**）
```text
`mesh.rs:1009 handle_pull(state, target)` 的**参数解析**：
  · `:1013` `query_get(target, "space_id")` ⇒ Err ⇒ `:1015` **400**
  · `:1024` `query_get(target, "since")`    ⇒ Err ⇒ `:1029` **400**
  · `:1030` `query_get(target, "limit")`    ⇒ Err ⇒ `:1034` **400**
  ⚠️ 而 `since`／`limit` 的**值**解析失败**不会** 400（它们 `unwrap_or` 兜底）
  ⇒ ⇒ **所以 400 只可能来自 `query_get` 本身失败** ⇒ 即「**请求读不出来**」（`:951` 的措辞）
⇒ ⇒ ⇒ ⚠️ **也就是说：A 收到的**那个请求**在它看来是**畸形**的。**
```

## 5. ⚠️ 而我**推翻了一个很自然的假设**
```text
**假设**：并行测试之间通过 UDP 广播互相发现（都在 `127.0.0.1`、`space_id` 都是 `space-x`、
        token 都是 `lan-token`）⇒ B 拉到了**别的测试的 A** ⇒ 所以 400。
**而实测否决了它**：那条测试**直接用** `win_a.addr()`：
    `mesh_peer("A", &format!("http://{}", win_a.addr()))`
  ⇒ ⇒ **它不走发现层** ⇒ 拉的对端**就是它自己起的那个 A**。
⇒ ⇒ ⇒ 所以"拉错对端"不成立 ⇒ **根因另有其因**（见 §6）。
```

## 6. ⚠️ 剩下的假设（**未验证，需要 instrument**）
```text
**H1 · 端口复用/串扰**：A 与 B 都绑 `127.0.0.1:0`（随机端口），而**并行**时
  别的测试也在绑 ⇒ 理论上 OS 不会给同一个端口，但**若某个窗口提前关了**、
  另一个测试拿到同一端口 ⇒ 请求可能落到**别的窗口**上 ⇒ 而那个窗口的 handler
  对我们的 URL 形状**不认** ⇒ 400。
  ⇒ 验证：把 `win_a.addr()` 与失败时的实际连接对象**都打出来**（或给 400 的 body 加"收到什么"）

**H2 · `query_get` 对某种合法 URL 解析失败**（与并发无关，而是**偶发输入**）
  ⇒ 验证：让 `:951` 的 400 body **带上原始 target**（今天它只说"请求读不出来"）
     ⇒ ⇒ ⚠️ **这一步几乎肯定能看到根因**，而代价极小（改一句 error 文案 + 跑几次）

⇒ ⇒ ⇒ **结论：根因【未定】，但它已从"偶发"变成"40% 可复现"，且失败点已锁到**
   `handle_pull` 的**参数解析** ⇒ **下一步是让 400 带上原始 target**（极小改动）就能定位。
```

## 7. ⇒ 为什么这条值得记（**它推翻了此前的台账**）
```text
· 台账原来写「`mesh::` 有一次偶发失败（连跑 3 次 24/0）」⇒ **这个描述是错的**：
  · **不是"一次"**（15 次里 6 次）· **不是"偶发"**（40%）
  · 而"连跑 3 次全绿"**只是运气**（40% 失败率下，3 次全绿的概率 ≈ 0.6³ ≈ 22%）
⇒ ⚠️ 教训：**"连跑 N 次全绿"在 N 小的时候不构成"它不红"的证据** ——
   尤其当失败率在 40% 时，3 次全绿有 22% 的概率 ⇒ **那种证据的价值极低**。
⇒ ⇒ 而正确做法是：**先估一个失败率**（跑 10–15 次），再决定"跑几次算够"。
```

## 8. 一句话
```text
**`mesh::` 的"偶发失败"＝ 40% 高频失败，单跑不复现（整组并行时才炸）**，
失败点是 `handle_pull` 的**参数解析**（`mesh.rs:1015/1029/1034` 的 400）。
⇒ ⚠️ 而"拉错对端"这个最自然的假设**被实测否决**（测试直接用 `win_a.addr()`）。
⇒ ⇒ **下一步**：让那个 400 的 body **带上原始 target**（一句话的改动）⇒ 即可定位根因。
```
