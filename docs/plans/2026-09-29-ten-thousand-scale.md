# 如何提高到 **10000 设备以上**实时规模

> upstream：容量压测（M1≈10／M2≈100／M3≈200 台）＋ [三条路线对比](2026-09-29-single-space-limit-three-routes.md)
> ＋ [L4 深度](2026-09-29-l4-forward-deltas-deep-dive.md)
> ⚠️ **本文先纠正我自己先前的两处说法**（§1）—— 它们直接改变 10000 的答案。

---

## 1. ⚠️ 先纠错：**L4 不是 "O(N²) → O(N)"**
```text
我在路线对比与 L4 深度里都写了 "L4：扇出 O(N²) → O(N)"。**这不对。**

准确的说法：
  · L4 降的是【**每次扇出的成本**】：从"每个订阅者 1 次 SQLite 查询"降到"1 次内存 socket 写"
  · **阶没有变**：扇出 = 写速率 × **收件人数**
    ⇒ 全空间广播（L4）下，收件人数 **仍然是 N** ⇒ **仍然是 O(N²)**（只是常数小得多）
  · 真正把**阶**降下来的是【**按页过滤**】：收件人从 N 降到 k（同页人数）
    ⇒ ⇒ 于是扇出 = 写速率 × k，而写速率 = 同页写者数 × r ⇒ **≈ k²（与 N 无关）**

⇒ ⇒ **结论：L4 是"降常数"，按页过滤才是"降阶"。** 本文后面全部按这个修正后的口径算。
```

## 2. 10000 台在全空间广播（L4）下为什么不可能 —— 一笔账
```text
设 α=10% 在写、r=2.5 改动/秒/写者、N=10000：
  写速率 = α·N·r = 0.1 × 10000 × 2.5 = **2500 写/秒**
  每次写要发给 N=10000 个订阅者（L4 全空间广播）
  ⇒ 总发送量 = 2500 × 10000 = **25,000,000 次/秒** ❌❌ 不可能

而且每台客户端的接收量：
  每客户端帧率 = α·r·N = 0.25 × 10000 = **2500 帧/秒** ❌ 客户端绝对吃不下
⇒ ⇒ **全空间广播到不了四位数，更别说五位数。**
```

## 3. 所以 10000 台的**唯一路**是：**按页订阅 + 只发给同页的人**
```text
设每页同页写者 3 人、同页在线 10 人（典型值）：
  单页写速率 = 3 × 2.5 = 7.5 写/秒
  每次写发给 k=10 人 ⇒ 75 次发送/秒（该页）
  ⇒ 每客户端帧率 = 3 × 2.5 = **7.5 帧/秒** ✅（不是 2500）
  ⇒ **总发送量 = Σ over 页（与 N 脱钩）** ✅
⇒ ⇒ 这才叫"降阶"：**每页的扇出只与"这一页有多少人"有关，与空间里总共多少设备无关。**
```

## 4. 到 10000 台要过的**五道关**（按顺序）

### 关一 · 服务端要维护「页 → 订阅者」映射（今天是「空间 → 订阅者」）
```text
今天：`broadcast::channel(64)` 是**每空间一个**；订阅是"订阅这个空间"
要改：每**页**一个（或一个"页键 → 订阅者集合"的路由表）
⇒ 内存：10000 设备 × 每台 1 页 ⇒ 10000 条映射 ⇒ 小 ✅
⇒ ⚠️ 而 channel 数量从"空间数"涨到"活跃页数" ⇒ `64 × P × 活跃页数`（P 已因增量变小）
```

### 关二 · **服务端必须知道"谁在看哪一页"** —— ⚠️ 而这对 E2E 是**元数据泄漏**
```text
今天**没有**这个信息（我在光标那片点过：`LanAnnounce` 里没有"我在看哪一页"）。
⇒ 要按页路由，客户端必须上报"当前页 + 订阅它"
⚠️⚠️ **但"我在看哪一页"本身就是内容元数据** —— 而个人空间是 E2E 的
   ⇒ 既有的 presence 口径是「**Personal (E2E) spaces are not meant to opt into presence —
     the client simply won't heartbeat for them**」⇒ 那类空间【不上报】
⇒ ⇒ 所以出现一个**结构性张力**：
   · 要让 E2E 空间也享受按页路由 ⇒ 必须上报"页标识" ⇒ 泄漏元数据 ❌
   · 不上报 ⇒ 那类空间只能全空间广播 ⇒ **到不了 10000**

⭐ 折中的技术路子（要在规格里论证，别在这里拍）：
   **用"页级不透明键"路由**：客户端上报一个**由空间密钥派生的页别名**（服务端不知道怎么解、也
   不知道对应哪一页），只用来做"这些订阅者关心同一个键"的路由
   ⇒ 服务端仍不懂内容 ✅，而路由粒度到页 ✅
   ⚠️ 但：多设备要**算出同一个键**（同一页在同一空间 ⇒ 同一键）⇒ 需要确定性派生
      ⇒ 而"同一页"是空间内的逻辑对象 ⇒ 用 `page_id` 的 HMAC(空间密钥) 即可
      ⇒ ⚠️ 还要防"服务端通过键的出现频率推断"（那属于另一层，要单独评估）
⇒ ⇒ **这一条要 owner 拍**（因为它触及 E2E 的元数据边界）。
```

### 关三 · 10000 条长连接的**服务端资源**
```text
· tokio 异步 ⇒ 可行，但要让运维可配：`ulimit -n`、事件循环线程数
· **内存**：每连接缓冲几十 KB ⇒ 10000 × 50KB ≈ **500 MB** ⚠️（要算准并写进部署文档）
· 心跳：SSE `KeepAlive` ≈15s ⇒ 10000/15 ≈ **667 帧/秒**的心跳 ⇒ 小但非零
· ⚠️ 反向代理：Nginx 的 `worker_connections` / `proxy_buffering off` 都要配（既有风险清单已提）
```

### 关四 · 每台客户端的接收量（按页后**不是问题**了）
```text
按页后：帧率 = 同页写者数 × r ≈ **7.5 帧/秒** ✅（对比全空间广播的 2500）
⇒ 所以"客户端吃不下"这个问题**被按页订阅顺带解掉了** —— 这也是它的主要价值之一。
```

### 关五 · 过了 10000 ⇒ **单机必然不够，要动存储**
```text
单机的硬墙：fd 数、内存、CPU、单写者
⇒ 要水平扩 ⇒ **被那个 `seq` 挡住**（`db.rs:19 seq INTEGER PRIMARY KEY AUTOINCREMENT`
  是**表级全局单调**，而客户端拿它当**空间水位**）
⇒ ⇒ 必须先做：**seq 改空间级**（`MAX(seq)+1 WHERE space_id=?`）⇒ 引入"同空间并发写抢序列"
   ＋ 广播跨机（外部队列）＋ 处理副本滞后
⇒ ⇒ ⇒ ⭐ **这就是 L6（换存储/序列模型）的真正用途** —— 它**不是**为"提高单空间上限"用的
   （那一项 L1/L4 更便宜），而是为【**过万**】用的。
```

## 5. 路线图（把上限一档一档抬上去）
```text
今天              ≈100 台（M2，实测）        读/秒 = 0.25·N²
+ 只写者订阅（L1） ≈200 台（M3，实测）
+ 增量 + L4        ≈300~800 台（推算）        瓶颈**转移到客户端**（α·r·N 帧/秒）
+ **按页订阅**      **~10000 台**（推算）       帧率与 N **脱钩** ← 五位数前必须过这一关
+ 多机（seq 改空间级 + 跨机广播）  >10000      ⚠️ 这一步才是 L6 的用途
```

## 6. 10000 台要 owner 拍的三件
```text
① ⚠️ **E2E 与"页级路由"的元数据边界**（关二）：允许上报"页级不透明键"吗？
   不允许 ⇒ 个人空间的实时规模就**封顶在"全空间广播"那一档**（几百台）。
② **L4 的非目标**（"别把长连接当同步引擎"）⇒ 见 L4 深度 §8（可改成"必须保留 pull 作补漏兜底"）
③ **是否接受"过万要换存储/序列模型"**（关五）—— 那是产品决定（自建零依赖的定位会变）
```

## 7. 一句话
```text
**到 10000 台的关键不是"服务端更快"，而是【让每一帧只发给该收到它的人】。**
  · L4 只降常数（仍 O(N²)）⇒ **到不了四位数**
  · **按页订阅才降阶**（收件人 N → k）⇒ 这是 10000 的唯一路
  · 而它撞一个 **E2E 元数据边界**（"谁在看哪一页"）⇒ 要 owner 拍
  · 过万之后才轮到"换存储/序列模型"（L6 的真正用途）
```
