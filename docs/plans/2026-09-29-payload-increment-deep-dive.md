# 「payload 整页 → 增量」深度分析（三条线的共同前提）
> 状态：**已收口**（分析）。证据：三条线的共同前提（见 `../specs/2026-09-29-realtime-body-requirements.md`）


> 上游：[L4 深度分析](2026-09-29-l4-forward-deltas-deep-dive.md) §5「L4 的真前置条件」
> 为什么单独立这一篇：**L4（转发）／文字提速／内存**三条线**全堵在它上面**。

---

## 1. 结论先说（一句话）
```text
**CRDT 层面【天生支持】增量；线层面【加个字段就够】；缺的只有一处 ——
  客户端今天【没有把增量留下来】（只回调"编辑发生了"，且只存整块 state）。**
⇒ ⇒ 所以第一步不是"改协议"，是"**让增量在客户端被留下**"。
```

## 2. 三层各自的实况（我逐行核过）

### 2.1 ✅ CRDT 层面：**Yjs 的 update 本身就是增量**
```text
`src/lib/crdt/yDocBridge.ts` 的会话接口（`:201-203` 注释原话）：
  「本会话就是这条用法的**唯一实现**：`openPageSession({ state })` 载入，
    **`edit()` 产增量**，`exportState()` 存回，`merge()` 收另一端的更新。」
⇒ ⇒ **增量天然存在**（每次 `edit()` 就是一条 Yjs update）：
   · **幂等**（重复应用无害）
   · **可乱序**（CRDT 自带因果序）
   · **小**（几字节 ~ 几 KB，取决于这次改了多少）
⇒ ⭐ 所以我们**不需要"算 diff"** —— 只需要"把已有的那条 update 留下来"。
```

### 2.2 ⚠️ 客户端层面：**两处"没留下来"**
```text
① **回调不给字节**：`yDocBridge.ts:233 onLocalEdit(cb: () => void)` 是**无参回调**
   ⇒ 它只告诉你"编辑发生了"，**不吐那一次 update 的字节**
   ⇒（而 `edit()` 内部显然拿得到 —— 只是没往外给）
② **库里只存整块 state**：
   `db.rs:1044  CREATE TABLE page_crdt (page_id PRIMARY KEY, **state BLOB**, updated_at)`
   写入处 `pageBinding.ts:74  writePageCrdtState(db, pageId, session.exportState(), at)`
   ⇒ ⇒ **只有"最新整块"，没有 update 日志** ⇒ 增量**当场不捕获就丢了**
```

### 2.3 ✅ 线层面：**加个并列字段就够，而且天然兼容**
```text
`src-tauri/src/crdt_wire.rs:22   pub const CRDT_WIRE_FIELD: &str = "crdt_state";`
载荷形状：`{ "crdt_state": { "v": 1, "state": <bytes> } }`
⇒ 加一个并列字段（如 `crdt_update`）即可
⇒ ⚠️ 而"**老对端读不懂这一项就忽略 ⇒ 与接线前逐字节相同**"是既有纪律
   （`sync.rs:209-217` 的注释明写）⇒ **加字段是安全的** ✅
   （而且 `with_wire_state` 自己就是"只在有 state 时才动载荷"的写法 ⇒ 同一模式可复用）
```

## 3. ⭐ 正确的形状：**增量日常 ＋ 全量兜底**（两条并存，不是替换）
```text
· **日常**：只发那一次的 update（小、幂等、可乱序）
· **兜底**：仍保留整块 `crdt_state`（用于：新设备首次 ／ 错太多 ／ 跳号回退）

⇒ ⇒ 为什么必须并存（三条都指向同一结论）：
  ① **L4b 的跳号回退**：发现跳号 ⇒ 回退去**全量拉** ⇒ 拿到的必须是"能补上的东西"
  ② **首收那条门**：`pageBinding.ts` 的血统判据里有一条「**任一方没有指纹（空状态）⇒ 视为相关**」
     ⇒ 新设备首收需要**完整 state**（否则指纹不全，后续判据会走偏）
  ③ **既有纪律**：今天 `ping`（落后）的兜底就是"全量拉一次" ⇒ 同一脉
⇒ ⇒ 所以形状是：**`crdt_state`（兜底）＋ `crdt_update`（日常）并存**，
   而不是"把 state 换成 update"。
```

## 4. 要做的事（按依赖排）
```text
**P1 · 让增量在客户端被留下**（最小、且是后面一切的前提）
  · ① `yDocBridge.ts`：把 `onLocalEdit(cb)` 扩成能给出**那一次 update 的字节**
       （或新增 `onLocalUpdate(cb: (u: Uint8Array) => void)`；
        ⚠️ 保持既有 `onLocalEdit` 语义不变 ⇒ 别动已接线的那条）
  · ② 落库时**同时**存这一次的 update（一张 `page_crdt_updates`，或直接进 outbox）
  · 验收：编辑一下 ⇒ 能取到一条**远小于整块 state** 的 update；
         且把它 apply 到"旧 state"上 ⇒ 结果与"新 state"一致（这是核心判据）

**P2 · 线加字段**（协议小改）
  · `crdt_update`（与 `crdt_state` 并列）＋ 老对端忽略未知字段
  · 验收：新旧版本互通（旧端忽略新字段、行为逐字节不变）

**P3 · 消费侧**（L4c 或今天的拉取都能用）
  · 有 `crdt_update` ⇒ 走"apply update"（轻）
  · 没有 ⇒ 退回 `crdt_state`（重，兜底）
  · ⚠️ **两者必须走【同一条应用路径】**（`apply_pulled_changes` → `apply_upsert`）
    ⇒ 不许新造"推送专用应用路"（第二份真相）
```

## 5. ⚠️ 五个风险（逐条）
```text
① **血统指纹不全**：只发增量 ⇒ 对端的 clientID 集合**逐渐**才齐
   ⇒ 所以**首收必须给全量**（§3-②）；否则 `lineagesRelated` 那条"空状态视为相关"的门会走偏。
   ⚠️ 这条要写进判据，否则症状是"偶尔判成不同血统 ⇒ 弹出冲突横幅"。
② **update 的幂等性要验**：Yjs 理论上幂等，但**我们要自己测**（重复 apply ⇒ 内容不变）
③ **乱序**：Yjs 可乱序 ✅，但"**编辑的先后**"（谁先谁后）仍要靠 CRDT 自己的因果序
   ⇒ 别在协议层再引入"必须按序"的假设（那会把 CRDT 的优势浪费掉）
④ **存储增长**：若把 update 全留成日志 ⇒ **无限增长**
   ⇒ 折中：**只在 outbox 里过一手**（发出去就不管，不全量留历史）
   ⇒ ⚠️ 而"离线攒改动"那段仍需要（既有的 outbox 形状）
⑤ **非正文那一半仍是整行**：标题/排序/父节点走 HLC ＋ **页级 LWW**
   ⇒ 它**本来就需要整行**（LWW 要整行覆盖）⇒ **不要把非正文也改增量**（那是错的）
   ⇒ ⇒ 所以"增量"只适用于**正文（CRDT state）那一半**。
```

## 6. 收益（为什么值得做）
```text
· **L4 的内存**：每空间常驻 64 × P；P 从"整页"降到"那次改动" ⇒ **量级下降**
· **传输量**：改一个字不再传整页 ⇒ 直接受益（今天连 L4 都不省传输）
· **文字提速**：payload 小 ⇒ 上传/广播/应用都快 ⇒ 这是"追 WPS 手感"的必要条件
· **顺带**：`crdt_state` 作为兜底仍完整 ⇒ 兼容与容错都不退
```

## 7. 与既有纪律的关系（要守住的）
```text
✅ **加字段天然兼容**（"读不懂就忽略 ⇒ 逐字节相同"是既有写法）
✅ **应用路径唯一**（`apply_pulled_changes` → `apply_upsert`）
✅ **血统判据不变**（首收给全量 ⇒ `lineagesRelated` 的门照旧）
✅ **"拉取语义一行不改"**（全量拉仍是兜底 ⇒ 语义未变）
⚠️ 而它**不碰**服务端（服务端仍"从不解析 payload" ⇒ 加字段对它是透明的）
   ⇒ ⇒ **这是它比 L4 便宜的地方：P1＋P2＋P3 可以完全在客户端侧做完。**
```

## 8. 一句话
```text
**"payload 改增量"不是"算 diff"，而是"把本来就有、却没被留下的那条 update 留下来"**；
  而它**可以完全在客户端侧落地**，服务端一行不用改（它反正从不解析 payload）。
⇒ 所以它是三条线的**共同前提里最便宜的一个**。
```
