# 并发**读**的上限是多少（L4 之后）
> 状态：**已收口**（分析）。证据：读上限的算式（见 `../plans/2026-09-29-l4-page-subscription-limits.md`）


> 由来：owner 2026-09-29「**并发写几万级别足够，并发读呢？上限是多少？**」
> ⇒ 承接 `horizontal-scale-limit-single-space`（那篇说"写"是单空间卡点）。本文算"读"这一侧。

---

## 1. ⚠️ 先看"读"在哪两种形态下含义不同
```text
【今天：通知 ＋ 各自拉】
  1 次写 ⇒ N 个通知 ⇒ **每个订阅者各自来拉一次**（每次 = 1 HTTP ＋ **2 条 SQLite 查询**）
  ⇒ ⇒ **读的总量 = O(N²)** ⇒ ⚠️ **这是今天真正的瓶颈**（服务端 CPU 4.33 核 @ N=200，实测）

【L4 之后：转发内容】
  1 次写 ⇒ 服务端**把增量直接推给该收到的人**
  ⇒ ⇒ ⚠️ **客户端不再各自拉** ⇒ **服务端不查库** ⇒
     读的开销从【SQL 查询】变成【**发送字节**】
⇒ ⇒ ⇒ 所以"读的上限"这个问题，**答案完全取决于是否做了 L4**。
```

## 2. ⭐ L4 之后：读的总量是多少（**这是关键算式**）
```text
先分清"单页"与"全网"：
· **单页**扇出 = k_p²（写者在页内 ⇒ 收件人 = 页内所有人）
· **全网**总扇出 = Σ_p (w_p × k_p) ≈ α · Σ_p k_p²
  ⇒ 若各页人数均匀（k̄）⇒ Σ k_p² = P · k̄² = N · k̄
  ⇒ ⇒ **总扇出 ≈ α · N · k̄**（次发送/秒）
⇒ ⇒ ⇒ ⭐ **它是【O(N · k̄)】—— 与 N 线性**（而 k̄ 很小，几十）
   ⇒ 这就是"降阶"的准确含义：**N² → N**（系数从 N 变成 k̄）
```

## 3. 算给你看（**读的上限**）
```text
**总扇出** ≈ α · N · k̄ 次发送/秒

取 α=10%（在写比例）、k̄=20（平均同页人数）、帧 ≈ 500 字节（一排字的增量）：
  · N = 100000  ⇒ 总扇出 **200,000 次/秒** ⇒ 出带宽 ≈ **100 MB/s**
  · N = 200000  ⇒ 总扇出 **400,000 次/秒** ⇒ 出带宽 ≈ **200 MB/s**
  · 若 k̄ = 50（大页多）⇒ 翻 2.5 倍 ⇒ N=200000 时 ≈ **500 MB/s**

⇒ ⇒ ⇒ **对照单机能力**：10 GbE ≈ **1.25 GB/s**；1 GbE ≈ 125 MB/s
   ⇒ **单机 10GbE 能扛 N≈10 万（k̄=20）；到 20 万+ 或 k̄ 大 ⇒ 要分网关** ✅
```
**⚠️ 另一道：网关的连接数与内存**
```text
每设备一条长连接（实测口径：每连接缓冲几十 KB）
  · 20 万连接 × 约 25 KB ≈ **5 GB** ⇒ 单网关吃不消，**要几个网关**（而它们**无状态 ⇒ 加就行**）✅
```

## 4. ⭐⭐ 所以"读"与"写"的可扩性**正好相反**
| | **写** | **读** |
|---|---|---|
| 瓶颈 | ⚠️ **单写者（架构单点）** | ✅ **出带宽 ＋ 网关连接数** |
| **能否靠加机器扩** | ❌ **不能**（同一个空间不能两个写者） | ✅ **能**（加网关／加带宽） |
| 今天上限 | ≈8000~20000 台（算式，单写者） | ⚠️ 受"通知+拉"的 **O(N²)** 拖累 |
| **L4 之后** | 不变（仍卡写者） | ⭐ **≈10 万（单机 10GbE）→ 20 万+（分网关）** |
| 规模化手段 | ⚠️ **必须改架构**（seq 按页分片） | ✅ **加机器** |

## 5. ⇒ 结论（照 owner 的口径）
```text
**"并发写几万级别足够" ⇒ 那么"读"完全不是瓶颈** ✅

  · 写：几万/秒 ⇒ 对应 N ≈ 8 万~20 万台（α=10%, r=2.5）
  · 读：**在同一个 N 下**，总量 ≈ α·N·k̄ = 200,000 次发送/秒 ⇒ 出带宽 ≈ 100 MB/s
    ⇒ ⇒ **单机 10GbE 轻松放下**，且**再加人就是加网关**（可横向扩）
⇒ ⇒ ⇒ **也就是说：读的上限比写高得多，而且它是唯一"能靠加机器扩"的那一侧。**

⇒ ⚠️ 前提是**做了 L4 转发**（否则读仍是 O(N²) 的 SQL 风暴 —— 而那是今天的形态）。
```

## 6. 一句话
```text
**读的上限不由"服务端 SQL"决定**（L4 之后服务端**不查库**了），而由两样决定：
  **① 出带宽**（≈100~200 MB/s @ N=10~20 万）**② 网关连接数／内存**（要几个网关）
⇒ 而**这两样都能靠加机器解决** ⇒ ⭐ **读这一侧是可以横向扩的。**
⇒ 反过来，**写那一侧不能**（单空间一个写者）—— 所以单空间的卡点**永远是写**。
```
