# 「空间清理 / 存储管理」实现方案

> 目标：为本地优先的 ShuyoNote 提供**空间可归因 + 可控清理**——用户能看到「谁在占空间」（数据库 / 附件 / 回收站 / 版本历史 / 软删空间 / 临时文件），并安全地清理「无引用 / 已丢弃」的字节，释放磁盘空间却**永不误删在用数据**。遵循[设计哲学](design-philosophy.md)「本地优先 + 数据主权 + 内容寻址去重」。

## 1. 背景与竞品对照

| 竞品 | 空间管理能力 | 关键点 |
|------|-------------|--------|
| Obsidian | 附件管理 + 存储统计 | 插件可看附件占用、清理主题/附件 |
| 思源笔记 | 资源清理 / 数据存储 | 数据仓库占用、清理未用资源 |
| Notion / FlowUs | 云端配额 | 云容量/配额，用户关心的是「剩余多少」 |
| ShuyoNote 现状 | 无 | **本地磁盘**是用户最关心的资源；但应用既无占用统计，也无清理入口——大量附件/历史会静默增长 |

**结论**：本地优先应用的空间是「**你的硬盘**」——应用必须**透明展示**占用构成，并给出**安全可控**的清理。这与「数据主权 / 本地优先」高度契合，也是当前缺失的一块。

## 2. 现状盘点（代码已核实）

| 分项 | 存储位置 | 现状 | 缺口 |
|------|----------|------|------|
| 附件 | `attachments/`（内容寻址 hash） | `save_image`/`import_attachment_files` 按 hash 去重；`remove_attachment` 仅在 hash **零引用**时删除磁盘文件 | 无全库「孤立附件」扫描/清理；版本字节随内容增长 |
| 数据库 | `shuyonote.db`(+WAL) | 页面/属性/派生索引（FTS/blocks/backlinks/db_views） | 无统计 |
| 回收站 | `pages.deleted_at` | 软删保留、可恢复 | 无「清空回收站」物理释放 |
| 版本历史 | `page_versions` | `MAX_VERSIONS_PER_PAGE=50`，相邻相同快照自动去重 | 无「按阈值清理」 |
| 软删工作空间 | `workspaces.deleted_at` | 整棵页树保留、可恢复 | 无物理清理（`delete_workspace` 为软删） |
| 临时文件 | 备份快照/解包目录、上传 `.part` | `backup.rs` 临时快照 + 解包目录；`import_attachment_files` 用 `.part` 暂存 | 异常中断残留，无清理 |

## 3. 核心概念与清理原则

- **内容寻址已去重**：相同内容只占一份——清理**不是去重**，而是删除「**无任何引用**」或「**被明确丢弃**」的字节。
- **三条红线**：
  1. 只清「**真孤儿**」，不碰「**有意的保留**」；回收站/版本历史/软删空间是主动的可恢复保留，默认保住。
  2. 删除字节前必须**确认零引用**（复用 `remove_attachment` 的判据）；清空/清理须**二次确认 + 用量预览**。
  3. **透明 + 可控**：展示占用构成、给出清理项与结果（释放多少空间），绝不静默销毁可恢复数据。
- **分项归类**：附件（大头）、数据库、回收站、版本历史、软删空间、临时文件——各自可归因、可单独清理。

## 4. 后端命令

```rust
// 各分项占用统计
storage_stats() -> { db_bytes, attachment_bytes, attachment_count,
                     trash_count, trash_bytes, version_count, version_bytes,
                     deleted_workspace_count, temp_bytes, ... }

// 清理项（各返回释放字节数，供 UI 提示）
clear_trash()                      -> u64   // 物理删除软删页面树 + 级联释放附件引用
cleanup_orphan_attachments()       -> u64   // 删除 hash 零引用的磁盘字节（列目录→比对→删）
cleanup_old_versions(max_keep?)    -> u64   // 每页保留最近 N 份（默认 50）之外的历史
cleanup_temp_files()               -> u64   // 删除备份临时/解包目录、残留 .part
purge_deleted_workspace(id)        -> u64   // 物理删除软删工作空间整棵页树 + 引用
```

> 实现要点：
> - 数据库备份用 rusqlite 在线备份 API（WAL 一致）；`storage_stats` 直接查 SQLite 行数与 `attachments` 表、`page_versions` 表，磁盘字节用 `fs::metadata`。
> - 孤立附件：`list_attachment_hashes` 已有磁盘 hash 列表；与 `attachments` 表 hash 集合做差集 → 零引用孤儿。
> - `clear_trash`/`purge_deleted_workspace` 需级联删除 `page_props`/`page_tags`/`page_versions`/`attachments`（引用）/`backlinks`/`blocks` 相关行，再按引用计数删字节。

## 5. 前端设计（「存储 / 空间」面板）

- 入口：侧边栏底部「存储」按钮（与备份/主题同组）或命令面板「空间统计」。
- 面板内容：
  - **占用概览**：各分项条形/数字（数据库 / 附件 / 回收站 / 版本历史 / 软删空间 / 临时文件）。
  - **清理项**（各带删除前用量预览 + 二次确认 + 结果 toast「释放 X MB」）：
    - 清空回收站 · 清理旧版本 · 清理孤立附件 · 清理临时文件 · 清理软删空间。
- 进度：长任务复用现有 `backup-progress` 事件模式（阶段/文件数/字节），前端进度条 + 忙碌态。

## 6. 实施顺序（里程碑）

- **M14.1 空间统计面板**：后端 `storage_stats` + 前端展示各分项占用。验收：能看清占用构成。
- **M14.2 清空回收站**：`clear_trash`（软删页面树物理删除 + 附件释放）+ 二次确认 + 结果提示。
- **M14.3 清理孤立附件**：`cleanup_orphan_attachments`（零引用字节）+ 用量预览。
- **M14.4 深化（可选）**：清理旧版本历史（按阈值）、清理临时文件、清理软删工作空间。

## 7. 测试与验收标准

- [ ] `storage_stats` 各分项数值准确（含子目录/空目录/无附件边界）。
- [ ] 清空回收站后，软删页面与其附件引用被物理清理，其他空间数据不受影响（M10 隔离）。
- [ ] 清理孤立附件只删「零引用」字节，正在使用的附件完好。
- [ ] 清理版本历史只删超出阈值的快照，保留最近 N 份。
- [ ] 删除前均有二次确认 + 用量预览；完成给出【释放 X MB】。
- [ ] 清理过程不阻塞 UI（async + 进度）；触发后相关列表/侧栏刷新。
- [ ] 撤销/误删防护：清理前读占用、清理后 reload（回收站/侧栏/版本历史）。

## 8. 风险与取舍

- **最大风险是误删在用字节**：所有删除以「零引用」为准；清理项均二次确认；优先做「能精确定位为孤儿」的清理（孤立附件、清空回收站），慢而稳。
- **附件字节与版本历史并存**：版本历史快照只存内容文本，不复制附件字节（附件独立内容寻址），清理版本历史不影响附件。
- **软删空间清理是破坏性大操作**：并入「清空/深层清理」，默认不做，需用户显式触发。
- **别静默自动清理**：默认不自动删除任何东西；只提供「统计 + 用户主动清理」，保持可恢复性优先。
- **本地优先语境**：空间在你硬盘，透明可控比「默认给最省」更重要——优先展示，其次安全清理。

## 9. 结论

「空间清理 / 存储管理」补齐本地优先应用的一块核心：**透明的空间地图 + 安全可控的清理**。按 M14.1 统计 → M14.2 清空回收站 → M14.3 清理孤立附件 收紧推进；深化项（版本/临时/软删空间）作为可选后续。配套设计理念见[设计哲学](design-philosophy.md)「本地优先 + 数据主权 + 内容寻址去重」与「别静默破坏可恢复数据」。
