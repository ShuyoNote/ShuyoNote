# 插件体系进化方案（M11 重基线：从「能跑的 L1」到「长得出生态」）

> 目标：把 M11 已落地的「磁盘命令插件」从**能跑**推进到**能长出生态**——先补运行时限与故障可见性，再冻结 ABI、统一能力层、补齐声明式贡献面与触发面，最后按需引入沙盒 UI 与分发；并把**运行时拓扑 / 权限模型 / 插件标识 / 数据存储**四类不可逆决策一次定对，避免二次返工。
> **北极星（定位）**：做**第一个「有权限模型的可信插件体系」，且作用在端到端加密、可自托管的本地数据上**——**做第一，不做更大**：不比能力条数（不做 Obsidian 式能力广度军备竞赛），比「**用户敢装**」与「**插件碰不到加密边界之外的东西**」。判据见 §1.1。
> 关联：[插件方案（M11 原始）](2026-08-22-plugin-plan.md) · [薄 Agent 接口方案](2026-08-24-thin-agent-interface-plan.md) · [设计哲学 §5.8 插件红线 / §8 IPC 最小暴露面](../design-philosophy.md) · [系统架构](../architecture.md) · [路线图](../roadmap.md)
> 状态：**提议（未实现）**。落地进度回填 [roadmap.md](../roadmap.md) 的 M11 段与 [docs/README.md](../README.md) 方案索引。
> 术语：本文「插件」**专指磁盘插件**（`manifest.json` + 代码，跑在受限运行时里）。`src/plugins/registry.ts` 里那 10 组硬编码命令是**内置命令组**，不属插件体系——见 §6.3 正名。

> [!] **本次明确不做**：任意文件读写 / 默认联网 / shell / 把插件代码放进主 renderer（红线）；块级插件间调用与依赖解析；插件市场与签名体系（排最后一档，且以「有作者文档 + 有真实第三方插件」为硬闸门）。

## 1. 定位、目标与非目标（Scope）

### 1.1 北极星：做第一，不做更大

**定位**：成为**第一个「有权限模型的可信插件体系」，且作用在端到端加密、可自托管的本地数据上**。

为什么这是唯一能"做第一"的定义——三家对标物各自缺一块：

| 对标 | 有权限模型？ | 作用在 E2EE 数据上？ | 可自托管？ |
|---|---|---|---|
| Figma 插件 | ✅ 沙箱无浏览器 API + `networkAccess.allowedDomains`（粒度到路径）+ 公开 `reasoning` | ❌ 云端文档 | ❌ |
| VS Code 扩展 | ✅ 扩展宿主进程隔离 | ❌ 开发工具，不碰用户私密数据 | ➖ |
| Obsidian 插件 | ❌ **官方承认做不到**：「由于技术限制，Obsidian 无法可靠地把插件限制到特定权限或访问级别，插件继承 Obsidian 的访问级别」——插件可读本机文件、联网、安装其他程序 | ❌ 明文 vault | ➖ |
| **ShuyoNote（本方案）** | ✅ 声明权限 + 逐调用后端校验 + 写经确认 | ✅ M15 每空间物理隔离 + E1 SQLCipher 静置加密 | ✅ 自建 sync-server |

> 上表事实出处：[Figma · How Plugins Run](https://developers.figma.com/docs/plugins/how-plugins-run/)（沙箱无浏览器 API、UI 走 iframe + 消息传递）、[Figma · Making Network Requests](https://developers.figma.com/docs/plugins/making-network-requests/)（`allowedDomains` 域/路径粒度、`reasoning` 公开）、[Obsidian · Plugin security](https://obsidian.md/help/plugin-security)（"cannot reliably restrict plugins to specific permissions or access levels"）。

**没有任何一家把「插件 + 权限模型 + E2EE + 自托管」四件事凑齐。** ShuyoNote 的零件（M15 隔离 + E1 加密 + M11 受限运行时 + M17 白名单宿主）恰好就是这四件事——缺的是把它们连成一体（§3.5 权限、§3.9 权限×加密边界、M11.6/M11.7）。

**分轴结论（避免过度承诺）**：按本方案**完整实施后**的准确水平是"**分轴有别**"，不是"全面对齐业界顶级"。

| 轴 | 结论 | 依据 |
|---|---|---|
| 权限模型 / 沙箱哲学 / 声明式贡献面 | **对齐或超出**（与 Figma 同族；比 Obsidian 严格一个身位） | §3.4 / §3.5 / §3.6 |
| ABI 工程（单一事实源 + 生成 + 门禁 + 版本化 + 类型包） | **高于平均水平** | §3.2 / §4 |
| **加密边界内的可信性** | **业界无先例**（本体系真正的差异点） | §3.9 / §3.10 |
| 隔离强度（进程隔离 / 内存上限 / 崩溃隔离） | **低于顶级**，分两段闭合：**内存炸弹**在 M11.5 就闭合（限流分配器，§3.11）；**原生崩溃 / 段错误 / OS 级账目**要等 M11.13 子进程——在那之前低于 VS Code/Chrome、与 Figma 同级 | §3.11、§4 决策 9、M11.5、M11.13 |
| 开发者体验（console / 断点 / source map / 性能） | **结构性低于顶级**——Boa 0.21 连 `console` 都没有、无 devtools、无 source map、解释执行无 JIT | §7 |
| 供应链与治理（自动扫描 / 评分 / 开发者政策 / 披露流程） | **低于顶级**，排在 M11.11（带闸门） | §5 |
| 生态规模（插件数与采用度） | **远低于顶级**，且**非架构可解**（取决于用户规模） | 本节下段 |

> **不要把"对齐业界顶级实践"当验收标准。** 它会把你推向两条错路：补**能力广度**（要交出 renderer 全信任，等于放弃红线）或补**引擎级 DX**（等于重做运行时）。本方案的验收标准是下面四条判据，以及"**不欠债**"（四类不可逆决策定对）。

**成功判据**（替代"我们是不是顶流"这种问法）：

| 判据 | 达标的含义 | 承载档 |
|---|---|---|
| **用户敢装** | 安装时看得到权限清单**与每项权限的理由**；写操作经确认；插件拿不到未声明的能力 | M11.6 / M11.7 |
| **碰不到加密边界之外** | 空间级能力只在本空间解密后可读；锁定空间不可读；插件数据落在该空间库内，随空间加密 / 备份 / 搬移 | M11.6 / M11.7（§3.9） |
| **有人愿意写** | 只看作者文档就能写出可安装可运行的插件；开发期能校验、能看日志 | M11.6 |
| **不返工** | ABI / 权限 / 标识 / 存储四类决策一次定对 | M11.6（§4） |

> **"能力条数对标 Obsidian"不是判据，也永远达不到**——那需要把插件放进 renderer 给全信任，等于放弃红线（设计哲学 §5.8）。这是**产品选择**，不是工程差距。能力广度只做到"够写出有价值的插件"（§5 M11.7/M11.9）即可，不再往上堆。

### 1.2 做

- **P0 前置硬化**：插件再也无法挂死窗口、无法泄漏线程；所有插件失败路径对用户可见；禁用成为后端强制而非 UI 假象。
- **P0 ABI 与权限**：冻结 v1 契约（`api.*` + `apiVersion`），建立**能力注册表单一事实源**，manifest 声明权限、安装时逐条授权、后端逐调用校验。
- **P1 能力扩容**：把「能干什么」从 4 个函数扩到一组语义能力（读 + 受控写），并**与既有 AI 语义工具层合并为同一份实现**。
- **P1 触发面**：斜杠菜单 / 上下文菜单 / 事件钩子 / 插件设置 / 命令参数表单 / 结构化返回。
- **P2 声明式贡献面**：无代码插件（manifest 声明面板、视图、主题 token、命令参数）。
- **P3（有信号才启动）**：沙盒 UI 插件（原 M11.3）、分发与信任（原 M11.4）。

### 1.3 不做（非目标，且要写进文档避免被反复提）

- **能力广度军备竞赛**：以"插件条数 / API 数量对标 Obsidian"为目标（§1.1）。能力只做到"够用"，把预算放在**可信**上。
- 插件执行任意命令 / 任意路径 / 默认出网（能力缺席是本体系安全的**唯一**来源，见 §8.1）。
- 插件常驻实例、后台任务、定时器（§3.6 一次性执行不变式）。
- 插件间依赖与互调、插件改核心 UI 布局。
- 在作者文档与真实第三方插件出现之前做市场 / 评分 / 推荐位。

## 2. 现状盘点（代码已核实）

| 维度 | 现状 | 证据 | 症结 |
|---|---|---|---|
| 能力面 | 5 个宿主函数：`register` / `__get_current_page` / `__pages`（**返回数量**）/ `__toast`（**只写 stderr**）/ `__insert` | `src-tauri/src/plugins.rs:198-285` | 一个插件能做的极限 = 读当前页 JSON + 往页尾插纯文本 → **没人有动力写** |
| 运行时 | 每次调用新建 `Context`、重新 eval 整份源码 | `plugins.rs:296-313` | 无常驻状态（**这是优点**，见 §3.6）；但也无事件、无设置、无跨命令状态 |

| 权限 | 无声明、无授予；`enabled` 仅前端过滤 | `plugins.rs:478-524` 无 `enabled(` 调用 | 「禁用」是 UI 假象；能力一旦扩容即全有全无 |
| ABI | 无 `apiVersion`；未知字段静默忽略；契约（`__*` 全局函数）本身就是实现细节 | `plugins.rs:56-69`、`:256-285` | 无兼容闸门；改 API = 静默破坏已有插件 |
| 状态 | `meta.plugin_state` 泛 KV，key = `plugin_enabled::{id}`；卸载不清行；`demo` 卸载后每次启动复活 | `plugins.rs:391-413`、`:541-552`、`:367-389` | 残留行 → 重装继承旧状态；不可卸载的内置插件 |
| 存储 | 无插件自己的数据存储（无 `getSetting/setSetting`） | 无 | 插件无法保存配置 |
| 分发 | 本地文件夹选择器；安装**先拷贝后校验** | `plugins.rs:554-579`（`:568` 拷贝、`:569` 校验） | 失败留半残目录 → id 永久占用 |

## 3. 目标架构

### 3.1 分层总览

```
        ┌──────────────────────── 触发面（都是「一次性调用」）────────────────────────┐
        │ 命令(Ctrl+K) · 斜杠菜单 · 页面/文件右键 · 编辑器菜单 · 事件钩子 · 面板数据请求 │
        └───────────────────────────────────┬───────────────────────────────────────┘
                                            │
        ┌───────────────────────────────────▼───────────────────────────────────────┐
        │                      能力注册表 Capability Registry（单一事实源）             │
        │  id · 标题 · 参数 schema · 读/写 · 所需权限 · scope · since/deprecated · 实现  │
        │  生成物 → api shim(JS) · 面向作者的文档 · Rust 绑定表 · 一致性门禁            │
        └──────┬──────────────────────────────┬───────────────────────────────┬──────┘
               │ Transport A                  │ Transport B                   │ Transport C
               │ Boa 原语 __cap/__log         │ postMessage（沙盒 UI）         │ LLM 工具调用（已存在）
               ▼                              ▼                               ▼
      ┌────────────────┐            ┌──────────────────┐            ┌──────────────────┐
      │ declarative 档  │            │ logic 档 (Boa)    │            │ ui 档（沙盒 WebView）│
      │ 纯 manifest     │            │ 无 UI            │            │ 自带 UI（后置）      │
      └────────────────┘            └──────────────────┘            └──────────────────┘
               └──────────────┬───────────────┴──────────────┬───────────────┘
                              ▼                              ▼
                    宿主实现（Rust 命令 / 前端语义层）——只此一份，不再第二遍实现
```

### 3.2 能力注册表：单一事实源

**问题**：现在能力定义散在 5 处（Rust 宿主函数、`api.ts`、`commands.ts`、`web.ts` 兜底、`src/lib/ai/tools.ts`）。再加一个消费方（插件）就会出现第二、第三份实现，必然漂移。

**做法**：新建 `capabilities/capabilities.json` 作为唯一事实源，条目形如：

```json
{
  "id": "pages.search",
  "title": "搜索页面",
  "kind": "read",
  "scope": "current-space",
  "permission": "read:pages",
  "since": "1.0",
  "argsSchema": { "type": "object", "properties": { "q": { "type": "string" }, "limit": { "type": "number" } }, "required": ["q"] },
  "resultSchema": { "type": "array", "items": { "type": "object" } },
  "impl": { "rust": "search", "web": "api.search" }
}
```

生成 + 门禁（沿用仓库既有的 `scripts/check-web-commands.mjs` 习惯）：

| 生成物 | 用途 |
|---|---|
| `scripts/gen-capabilities.mjs` | 由 JSON 生成下列各项 |
| `src/lib/capabilities/api.ts` | TS 侧类型化调用 + AI 工具定义（**替换** `src/lib/ai/tools.ts` 里的手写清单） |
| `src-tauri/src/capabilities_gen.rs` | Rust 侧方法表（method → 实现 + 权限） |
| **`packages/plugin-types/index.d.ts`（`@shuyonote/plugin-types`）** | **面向作者的 TypeScript 类型包**——由注册表生成，作者侧获得 IDE 补全与编译期检查。对齐 Figma `@figma/plugin-typings` / VS Code `@types/vscode` / Obsidian `obsidian.d.ts` 的既有实践；**没有它，作者只能靠猜和反复试跑** |
| `docs/plugin-api.md` | **面向插件作者的 API 文档**（本方案最关键的一份交付） |
| `scripts/check-capabilities.mjs` | 门禁：每条能力必须同时具备 权限、实现、文档、测试；生成物（含类型包）与源一致（未重新生成则失败） |

### 3.3 传输无关：同一份 `api.*`，两种传输

**这是"少走弯路"的核心决定**：插件看到的 ABI 是**生成的 JS shim**，不是 Rust 宿主函数名。

- Boa 只注册两个原语：`__cap(method, argsJson) -> resultJson` 与 `__log(level, msg)`。
- 生成的 shim 把 `api.pages.search({q:"x"})` 翻译为 `__cap("pages.search", '{"q":"x"}')`，并把 `register(cmd)` 一并定义好。
- Transport B（沙盒 UI 插件，后置）用**同一个 shim**，只把 `__cap` 换成 `postMessage` RPC。

→ 于是：换引擎、加传输、改宿主实现，**都不破坏插件 ABI**；`__insert` 这类今天的内部函数名不再是契约（`__*` 降级为私有原语）。同时天然修掉今天"`__pages()` 却返回数量"这类命名误导。

### 3.4 运行时三档（一个插件一个档）

| 档 | 代码 | 运行时 | 能贡献 | 何时够用 |
|---|---|---|---|---|
| `declarative` | 无 | 无 | 命令/菜单/斜杠项/设置/面板与视图/主题 token/命令参数 | **多数插件**：统计面板、模板包、主题、导入触发 |
| `logic` | `main.js` | Boa（无 UI） | 上述 + 计算、批处理、读写能力调用 | 自动打标签、批量整理、报告生成、导入转换 |
| `ui` | `main.js` + UI 资源 | 沙盒 WebView（后置） | 上述 + 侧栏面板/自定义块/自定义视图 | 画布式、富交互（少数插件） |

**规则**：先穷尽 `declarative`，其次 `logic`，最后才 `ui`。绝大多数"我想要一个插件面板"的需求应由声明式渲染器满足——这能省掉一整个沙盒渲染面。

### 3.5 权限模型

manifest 新增 `permissions: []`（**默认空 = 零能力**），安装时把清单摊给用户逐条确认，**后端在每次能力调用时校验**（不是靠 UI 隐藏）。

| 权限 | 说明 | 风险 |
|---|---|---|
| `read:page.current` | 当前页正文 | 低 |
| `read:pages` | 空间内页面列表 / 搜索 / 单页读取 | 低 |
| `read:pages.all-spaces` | 跨空间读取 | **中**（标黄） |
| `read:tags` / `read:backlinks` | 标签、反链 | 低 |
| `read:files` | 附件元数据（**不含字节**） | 低 |
| `write:page.current` | 当前页插入纯文本（等价今天的 `__insert`，即时生效） | 低 |
| `write:pages` | 建页 / 追加块（**走草稿确认**） | 中 |
| `write:properties` / `write:tags` | 改属性 / 加标签（**走草稿确认**） | 中 |
| `write:clipboard` | 写剪贴板 | 中 |
| `kv:own` | 自己的键值存储 | 低 |
| `ui:panel` / `ui:theme` / `ui:command-args` | 贡献 UI / 主题 / 命令参数表单 | 低 |
| `net:https:<host>` | 出网（**域白名单**，走 `coreHttp`） | **高**（标红） |

**写操作三档中介**（把"给写能力"变安全的那把钥匙）：

1. **即时**：只作用于当前页、只写纯文本（今天的 `__insert`）。
2. **草稿确认**：建页 / 改属性 / 加标签 → 产出草稿 → 用户在既有预览面板确认 → `applyDraft()` 落库。**这套机制已存在**（`src/lib/ai/host.ts:141-173` + `src/lib/ai/apply.ts`），直接复用。
3. **永不授予**（不进权限表）：删除 / 回收站、加密与密钥、同步配置与账户、任意 SQL、任意路径、执行外部程序。

**权限的"理由"要公开**：manifest 的 `permissions` 用对象形式而非纯字符串数组，每项带 `reason`（对齐 Figma `networkAccess.reasoning` 的做法，其理由会显示在插件目录页上）：

```json
"permissions": [
  { "id": "read:pages", "reason": "为生成每周阅读统计，需要读取本空间的页面标题与字数" },
  { "id": "write:tags", "reason": "按规则自动补标签，写入前会给你确认" }
]
```

安装/授权界面显示「权限 + 理由」，而不是只列权限名——**这是"用户敢装"的第一道门**（§1.1 判据）。理由为空的权限项在校验命令里给出警告。

### 3.6 一次性执行不变式（保持，明确写进契约）

任何入口（命令 / 事件 / 面板请求）= **一个全新 Context + 一次调用**；禁止常驻实例、定时器、监听器。

- 理由：与现有实现一致；无泄漏面、无跨调用污染、易审计；热重载与卸载天然干净。
- 事件的做法：manifest 声明 `hooks: [{ "on": "page.saved", "command": "on-save" }]`，宿主在事件发生时**调用插件的某个命令并把 payload 作为参数传入**。
- 代价（写入非目标）：插件不能做后台任务 / 常驻调度。要后台能力时应当是**宿主提供能力**（如"注册一个定时导入源"），而不是放开常驻实例。

### 3.7 存储模型

`plugin_state` 泛 KV 存一切是残留问题的根源（评估里"卸载不清行 / demo 复活"都是它）。改为两张表：

```sql
-- 安装记录：一行 = 一个已安装插件（卸载即删行，残留问题从结构上消失）
CREATE TABLE plugin_install (
  plugin_id     TEXT PRIMARY KEY,
  version       TEXT NOT NULL,
  enabled       INTEGER NOT NULL DEFAULT 1,
  installed_at  INTEGER NOT NULL,
  source        TEXT NOT NULL DEFAULT 'local',  -- local | zip | url | bundled
  content_hash  TEXT,
  seeded        INTEGER NOT NULL DEFAULT 0      -- bundled 播种标记：卸载后不再复活
);

-- 插件私有数据：命名空间隔离 + 作用域 + 配额
CREATE TABLE plugin_data (
  plugin_id  TEXT NOT NULL,
  scope      TEXT NOT NULL,   -- 'app' | 'space:<id>'
  key        TEXT NOT NULL,
  value      TEXT NOT NULL,
  updated_at INTEGER NOT NULL,
  PRIMARY KEY (plugin_id, scope, key)
);
```

- 配额：默认 256 KB / 插件（每个 scope 独立计数；超限报错而非静默截断）。
- 纳入整库备份 / 导出；**默认不参与同步**（见 §4 决策 7）。
- 迁移：读 `plugin_state` 的 `plugin_enabled::{id}` → 写入 `plugin_install.enabled`，迁移后清空旧 KV。

**落库位置 = 加密边界（这条决定"可信"能不能成立）**：

| 表 | scope | 物理位置 | 是否随空间加密 |
|---|---|---|---|
| `plugin_install` | app 级 | `meta.db` | ❌ 不加密（只存安装记录：id/版本/开关/hash，**不含用户内容**） |
| `plugin_data` | `app` | `meta.db` | ❌ 不加密 → 仅允许放**非敏感**配置（主题偏好等），文档须明写 |
| `plugin_data` | `space:<id>` | **该空间自己的 `spaces/<ws_id>/shuyonote.db`** | ✅ **随该空间 SQLCipher 一起加密**，并随空间备份 / 导出 / 搬移 |

> ⚠️ **反例（必须避免）**：把 `plugin_data` 整张表放在 `meta.db`。`meta.db` 是明文的（加密配置本身就明文存在那里，见 [身份与隐私模型 §5.1](../identity-privacy-model.md)），空间级插件数据一旦落进去就**静默逃出 E2EE 边界**——插件明明只在加密空间里工作，数据却明文躺在磁盘上。这是本方案里最容易被忽略、后果最重的一条落库约定。
>
> 因此：`plugin_data` 的 DDL **同时存在于** `meta.db`（app scope）与每个空间库（space scope），由宿主按 scope 路由，**插件只看到 `api.kv.get/set(key, scope?)`，看不到库的差别**。

### 3.8 标识与分发

- **插件 id 收紧为单段 `^[a-z0-9][a-z0-9-]{0,38}[a-z0-9]$`**（无点、无斜杠、无下划线）。一次性消灭"路径穿越 / 隐藏目录 / 作用域歧义"三类问题，也让 `plugin_data(plugin_id,…)` 与状态键无歧义。目录名 = id（沿用今天的校验），**id 不可变、不可改名**，显示名随意。
- 只做**增量兼容**：已有 `demo` 等合规 id 不受影响；不合规 id 报明确错误而不是静默跳过。
- 分发四步递进（都要"先校验后落盘"）：本地目录（现状）→ zip（manifest 校验 + sha256）→ URL（sha256 校验）→ 签名（`publisher` 公钥）+ 撤销列表 + **只提示不自动**的更新检查。

### 3.9 权限 × 加密边界（本体系的差异化所在）

其他家不需要处理这件事（Figma 在云上、Obsidian 的 vault 是明文），所以**这一节就是"做第一"的技术内容**。三条硬约束：

1. **空间级能力只作用于活动空间**：`read:pages` / `write:pages` 等默认 scope = `current-space`，宿主注入的上下文**只含当前空间的解密数据**。插件无法"顺手"读到别的空间——不是靠自觉，是靠宿主不给。
2. **锁定空间不可读**：E1 加密默认关、开启后启动即锁定（`SESSION_KEY` 不落盘，锁定态不读空间）。因此：跨空间能力（`read:pages.all-spaces`）在目标空间锁定时必须**返回明确错误**（`space_locked`），不得静默返回空、更不得触发隐式解锁；插件调用不得成为绕过启动锁的通路。
3. **插件数据随空间加密**：见 §3.7 落库表。space scope 的数据进空间库（加密、随备份/搬移），app scope 只允许非敏感配置。

**权限 → 数据的映射表**（实现时逐条落地，并作为 M11.6 的验收项）：

| 能力 | scope | 碰得到的数据 | 加密边界行为 |
|---|---|---|---|
| `page.current` / `editor.insertText` | `current-space` | 当前页 | 锁定态不可用 |
| `pages.list` / `pages.search` / `pages.get` | `current-space` | 本空间页面 | 锁定态不可用 |
| `tags.list` / `backlinks.list` / `files.list` | `current-space` | 本空间标签 / 反链 / 附件元数据 | 锁定态不可用 |
| `pages.*`（`read:pages.all-spaces` 授权后） | `all-spaces` | 多空间 | **逐空间检查**；任一目标空间锁定即 `space_locked` |
| `kv.own` | `app` / `space:<id>` | 自己的数据 | space scope 落空间库（加密） |
| `net:https:<host>` | — | 出网 | 与加密无关，但**默认不授予**，且需域白名单 + 理由公开 |

> 派生要求：能力注册表（§3.2）的每条能力**必须声明 `scope`**，门禁脚本（`check-capabilities`）校验"声明了 scope 的能力都有对应的锁定态测试"。

### 3.10 审计与可见性（"可信"要给证据，不能只给承诺）

顶级扩展体系（Chrome / VS Code / Android）都有一条"**哪个扩展做了什么**"的轨迹；本方案上一版只做了作者侧的日志，缺了用户侧的证据链。补四样：

1. **权限使用审计轨迹**：每次能力调用记录 `(plugin_id, capability, scope, 时间, 结果)`，**只记元数据、不记内容**（不落正文/不落键值），环缓冲 + 设置页「插件活动」可查（"这个插件用过 3 次 `read:pages`、最近一次在 10 分钟前"）。
2. **失败原因的稳定错误码**：`space_locked` / `permission_denied` / `timeout` / `loop_limit` / `plugin_error` 等，**在 `docs/plugin-api.md` 里列表化**，作者可据此分支处理，用户看到的是人话而不是堆栈。
3. **运行态可见 + 可取消**：见 M11.5（长任务有可见状态，用户能随时中止）。
4. **作者侧日志**：`__log(level, msg)` 环缓冲 + 面板可查（替代今天只写 stderr 的 `__toast`）。

> 为什么这属于架构而非"打磨"：本体系的定位是「**用户敢装**」（§1.1）。**敢装的前提是装完能看见它在干什么、出问题能查到、不想要能停掉**——这三件事都是宿主提供的可见性，插件自己给不了。

### 3.11 资源与故障隔离：已核实的边界矩阵（2026-09-10 核实）

> 本节是 M11.5「资源上限」与 §4 决策 9、M11.13 的判断依据。核实方式：读 vendored 源码 + 查最新版 API 文档 + 查上游 issue。

**结论一：Boa 无法设分配预算（已定论，且上游不会给）**

- `boa_engine` **0.21.1（当前）与 0.22.0（最新，2026-08-28）** 的 `RuntimeLimits` 都只有 4 项：`loop_iteration` / `stack_size` / `recursion` / `backtrace_limit`——**没有任何堆或分配预算**。
- `boa_gc` 0.21.1 只暴露 `force_collect()` / `has_weak_maps()` / `finalizer_safe()`，**无分配计量、无上限**。
- 上游唯一相关 issue（[boa-dev/boa#2350 "Runtime limits on bad neighbors"](https://github.com/boa-dev/boa/issues/2350)，2022-10 开、**至今未关**）正文只要 **循环 + 递归/栈深**——**根本没提内存**。→ 不要指望等上游。

**结论二：能定制"分配失败行为"的官方钩子用不了**

- stable Rust + 链接 std 时，不可失败分配失败 → `std::alloc::handle_alloc_error` → **打印后 abort 进程，不 unwind**（[std 文档](https://doc.rust-lang.org/std/alloc/fn.handle_alloc_error.html)）。
- 唯一能改此行为的 `set_alloc_error_hook` 是 **nightly-only 实验 API**（[`alloc_error_hook` #51245](https://doc.rust-lang.org/std/alloc/fn.set_alloc_error_hook.html)）→ **稳定版用不了**。
- ⇒ **"让限流分配器返回 null"是错的做法**：它把"可能被 OS 回收"变成"必定 abort 应用"。**要做就 panic**（结论四）。

**结论三：Boa 内部哪条路径优雅失败、哪条会拖垮进程**（逐条源码核实）

| JS 构造 | Boa 行为 | 后果 |
|---|---|---|
| `new ArrayBuffer(n)` / `new Uint8Array(n)`（n 巨大） | `try_reserve_exact` → **抛可捕获的 RangeError**（`array_buffer/mod.rs:969`、`array_buffer/shared.rs:594`） | ✅ 优雅 |
| `'x'.repeat(3e9)` | 有 `MAX_STRING_LENGTH = u32::MAX`（≈4GB）的 `checked_mul` 保护（`string/mod.rs:253,720`） | ⚠️ 是**规范形状**的保护、不是预算：4GB 本身足以压垮机器，之后仍走不可失败分配 |
| dense array 填充 / 对象与字符串累积 / 循环 `push` | **不可失败分配**（`with_capacity` 等 54 处） | ❌ 失败 = abort |

**结论四：进程内可行解 = "超预算就 panic"的限流分配器**

本仓库的条件恰好适合：`Cargo.toml` **无 `[profile]` 覆盖** → 默认 **`panic = "unwind"`**；且**插件线程 panic 今天已有处理路径**（`plugins.rs:351-352`：`Disconnected → "插件线程异常退出"`）。再叠加 §3.6 的**一次性执行**（每次调用新建 `Context`、用完即弃），unwind 出来把整个上下文丢掉是安全的。

→ **每插件字节预算 + 超预算 panic = 线程 unwind → 干净错误 → 应用存活**，可以落在 M11.5，不必等子进程。三个前置必须同时满足：① 保持 `panic = "unwind"`；② 插件线程执行 JS 期间**不持有会被 poison 的锁**（DB 锁已在超时整改中移出执行路径，其余需审计）；③ panic 路径**不做格式化分配**（预留余量，避免二次失败转 abort）。

**结论五：仍然只有子进程能兜的部分（M11.13 的真实剩余价值）**

| 故障 | 进程内能否兜住 |
|---|---|
| 死循环 | ✅ loop 限额（M11.5） |
| 软件 panic | ✅ **今天就已兜住**（`Disconnected` 分支） |
| 分配炸弹 | ✅ 结论四（M11.5 新增） |
| **原生崩溃 / 段错误 / UB**（Boa 是含 unsafe 的年轻引擎） | ❌ 只有 OS 进程边界能兜 |
| **OS OOM-killer / 系统级内存压力** | ❌ 只有 OS 级限制能兜 |
| 精确的进程级资源账目与可见性 | ❌ 只有 OS 级限制 |

→ M11.13 仍然必要，但**紧迫性下降**：从"P0 阻塞能力扩容"改为"**与分发（M11.11）绑定的硬前置**"（第三方插件进场前必须具备进程级隔离），并保留"一旦观察到 Boa 段错误即升 P0"。
→ 另：**线程级内存上限在任何主流 OS 上都不存在**，所以"同进程多线程"这条路本身是死的，子进程是唯一形态。

**附：为什么不指望"沙盒 iframe 免费拿到进程隔离"**
iframe 能提供**能力**隔离，但不能当作**内存**边界：macOS WKWebView 下同 WebView 内的 iframe 通常与宿主共享 WebContent 进程，WebView2 + 自定义协议源亦然。**（此条需在 M11.13 设计阶段实测确认，本文不作为结论使用。）**

| # | 决策 | 备选 | 建议 | 为什么不可逆 | 现在定的代价 → 以后改的代价 |
|---|---|---|---|---|---|
| 1 | **运行时拓扑** | 只用 Boa / 只用沙盒 UI / 两者并存 | 能力层**传输无关** + 三档运行时；`logic` 用 Boa，`ui` 后置 | 若先用 Boa 铺开 API、日后 UI 档用另一套 ABI，则插件要重写、权限要重做 | 1–2 人日写 shim + 抽象 → 否则等于重做 ABI |
| 2 | **契约命名与版本** | `__*` 直接暴露 / `api.*` + `apiVersion` | 冻结 `api.*` 为 v1；`__*` 降为私有原语 | 名称一旦被插件依赖即冻结 | 现在几乎免费 → 以后改名 = 全量插件失效 |

| 5 | **插件标识方案** | 点分 `a.b` / 带斜杠 `@a/b` / 单段短横线 | 单段 `[a-z0-9-]`，不可改名 | id 进路径、进状态键、进数据表、进分发标识 | 现在一行校验 → 以后改名要迁移用户数据 |

| 7 | **插件数据是否同步** | 同步 / 默认不同步 | 默认不同步，可声明 `sync:data`（空间级、E2EE 兼容） | 与 E2EE / 空间模型耦合，事后改要动同步协议 | 现在只写文档与默认值 → 以后改协议代价高 |
| 8 | **执行模型** | 一次性 / 常驻实例 | 保持一次性（事件 = 带 payload 的调用） | 常驻实例引入生命周期、泄漏、热重载、崩溃隔离一整套 | 现在零成本（就是现状）→ 以后回收极难 |
| 9 | **隔离强度** | 同进程线程（现状）/ 独立子进程 | **两层**：① 进程内先用"超预算 panic 的限流分配器"把分配炸弹挡住（M11.5，§3.11 结论四）；② **仍定子进程化 + OS 级资源限制**（M11.13），因为段错误/UB 与 OS 级账目只有进程边界能兜 | ① **Boa 无分配预算 API**（0.21.1 与最新 0.22.0 皆无，上游 issue 不涉内存）——这条已核实完毕，不存在"以后能设"的选项；② **线程级内存上限在任何主流 OS 上都不存在**，所以子进程是唯一形态；③ 一旦有存量插件再改宿主，等于重做 `RunState` / 命令路由 / 超时取消 | 现在：分配器约 1–2 人日 + 子进程化 1–2 周 → 以后：若等到第三方插件进场再改，等于重做宿主与 IPC，且期间一直暴露在"插件可弄崩应用"之下 |

**可延后决策**（明确列出，避免在这些处反复纠结）：市场 / 签名 / 评分与开发者政策、自定义编辑器与任意 UI、主题 CSS 深度、每空间独立安装、插件依赖与互调、插件崩溃上报。

> **注**：「是否把 Boa 换成浏览器引擎」**不在可延后清单里**——因为它决定开发者体验的天花板（Boa 0.21 无 `console`、无 devtools、无 source map、无 JIT），是**结构性**的，不是可以"以后顺手换"的工程项。它的结论是：**接受这一轴低于顶级，并把预算投到"可信"上**（§1.1 分轴结论、§7）。

## 5. 里程碑

> 粗估为单人全职。**M11.5 → M11.6 → M11.7 是刚性序列**：跳过 M11.5 后续都建在沙地上，跳过 M11.6 则在 M11.10 要重做一遍。**M11.13 不阻塞 M11.7**（分配炸弹已在 M11.5 闭合），它与 M11.11 绑定为分发硬前置，并在出现 Boa 段错误时升 P0（依据 §3.11）。

### M11.5 前置硬化（时限 · 可见性 · 一致性）— 3–5 人日

**交付**

- 两个 `Context` 都设 `RuntimeLimits`：`set_loop_iteration_limit(1e7)`（+ 明确的 stack / recursion 预算），死循环变成**可捕获的 JS 错误**而不是永久线程。
- **资源上限：已核实结论 + 进程内可行的真实防线**（这是安全缺口，不是打磨）——完整结论见 **§3.11**。要点：Boa **无法设分配预算**（0.21.1 与最新 0.22.0 皆无，上游也不会给）；但**进程内有可行解**：装一个 **thread-local 限流分配器**，超预算时 **panic（而不是返回 null）** —— panic 会 unwind 插件线程，被既有 `Disconnected` 分支转成干净错误（`plugins.rs:351-352`），应用存活。本档交付：① 该分配器 + 每插件字节预算 + `alloc/alloc_zeroed/dealloc/realloc` 全路径计数；② 审计并保证**插件线程执行 JS 期间不持有会被 poison 的锁**（DB 锁已在超时整改中移出）；③ panic 路径**不做格式化分配**（预留余量，避免二次分配失败→abort）；④ 体积/文件数/单次返回值上限作为纵深；⑤ 测试：**一个分配炸弹插件只终结该次调用，应用存活**。
  > 前提核实过：仓库 `Cargo.toml` **无 `[profile]` 覆盖** → 用的是 Rust 默认 `panic = "unwind"`（若将来改成 `abort`，本条防线立即失效，需同步改回或改走 M11.13）。
- **`loop_iteration_limit` 要按"内存"重算（不只是 CPU）**：它同时是「分配循环」的实际内存上限——峰值 ≈ **迭代次数 × 每次迭代分配**。原写的 `1e7` 过大（1e7 × 数十字节 = 数百 MB～GB 级），改为 **discovery 与 run 分档**（run 取 `1e6` 量级），并在注释里写明这个乘法关系，避免以后有人随手调大。
- discovery 也走带超时的工作线程；`list_plugins` 改 `async`（对齐仓库里 75 个 async 命令的既有习惯），install 同理。
- 卸载删 `plugin_install`（当前是 `plugin_state`）行；`demo` 用 `seeded=1` 标记，卸载后不再复活。
- 安装**先校验 manifest + 入口文件，再拷贝**；拷贝失败清理半残目录。
- `run_plugin_command` 后端校验 `enabled` 与权限（当前完全不校验）。
- 错误可见：`store/plugins.ts` 的 `console.error` → 接入既有 toast / confirm；`CommandPalette` 不再无条件报"已切换插件状态"。
- `read_manifest` 的 `main` 校验改为"单个 `Component::Normal`"（当前误拒 `./main.js`、放行 `..`）。
- 插件日志从 stderr 改为环缓冲 + 面板可查；`__toast` 接通 UI。
- **长任务运行态可见 + 用户可随时取消**（对齐 Figma 的 "Running [plugin]" 提示与取消入口）：loop 预算是确定性兜底，可见性解决"看起来卡住了"。取消 = 宿主丢弃该次调用结果并记录，不再有半途写入。
- 测试：沙箱逃逸回归（断言 `fetch`/`fs`/`window`/`document`/`invoke`/`require` 均不可达）、循环阈值、超时、manifest 拒绝矩阵、持久化往返、卸载清理；**`cargo test` 进 CI**。

**验收**：一个 `while(true)` 插件既不挂窗口也不泄漏线程（有测试断言）；**一个分配炸弹插件（如 `new Array(1e9).fill(0)`）只终结该次调用、应用存活（有测试断言）**；所有插件失败路径 UI 可见；禁用插件 IPC 不可执行；运行中的插件有可见状态且用户能取消；**资源结论已落地（§3.11，M11.13 去留已定并写进路线图）**。

### M11.11 分发与信任（原 M11.4，重编号）— 1–2 周

**硬前置**：**M11.13（进程级隔离）必须先于 M11.11a 完成**——第三方插件（不是用户自己挑的目录）进场前，必须有"插件无法弄崩应用"的边界。见 §3.11 结论五。

**与「绝不跟踪」对齐（不可协商）**：索引只含版本与兼容性事实；排序在本地算；禁止下载计数上报、应用内评分、埋点式热门、竞价推荐位；「评价」的载体是社区帖子（`discussionUrl`）。见[分发策略 §6](2026-09-10-plugin-distribution-strategy.md)。

**交付**：`sync:data` 声明 + 空间级 `plugin_data` 增量同步（E2EE 兼容）。

**前置**：M11.6 的存储模型 + 同步协议确认。

### M11.13 隔离强度：插件宿主子进程化 + OS 级资源限制 — 1–2 周（**已判定必有，绑定分发**）

**为什么单列**：Boa 无分配预算 API（**已核实**，含最新版；见 §3.11）。M11.5 的"超预算 panic 限流分配器"能挡住**分配炸弹**，但挡不住**原生崩溃 / 段错误 / UB**（Boa 是含 unsafe 的年轻引擎）与 **OS OOM-killer**——这三样只有 OS 进程边界能兜。

**排期（依据 §3.11 结论五）**：~~原为"M11.5 评估后再定"~~ → **评估已完成**，结论是：
- **不再阻塞 M11.7**（分配炸弹已在 M11.5 闭合，紧迫性下降）；
- 改为 **与 M11.11（分发）绑定的硬前置**：**第三方插件进场前必须完成进程级隔离**；
- **保留升级条款**：一旦观察到 Boa 段错误 / 应用级崩溃与插件相关，立即升 P0 插到最前。

> 不接受"降级为不做"：一旦有了存量插件再改宿主，等于重做 `RunState` / 命令路由 / 超时与取消，代价远高于现在做。

**交付**：插件宿主挪到**独立子进程**（Boa 与沙箱都在该进程内）；宿主 ↔ 子进程走**私有 IPC**（非通用 `invoke`）；**OS 级资源限制**（内存 / CPU / 句柄）；子进程崩溃或 OOM 只终结该次调用，主进程存活并给出可见错误；超时与取消改为**跨进程可中止**（顺带彻底解决 M11.5 里"超时只是遗弃线程"这一遗留）。

**验收**：一个无限分配内存的插件不会让应用崩溃（应用存活 + 明确错误提示，有测试）；一个 panic 的插件不带走主进程；资源上限在 OS 层真实生效（可观测的进程内存上限）。

## 7. 风险与取舍

| 风险 | 说明 | 缓解 |
|---|---|---|
| **Boa 与浏览器方言差异** | 作者在浏览器里写好、在 Boa 里跑不起来 | 开发期校验命令（Boa 真解析）+ 打包预设 + 兼容性文档；**不把"换引擎"当可延后项**（见下行"引擎选型决定的 DX 上限"） |
| **双运行时支持面翻倍** | `logic`(Boa) + `ui`(沙盒 WebView) 两套引擎 | 传输无关 shim + 一个插件一个运行时 + 同一权限模型；若 `ui` 档长期无真实需求则不做 |
| **能力扩容 = 攻击面扩容** | 每加一个能力都在削弱"薄即安全" | 权限声明 + 写中介 + 永不授予清单 + 每次调用后端校验 + 权限矩阵测试 |
| **声明式滑向自研 UI DSL** | 越做越像自造框架，成本失控 | 只做**能映射到现有 UI 原语**的声明（数据库透镜 query/columns、设置 schema、参数表单、主题 token）；超出部分一律交给 `ui` 档 |
| **生态冷启动** | 有 API 没人写 | 先文档 + 示例 + 本地 zip 安装；市场最后做且有闸门 |
| **与 YAGNI / 反过度设计冲突** | 仓库哲学反对铺大摊子 | 用**闸门**代替删除：M11.10/M11.11 明确"有信号才启动"，而不是从路线图里划掉 |
| **工程量递延到后期才暴露** | M11.9 声明式渲染器可能比预期重 | 先做最小声明集（命令参数 + 设置 + 面板 query/columns），按真实插件需求增量扩 |

## 8. 弯路清单（明确不做）

1. **不做语言特性黑名单**（拦 `eval` / 原型链 / `Function`）。原始方案 §6 的"阻断 require/eval"是错的方向：真正起作用的是**能力缺席**，拦语言只会烧工时还漏。`eval` 在无宿主能力的沙箱里没有逃逸价值。
2. **不让插件进主 renderer**，不暴露 Tauri `invoke`，更不自动暴露全量命令面（111 sync + 75 async）——那等于把"IPC 最小暴露面"（设计哲学 §8）作废。
3. **v1 不放 `net` / `fs`**。要放必须走声明权限 + 域白名单 + `coreHttp` + 标红授权。
4. **不先做市场 / 签名 / 评分**：没有作者文档与真实第三方插件时，市场是空转。
5. **不在两处实现同一能力**（Rust 与 TS 各一套语义工具）。这是"漂移"的标准剧本，仓库已有 5 处同义清单。
6. **不给插件常驻实例 / 定时器 / 后台任务**（一次性执行不变式）。
7. **不把 `plugin_state` 当万能 KV**（安装记录 → `plugin_install`，插件数据 → `plugin_data`）。
8. **不让插件 id 可改名、含点或斜杠**（id 进路径、状态键、数据表、分发标识）。
9. **不在声明式贡献面穷尽之前上任意 UI**。
10. **不让「内置命令组」继续叫插件**（避免第三次返工）。
11. **不打能力广度军备竞赛**：不为了"插件条数 / API 数量对标 Obsidian"去加能力（§1.1）。能力只做到"够写出有价值的插件"，超出部分一律不要——那需要交出 renderer 全信任，是放弃红线换来的假领先。
12. **不让插件数据离开加密边界**：`plugin_data` 的 space scope 必须落空间库（§3.7），不得图省事统一塞 `meta.db`——那会让"作用在 E2EE 数据上的可信插件"这句定位当场失效。
13. **不让插件成为绕过启动锁的通路**：锁定空间必须 `space_locked` 报错，不得静默返回空、更不得隐式解锁（§3.9）。
14. **不用"对齐业界顶级实践"当验收标准**（§1.1 分轴结论）。它会把你推向两条错路——补**能力广度**（要交出 renderer 全信任）或补**引擎级 DX**（等于重做运行时）。用四条判据 + "不欠债"验收。
15. **不把内存 / 崩溃隔离含糊掉**：已核实 Boa 无分配预算 API（含最新版）→ 必须显式记账（§3.11 矩阵、§4 决策 9、M11.5 限流分配器、M11.13 绑定分发），**不能藏在"后续打磨"里**；同时也**不假称已解决**（段错误/UB 与 OS 级账目在 M11.13 之前确实没兜住）。
16. **不为"看起来对标了 Figma"而堆仪式**：Figma 的细节只学**有实质作用的**（权限理由公开、运行态可取消、域白名单粒度），不照抄与自身问题域无关的部分。
17. **不用"限流分配器返回 null"这种错解**：stable Rust 下不可失败分配失败 = 打印后 **abort**（可定制的 hook 是 nightly-only），返回 null 等于确定性弄死应用。要么 **panic 让它 unwind**（§3.11 结论四），要么走进程边界。

---

## 9. 结论

M11 的地基（能力隔离 + 持久化 + 装/卸/启停）已经对了，**这一层不要动**。真正要补的是三件事，顺序不能换：

1. **先补时限、资源上限与可见性**（M11.5）——否则后面每加一个能力，都在放大一个会挂死窗口、会泄漏线程、**可能把应用内存吃光**、失败了还静默的运行时。资源上限若证实做不到（Boa 无堆 API），就是 M11.13 前移的信号。
2. **再冻结 ABI 与权限**（M11.6）——`api.*` + `apiVersion` + 单一能力注册表 + manifest 权限 + **类型包** + **审计轨迹**；这是唯一能让"以后加能力不算破坏"的做法，也是"用户敢装"的落点。
3. **然后才扩能力**（M11.7）——**且靠已有资产扩容**：AI 语义工具层（`src/lib/ai/tools.ts`）已经具备"白名单 + 读写区分 + 写经确认"三个性质，插件方案当年也写明"AI 宿主与 L1 插件同层"。把两者合并成一个能力层、两个消费者，是本方案投入产出比最高的一步。

UI 插件（M11.10）与分发治理（M11.11）不是不做，而是**有闸门地后置**：前者等声明式贡献面穷尽，后者等真实第三方插件出现。**而社区上线最该先铺的不是市场，是[贡献阶梯](2026-09-10-plugin-distribution-strategy.md)**（模板 → 主题 → 声明式配方 → 逻辑插件 → UI 插件）——前三级是惰性数据，**今天就能安全开放**，并把「社区能否贡献」与「M11.13 安全闸门何时完成」解耦。

一句话：**先把地基建牢，再把契约冻结，然后靠"一个能力层"扩容；UI 与市场用闸门等信号，而不是用来撑门面。**

补一句定位层面的话（§1.1）：这条路径的终点**不是"插件能力最多的笔记应用"**（那需要交出 renderer 全信任，等于放弃本地优先的红线），而是**"第一个让用户敢在加密数据上装插件的体系"**——Figma 有权限模型但没有加密数据，Obsidian 有数据但没有权限模型，VS Code 两者都不在其问题域内。**这个位置目前空着，而且只有"薄 + 可信"才有资格占。** 所以本方案刻意把能力面压在"够用"，把预算全押在权限、加密边界、审计可见性与作者体验上。

最后把预期校准到准确刻度（避免本方案自己制造过度承诺）：

> 按本方案**完整实施后**，在「权限模型 / 沙箱哲学 / 声明式贡献 / 加密边界内的可信性 / ABI 工程」这几轴上，达到**对齐甚至超出**业界水平；在「隔离强度」上**分两段闭合**——内存炸弹在 M11.5 就闭合（已核实 Boa 无分配预算 API，故用"超预算 panic 的限流分配器"，§3.11），**原生崩溃 / 段错误 / OS 级账目要等 M11.13 子进程**；在「开发者体验」上**结构性低于顶级**（Boa 无 console / devtools / source map / JIT，这是选型决定的，不是文档能补的）；在「供应链治理与生态规模」上**低于顶级**（前者排 M11.11 且带闸门，后者取决于用户规模而非架构）。**这不是"全面对齐顶级实践"，而是"在一个别人没有的维度上做到第一，并在其余维度上不欠债、不假称。**
