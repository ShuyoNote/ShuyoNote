# L4「服务端转发增量」深度分析
> 状态：**已收口**（分析）。证据：三条决定性事实 ＋ 丢帧风险（见 `../plans/2026-09-29-payload-increment-deep-dive.md`）


> 上游：[三条路线对比](2026-09-29-single-space-limit-three-routes.md)（L4 = 唯一能到四位数的路线）
> ⚠️ 本文结论里有**两条推翻了我先前的话**，见 §7。

---

## 1. L4 到底改什么（一句话）
```text
今天：1 次写 ⇒ N 个【通知】⇒ N 次 pull（每次：1 次 HTTP ＋ **2 条 SQLite 查询** ＋ 传一整页 payload）
L4  ：1 次写 ⇒ 1 次 broadcast（**帧里带 payload**）⇒ N 个订阅者**直接应用**
⇒ **服务端的工作量从 O(N²) 降到 O(N)**（每个订阅者 0 次查询；每次写 1 次 broadcast）
```

## 2. ⭐ 三条决定性的事实（我逐行核过，它们决定 L4 成不成立）

### 2.1 ★ 服务端**从不解析 payload** —— 所以转发它**不增加服务端的"知识"**
```text
`sync-server/src/sync.rs:129` 原话：
  「**The server never parses `payload`**, so which project a change belongs to
    can only come from the client.」
⇒ ⇒ 这是 L4 在**许可/E2E 那两条线上安全**的根本理由：
   **转发 ≠ 理解。** 服务端今天已经是"哑且盲"的，L4 之后**仍然是**。
   ⇒ 与 `INV-LIC-no-server-in-client`（不许把服务端实现搬进客户端）**不冲突**：
     转发字节不改服务端的性质，也不让客户端依赖服务端实现。
   ⇒ 个人空间内容本就是密文 ⇒ 转发密文更无问题。
```

### 2.2 ⚠️ 但 **payload 是【整页】** —— 这是 L4 最硬的前置条件
```text
`src-tauri/src/sync.rs:209-217   record_page_upsert()`：
  ① `serde_json::to_string(page)`            ⇒ **整行 PageDetail**
  ② `with_wire_state(&payload, &state)`      ⇒ **整块 CRDT state** 挂在 `CRDT_WIRE_FIELD` 上
  ③ 再 `with_stamp(...)`                     ⇒ 本机戳
⇒ ⇒ **payload = 整行 PageDetail ＋ 整块 CRDT state ＋ 戳** —— **不是增量**。
（两条既有注释佐证：「**没有状态 ⇒ 载荷逐字不变**」「老对端读不懂这一项就忽略 ⇒ 与接线前**逐字节相同**」）

★ 由此推出内存模型（**修正压测员"每接收者 64 条"的说法**）：
   tokio `broadcast` 的环形缓冲是 **channel 级【共享】**的（不是每个接收者一份）
   ⇒ 每空间常驻 ≈ **64 × P**（P = 单条 payload 大小）
      · P = 10 KB  ⇒ 640 KB/空间       ✅
      · P = 100 KB ⇒ 6.4 MB/空间       ⚠️
      · P = 1 MB   ⇒ 64 MB/空间        ❌
   ⇒ ⇒ **P 随页面大小增长**（整页）⇒ **大页面会让 L4 的内存失控**
```

### 2.3 ✅ 而"应用一条变更"的路径**已经存在** —— 所以客户端改动比想象的小
```text
`src-tauri/src/sync.rs:2626  apply_pulled_changes()` ⇒ 内部 `:2776 apply_upsert(&c, &page, change.seq, stamp_wins)`
⇒ ⇒ **这是"按 seq 应用一条变更"的唯一实现。**
⇒ L4 的正确形状：把 SSE 帧里带来的 payload **喂进同一条路径**，
  而**不是**新造一条"推送专用应用路"。
⇒ ⇒ 数据来源变了（pull → push），**应用路径不变** ⇒ **"第二份真相"的风险其实低**
   （本仓最忌的"同一件事两处实现"在这条路上可以避免）
```

## 3. ⚠️⚠️ L4 引入的**新风险**：从"可丢的通知"变成"可丢的数据"
```text
今天：`Lagged`（channel 满）⇒ 服务端发 `{"type":"ping"}` ⇒ 客户端**拉一次** ⇒ 补上
      ⇒ **丢通知是无害的**（拉一次就恢复）—— 这是今天设计的容错基础。
L4  ：帧里带的是**数据本身** ⇒ 丢帧 ＝ **丢数据**（不是"通知丢了"）
      ⇒ ⇒ **补漏机制从"可选"变成【必需】**
⇒ ⇒ 所以 **"帧带 `seq`" 不是可选项，是 L4 的必需件**：
   客户端收到跳号 ⇒ **立刻回退去 pull**（既有拉取路径仍在）
   ⇒ ⇒ ⭐ 这一点很关键：**它让"拉取语义一行不改"这条非目标其实仍然守得住** ——
      pull 从"唯一的取数方式"变成"**补漏的兜底**"，语义（by seq、幂等）**没变**。
```

## 4. ⚠️ 而 L4 **不省传输量**（这条我先前说错了）
```text
L4 省的是：**N 次 HTTP 往返** ＋ **2N 次 SQLite 查询**（⇒ 服务端 CPU 大降）
L4 不省：**传输量** —— 今天 N 份整页（HTTP），L4 之后 N 份整页（SSE）⇒ **一样多**
⇒ ⇒ 所以 L4 的两大收益是【延迟少一跳】＋【服务端 CPU 从 O(N²) 到 O(N)】，
   **不是**带宽。要省带宽得**同时**做"payload 改增量"（见 §5）。
```

## 5. 因此 L4 的真前置条件是**两件一起做**
```text
① **payload 改增量**（而不是整页）
   ⇒ 否则：(a) 内存 64 × 整页 失控  (b) 传输量一点没省
   ⇒ ⚠️ 而"整块 vs 增量"正是我先前在 §9.5 毛刺②里点过的**同一个问题**
      （一次上传带整页 state、成本 O(整页) 而非 O(改动)）
   ⇒ ⇒ **它们是同一件事** ⇒ 一起做才成立
② **帧带 `seq`**（跳号检测 ＋ 回退拉）
   ⇒ 见 §3：这是 L4 的安全网，不是优化
```

## 6. 分批落地（每步可独立验收，且 L4c 之前全部安全）
```text
**L4a · 帧加 `seq`（纯加字段，不改行为）**
   ⇒ 服务端在 push 帧里带 `seq`（它本来就有）＋ 客户端只是**记录**它
   ⇒ 验收：帧里能看到 seq；客户端日志能看到跳号检测（人为丢帧验证）
   ⇒ 风险：零（不改任何取数行为）

**L4b · 客户端加"跳号 ⇒ 回退 pull"（行为仍不变）**
   ⇒ 补漏机制就位，但数据仍全部来自 pull
   ⇒ 验收：人为丢帧 ⇒ 客户端确实回退拉一次 ⇒ 数据不漏
   ⇒ 风险：零（不改变今天的取数路径，只是多一条保险）
   ⇒ ⭐ **做到这一步，"L4 的安全网"就已经在了** —— 而它本身对今天也有价值
     （今天 ping 是全量拉的触发，跳号检测能让它更精准）

**L4c · 帧带 payload ＋ 客户端改走"应用"路径（真正的 L4）**
   ⇒ ⚠️ 前置：payload 已改增量（§5①）
   ⇒ 验收：pull 次数断崖式下降；端到端延迟少一跳；内存不涨；跳号回退仍生效
   ⇒ 风险：中（这是唯一改变取数路径的一步）
```

## 7. ⚠️ 本文推翻/修正了我先前的两处说法（如实记）
```text
① 我说 L4"省掉 N 次 HTTP ＋ N 次 SQLite 查询" ⇒ 对，但我暗示它省传输量 ⇒ **错**（见 §4）
   它省的是**请求数与查询数**（⇒ 服务端 CPU），**传输量不变**（除非同时做增量）。
② 压测报告里"`broadcast::channel(64)` 是**每接收者** 64 条" ⇒ **不准确**：
   tokio 的环形缓冲是 **channel 级共享**的 ⇒ 常驻是 64 × P **per space**，不是 × 订阅者数。
   ⇒ 结论方向不变（P 大仍会失控），但量级要说准。
```

## 8. 与既有非目标的冲突（要 owner 拍，但比先前想的轻）
```text
那条流设计稿的明文非目标：
  · 「**拉取语义一行不改**（仍是 pull by seq ＋ 既有的合并/落盘）」
  · 「**别把长连接当同步引擎**」
⇒ 本文的分析说：**第一条其实守得住**（§3：pull 成为补漏兜底，语义未变）
  而**第二条确实被推翻**（L4 之后，长连接就是取数通道，不只是通知）
⇒ ⇒ 所以要 owner 拍的其实只有**一条**（"别把长连接当同步引擎"），
   而且可以把它改成：「长连接**可以**承载数据，但**必须**保留 pull 作为补漏兜底，
   且不许在长连接上做第二套合并/落盘」（这才是真正该钉的不变式）
```

## 9. 判据（要立的）
```text
· **帧里必须有 `seq`，且客户端必须检测跳号**（人为丢帧 ⇒ 必回退拉一次）—— 变异：去掉跳号检测 ⇒ 数据漏 ⇒ 判据红
· **应用路径唯一**：推来的 payload 与拉回的 payload 走**同一个** `apply_pulled_changes`
  ⇒ 文本级：`apply_upsert` 的调用点不许新增（推/拉都经 `apply_pulled_changes`）
· **内存上界**：每空间 channel 常驻 ≤ 64 × P_max（P_max 要定，并测）
· **不许在长连接上做第二套合并**（INV：推来的数据必须过既有应用路径）
```

## 10. 结论
```text
**L4 可行、且是唯一能到四位数的路线；但它的形状被三件事实钉死：**
  ① 服务端**从不解析 payload** ⇒ 转发它在许可/E2E 上安全 ✅（转发 ≠ 理解）
  ② **payload 是整页** ⇒ 必须先改增量，否则内存与带宽都失控 ⚠️（最硬前置）
  ③ **应用路径已存在**（`apply_pulled_changes`）⇒ 客户端改动比想象的小，
     且**不会造第二份真相** ✅
**而它最大的隐性代价是：丢帧从"丢通知"变成"丢数据" ⇒ 补漏机制（帧带 seq ＋ 跳号回退）是必需件。**
⇒ 落地建议：先做 **L4a/L4b**（帧带 seq ＋ 跳号回退）—— **它们零风险，且对今天也有价值**；
  payload 改增量之后再上 **L4c**。
```
