## 0. 一句话 ＋ 先说实说

一句话：**"LLM wiki" 真正缺的不是"生成能力"，而是"库这一层的可追溯入口"** ——
生成器（P4 跨库总结 + 强制引用）、取材（`files.search` / `files.read`）、诚实层（覆盖度）、
回滚（版本历史）、增量（`text_stale` 补算队列）**都已存在**；本文讨论的是
**何时生成、生成成什么形状、写进哪一层**。

⚠️ **实话三条**：

1. **我没跑过真机生成流程，也没量过模型成本。** 下面每一条"已存在"都是**实读代码 / 测试 / 文档**得到的（见 §1 的证据列），
   但 **"生成一页要多久、一次全库要花多少 token" 这两个数我一次都没测过** —— 那是本文最大的未知。
2. **这不是新引擎，是接线问题。** P4 已经能把整库总结成带强制引用的文本（真模型 live 读数：`droppedInventedRefs = 0`）。
   ⇒ **风险不在能力，在治理**（见 §3 风险列与 §4）。
3. **本文不碰的**：不动用户已有页（§4）；⚠️ **2026-10-05 订正**：原先这里写「不允许走远端 provider」，
   那是把**抽取**那条线（`localTranscribe` / `localVision`）的红线错当成了 wiki 生成的约束 ——
   owner 已明确「个人版**未加密空间**可以使用云端大模型」。现在的口径是：**未加密空间可用云端、
   加密空间只能用本机**（判据 `src/lib/ai/loopback.test.ts`）；**抽取**那条线不受影响，仍然只允许本机；
   不做全库定时重跑。本文也**不复制**任何既有判据正文 —— 只引用（本工作区最贵的一课是"一条判据被抄了 7 份"）。

## 2. 问题定义（一句话）

> **库能"被回答"，但还不能"被浏览"。**

现在的能力链是"你问 → 它答"（`files.search` → `files.read` → 总结 + 强制引用）。
缺的是**一层可浏览、可追溯、并且知道边界**的入口：新会话/新用户进来时，**没有任何一页能说清**
"这张库里有什么、主题怎么分、**哪些材料我还没抽到**"。

第三句是关键：**wiki 页如果不说覆盖度，用户会把"我没抽到"读成"库里没有"** ——
这正是 `files.read` 那条口径要防的同一件事（F4 / F5）。

## 3. 四个选项（按"能省多少 / 风险"排）

| # | 动作 | 省 | 风险 | 依据 |
|---|---|---|---|---|
| **A** | **库地图（只读派生视图）**：一页列出主题分区 ＋ 回链 ＋ **覆盖度**；不写新观点、不落用户空间 | 冷启动"库里有什么"这一问 | **低**（只读、可重建、不碰用户数据） | F2–F6 |
| **B** | **专题页 / 实体页 ＋ 增量维护**（相关页变化后重算） | 反复问同一主题 | **中**（错误沉淀 ⇒ 自污染；必须带"接受"闸门） | F3–F7 |
| **C** | **AI 记忆层**（把对话结论沉淀成页，后续问答优先读它） | 跨会话记忆 | **高**（把"猜测"变"数据"，且会被后续生成当权威引用） | F3 的反面 |
| **D** | **受控编辑**：AI 维护标记 ＋ diff ＋ 一键回滚 ＋ 全局开关 | —— | 低（版本历史已存在） | F2 / D |
| **A＋B＋D** | 只读地图先上；专题页**用户点「接受」才物化**；AI 产物永远带三字段（回链 / 覆盖度 / 生成时戳＋端点） | 最大 | 中 | F3–F6 |

**住哪一层（本方案唯一"非此即彼"的抉择）**：

| | 住正文（`pages`，会同步） | 住本机派生层（不同步） |
|---|---|---|
| 多端可见 | ✅ | ❌ 换机消失 |
| 多端 AI 各自生成 | ❌ 冲突 / 抖动 | ✅ 互不影响 |
| 版本历史 / 回滚 | ✅ 现成 | ❌ 需另做 |
| 用户可编辑 | ✅ | ❌ |
| 参与检索 / 嵌入 | ✅ | ✅（若也进分块层） |

## 4. 明确**不做**的（边界，写下来免得后人"顺手补上"）

| 不碰 | 为什么 |
|---|---|
| **自动写进用户已有页** | AI 改动用户数据是**不可逆的信任损失**；"接受"闸门是底线 |
| **把 wiki 生成送到远端 provider** | 破 F10 红线 |
| **全库定时重跑** | 成本无上限；增量（F7）已经给了正确的形状 |
| **为 wiki 新开一套存储** | F8 已收口派生层写入者；新开一套等于绕开门禁 |
| **在 wiki 里复制正文 / 判据原文** | 本工作区最贵的一课："一条判据被抄了 7 份" ⇒ **只引用，不定义** |
| **把 wiki 当"事实出处"** | 冲突时以它**引用的真出处**为准（与 `docs/README.md` 的索引口径一致） |

## 5. 验收判据（改完跑什么，不靠肉眼）

```bash
pnpm verify                              # 默认组（改 AI / 能力面会碰 contract 组）
pnpm verify:list                         # 先查真实门禁 id，别猜
node scripts/check-derived-writers.mjs   # 派生层写入者没被绕开
node scripts/check-plan-status.mjs       # 本文自身的状态行口径
```

**附加判据（本次新提，建议落成断言）**：

- **引用准确率**：wiki 页的回链**全部来自输入**（沿用 P4 的 `droppedInventedRefs = 0` 判据）；
- **覆盖度齐全率 = 100%**：每页都能说出"料够不够"；**没有读数时必须显式写"未知"，不许留空**
  （与 `files.read` 同一口径 —— 空串 = 未知，不是"完整"）；
- **只读默认**：生成动作**不改任何 `pages` 行**（判据：生成前后 `pages` 表的内容指纹不变）。

> ⚠️ 这三条**目前没有门禁**。若采纳 A，建议**同时把它们写进对应测试**
> （`src/lib/ai/librarySummary.test.ts` 与覆盖度那一组），否则"可信"又会退回成手感问题 ——
> 与本仓「能漂的数字不该手写在散文里」是同一条口径。

## 6. 推荐 ＋ 沉默默认

**先做 A（库地图，只读派生视图）**，并把 D 的三字段（回链 / 覆盖度 / 生成时戳＋端点）作为**输出契约**写死；
**B 单独一片**，且必须带"接受才物化"；**C 暂不做**。

理由：A 的风险低、成本是"接线"（F2–F6 已有），并且它**顺带把 F12「面板侧消费抽取结果」那条缺口变成有真实用例**
（面板里第一次有了"消费派生结果"的界面，而不是只有"生成派生结果"）。
B 的价值更大，但它把"可信"推到了台前 —— **没有引用准确率与覆盖度齐全率这两条判据，B 不该上**。

> **沉默默认**：若 owner 未拍板，按**什么都不改**处理（A / B / C / D 均不动）。
> 与本工作区既有口径同源：信箱「24h 默认结清、只能取零风险项」、五档契约「沉默 ⇒ 维持现状」。
> ⚠️ 本条特别适用：它要动的是**用户数据归属与可见行为** —— 沉默绝不能替 owner 决定。
