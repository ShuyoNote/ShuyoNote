# 「薄 Agent 接口」AI 能力方案

> 目标：给 ShuyoNote 加**可选、本地优先、安全**的 AI 能力，而**不是**嵌入一个能跑任意 shell / 读写任意文件的 Agent 运行时（如全量 dsh）。方案走**「ShuyoNote 暴露一组语义化工具 + 受限 Agent 宿主」**的中间路径，兼容现有插件安全红线（M11）与「AI 是可选增强、倾向本地接入」的定位。
> 关联：[设计哲学](../design-philosophy.md)（§5.8 插件沙盒红线 / §8 IPC 最小暴露面 / §10 「不是云端 AI 工作流依赖」）/ [插件方案](2026-08-22-plugin-plan.md)（M11）/ [本地优先方案](2026-08-15-local-first-note-app-plan.md)（数据层）。
> ⚠️ 本方案为**提议**，未实现；`docs/README.md` / `roadmap.md` 按「规划（待里程碑落地）」登记，**未标记 ✅**。

---

## 1. 背景与动机

用户多次问「把 dsh 集成进 ShuyoNote 有何利弊」。经盘点，**全量嵌入 dsh（DeepSeek Harness）** 与本项目的设计红线正面冲突——dsh 的立身之本是「能执行任意 bash/pwsh + 读写任意文件 + 多步工具编排」，而 ShuyoNote 明确要求：

- **IPC 最小暴露面**（§8）：前端只调语义命令，不暴露任意 SQL / 任意文件路径。
- **插件安全红线**（§5.8）：受限运行时 + 白名单 API，**别让插件直接进 renderer / 执行任意命令**。
- **本地优先 + 倾向本地 AI**（§10）：AI 是可选增强，避免数据外泄，不成为卖点依赖。
- **反过度设计（YAGNI）/ 价值÷工程量**（§9）：平台级延后、不虚构进度。

> **对比：全量 dsh 与「薄 Agent 接口」**。真正想要的价值是「AI 能对笔记库做**复杂多步操作**（跨页引用分析、按语义重构、自动打标签）」，这需要 agent 的**多步工具调用**；但代价是不该让 agent 得到**任意命令 / 任意文件**的权限。两者不是同一件事。

## 2. 两条路线对比

| 路线 | 做法 | 收益 | 成本 | 安全风险 | 结论 |
|------|------|------|------|----------|------|
| **A. 全量嵌入 dsh** | 把 Cordis/dsh Agent 运行时做成进程内服务或双进程 + IPC | 白嫖成熟 Agent 栈（LLM 驱动 + 任意工具 + 子代理 + 工作流） | **极高**：50+ 子包、独立进程/Web UI、状态/生命周期重理；违背 YAGNI | **红线上冲突**：附赠「能执行任意 shell」的远程执行引擎；笔记模板/包可带 agent 指令 → 本机任意命令执行入口 | ⚠️ **不推荐** |
| **B. 薄 Agent 接口** | ShuyoNote 暴露**语义化工具**（search_pages/read_page/create_page/append_block/get_backlinks…）+ 受限 Agent 宿主（可选接本地 LLM） | 拿到「AI 对笔记库多步操作」的核心价值；零新增任意命令/文件暴露；控制工程量 | 中：实现语义工具 + 宿主 + 权限/隔离 | 低：工具全是现有语义命令，天然最小暴露面 | ⭐ **推荐** |

## 3. 推荐架构：语义化工具 + 受限 Agent 宿主

```
┌──────────────────────────────────────────────────────────────┐
│  AI 宿主 (受限 Agent)                                          │
│  · 只能调用「白名单语义工具」                                  │
│  · 无 shell / 无任意文件读写 / 无网络（默认）                   │
│  · 结果经审核后才落库（AI 不直接改库，或走受限「提交预览」）     │
└───────────────┬──────────────────────────────────────────────┘
                │ 只暴露语义工具
┌───────────────▼──────────────────────────────────────────────┐
│  ShuyoNote 语义工具层 (复用现有平台命令)                        │
│  search_pages  → api.search(query, limit, allSpaces)          │
│  read_page     → api.getPage(id)                              │
│  create_page   → api.createPage(...)                          │
│  append_block  → (新增语义命令：页尾追加文本/块)               │
│  get_backlinks → api.getBacklinks(id)                         │
│  list_files    → api.listPageAttachments(pageId)              │
└──────────────────────────────┬────────────────────────────────┘
                               │ 数据一层（不变）
                     SQLite (pages/props/attachments/backlinks)
```

**核心原则**：
1. **工具即现有语义命令**：`search_pages` 复用相关度搜索、`read_page` 复用 `get_page`、`create_page` 复用 `create_page`、`get_backlinks` 复用 `get_backlinks`。**零新增任意 shell / 任意文件路径暴露**。
2. **AI 是可选增强**：默认关，用户显式开启并选择模型（倾向本地 LLM，避免笔记出网）。
3. **落库经审核**：AI 产出的修改（新建/追加块）先给用户**预览确认**再落库，防止 agent 误改笔记。
4. **复用 M11 插件界线**：AI 宿主走的权限模型与 L1 插件同层——受限白名单 API，不进 renderer、不执行任意命令。

## 4. 语义工具清单（初版）

| 工具 | 后端命令 | 说明 |
|------|----------|------|
| `search_pages(query, limit, all_spaces)` | `search` | 现有相关度搜索；可选跨空间。 |
| `read_page(id)` | `get_page` | 读取页面正文（content_text）+ 元数据。 |
| `read_block(pageId, blockId)` | `get_page_blocks` | 读取某页块列表，AI 定位到块。 |
| `create_page(parentId, title, content)` | `create_page` | 新建页面（AI 代建）。 |
| `append_block(pageId, text)` | （新语义命令） | 在指定页尾部追加文本/块（受限写入）。 |
| `get_backlinks(id)` | `get_backlinks` | 查谁引用了该页/块。 |
| `list_files(pageId)` | `list_page_attachments` | 列出页面/文件夹的文件。 |

> 注意：**不给** `run_shell` / `read_arbitrary_file` / `write_arbitrary_file` / `network` 类工具——那是红线。可选项是「本地模型管道」而非「任意命令」。

## 5. 利弊（诚实标注）

### 利
- **拿到核心价值**：AI 能对笔记库做多步、语义化操作（整理、跨页引用分析、按结构重构、自动打标签），这是普通 RAG 问答做不到的。
- **安全**：工具全是现有语义命令，天然满足「IPC 最小暴露面」；无任意 shell/文件/网络暴露。
- **贴合定位**：AI 是可选增强，默认关、倾向本地模型，避免数据外泄；不违背「本地优先」。
- **工程量可控**：无需重写存储层 / 引大型运行时，只加一层「语义工具描述 + 宿主 + 审核 UI」。
- **可复用**：宿主可同时消费 `src/lib/platform/` 的 driver 抽象（桌面/浏览器同构），未来接本地模型即可。

### 弊 / 取舍
- **AI 价值有限**：只做语义工具，Agent 不能跑任意命令，所以「AI 运维本地 / 调外部系统」类场景做不了——这是**刻意**的（安全取舍）。
- **需可信 LLM**：默认倾向本地模型；若用户坚持接云端，需在工具描述里**限定笔记子集**、并提示出网隐私。
- **审核 UX 成本**：「AI 修改需预览确认」会增加交互；但这是**必要的安全护栏**，否则 AI 可直接改用户笔记。
- **幻觉风险**：AI 可能给出不准确结论或**伪引**——需要「只读分析准、写操作需确认」的约束，且不把 AI 输出当事实源（与「能重建的绝不是事实源」信条一致）。
- **不是「全平台 Agent」**：本方案不谋求「在笔记里跑任意 Agent 工作流」；那是另一个方向，与本方案安全优先的取舍相悖。

## 6. 安全边界（红线）

- **无任意命令**：不暴露 shell / bash / pwsh。
- **无任意文件读写**：只读走 `get_page` / `get_page_blocks` / `get_backlinks` / `list_files`；写只走 `create_page` / `append_block`（限定作用域 + 审核）。
- **无默认网络**：AI 模型调用可选；工具层不暴露任意 URL 抓取。
- **落库经审核**：AI 的写操作进「预览待确认」，用户确认后才落库。
- **受限运行时**：AI 宿主用受限 API + 会话隔离，复用 M11 插件界线；不直接把 AI 宿主放进 renderer。

## 7. 里程碑建议

- **A1. 语义工具层**：封装 `search_pages`/`read_page`/`read_block`/`create_page`/`append_block`/`get_backlinks`/`list_files`（多数复用现有命令；新增 `append_block`）。
- **A2. 受限 Agent 宿主**：接入一本地/可选 LLM；工具白名单 + 会话隔离；「只读分析」优先。
- **A3. 审核落库 UI**：AI 新建/追加块先预览确认；可加「AI 建议」侧栏，不直接改库。
- **A4. 隐私开关**：默认关；用户开启并选模型；跨出网时明确提示并限定笔记子集。

## 8. 测试与验收标准

- [ ] AI 只读分析（如「找出所有引用 `[[某页]]` 但未回链的页」）返回可用的语义结果。
- [ ] AI 新建 `create_page` / 追加 `append_block` 需经用户确认后才落库；不确认不落库。
- [ ] 工具层**无** shell / 任意文件 / 网络暴露（对照 §6 红线逐项核对）。
- [ ] 默认关闭；开启时隐私提示明确；本地模型不触发云端出网。
- [ ] 容器/CI 测试：工具层命令集为语义命令子集，滥用即拒绝。
- [ ] 现有 `scripts/smoke-web.mjs` 无回归。

## 9. 结论

「把 AI 加进 ShuyoNote」值得做，但**不是**全量嵌入 dsh——那是把"能执行任意命令的运行时"塞进"最小暴露面的本地笔记"，安全模型上对撞。推荐 **薄 Agent 接口**：ShuyoNote 暴露一组**语义化工具** + 受限 Agent 宿主（默认关、倾向本地模型、写操作经审核）。这既拿到「AI 对笔记库多步操作」的核心价值，又守住「本地优先 / 最小暴露面 / 插件沙盒」红线和 YAGNI。**若你的目标是"在笔记里跑任意 Agent 工作流"而非"AI 增强笔记"，则是另一个方向，需另起方案并重新权衡安全边界。**

配套取舍见 [设计哲学](../design-philosophy.md)（本地优先 + 数据可移植 + 插件安全红线）。
