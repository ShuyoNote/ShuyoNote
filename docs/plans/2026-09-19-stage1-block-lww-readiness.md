# 阶段 1（块级 LWW ＋ 冲突提示）的**前置问题**：每块的"最后修改"从哪来？（2026-09-19）

> 状态：**已定（2026-09-20 所有者拍板：三条按建议执行，见 §6）—— 阶段 1 开工；第一切片（纯函数）已落地（2026-09-22，见 §8）。** 上位：[全量 CRDT 冲刺计划](2026-09-18-crdt-full-migration-plan.md) §3 阶段 1。
> 起因：阶段 0 的接口收口已经把"怎么合"收进了一处（`doc_content::merge` ↔ `docContent.shouldTakeRemote`），
> 计划里写着"阶段 1 把它换成块级 LWW，调用方一行不改"。**但那个函数今天是纯函数**：
> 它的全部输入是 `(local.syncSeq, local.dirty, remoteSeq)` —— 里面**没有任何块的信息**。
> 本文件把"要让它变成块级，缺的是什么"说清楚，并给出选项与我的建议。

---

## 1. 事实（都在今天的代码里，不是推测）

| 事实 | 出处 |
|---|---|
| 一页的内容是**一份 JSON blob** | `pages.content_json` |
| 版本读数是**页级**的：`sync_seq` / `dirty` | `pages` 表（`src-tauri/src/db.rs:929-938`）；`doc_content::local_state` 读的就是这两列 |
| **派生表 `blocks` 里没有任何版本信息** | `db.rs:696-701`：只有 `block_id / page_id / created_at / updated_at` —— 它是**派生索引**，不是版本存储 |
| 全仓**没有** `block_seq` / `block_rev` 之类的字段 | `git grep` ⇒ 0 命中 |
| 合并点今天是**纯函数**，且只有页级输入 | `doc_content::merge(local: Option<LocalState>, remote_seq) -> MergeDecision`（`doc_content.rs:134`） |
| 远端一次变更携带的是**整页**负载 | `sync::record_page_upsert` → `serde_json::to_string(page)`（`sync.rs:127`） |

⇒ **结论**：要做"按块比谁更新"，必须**新造一个"每块的最后修改"的量**，并且要决定它**住在哪**。
这不是实现细节 —— 它决定线格式、旧客户端兼容、以及将来 CRDT 那一步要不要重做。

## 2. 三个选项

| | 做法 | 代价 | 与 C 的关系 |
|---|---|---|---|
| **(a) 块级 rev 作为**声明的节点属性**（推荐） | 复用我们已经为 blockId 建好的那条路：`__blockRev` 声明在模型节点上，落盘/上行仍写老 `type` + 一个 `blockRev` 字段（**双形态**） | 每块多一个字段；**旧客户端保存时会把它弄丢**（见 §3 的风险）；合并要真的做"按 id 取并集、逐块比 rev" | rev 这一层到了 C 会被 Yjs 的 clock 取代 ⇒ **要写清"它是过渡量"**，别让下游依赖它 |
| (b) 从 `changes`（outbox）里推断 | 不新增字段，靠历史推"哪块变了" | 服务端只存页级 payload ⇒ **推不出来**（我们手上没有"发送方当时的那一版"）；除非把每块单独记一条 change ⇒ 那等于把页级 outbox 拆成块级日志，**协议大改** | 与 C 的 update 日志**方向一致**，但等于提前做一半 B/C |
| (c) 跳过 A，直接上 Yjs | 不做块级 LWW，块级因果交给 CRDT | 阶段 1 的收益（"改不同块都保留"＋冲突提示）**要么等，要么就没有** | 最彻底，但计划里说 A 的成果（冲突提示 UI ＋ 块级比较基础）**在 C 时代仍然需要** |

**我建议 (a)**，理由有三：
1. **机制已经存在**：blockId 的"声明字段 + 双形态（内存 `shuyo-*` / 落盘老 `type` + 顶层字段）"就是为这类
   "必须穿过 CRDT 绑定又不许破坏老客户端"的元数据设计的（`docs/plans/2026-09-18-crdt-block-id-ownership.md`）；
   再加一个 `blockRev` 是**同一条路**，不是新发明。
2. **它可停可退**：rev 只影响 `merge` 一个函数与一个字段；若随后直接上 C，把 rev 当作被 Yjs clock 取代的过渡量删掉即可。
3. **(b) 事实上推不出来**（见上表），而 (c) 会让阶段 1 的 UI/判据重新变成"等 C 一起做"。

## 3. ★ 必须一起定的两个问题（它们比选项本身更容易埋雷）

### 3.1 旧客户端把 `blockRev` 弄丢时，算谁赢？

老客户端（不认识新字段）保存一页时会**把它删掉**（§1.3 的通用形态：不在 `exportJSON` 里的字段一律丢 ——
它们甚至看不到它）。于是"这块的 rev 是多少"会出现**空缺**。三条路，**必须选一条并写成判据**：

- **(i) 缺失 = 最旧** ⇒ 对方只要碰过这一页，它的块就永远输给有 rev 的一侧（**可能吞掉真实的新编辑**）；
- **(ii) 缺失 = 最新** ⇒ 老客户端碰过的页会**整页赢**（退化回页级 LWW，但不会静默吞更新）；
- **(iii) 缺失 = 触发提示**（不静默判）⇒ 落到"冲突不许静默丢"那条不变量上，代价是要有提示 UI。

**我倾向 (iii)**：它把"我们判不了"如实交给用户，而 (i) 是唯一会让**真实更新被静默吞掉**的选项。
（这也正是冲刺计划 §1 里那句"上了 CRDT 也没有冲突"的同一类问题：**判不了 ≠ 可以静默**。）

### 3.2 rev 要不要参与同步？（建议：**不参与**，与派生索引同一纪律）

如果 rev 进同步负载，它就变成协议的一部分，将来换 C 要再做一次迁移。
**建议**：rev 只在本机的合并判定里用（"我看到的这一版比远端那版新"），**不上行、不入库、不参与冲突判定以外的任何事** ——
与"派生索引可重建、不参与同步"（冲刺计划 §5 不变量 2）同一条纪律。代价：跨设备无法用它判"谁先"，
所以判定只能是**本机视角的保守判定**；这条要写进文档，别让人以为它能做全局定序。

## 7. 实现口径（2026-09-20，开工前先把 §2(a) 与 §3.2 那处**字面冲突**解掉）

§2(a) 说 `blockRev` **落盘/上行都写**，§3.2 说它"**不上行**"。两句不能同时成立 —— 而**哪一种**决定
第一切片怎么写。按裁定的意图把口径定死（写在这里，实现与判据都以本节为准）：

**`blockRev` = 每块的 Lamport 计数器，随 `content_json` 走（因为 `content_json` 本来就是同步负载）。**

- **它「不参与同步」的正确含义**是：**不新开协议字段、不加数据库列、不做全局定序** ——
  不是"不上行"。若真不上行，远端那一侧的 rev 本地根本看不见，逐块判定就无从谈起（`merge` 只有页级输入，
  正是 §1 那个事实）。
- **编辑一块** ⇒ 该块 `rev = max(整页见过的 rev) + 1`（Lamport）；页级 `sync_seq` / `dirty` 照旧不动。
- **合并逐块判定**（在页级 ④ 之后，页级语义不被推翻）：

  | 情形 | 判定 | 依据 |
  |---|---|---|
  | **两侧内容逐字节相同** | **无事**（`identical`） | **先判它**：老客户端"打开—原样保存"会剥掉 `blockRev` 而**内容未变** ⇒ 那次**不许提示**（否则提示每次同步都冒出来 ⇒ 噪声 ⇒ 用户学会忽略 ⇒ 等于静默；回复信 §三）。⚠️ 前提是**块片段里不含 `blockRev`** —— 否则这一行永远不成立（见 §8 第一条读数） |
  | `remote.rev > local.rev` | 用远端那一块 | 远端这一块有本地没见过的编辑（顺序编辑：后者编号更大） |
  | `remote.rev < local.rev` | 留本地那一块 | 本地这一块有远端没见过的编辑 |
  | `rev` 相等且块内容相同 | 无事 | 两侧都还没碰（已被上面那行蕴含，保留原表述以便对读） |
  | **`rev` 相等但内容不同** | **冲突 ⇒ 提示**（不静默选边） | 并发同改同一块：两侧都从同一 base 加一 ⇒ 编号必然相等 —— 这正是 (iii) 要接住的情形 |
  | **任一侧缺 `blockRev`** | **冲突 ⇒ 提示** | 老客户端产物（字段被 `exportJSON` 剥掉，见 §3.1 的 (iii)）⇒ 判不了就不判 |

  ⇒ 这套规则**不需要额外的"基线"存储**：`rev` 相等本身就等价于"两侧都没见过对方的改动"，
  而"先后编辑"必然表现为编号不等。这也解释了 (a) ＋ (iii) 为什么是一对。
- **只读的那一半**：`rev` 不许进 FTS / 反链 / 导出 / 版本历史，也不许当"最后修改时间"用 ——
  它是过渡量，到了 C 由 Yjs clock 取代（与 §5 不变量 2 同一条纪律）。

**第一切片据此可写成纯函数**，输入就是两份"块表"（`blockId → (rev, 该块的 JSON 片段)`）+ 页级读数，
输出 `{ 选中的块集合, 冲突块集合 }`；不碰 SQL、不碰协议、不碰 UI。

### 8.1 ★ 实现时才发现的一条口径：**块片段里不含 `blockRev`**

判定表第一行是"两侧内容**逐字节相同** ⇒ 不许提示"。**第一次跑场景 H 那条反判据就红了** ——
因为夹具把 `blockRev` 留在了块片段里：老客户端"打开—原样保存"剥掉 `blockRev` ⇒ 两个片段**逐字节不同**
⇒ 判定表第一行**永远不成立** ⇒ 每次同步都提示（正是反判据二禁止的"噪声 ⇒ 用户学会忽略 ⇒ 等于静默"）。

⇒ 口径定死：`BlockSnapshot.json` 是**去掉 `blockRev` 之后**的块片段，rev 单独走 `rev` 字段；
去 rev 的动作由**调用方**在"提取块表"那一步做（下一片的双形态读写里就是它）。
两份实现的文件注释里都写死了这条（`doc_content.rs` / `docContent.ts`）。
**这条是判据抓出来的，不是想出来的** —— 记在这里，免得下一片有人在提取时又把 rev 塞回去。

| **没有块级删除 / 墓碑** | 只在一侧的块 ⇒ `only-local` / `only-remote`，**保留**（页级 LWW 时代它会被整页覆盖掉） | Rust `block_only_on_one_side_is_kept` ↔ TS「只在一侧的块」 |
| **顺序 / 移动不参与合并** | 顺序取**页级胜方**那一侧，另一侧多出来的块按自己的顺序**追加在表尾** | Rust `order_comes_from_the_page_level_winner_and_extras_are_appended` ↔ TS「顺序边界」 |
| **页级语义不被块级推翻**（裁定 ④） | 页级说"留本地"（`dirty` 或本地 `seq` 更靠后）⇒ **整页不动**，不走块级 | Rust `page_level_keep_local_never_consults_blocks` ↔ TS「④ 页级留本地时整页不动」 |
| **`rev` 是过渡量** | 不进 FTS / 反链 / 导出 / 版本历史，不当"最后修改时间" | 由 `merge_blocks` 的签名（只有块表与页级判定）在结构上保证 |
