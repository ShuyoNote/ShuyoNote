## 1. 决策要回答的到底是什么

阶段 2 不是"加个字段"，而是**把合并从客户端搬到服务端**：

| | 今天（阶段 1 ＋ 客户端合并） | 阶段 2（服务端开算） |
|---|---|---|
| 合并发生在哪 | 客户端（Web：`applyChange` 当场合并；桌面：收进旁路表 ⇒ 打开页面时合并，第 43 轮） | 同步服务 |
| 服务端懂不懂内容 | **不懂**（"never parses payload"，哑且盲） | **懂**（要解 Yjs 更新） |
| 端到端依赖 | 每台设备都会合并 | 服务端合并、客户端当哑终端 |

## 2. 现在具备什么（本冲刺的读数）

| 输入 | 读数 | 出处 |
|---|---|---|
| **格式层互操作** | ✅ JS `yjs` 与 Rust `yrs` 在同一批 fixtures 上**投影逐字节相同** | 尖刺 §3.1 |
| **失败形态** | 读事务里再要写事务 ⇒ **卡死**（不是报错）⇒ 口径：每页独立、请求内短命 Doc、根句柄先取好 | 尖刺 §3.2 |
| **状态体积** | **线性、约 158 B/块**；200 块 ≈ **31.6 KB**（同页落盘 JSON 是 51.1 KB ⇒ 状态更小） | 本文件 §4 |
| **增量编辑** | 50 块时追加一块：8026 → 8115 B（**+89 B**）⇒ 不是"每次重传全量" | 本文件 §4 |
| **客户端两侧** | 推（两侧都挂状态）＋ 收（Web 当场并、桌面收进旁路表后打开页面并/承接）**都已闭环** | 冲刺 §12/§13 |

## 3. 建议：**暂缓**，直到下面任一条成立

1. **需要"权威视图"**：产品要服务端给出"这一页现在到底是什么"（例如导出/搜索/审核在服务端做），
   而"客户端各自合并"给不出同一个答案；
2. **需要服务端做拒绝/收敛**：第二条血统要在服务端被**挡住或收敛**（客户端只能"发现并拒绝合并"，
   S8 那条护栏就是这个边界）；
3. **客户端覆盖不了的场景**：例如某类客户端（Web/移动）长期不打开页面 ⇒ 它的合并永远不发生，
   而业务上要求"打开即一致"；
4. **面 5（E2EE 快照）落地时一并做** —— ⚠️ 这一条是**硬约束**：服务端要合并就得**看得懂内容**，
   与"加密存储"直接冲突；边界决策 §6.3 已经写明"面 5 施工单必须与合并逻辑同批设计"。
   ⇒ **不要**在没有隐私口径之前先落一半。

## 4. 体积读数（`src/lib/crdt/stateSizeReading.test.ts`，可复跑）

用的是**应用自己那份**实现（`openPageSession` / `exportState`），不是估计值。
正文每段是约 30 字中文（与真实笔记同量级）：

```
   块数    CRDT 状态     落盘 JSON（对照）    平均
    1      167 B         341 B             167.0 B/块
   10     1545 B        2609 B             154.5 B/块
   50     8026 B       12769 B             160.5 B/块
  200    31576 B       51069 B             157.9 B/块
```

增量编辑（50 块时追加一块）：**8026 B → 8115 B（+89 B）**。

⇒ 结论：**状态比它替代的那份 JSON 更小**，且增量是"按块"的。所以"服务端存不下/传不动"这条
**不成立**（至少到这个规模不成立）。

## 5. 如果决定做，改动面与判据（先写清，免得到时候各自理解）

**改动面**（比"加个字段"大，但也不是从零）：
- 服务端接 `yrs`（尖刺已证可行）＋ 一张"每页状态"表（或复用现有 payload 列）；
- 一个合并端点（收 update ⇒ 合并 ⇒ 存回 ⇒ 回吐合并结果），**每页独立、请求内短命 Doc**；
- 一条迁移（存量页首次合并时建状态）；
- **隐私口径重定义**（服务端从此看得懂明文；面 5 的输入约束）。

**承重判据**（缺一条就不算做完）：
1. **幂等**：同一批 update 重放 ⇒ 状态与投影都不变；
2. **不丢块**：与客户端合并的结果**逐字节相同**（同一批 fixtures 两侧对拍，与尖刺同一手法）；
3. **降级**：不认识版本的老载荷 ⇒ 走今天那条路（**不猜**、不改字节），与 S4b-0 那张表一致；
4. **并发口径**：请求内短命 Doc ＋ 根句柄先取好（尖刺 §3.2 的失败形态就是"卡死"，服务端上不可接受）；
5. **体积不发散**：连续 N 次编辑后状态不因合并而膨胀（要定 GC/压缩口径）。

## 6. 明确**不做**的

- 不做"服务端 rebase 两条血统"（那要从投影 JSON 重放 ⇒ 撞 S1 红线：从 JSON 新建不可合）；
- 不做"服务端加密状态合并"的半套（面 5 未定 ⇒ 见 §3.4）；
- 不因为"形式上是阶段 2"就动工 —— 阶段 1 ＋ 客户端合并**今天能满足产品需求**，
  上面 §3 的四条触发条件才是它的启动条件。
