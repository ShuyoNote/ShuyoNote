# 取证：**合并产物不推送** vs **被游标消费掉的远端变更**（2026-09-22）

owner 点名的下一片是"**先取证，不改语义**"。本文件只放证据与候选修法，**没有改任何行为**。
判据落在 `scripts/verify-two-device-sync.mjs` 场景 L / M（脚本断言 47 → **64**）。

## 1. 两句要分开证的话

| # | 命题 | 结论（本节先给答案，证据在 §3） |
|---|---|---|
| **M** | 合并产物写回时 `dirty = 0` ⇒ **不推送**，这件事**本身**会不会丢编辑？ | **不会**：服务端只有 change log（没有 page 表），任何设备按序折 log 都能**推导出**同一份产物 ⇒ 不推不等于丢。 |
| **L** | 页级「保留本地」（dirty 优先）时，那条远端变更**被游标消费掉**会不会丢？ | **会（视图级分歧）**：跳过即消费 ⇒ 那台设备**再也取不回**对端那笔编辑，直到**有人再推一次**；层里**一条痕都没有**。 |

⇒ 真正要修的**不是**"合并产物要推送"，而是 **"没被应用的变更不许被游标吃掉"**。

## 2. 结构事实（都可查）

**服务端**（`shuyonote-sync-server`）：
- `src/sync.rs::push` 只把整页 JSON `INSERT` 进 `changes`（`UNIQUE(space_id, device_id, device_seq)` 去重），
  **从不解析 payload**；`pull` 只 `SELECT ... WHERE space_id=? AND seq>? AND device_id!=? ORDER BY seq ASC LIMIT ?`。
- 全仓 grep：**没有 page 表、没有 content 列、没有"最新版"端点**（`backup.rs` 只是整库快照）。
  ⇒ 服务端对"一页当前是什么"没有任何独立事实，**真相 = change log**。

**客户端**（两边都是"全局游标 + 消费即推进"）：
- Rust `sync.rs::do_pull`：`apply_upsert(...)?` 之后 `if change.seq > max_pulled { max_pulled = change.seq }`；
  而 `apply_upsert` 在"页级保留本地"那一支是 `return Ok(0)` ⇒ **照样推进**。
- Web `platform/web.ts::doPull`：`try { applyChange(store, c) } catch {}` 之后**无条件** `maxSeq = c.seq`。

## 3. 证据（真 `SqliteStore` ＋ 真 `applyChange` ＋ 真 `mergeBlocks`）

### 3.1 场景 M —— 合并产物不推送**本身不丢**（4 台设备）

```text
✓ M: X 在 pull 时拼出了合并产物（边上边合）
✓ M: ⚠️ 合并产物落库时 `dirty = 0` ⇒ 不会被推上去（这就是被点名的那件事）
✓ M: 落后的老设备 D 只吃 seq3 ⇒ 也拼出同一份产物（不推送合并产物不影响它）
✓ M: ★★ 全新设备按序折 log ⇒ 与 X 手上的合并产物**逐块相同**（⇒ 不推送本身不丢数据）
✓ M: 这一路没有冲突要裁决（两端改的是不同块）
```

为什么必然如此：合并产物 = 「远端那一版」按块替换上「本地 rev 更大」的那几块；
而"本地 rev 更大"意味着**那些块来自更早的一次 push**（能被吃下远端 ⇒ 那一页当时 `dirty=0` ⇒ 本地内容已推过）。
⇒ 产物是 log 的函数，谁折都得到它。**块级 LWW 在这里顺手挡住了一件事**：
一份"较旧的 payload"（例如某台设备基于旧基线推上来的整页 JSON）**不会**把本地 rev 更高的块回滚
（场景 M 的 D、以及场景 L 的 A 都是这条在兜）。

### 3.2 场景 L —— 跳过即消费，**会丢视图**

```text
✓ L: 远端 seq2 被**跳过**（页级 dirty 优先本地 —— 裁定 ④，语义正确）
✓ L: 跳过之后 B 手上没有 A 的 b1 编辑（这一步是设计如此）
✓ L: ⚠️ 而且**一条痕都没有**（页级跳过不落块级冲突表）
✓ L: ⚠️ 但游标**照样推进**到了 seq2 —— 那条远端变更已被消费
✓ L: ★★ 再同步一次之后 B 仍然**看不到** A 的 b1 编辑（游标已越过 seq2 ⇒ 不会再取）
✓ L: ★★ 合并之后 A 两边编辑都在（⇒ A 的编辑没丢，丢的只是 **B 的视图**）
✓ L: ★★ 全新设备按序折 log ⇒ 两边编辑都在（log ＋ 块级 LWW 是收敛的）
✓ L: 只有**再有人推一次**（A 再保存/再同步）B 才拿回 A 的编辑 ⇒ 在那之前是一段没人看见的分歧
```

时序：`seq1 基线` → A 改 b1 推 `seq2` → B **本地改 b2（dirty=1，未推）** 时 pull 到 `seq2`
⇒ 页级 `KeepLocal`（裁定 ④ 的语义，**正确**）⇒ B 的内容仍是它那一版，而**游标已经越过 seq2**；
B 随后推 `seq3`、再同步：什么也取不到 ⇒ B 长期停在"没有 A 的 b1 编辑"的状态。

**"静默"到什么程度（分平台，如实）**：

| 面 | 用户能看到什么 |
|---|---|
| 桌面 | P0.1 的 `SyncConflict` 横幅会弹（因为应用前 `dirty != 0`）——但只说"**这一页**被多人同时修改"、"哪一块被跳过了"没有；而且见 §4 的 F3：两个按钮不动数据 |
| Web | `doPull` 不产出任何冲突面（那侧的报告没有 conflicts 字段）⇒ **完全静默** |
| 层 / 表 | 块级冲突表 `page_conflicts` **没有行**（跳过发生在页级，根本没走到块级判定） |

## 4. 顺带抓到的第三个洞（F3）：P0.1 那两个按钮**不动数据**

`src/components/SyncPanel.tsx`（`sync-conflict-banner`）：

```tsx
<button onClick={() => { setConflicts([]); setStatus("已保留本地改动（下次同步会推送你这份）"); }}>保留本地</button>
<button onClick={() => { setConflicts([]); setStatus("改用服务端版本（已放弃本地未推送改动）"); }}>采用服务端</button>
```

两条都只 `setConflicts([])` + 改一行状态文案，**没有任何数据动作**：
「采用服务端」说的"已放弃本地未推送改动"是**假的**（`dirty` 还在，下一次 push 照样把本地那版推上去）。
这正是 AMD 在 `conflict-banner.reply-1` §二 要的那条口径（"看得见之后必须有怎么处理"）在**旧横幅**上的版本。

## 5. 根因：**又是"一个值表示两件事"**（与 `RemoteMerge` 那次同类）

`apply_upsert` 今天返回 `usize`，`0` 同时表示：

1. "应用了远端、而且**没有**未裁决冲突"；
2. "**压根没应用**（页级保留本地）"。

⇒ 调用方（游标）分不出这两种，于是把"没应用"的那条也当"处理完了"→ 推进游标 → 再也取不回。
这与 `RemoteMerge` 当时那个 `Option` 是**同一类错误**（同一个冲刺里第二次出现）：
**返回值必须先说清"发生了什么"，再谈计数。**

## 6. 候选修法（**都还没做**，等两边 ＋ owner 拍板）

| 方案 | 做法 | 代价 / 坑 |
|---|---|---|
| **A. 不消费未应用的变更**（朴素版） | 游标只在"真的应用了"时推进 | ⚠️ **livelock**：若那条变更**永远**应用不了（例如该页 `sync_seq` 已经 ≥ 它的 seq ⇒ 页级永远 `KeepLocal`），游标会卡在那里，`limit=500` 的窗口下**更新的变更永远取不到** ⇒ 比现在更糟 |
| **B. 跳过也留痕 ＋ 给出"怎么收场"**（推荐方向） | ①`apply_*` 的返回值把"**没应用**"与"应用了且无冲突"分开（消灭 §5 的混义）；②页级 `KeepLocal` 时把**那一版远端内容＋它的 seq** 记在一处本地"未取回的远端版本"（每页只留最新一条，规模有界）；③界面据此给**真的会改数据**的三选一：**合并这一页**（走块级合并）／**采用远端**／**保留本地**（= 现状） | 要加**一处本地存储**（新表或 `pages` 上的一列；不同步、不进导出）。好处：游标可以照旧推进（不会 livelock），因为被跳过的 payload **已经在本地存下了** ⇒ 不依赖"再有人推一次" |
| **C. 按页回退游标（不加存储）** | 每次 pull 的 `since` 取 `min(全局游标, 各页 sync_seq)` ⇒ 页面落后就重放它那一段 | 不用新表，但**重放窗口无界**（一页长期 dirty ⇒ 每次都重放它后面所有变更）；且要证明"重放已应用的变更是幂等的"（块级合并看起来是，但要有判据） |
| **D. 什么都不做** | 把 §3.2 的窗口写进已知边界，等阶段 2（Yjs）自然消掉 | 阶段 2 之前，用户可能长期看到"两台设备不同的内容"，且只有"再保存一次"能自愈 |

**我倾向 B**，理由是它把这件"静默"变成**可看见 ＋ 可收场**，而且顺手把 §5 那条混义返回值改对（与 `RemoteMerge` 的教训一致）。
但 B 要加本地存储 ⇒ **属于语义/存储改动，必须先拍板**（这也正是这份文件只取证不动手的原因）。

## 7. 边界与"结论翻转条件"（如实写）

1. **M 的结论依赖"服务端没有 page 表"**：若将来给服务端加一张"每页最新快照"（例如给 Web/检索/社区用），
   **M 立刻翻转** —— 那时"合并产物不推送"会让快照里缺块，必须让合并产物也进 log。这条写在这里当触发器。
2. `pull` 的 `exclude_device` 会让返回的 seq **有空洞**（自己的 push 不在里面）⇒ 任何"连续性"判断都不能按
   `seq+1` 硬算，只能按**取回列表里的顺序**算。
3. `limit=500`：游标语义一旦改错（方案 A 的 livelock），窗口饱和时是**永久饥饿**，不是"慢一点"。
4. **本片不动语义**：场景 L 的三条 ★★ 是**取证的判据**（钉住今天的坏行为）。修法落地时它们要**反过来断言**
   （B 必须拿得到 A 的编辑）—— 这句也写进了脚本注释，免得下一个人以为那三条是"应该保持的行为"。

## 9. 验收期顺带观察：**内容逐字节相同、只有 `updated_at` 在变的重复推送**（2026-09-22，**未定因**）

真机验收（桌面 1.91.10 ＋ 手机，同一空间 `test`）直接读服务端 `changes` 表看到的：

| 端 | 页 | 推送次数 | 相邻两次的差异 | 间隔（秒） |
|---|---|---|---|---|
| 手机 `5009e10b…` | `e5437d46…`（空页：`content_text=""`、`content_json` 268 B） | **37** | **只有 `updated_at`** | 1.3 / 2.6 / 5.3 / 6.7 / 556 / 6.4（burst 之后长静默） |
| 桌面 `a6919f0d…` | `3b85e4ce…`（`title="开始"`，text 264 B） | 3 | **只有 `updated_at`** | 10.7 / 10.8 |

复跑方式（判据式）：把同一 `entity_id` 的 `payload` 逐条 `json.loads` 再比顶层键 —— 除 `updated_at` 外
**一个字段都没变**；`changes` 表里 **(device_id, device_seq) 没有重复**（⚠️ 我中途写过一句"同一 `device_seq`
存了三行"，那是我自己的查询把每行和自己比了，**已更正**）。

已经排除的解释：

1. **不是脏标记卡住**：事件之后读桌面 `pages` 表，那两页 `dirty=0`、`text_stale=0`
   （推送成功确实会把 `dirty` 清掉）；
2. **不是游标没推进导致的同一笔重放**：同一设备的 `device_seq` 逐次 +1 ⇒ 每次都是**新的本地变更**。

仍可能的解释（**未证实**）：编辑器/自动保存那条路在内容没变时也盖 `updated_at` 并置 `dirty`
⇒ 每轮同步就多推一笔 no-op 变更。为什么值得单独记：它让"两台设备都同步完了"**永远不成立**（日志一直长、
附件清单每轮重算），也让 L/M 那两条的现场判断更难（光看 log 分不出"这一笔到底是不是有人在编辑"）。
若要收口，建议与 §6 的方案 B 一并拍 —— 两者都落在"**谁把 `dirty=1` 写下去**"这一层。
