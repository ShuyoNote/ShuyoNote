# 「虚拟局域网」这条路 —— 分析
> 状态：**已收口**（分析）。证据：三个好消息 ＋ 两处代价（见 `../specs/2026-09-29-virtual-lan-requirements-spec.md`）


> 起因：owner 在讨论「个人版只提供局域网直连（⇒ 失去远程多端同步）」之后问：
> 「**虚拟局域网呢？**」
> ⚠️ 核查结果：**仓库里从来没有提过 VPN / Tailscale / ZeroTier / WireGuard（0 命中）**
> ⇒ 这是一条**全新方向**，此前未被考虑过。

---

## 1. 这条路是什么
```text
问题：局域网直连 = **必须同一物理网段** ⇒ 出了办公室/家就看不到自己的设备。
提议：用 VPN（Tailscale / ZeroTier / 自建 WireGuard）把不同地点的设备放进
      【同一个**虚拟**网段】⇒ 直连能力保留，而跨地点也能连。
⇒ ⇒ 目标：**同时拿到**「局域网直连的简单性」与「远程多端同步」。
```

## 2. ⭐ 三个核出来的好消息

### 2.1 ✅ **我们的发现层已经支持"没有广播、只有对端清单"**
```text
`src-tauri/src/lan.rs:476  pub fn announce_targets(port: u16, peers: &[Peer]) -> Vec<SocketAddr>`
  = `default_targets(port)`（广播）**＋ 逐个已知对端的单播**（`:478-489`）
⇒ ⇒ **只要有"对端清单"，广播可以完全不要** ⇒ 而 VPN 恰好能给清单
   （Tailscale 的 `status`/本地 API、`zerotier-cli listpeers`、或用户手填）
⇒ ⚠️ 而这是必须的：**UDP 广播在 WireGuard 这类三层隧道里通常不通**
   （ZeroTier 有 multicast 转发但要显式开；Tailscale 不支持广播、但内置 mDNS 转发）
```

### 2.2 ✅ **"不承诺 NAT 穿透/中继/跨网段"这条非承诺【不需要改】**
```text
拓扑决策文档明确写：「**不承诺**：跨网段 / NAT 穿透 / 中继 / Web 参与。」
⇒ 在 VPN 路线下，穿透与跨网段是【**VPN 做的**，不是我们做的】——
   我们只承诺"**只要两台设备在同一个网段（哪怕是虚拟的），我们就能直连**"。
⇒ ⇒ ⇒ **这条非承诺可以原样保留**（我们不新增承诺，只是"别人把网段建好了我们就能用"）。
```

### 2.3 ✅ 而它顺手解决了"加密"这件事
```text
VPN 自带**传输加密**（WireGuard/ZeroTier/Tailscale 都加密隧道）
⇒ ⇒ **数据在网络上是加密的** —— 而我们**不需要自己实现 E2E**
⇒ ⚠️ 但要分清两种加密：
   · **传输加密**（VPN 提供）：防窃听
   · **端到端加密**（我们今天做的）：**服务端也看不懂**
   ⇒ 在 VPN 路线上，"服务端"就是用户自己的隧道（自建 WireGuard ⇒ 完全自己）
     或用 Tailscale 的中继（它只转发、看不懂内容，但知道"谁连谁"的元数据）
   ⇒ ⇒ 所以：**VPN 路线 ≠ 放弃加密，而是"把加密的责任交给 VPN"**
```

## 3. 于是"个人版"可以这样（三档并存，复杂度阶梯上升）
```text
① **默认：局域网直连**（同一物理网段）—— 零配置、零服务端、有光标
② **进阶：虚拟局域网**（跨地点）—— 用户装 VPN ⇒ 跨地点 + 传输加密 + 有光标
   ⚠️ 而对我们来说，②与①是**同一条代码路**（都走网格，只是网段是虚拟的）
③ **可选：我们的服务器同步**（加密后传）—— 零 VPN 门槛 + 跨地点
⇒ ⇒ ⇒ ⭐ **关键：②几乎不增加我们的复杂度** ——
   发现层已支持单播清单；网格、光标、按页逻辑**全部复用**。
```

## 4. ⚠️ 这条路的代价（逐条，别美化）
```text
① **用户门槛**：要装 VPN（Tailscale 之类）
   ⇒ 而"零配置"正是**我们服务器存在的价值** ⇒ 所以②不能当默认
② **发现层要能"从 VPN 拿清单"**
   ⇒ 三条实现路：VPN 的 CLI/API（`tailscale status --json` / `zerotier-cli`）、
     用户手填对端、或 VPN 的 DNS/主机名
   ⇒ ⚠️ 跨平台：三个桌面 + 两个移动端都要各自接 ⇒ **这是主要工作量所在**
③ **延迟分两档**：打洞成功 ⇒ 直连 20~50ms ✅；失败 ⇒ 中继 **100~300ms**
   ⇒ ⚠️ 光标要 ~100ms ⇒ **打洞成功时可行，中继时勉强**（要实测）
④ **企业网可能禁 UDP/打洞** ⇒ 退回中继或直接不通
⑤ **文案要改**：界面写"局域网直连""同网段"在虚拟网段下**不准确**
   ⇒ 需要区分措辞（例如「附近的设备」在两种情形下都成立）
⑥ **信任模型**：用 Tailscale ⇒ 元数据经它的协调服务器；自建 WireGuard ⇒ 完全自主
   ⇒ ⇒ 要如实写进文案（别让用户以为"用了 VPN 就完全不经第三方"）
```

## 5. 它解决了什么、没解决什么
| 问题 | 虚拟局域网能否解决 |
|---|---|
| 个人版缺远程多端同步 | ✅ **解决**（这是它最大的价值） |
| 不想让我们的服务器接触内容 | ✅ 解决（内容走 VPN 隧道，不经我们） |
| 个人版想要光标 | ✅ 解决（局域网那条通道，只是跑在 VPN 上） |
| 不用实现 E2E 加密 | ✅ 传输加密由 VPN 提供 |
| 用户零配置 | ❌ **不解决**（要装 VPN）—— 这正是我们服务器的价值 |
| 打洞失败时的延迟 | ⚠️ 部分（中继 100~300ms，光标勉强） |
| 企业禁 UDP 的网络 | ❌ 不解决 |

## 6. 结论
```text
**"虚拟局域网"是一条【技术上几乎白捡】的路：**
  · 发现层已支持单播清单（不用广播）
  · "不承诺穿透/跨网段"那条非承诺**原样保留**（穿透是 VPN 做的）
  · 网格/光标/按页逻辑**全部复用**
  · 而且**顺手解决了"加密"**（VPN 提供传输加密 ⇒ 我们不必实现 E2E）

**代价集中在两处**（都不在核心架构上）：
  · **用户要装 VPN**（⇒ 所以它是【进阶路径】，不是默认路径）
  · **发现层要接各平台的 VPN 清单来源**（⇒ 主要工作量在这里）

⇒ ⇒ **建议定位**：
   ① 默认 = 局域网直连（零配置、零服务端）
   ② 进阶 = **虚拟局域网**（跨地点；用户自带 VPN；我们只负责"在一个网段里就能直连"）
   ③ 可选 = 我们的服务器同步（加密后传；零 VPN 门槛）
⇒ 三档的复杂度阶梯清晰，而且①②共用同一条代码路。
```

# 附：owner 裁定（2026-09-29）＋ 「局域网直连」与「虚拟网段」到底差在哪

## 0. owner 两条裁定
```text
① **定位：进阶路径**（不是主推路径）⇒ 默认仍是局域网直连，虚拟局域网是"进阶"
② **清单来源：通用**（不绑定某一家 VPN）⇒ 不把 Tailscale/ZeroTier 写死
③ 反问：「**局域网直连和虚拟网段不一样吗？**」⇒ 见下（答案是"一半一样、一半不一样"）
```

## 1. ✅ 从**代码**看：**是同一件事**（我核过了）
```text
· 都走**同一个网格**：`GET /mesh/pull`（对等拉取）
· 都用 **`mesh_bind`**（`mesh.rs:393` —— **每个空间各自一个监听地址**）
· 都认 **`hub_base`**（"你可以直接来拉我，我在 `<base>`"）
· ★ **代码里【没有任何"网段前缀/subnet"判断】**
  （grep `prefix|subnet|same_net|/24|netmask|mask` ⇒ 命中的全是**字符串前缀**，不是 IP 前缀）
⇒ ⇒ **网格不在乎你在哪个网段** ⇒ 这是"同一件事"的部分，也是这条路便宜的原因。
```

## 2. ⚠️ 但有三处**真的不一样**（这才是"不一样"的部分）
```text
① **发现方式**（唯一的功能性差别）
   · 局域网：**UDP 广播**自动发现（零配置）
   · 虚拟网段：**广播通常不通**（三层隧道）⇒ 必须靠"**对端清单**"
   ⇒ 而好消息：`lan.rs:476 announce_targets` **已经支持"已知对端单播"** ⇒ 只要有清单就行。

② ⚠️ **报出去的地址**（这是真正会踩的坑）
   `announced_base` 报的是「**窗口实际绑上的地址**」。
   · 局域网：绑**物理网卡** IP ⇒ 同网段对端连得上 ✅
   · 虚拟网段：若**还绑物理网卡 IP** ⇒ **VPN 里的对端连不上** ❌
   ⇒ ⇒ **用户必须绑【VPN 网卡上的地址】**（或绑 `0.0.0.0` 让系统选）
   ⇒ 而 `mesh_bind` 是**用户填的** ⇒ 所以这是**配置门槛**，不是代码缺陷
     （但文案必须指引清楚，否则用户会"装好了却连不上"且不知道为什么）。

③ **配置门槛**
   · 局域网：插上同一个 Wi-Fi 就互见（**零配置**）
   · 虚拟网段：要装 VPN ＋ 要填对地址（**有门槛**）
   ⇒ ⇒ 这正是 owner 把它定为【进阶】的理由 ✅
```

## 3. 所以"不一样吗"的准确回答
```text
**一半一样、一半不一样：**
  · **一样**：网格本身（拉取／合并／水位／空间身份）——**代码完全复用**，一行不改
  · **不一样**：① 发现（广播 vs 清单）② 报出去的地址（物理网卡 vs VPN 网卡）
               ③ 门槛（零配置 vs 要装要配）
⇒ ⇒ 一句话：**它们是"同一条路，两种进入方式"** ——
   路是同一条（网格），进入方式不同（一个自动发现、一个要清单 ＋ 对地址）。
```

## 4. ⚠️ 由此得出一条**文案**要求（既有文案刚定稿，所以要点名）
```text
界面现在写的是「**局域网直连**」＋「**同网段**」——
  在虚拟网段下这两句**不准确**（用户会想"我明明不在同一个 Wi-Fi"）。
⇒ 建议：
   · **总称用「附近的设备」**（两种情形都成立：虚拟网段里的设备也是"附近"的）
   · 具体路径在**说明文字**里区分（局域网自动发现 ／ 虚拟网络需填地址）
   ⚠️ 这条改动会碰到刚定稿的文案 ⇒ **要 owner 点头**（本文件只提要求，不改文案）
```
