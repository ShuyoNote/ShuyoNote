# 插件分发策略（M11.11 前置细化：协议而非平台）

> 目标：把「插件市场」从**平台工程**降级为**协议 + 索引**——复用仓库**已有**的静态清单 + 签名设施（`latest.json` + minisign），让社区 / 企业 / 个人都能托管索引；并用**贡献阶梯**把社区贡献从「写代码」前移到「模板 / 主题 / 声明式配方」，使**社区上线当天就能产出真实贡献**，而不必等 M11.13 安全闸门。
> 关联：[插件体系进化方案](2026-09-10-plugin-evolution-plan.md)（§5 M11.11 / M11.13、§3.9 权限×加密边界、§3.10 审计与可见性） · [免费/开源社区出口指南](../free-site-export-guide.md)（「可发现但克制、绝不阻塞、绝不跟踪」） · [路线图 P3 社区插件市场](../roadmap.md) · [设计哲学](../design-philosophy.md)（§9 反过度设计 / §5.8 插件红线）
> 状态：**提议（未实现）**。落地进度回填 roadmap M11.11 段与本文件 §8。

> [!] **本次明确不做**：自建商店服务与 CDN 文件托管；**下载计数 / 埋点式排行**（违反「绝不跟踪」）；**应用内市场 UI 先于安全闸门上线**；竞价推荐位；中央账号体系（社区已有身份就复用，没有就不强求）。

---

## 1. 判断：市场解决「发现」，我们缺「供给」

| 事实 | 含义 |
|---|---|
| 第三方插件 **0** 个、作者文档 **0** 份 | 没有可被发现的东西 |
| 开发者体验**结构性偏弱**（Boa 无 `console` / devtools / npm、无 JIT，见进化方案 §1.1 分轴结论） | 让人「写代码」的门槛比竞品高 |
| 社区即将上线 | 有**招募作者**的场，不等于有**可陈列的插件** |

**结论**：**先做供给，市场最后做。** 一个空商店比没有商店更伤——它在对外宣告「没人给这个平台写插件」，并直接击穿进化方案主打的「**用户敢装**」定位。

---

## 2. 「依托社区」的正确姿势：社区当**索引宿主**，不当市场后端

| 能力 | 社区能省 | 社区省不下 |
|---|---|---|
| 身份 | ✅ 统一账号 → publisher 身份 | — |
| 发现 | ✅ 讨论、答疑、口碑 | ⚠️ **结构化元数据**（版本 / 兼容矩阵 / 更新通道 / 撤回）——论坛条目给不了 |
| 审核 | ✅ 版主管帖子 | ❌ **代码审查**（版主无法判断 JS 会不会偷数据）、**安全事件响应** |
| 托管 | ⚠️ 可承载**索引** | ❌ **文件托管与滥用处置**（CDN 成本、侵权/恶意下架的法定流程） |

→ 所以不要「在市场前面挂一个社区 tab」，而是：**社区 = 一个索引宿主 + 一个讨论分类**。这是全部「依托」。

## 3. 分发协议（三件套）

### 3.1 `plugin-index.json` 规范

索引是一个静态 JSON，可托管在任意静态可达的位置（代码托管站的 release / Pages / 企业内网 / 本地文件）。

```json
{
  "indexVersion": 1,
  "owner": { "id": "shuyo-community", "name": "数友社区", "url": "https://…" },
  "generatedAt": "2026-09-10T12:00:00Z",
  "plugins": [
    {
      "id": "weekly-report",
      "name": "周报生成",
      "version": "1.2.0",
      "apiVersion": "1.0.0",
      "minAppVersion": "1.85.0",
      "runtime": "logic",
      "description": "按模板汇总本周改动，生成周报页",
      "publisher": "alice",
      "license": "MIT",
      "homepage": "https://…",
      "discussionUrl": "https://…/t/123",
      "changelogUrl": "https://…/CHANGELOG.md",
      "permissions": [
        { "id": "read:pages", "reason": "读取本周有改动的页面标题与时间" },
        { "id": "write:pages", "reason": "把生成的周报写入新页面（写入前会给你确认）" }
      ],
      "downloadUrl": "https://…/weekly-report-1.2.0.zip",
      "size": 20481,
      "sha256": "9f2c…",
      "signature": "untrusted comment: …\nRWQ…"
    }
  ]
}
```

| 字段 | 必填 | 说明 |
|---|---|---|
| `id` | ✅ | 必须符合进化方案 §3.8 的收紧规则：单段 `^[a-z0-9][a-z0-9-]{0,38}[a-z0-9]$`；**不可改名** |
| `version` | ✅ | semver；与 manifest 内一致 |
| `apiVersion` | ✅ | 语义化（`"1.0.0"`）；**未知 major 直接拒载** |
| `minAppVersion` | ✅ | 兼容矩阵的唯一事实来源（低于此版本的应用不展示安装按钮） |
| `runtime` | ✅ | `declarative` / `logic`（决定是否需要过 M11.13）。**`ui` 型暂不受理**：本版本没有 UI 插件宿主，索引里写它会被拒载——拒绝比"装上了什么都不发生"诚实 |
| `permissions[].reason` | ✅ | **安装界面必须显示「权限 + 理由」**（进化方案 §3.5） |
| `downloadUrl` / `sha256` / `size` | ✅ | `size` 用于安装前体积上限预检（M11.5 已定上限） |
| `signature` | 可选（阶段 2） | 发布者对**包（zip 字节）**的 minisign 分离签名；与 `publisherKey` **必须成对出现** |
| `publisherKey` | 可选（阶段 2） | 发布者的 minisign 公钥（裸 base64 或 `minisign.pub` 内容）。信任模型见下方「阶段 2 的落地口径」 |
| `license` | ✅ | AGPL 环境下的合规底线，至少声明 |
| `discussionUrl` | 建议 | 「评价」的载体是**社区帖子**，不是应用内埋点（§6） |
| `revokedAt` / `revokedReason` | 可选 | 撤回（§3.3） |

**索引本身**与 `plugin-index.json.minisig` 分离存放（沿用 Tauri updater 的 minisign 习惯）。
可照抄的样例：[`docs/plugin-index.example.json`](../plugin-index.example.json)；发布流程（打包 / sha256 / 签名）见[插件配方 § 发布](../plugin-recipes.md)。

**阶段 1 的落地口径（M11.11a 已实现，`src-tauri/src/plugin_index.rs`）**——规范之外，应用还会强制：

| 规则 | 为什么 |
|---|---|
| 索引与插件包只走 **https**（例外：本机回环地址，自托调试） | 明文 http 下"完整性"只剩一个裸奔的哈希，中间人能同时改包与索引里的哈希 |
| `indexVersion` 必须等于 1；`id` 走收紧规则；`version` / `minAppVersion` 必须 `x.y.z`；`sha256` 必须 64 位十六进制；`permissions[].reason` 不能空 | 这些是会**影响安装判定**的事实，写错就必须在拉索引时拒，而不是装上去之后才发现 |
| 体积上限：索引 4 MiB、签名 64 KiB、插件包 64 MiB（**下载途中**也守上限）、包内文件 ≤ 512 | 只看 `Content-Length` 会被"不报长度慢慢灌"绕过 |
| 解包只认普通文件与目录；反斜杠 / 绝对路径 / `..` 一律拒；解压后总体积封顶 | zip-slip 是"任意写"的经典入口，zip bomb 是下一步 |
| 顺序固定：**下载 → 体积 → sha256 → 解包到临时目录 → manifest 校验 → 拷贝进插件目录** | 任何时候都不留"半装的插件目录"占住那个 id |
| 给了公钥就**必须**验签通过（取不到 `.minisig` 也算失败） | 否则"签名服务器挂了"就成了绕过校验的开关 |
| 发布者签名（`signature`）阶段 1 **不校验**，但界面会显示"带了、未校验" | 不假装已经归因到发布者——那是阶段 2 的活 |

> 一处诚实的边界：索引签名用的是**用户自己填的公钥**，应用**不内置**任何"官方索引"。信谁是用户的选择（自托 = 自担）。

**阶段 2 的落地口径（发布者签名，已实现）**——索引声明的 key 本身证明不了"发布者是谁"（它来自同一份索引），
所以真正的约束力在**第一次之后**（TOFU，与 SSH 的 known_hosts 同一个思路）：

| 环节 | 应用怎么做 |
|---|---|
| 包里带 `signature` + `publisherKey` | 安装前按发布者公钥**校验包字节**；不对就拒绝（错误码 `publisher_key_changed` 之外的都归为验签失败） |
| 第一次见到某个插件的发布者 key | **装成功之后**才把它固定下来（装失败的东西不该留下信任记录），并显示 **16 位指纹**（`xxxx-xxxx-xxxx-xxxx`）让用户有机会在别处对比 |
| 之后每次安装/升级 | 与固定下来的那把比：一致 → 正常；**不一致 → 拒绝**，并把新旧指纹都摆出来 |
| 用户确认"这确实是发布者换了密钥" | 点「信任新密钥并安装」→ 带上显式同意（`trustNewKey`）重试，换掉信任记录并在插件日志里留一行 |
| 索引被换掉/被改 | **换不掉你已经固定过的 key**——这正是 TOFU 买到的东西 |

指纹由**后端**计算（前端不另算一份）：两个不一样的指纹恰好会让用户在最需要判断的时候判断错。
**仍然没做的**：按 key 撤回（撤回现在按"插件 + 版本"）、发布者身份的强绑定（那需要 index 之外的 key 分发渠道，
例如发布者官网/社区公告里公示指纹）。

### 3.2 分级信任（阶段化，避免一开始就上签名体系）

| 阶段 | 机制 | 信任对象 | 何时做 |
|---|---|---|---|
| **1** | 索引签名（`plugin-index.json.minisig`）+ 每条 `sha256` | 「**你订阅了谁**」——索引拥有者 | M11.11a |
| **2** | `publisher` 公钥 + 对插件包签名 | 「**谁发布的**」——可归因、可按 key 撤回 | M11.11b |
| **3** | 审查 + 安全评分卡 + 开发者政策 | 「**谁审过**」——社区/官方 curation | M11.11b（治理） |

> 阶段 1 的关键：**sha256 保证完整性、索引签名保证不可篡改**，而「该不该信这个索引」由用户自己决定（自托 = 自担）。这与本地优先 / 可自托管一致。

### 3.3 多源索引与撤回

- 应用维护**一组**订阅的索引 URL（类似 Homebrew taps / Scoop buckets），用户可增删：自建一个、订阅社区那个、企业内网再一个。
- **安装前必须显示「来源」**（索引 owner + 域名），用户确认后才装。
- 撤回两级（即 M11.11 的 kill switch）：
  1. **索引侧**：条目移除 / 标 `revokedAt` → 刷新后不再展示、已装的给出提示；
  2. **应用侧离线撤回列表**：随应用版本发布的已知恶意 `id`/`sha256` 名单，**离线也生效**（不依赖任何服务器）。

### 3.4 与既有设施对照：这是复用，不是新造

| 关注点 | 应用更新（已在跑） | 插件分发（本方案） |
|---|---|---|
| 清单载体 | 静态 `latest.json` 托管在 GitCode release | 静态 `plugin-index.json` 托管在任意位置 |
| 完整性 | minisign 公钥写死在 `tauri.conf.json` | 索引 `.minisig` + 每条 `sha256` |
| 端点 | `endpoints: [...]`（可多个） | 订阅索引 URL（可多个） |
| 用户动作 | 提示后手动更新 | 显示权限+理由+来源后手动安装 |

→ **边际成本≈0**：不新增服务、不新增依赖，只新增一个 JSON 规范与一个校验器。

## 4. 供给策略：贡献阶梯

社区上线最该铺的不是市场，是**门槛阶梯**——让贡献从「写代码」往下挪。

| 阶梯 | 形态 | 信任成本 | 审核成本 | 需要市场? | 需要 M11.13? | 现在能否开放 |
|---|---|---|---|---|---|---|
| 1 模板 | 结构预设 | 0 | 0 | ❌ | ❌ | ✅ **今天**（M9 已上线） |
| 2 主题 / 强调色 | token 集 | 0 | 0 | ❌ | ❌ | ✅ **今天**（M3 已上线） |
| 3 **声明式配方** | 无代码 manifest：命令 / 参数表单 / 设置 / 面板（query+columns）/ 斜杠项 | 0（纯数据） | 0 | ❌ | ❌ | ⏳ 需 M11.9（声明式贡献面） |
| 4 逻辑插件 | `main.js`（Boa） | 低 | 中 | ✅ | ✅ | ⏳ 需 M11.6 + M11.13 |
| 5 UI 插件 | 沙盒 WebView | 高 | 高 | ✅ | ✅ | ⏳ 需 M11.10 + M11.13 |

**为什么这是主要答案**：绝大多数社区贡献会落在**第 1–3 级的惰性数据**上——没有代码、没有安全面、**不需要市场、不需要审查、不需要等 M11.13**。它把「社区能不能贡献」与「安全闸门什么时候完成」**解耦**，社区上线当天就能有真实产出。

> 思源的「集市」同时售卖插件 / 主题 / 模板 / 挂件，证明了这条阶梯才是用户真实的贡献形态——不只是插件。

## 5. 一方先行：头 3–5 个插件必须自己写

生态冷启动的通行做法是**一方先行**（VS Code / Figma 早期都是官方扩展先铺）。

**挑选标准**：① 只有用插件 API 才做得出来（否则应该做进核心）；② 能在实现过程中暴露 API 设计缺陷（dogfooding）；③ 短小到可以当示例与模板。

**候选**（结合现有产品面）：

| 候选 | 用到的能力 | 同时验证 |
|---|---|---|
| 某具体工具的导入器（Markdown / HTML / 特定笔记格式） | 读文件元数据、建页、追加块（草稿确认） | 写路径与草稿确认是否好用 |
| Zotero / arXiv 取回（标题/作者/摘要/链接） | `net:https:<host>`（域白名单） | 网络权限与「理由」展示是否成立 |
| 周报 / 回顾生成 | 读页面与标签、建页 | 读能力面是否够 |
| 批量补标签 / 批量重构 | 读搜索 + 写属性（草稿确认） | 批量写的确认体验 |
| 自定义数据库视图（声明式，零代码） | 面板声明（query + columns） | M11.9 声明式是否够用 |

**这五个同时是**：API 可用性的实测 · 最好的文档示例 · 模板库 · **招募样板**（直接对着它们找 3 位最活跃用户共创，即满足 M11.11 的「≥3 个真实第三方插件」闸门）。

> 红线：**官方插件不享有任何特权旁路**——走同一 manifest、同一权限、同一 API（沿用原始插件方案 §11 的原则）。

## 6. 市场形态必须与「绝不跟踪」对齐

`free-site-export-guide.md` 已定调：社区侧要「**可发现但克制、绝不阻塞、绝不跟踪**」。

| 允许 | 禁止 |
|---|---|
| 索引里的**版本与兼容性事实**（`minAppVersion`、`apiVersion`） | 下载计数上报、安装成功率上报 |
| 排序：按名称 / 更新时间（**本地算，不上报**） | 应用内评分弹窗、星级投票 |
| 「热门」由**社区论坛投票**产生并写进静态索引 | 应用侧埋点生成的「热门」 |
| 每插件一个 **`discussionUrl`** 指向社区帖子 | 竞价推荐位、付费置顶 |
| 用户自托 / 企业内网索引 | 中央账号强绑定 |

## 7. 社区上线当天可执行清单

- [ ] **发布 `plugin-index.json` 规范**（本文件 §3.1 可作为公开版，一页纸）→ 社区当天就能托管一份索引
- [ ] 社区开设分类：**模板 / 主题 / 插件配方**（三级阶梯，先不叫「插件市场」）
- [ ] 置顶帖：《**20 行写第一个插件**》——对着当前 4 个宿主函数 + 示例插件即可写，不依赖 M11.6
- [ ] **主动招募 3 位共创作者**（找最活跃用户，共创 §5 的官方插件）
- [ ] 明确公示**当前边界**：插件仅桌面、能力面有限、无市场 UI——**先降低预期，再给路径**
- [ ] **不做**：应用内「插件市场」入口（空商店的负价值 > 收益）

## 8. 里程碑：M11.11 细分为 a/b/c

| 编号 | 内容 | 前置闸门 |
|---|---|---|
| **M11.11a 索引协议 + zip/URL 安装** ✅ 已落地 | `plugin-index.json` 规范 + 索引签名校验（阶段 1）+ `install_plugin` 支持 zip/URL + `sha256` 校验 + **先校验后落盘**；无商店 UI，仅「从索引安装（给 URL）」 | M11.6（`apiVersion`/权限）+ **M11.13 进程级隔离** |
| **M11.11b 治理与信任** | publisher 签名（阶段 2）+ 自动扫描 + **安全评分卡** + 开发者政策 + 漏洞披露流程 + 应用侧离线撤回列表 | M11.11a |
| **M11.11c 应用内市场 UI（最后）** | 订阅索引管理 / 搜索 / 兼容提示 / 更新 / 撤回提示 / 评分卡展示 | **M11.11b + 闸门（作者文档 + ≥3 真实第三方插件）** |

**M11.11a 落地情况（2026-09-10）**：协议 + 签名校验 + zip/URL 安装 + 前端「从索引安装（给 URL）」面板都已进代码；
索引样例 [`plugin-index.example.json`](../plugin-index.example.json)、发布流程写进[插件配方](../plugin-recipes.md)。
人工验收工具（本机回环，把示例插件打包 + 现成索引一起发出来）：`node scripts/plugin-index-demo.mjs <插件id> <端口>`。
**发布者签名（M11.11b 第二块，已落地）**：索引可给 `signature` + `publisherKey`，安装前校验包字节；
第一次装成功后把 key 固定下来（TOFU），此后换 key 一律拒绝并把新旧指纹摆给用户，用户可显式「信任新密钥并安装」。

**随后补上的一个缺口**：同 id 再装一次此前一律报「同名插件已存在」，于是索引里出现第二版的那一刻「安装」就成了死路。
现在按版本判定——升级/重装整体替换（先备份、失败回滚、不冲掉启用状态与授权快照），**明确降级拒装**；
界面按已装版本显示「安装 / 升级到 vX / 重装 vX」，升级时单独摊出新增权限。自动检查更新、多索引订阅仍属 c 档（要有订阅状态才谈得上）。

**撤回记忆（M11.11b 的第一块，已落地）**：拉索引时把被撤回的条目落库（`plugin_revocation`），
**运行与安装两条路都拦**，而且拦的是**那个版本**——索引后来发的修好的新版本不受影响。
用户说「仍然使用」就不再拦（索引拥有者不是用户的上司；这一层的职责是让他知道并明确表态），
表态被记住：同一版本的撤回再看到一次保住他的意思，**换成另一个版本的撤回则重新问他**
（否则一句「我知道」会顺着插件 id 无限延长到将来所有版本）。
**按发布者密钥撤回（M11.11b 补齐，已落地）**：索引顶层 `revokedKeys` + 落库的离线记忆；索引条目不可安装、
已装插件的运行被拦、安装前也先查这把 key——三条路一起收口，用户可显式「仍然使用」。
自动扫描、评分卡、开发者政策与漏洞披露流程仍留给 b 的其余部分。
**仍未做的**（按原计划留给 b/c，不许含糊）：自动扫描 / 评分卡 / 政策与披露（b 的治理部分）、应用内市场 UI / 多索引订阅（c）、
索引的"自动更新检测"（c）、以及 Windows RSS 那类与 M11.13 相关的遗留（见[隔离方案 §8.2](2026-09-10-plugin-host-isolation-plan.md)）。
**签名验收（已补上）**：本机没有 minisign 可执行文件、`tauri signer` 在此环境也起不来，所以验签测试最早用的是
minisign 官方测试向量（`minisign-verify` 自带用例里那对公钥/签名）。现在多了一层**自己签、自己验**的端到端夹具：
`scripts/minisign-fixture.mjs` 用 Node 的 Ed25519 + 一份带官方向量自检的 BLAKE2b-512 实现签出一个真包，
产物在 `src-tauri/tests/fixtures/`（一个真 zip + 两把一次性密钥各自的签名）。**独立实现签出来的向量被我们的校验器接受**，
比同一份代码自签自验更有说服力，而且它当场抓出了签名脚本里的一个真错误（全局签名该签 64 字节的签名本身，不是 74 字节的盒子）。
正式签名仍然用 minisign 本体。

> 关键取舍：**索引规范（M11.11a 的规范部分）可以在社区上线当天就发布**——成本一页纸，收益是社区从第一天就能托管索引；但**应用内市场 UI（M11.11c）最后做**。

## 9. 风险与取舍

| 风险 | 说明 | 缓解 |
|---|---|---|
| **恶意 / 仿冒索引** | 用户订阅了坏索引 → 装到坏插件 | 索引签名 + 安装前**显示来源（owner + 域名）** + 权限与理由逐条确认 + 离线撤回列表 |
| **无中央审核 = 责任真空** | 用户以为「有市场 = 审过了」 | 界面文案明确「来源」「未审查」「签名状态」；评分卡只展示**事实**不做好坏结论 |
| **供给侧投入挤占核心功能** | 官方 3–5 个插件 + 治理是长期人力 | 一方先行只做 3 个、每个都短；治理（M11.11b）严格挂在闸门后 |
| **官方一家独大** | 官方插件成为事实标准，社区无动机 | 官方插件走同一 API、无特权；文档与示例**从官方插件抽取**而非另写一套 |
| **AGPL / 许可证合规** | 分发第三方代码引入许可与下架义务 | `license` 必填；开发者政策写明许可与下架流程（M11.11b） |
| **声明式配方被忽视** | 大家都盯着「插件」，跳过第 1–3 级 | 社区分类**按阶梯命名**（模板/主题/配方），而不是按「插件」命名 |

---

## 10. 结论

一句话：**做协议、做阶梯、做一方先行的 3 个插件；市场等闸门。**

- **协议**（§3）：复用已有的静态清单 + minisign 设施，边际成本≈0，天然可自托管；「依托社区」= 社区托一份索引 + 开一个讨论分类。
- **阶梯**（§4）：把贡献门槛从「写代码」降到「模板 / 主题 / 声明式配方」——**这是唯一能在社区上线当天就安全开放的形态**，并把社区贡献与 M11.13 安全闸门解耦。
- **一方先行**（§5）：把「≥3 个真实第三方插件」这个闸门用自己的手先撬开（官方 3 个 + 招募 3 位共创）。
- **市场**（§8 M11.11c）：最后做，且做成「**订阅多个索引**」的形态，而不是自建平台——因为市场是一个**长期承诺**（审查 / 事件响应 / 兼容维护 / 下架流程），而它最容易烂尾、烂尾代价最大：一个装满过期插件、无人处理安全报告的商店，会精准击穿「用户敢装」。
