# 同步服务端：数据可见边界与威胁模型

> 你在用自建同步时最该问的一个问题：**服务端到底能不能看到我的内容？**
> 这页不写"我们很安全"，而是把**每一条数据落在哪里、服务端看得见什么**逐项列出来，并明确写出**防什么、不防什么**。

## 0.5 ★ 总口径（贯穿全部设计的一条边界，owner 2026-09-23 口述）

> **个人空间端到端加密（服务端只落密文）；团队空间放弃零知识，换取协同 / 检索 / AI。**

这句话是**一条设计边界**，不是"某个功能"：它是下面这些决定的**共同前提**（谁与它冲突，谁就要改）：

| 设计面 | 个人空间 | 团队空间 | 落点 |
|---|---|---|---|
| 同步存什么 | **只落密文**（服务端在数学上无法解密） | **明文** | 本页 §2/§3 |
| 合并能在哪一层 | **只能客户端**（服务端读不懂） | 客户端今天做；**服务端开算是允许的**（S5 阶段 2） | [S5 决策稿](plans/2026-09-23-s5-server-merge-decision.md) §1/§4 |
| 检索 / AI 放哪层 | **必须本机**（本地派生 ＋ 本机模型端点；派生缓存不进同步/备份） | **可以**放到服务端（服务端读得到内容） | [知识库 AI 覆盖方案](plans/2026-09-17-knowledge-base-ai-coverage-plan.md) §（本地派生口径） |
| 插件数据 / 空间级数据 | 必须落**空间库**（跟着空间一起加密） | 同左（按空间） | [插件进化方案](plans/2026-09-10-plugin-evolution-plan.md) §3.7/§12（落进 `meta.db` 就"静默逃出 E2EE 边界"） |
| 附件 | 可选端到端加密（push 前加密、pull 后解密，服务端只存密文） | 明文（与空间同档） | [架构](architecture.md) §附件 |
| 迁移/兼容 | 不考虑向后兼容（口径）；迁移时"一起升"可接受 | 同左 | [冲刺 §0](plans/2026-09-23-crdt-full-launch-sprint.md) §0 |

**这条口径带来的两个结论（比"以后再说"更硬）**：

1. **服务端合并（S5 阶段 2）不是"隐私上不行"，而是"只对团队空间行"** —— 服务端要合并就得看得懂内容，
   而团队空间**恰好已经放弃零知识** ⇒ 隐私冲突**由作用域化解**，不需要"先答面 5 才能做"。
   ⚠️ 但反过来说死了：**个人空间的载荷永远不上服务端合并**（它到服务端时是密文，服务端也没有密钥）。
2. **个人空间的检索/AI 只能在本机** —— 这条不是"今天这么做"，而是**边界要求**：任何"把个人空间内容
   发到服务端算"的做法都与本口径冲突（本机模型端点 `<本机>:8080` 那类是同口径内的）。

## 1. 两种空间，两种边界（先看这个）

| | 个人空间 | 团队空间 |
|---|---|---|
| 内容在服务端的形态 | **开启端到端加密后 = 密文**；未开启 = 明文 | **明文** |
| 服务端能做检索 / 内网 AI 吗 | 不能（服务端读不到内容） | 能 |
| 谁持有解密能力 | 只有你的设备（口令派生） | 服务端 + 该空间的成员 |

> ⚠️ **先讲清前提**：个人空间的"服务端只见密文"成立于**你已给这个空间开了端到端加密**。
> 加密开关在你手上（本地静置加密默认关，见 [身份与隐私模型](identity-privacy-model.md) §5）。
> 未开启时 `payload` 就是明文——所以"服务端看不到"这句话，**只在加密开启时成立**，§3.1 的表也按这个前提读。
> ★ **这个开关的作用域已按 §0.5 改完（2026-09-24）**：它现在是**按空间**的（个人空间密文 / 团队空间明文
> **可以同时成立**）—— 应用级那套（一开全都加密、一关全都明文）连同它的解锁兜底与迁移/轮换已整条删除。

**这是产品选择，不是"以后会改"。** 团队空间要多人协作、服务端检索、内网 AI，就必须让服务端能读到内容；
个人空间不需要这些，因此保留零知识。两者**不要混着讲**：

- 对个人用户：**开启加密后，服务端只见密文**；
- 对团队用户：**服务端能见明文**，换来的是权限、审计、检索、内网 AI。
  说"团队空间也是端到端加密"是不准确的，本页不会这么说。

## 2. 什么落在服务端

### 2.1 数据库（SQLite，WAL 模式，单文件）

| 表 | 存什么 | 明文 / 密文 |
|---|---|---|
| `changes` | 同步变更日志：`entity`（类型）、`entity_id`、`op`（操作）、`updated_at`、`device_id`、`space_id`、`project_id` | **元数据明文**；`payload` 在**加密开启时是密文、未开启时是明文**。服务端**从不解析 payload**，因此也无从判断是哪一种 |
| `attachment_meta` | 附件索引：`hash`（SHA-256）、`mime`、`space_id` | 明文 |
| `device_keys` | 设备密钥的 **SHA-256 指纹**、所属空间、签发/作废时间 | **库里没有明文密钥** |
| `users` | 邮箱、显示名、`password`（Argon2id 哈希）、状态 | 邮箱明文；**口令不可逆** |
| `sessions` | 会话 token、用户、过期时间 | **token 明文入库**（见 §4 与 §7） |
| `spaces` / `space_members` | 空间名、成员与角色 | 明文 |
| `audit_log` | 认证 / 空间 / 成员 / 设备密钥等动作，带**哈希链**（v12） | 明文，可校验是否被篡改 |
| `projects` / `project_members` | 项目与其成员（v13） | 明文 |

字段级的协议说明见 [同步机制详解](SYNC.md) §二。

### 2.2 文件系统

附件按 `attachments/<space_id>/<前两位hash>/<hash>` 分桶存放。文件名就是内容哈希，
所以**服务端无法从路径或文件名推断内容**。

### 2.3 一句总结

服务端拿到的是一份**能同步、能鉴权、能审计，但在加密开启后读不出个人空间内容的账本**：
"谁、哪台设备、什么时候、改了几条、多大的密文"，而不是"改了什么"。

## 3. 逐项对照表

### 3.1 个人空间（**已开启**端到端加密）

| 数据项 | 服务端 | 备注 |
|---|---|---|
| 笔记标题、正文、标签 | ❌ **看不到**（只有密文） | 加密在本机完成；**未开启加密时为明文**（见 §1） |
| 附件内容 | ❌ **看不到**（只有密文） | 落盘的是加密后的字节 |
| 空间名称 | ✅ 看得到 | 便于你在设备上辨认 |
| 成员 / 设备标识 | ✅ 看得到 | 用于鉴权与冲突合并 |
| 变更的**类型、记录 ID、操作、时间** | ✅ 看得到 | 见下方"元数据提示" |
| 密文长度 | ✅ 看得到 | 因此**大致能推断内容量级** |
| 附件的 SHA-256 指纹 | ✅ 看得到 | 用于去重与完整性校验 |
| 附件 MIME | ✅ 看得到（**客户端自报**） | 服务端不校验内容类型 |
| 设备密钥明文 | ❌ **看不到** | 库里只有指纹，明文只在签发那一刻返回一次 |
| 空间加密口令 / 密钥 | ❌ **看不到** | 从不离开你的设备 |
| 审计事件（登录、成员变更、密钥签发/作废） | ✅ 看得到 | 这是审计能力的前提 |

> **元数据提示（重要）**：`entity_id` 是明文，配合 `op` + 时间戳 + 设备，服务端可以还原出
> "**某条记录在什么时候被哪台设备改过几次**"。也就是说：**内容保密，但变更模式不保密**。
> 不要对外说"服务端什么都不知道"——准确的说法是"**服务端看不到内容**"。

### 3.2 团队空间（账号体系）

| 数据项 | 服务端 | 备注 |
|---|---|---|
| 笔记内容、附件内容 | ✅ **看得到**（明文） | 换取协作 / 检索 / 内网 AI |
| 成员邮箱 | ✅ 看得到 | 账号体系的必然结果 |
| 成员口令 | ❌ 不可逆（Argon2id 哈希） | 与"能读到明文内容"是两件事 |
| 角色与权限 | ✅ 看得到 | 鉴权依据 |
| 审计记录 | ✅ 看得到 | 带哈希链，可验证未被篡改 |

## 4. 口令、密钥与凭据

| 凭据 | 服务端怎么存 | 推到极致会怎样 |
|---|---|---|
| 账号口令 | Argon2id 哈希 | 拖库也拿不到原口令 |
| 设备密钥（无账号部署） | **只存 SHA-256 指纹** | 拖库**拿不到钥匙**，与口令同理 |
| 个人空间加密密钥（**加密开启时**） | **不存在服务端** | 拖库**无法解密内容** |
| 会话 token | **明文入库**，有效期 30 天，登出即删 | ⚠️ 拿到数据库文件的人**能冒用未过期的会话**——已知取舍，见 §7 |

设备密钥的设计值得单独说：它面向"**自己一个人用、不想建账号**"的部署——没有账号体系，
客户端填一把钥匙就能同步。服务端库里只有 `SHA-256(钥匙)`，**明文钥匙只在签发响应里出现一次，
服务端自己也取不回**；作废时该钥匙对应的成员行一并删除，不留幽灵成员。
设计与机制见 [身份与隐私模型](identity-privacy-model.md) §3。

## 5. 威胁模型：防什么、不防什么

### 5.1 设计上要防的

| 攻击 | 怎么防 |
|---|---|
| 服务商 / 运维偷看个人空间内容（**加密开启时**） | 服务端只有密文，密钥不落服务端 |
| 数据库被拖走 | 口令是 Argon2id、设备密钥只有指纹、空间密钥不在库里 |
| 传输被窃听或篡改 | 部署层强制 TLS（见 §8） |
| 服务端被入侵后偷改审计记录 | 审计**哈希链**，逐行链接前一行，并提供校验接口 |
| 越权访问他人空间 / 项目 | 每个接口先过 `require_space` 角色校验（viewer < editor < admin < owner） |
| 附件路径穿越（读任意文件） | 哈希必须是 64 位十六进制，**原始输入不进入路径拼接** |
| 上传内容被替换 | 服务端边收边算 SHA-256，与声明的哈希不符即删除并拒绝 |
| SQL 注入 | 全部参数化查询 |

### 5.2 **明确不防**的（请按这个来评估风险）

1. **你自己的设备被拿走。** 设备上有解密能力，也有会话凭据。这是本地优先的固有代价。
2. **团队空间里权限之内的成员。** 服务端有明文，能读磁盘的部署方、有 `admin` 权限的人都看得到内容。
   团队版靠**权限 + 审计**管理，不靠加密。
3. **元数据。** 见 §3.1 的提示：谁、什么时候、改了几条、多大密文——这些不保密。
4. **恶意或被入侵的服务端。** 服务端能决定给你下发什么、要求你上传什么。
   客户端侧的防护（路径校验、插件沙箱、URL 白名单）见 [客户端安全审计](SECURITY.md)，本页不覆盖。
5. **部署方自己的能力。** 客户自己部署时，客户就是运维方；我们提供的边界是"软件不主动泄露"，
   而不是"防住服务器的主人"。

## 6. 可现场验证的机制（不靠承诺，靠能跑）

| 机制 | 怎么自己验证 |
|---|---|
| 审计未被篡改 | `GET /spaces/{id}/audit/verify` → 返回 `ok` / `first_broken_id` / `head_hash`；用 SQL 手改一行中间记录，校验即失败 |
| 数据库健康 | `GET /health/db` —— 完整性检查 + 附件目录可读写 |
| 备份可恢复 | 定时备份（WAL 安全快照 + 附件，保留最近 7 份），恢复与演练脚本随部署文档交付 |
| 上传完整性 | 故意用错误的哈希上传 → 400，临时文件被删除 |
| 附件寻址安全 | 用非 64 位十六进制的哈希请求 → 400 |
| 设备密钥不可逆 | 查 `device_keys` 表 → 只有 `key_hash`，没有任何字段能还原出钥匙 |

| 1 | **端到端加密的跨设备可解性属架构级未决**：E2EE 复用本地静置加密的密钥路径，"跨设备可解"需要产品决策（此前已做"**不丢数据**"止损：解密失败即报错、游标不推进） | 多设备加密场景下可能反复遇到无法解密的变更 | **未闭合**，需产品决策；细节见 [客户端安全审计](SECURITY.md) §四 |
| 2 | 服务端**自身不提供 TLS** | 直接暴露端口即为明文传输 | 部署必须前置 TLS 反代（Nginx / Caddy）；见 §8 |
| 3 | **无限速、无失败锁定**；唯一措施是登录失败固定延时 400ms | 口令爆破、接口刷量 | 部署层限速；内网部署 |
| 4 | 上传大小上限默认值过大（`--max-body-mb` 默认 `2097152` MB） | 磁盘可能被打满 | **部署时显式设置**为业务实际需要的值 |
| 5 | 附件 MIME 由**客户端自报**、原样入库并出现在附件列表里；下载固定返回 `application/octet-stream` | 列表中的 MIME 不可信；服务端不校验内容类型 | 已知；不作为安全边界使用 |
| 6 | 会话 token **明文入库**（§4） | 拿到数据库文件者可冒用未过期会话 | 有效期 30 天、登出即删；设备密钥路径不受影响（只存指纹） |
| 7 | **锁定态附件明文落盘**（E1 静置一致性，客户端侧） | 加密开启时可能出现明文窗口 | 见 [客户端安全审计](SECURITY.md) §四 |

> （`canonicalize` / `is_valid_attachment_hash` 等；结论与证据见 [客户端安全审计](SECURITY.md) §三）。

## 8. 部署前提（自建方必须知道）

1. **必须前置 TLS**（Nginx / Caddy 终止），不要裸暴露同步端口；
2. **必须显式设置** `--max-body-mb`、备份目录与备份间隔；
3. **内网部署同样建议**加访问控制，不要默认认为内网可信；
4. 备份要**同时包含**数据库与附件目录，并定期做恢复演练；
5. **升级前先备份**——升级是幂等迁移，但备份是唯一的后悔药。
