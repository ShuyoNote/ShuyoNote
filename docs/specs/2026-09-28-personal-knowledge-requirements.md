## 3. 要什么

1. **一份本体**：从 `capabilities/capabilities.json`（25 条）**导出**，不许手抄第二份 ✗ ——
   判据：注册表改了 ⇒ 本体这一部分**必须跟着改**（对账门禁 ✓）
2. **本机检索（个人空间）**：先全文（FTS5 已有 ✓），语义检索**最后**（今天依赖 0 ✗）——
   判据：**断网可用** ✓ ／ 每条结果**带回链** ✓ ／ 锁定空间 ⇒ **大声失败**（不是空结果 ✓）
3. **知识地图与主题页（个人空间）**：基于既有标签/双链/块 ——
   判据：每条断言能点回原文 ✓ ／ 生成物**只描述结构、不含正文** ✓ ／ **源一改就标脏** ✓
4. **结构可共享、内容按权限解密（团队空间）**：共享"地图/骨架/索引"，正文按权限 —
   判据：**导出的共享物里零正文**（机器可查 ✓）
5. **审计**：外部/团队调用与插件调用进**同一审计轨迹**，能答"谁读过、谁写过"——
   判据：删掉那一处审计调用 ⇒ 判据红 ✓；⚠️ 需先定**主体标识**（今天 `push_audit` 首参是 `plugin_id` ✗）
6. **一切皆派生物**：索引、wiki、地图都能**重建** ——
   判据：删掉索引 ⇒ 功能不降级（只是慢）✓ ／ 重建后**同一查询同结果集** ✓

## 4. 不要什么（明确排除，免得范围膨胀）

| 不做 | 为什么 |
|---|---|
| ❌ **个人空间的内容/向量出网** | 个人空间端到端加密（服务端只落密文）：`docs/sync-server-data-boundary.md:33` |
| ❌ **第二份能力清单 / 第二套检索语义** | 会与注册表、与既有过滤（软删／工作空间／`content_json` 收口）**漂移且不报错** |
| ❌ **为 ontology 而 ontology** | 本体是**派生物**，不是新真相源；描述**结构**，不描述**内容** |
| ❌ **wiki 与规范正文并存当真相** | 第二份真相源（本工作区与产品仓都栽过）；wiki 必须标"派生，非出处" |
| ❌ **先写用户向文档** | 文档先于功能是本仓踩过的坑（同 `2026-09-28-mcp-host-requirements.md` §4） |
| ❌ **服务端解析团队空间之外的任何内容** | 团队空间"明文"是**已声明**的口径；此外一律 ✗ |
