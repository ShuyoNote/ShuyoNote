### 1.2 本规格**新增**的三条（需求里没有，但企业版做到"可判"必须钉住）

> **为什么加**：企业版的三条口径里，有一条（"能不能推内容 ≠ 懂不懂内容"）**在需求里没有对应不变式**，
> 而另外两条（退订纪律／跳号补漏）是 L4 的**前置纪律**——它们退化了**不炸、测试可能仍绿**，只是规模或数据悄悄坏掉。
> ⇒ 按 [`README.md`](README.md) 的口径，这三条**今天都不该进 `INVARIANTS.md`**（判据未立），列在这里是为了**把判据的形状定下来**。
> ⚠️ **不许**把它们写回需求（需求是基准）；它们是**规格层的补充**。

| id | 口径（一句话 ＋ 出处） | 判据（要立的那条） | 会红证据 ／ 褪化了会怎样 |
|---|---|---|---|
| **INV-ENT-dumb-relay-not-understanding** | **"能不能推内容" ≠ "懂不懂内容"**：服务端转发字节**不许解析 payload** —— 转发增量/密文都不需要看懂它（出处：`l4-forward-deltas-deep-dive` §2.1 逐字："**The server never parses `payload`**"；`wps-scale-roadmap` §4 的"服务端不懂数据"；本 brief 的三条口径之②） | 文本级判据（**要立**）：服务端代码里**不许**对推送/转发的 `payload` 做反序列化或取字段 —— 唯一允许的动作是**计数与搬运**（今天 `shuyonote-sync-server/src/sync.rs:229-233` 的 push 帧只有 `type`/`space_id`/`accepted`，**没有**任何 payload 字段被读出）。<br>**变异**：在转发路径上加一句"顺手解析一下 payload 看有几页" ⇒ 必须红 | **❌ 无（要立）**。<br>**褪化了会怎样**：服务端一旦懂内容 ⇒ ① 加密空间的保密承诺没了；② "服务端要跑文档内核"＝**服务端内嵌客户端** ⇒ 破 `INV-LIC` 的许可边界（`realtime-body-requirements` §9.6 逐字列了这两条）。**而且它退化时测试全绿** —— 因为功能都还在 |

### 2.1 ⚠️ 三条**对齐纪律**（不写下来，"可判"就是假的）

```text
① **每个数必须带口径**：P4/P5/P6 都要写清 "在哪个 N、哪个 α（在写比例）、哪个 r（每人改动/秒）、哪个 k̄（平均同页人数）下量"。
   依据文档的算式是 W = α·N·r（写）与 扇出 ≈ α·N·k̄（读）—— 换了 α/r/k̄，"几万"就换一个意思。
② **实测 / 推算 / 目标 必须分开标**（§0 已定），且**宣传文案里只许写"目标"或"实测"**，
   不许把推算写成实测（这就是 `INV-ENT-write-is-the-ceiling` 要挡的东西的近亲）。
③ 计时类判据**不设墙钟门禁**：按本仓已付过学费的治法 —— **跑 3 次打印最快值 ＋ 数量级兜底**，
   不拿墙钟当门禁（先例：`graphLayout.test.ts` 的 250ms 判据实测 260ms 红、单独重跑 7/7 绿；`realtime-body-approach` §4 风险 6 逐字）。
```

### 2.2 ⚠️ 本规格发现的**一处口径冲突**（不是我能拍的，见 §6-W1）

```text
把 P4/P5/P6 三个目标数**换算到同一个 α=10%、r=2.5** 上（依据文档全程用的那组）：
  · P4 单空间 5 万台         ⇒ 写 = 0.25 × 50000 = **1.25 万写/秒**（推算）
  · P5 并发写 3 万/秒        ⇒ 反推 N = 30000 / 0.25 = **12 万台**（推算）
  · P6 读 20 万次发送/秒     ⇒ 反推 N ≈ **10 万台**（推算，k̄=20）
⇒ ⇒ **三个数不在同一个 N 上**：P4 说 5 万，P5/P6 反推都是 10~12 万。
⇒ ⚠️ 而 P5 还有**第二个问题：单位**。"3 万/秒"若按【事务】读，它**超出**依据文档给的
   批量写上限（**1~2 万事务/秒**，[`horizontal-scale-limit-single-space`](../plans/2026-09-29-horizontal-scale-limit-single-space.md) §3）
   ⇒ 那就需要 **seq 按页分片**（架构改动）—— 而需求 §2 WON'T 明说"不做"（那是 D 阶段）。
   若按【变更】读（一批合并成一次事务），则**必须报出批大小与事务数**，否则这个数不可判。
⇒ ⇒ 处置：**判据里必须同时写"N ＋ α ＋ r ＋ 单位"**；这一条**要 owner 拍**（§6-W1）。
```

## 3. 数据形状（**契约**：字段名、类型、谁产生、谁消费）

> 本节只写**新增／改动的**形状；既有字段的口径**逐字在代码里，本文件不重写**（重写就是第二份真相源）。
> ⚠️ 三个形状都**必须先定**才能开工对应分片；§3.1 是 §4 的硬前置（"按页路由无从谈起"）。

### 3.1 ① `push` 帧要带上"改了哪些页"（**今天没有**）

**今天的形状**（逐字，服务端 `shuyonote-sync-server/src/sync.rs:229-233`）：

```json
{ "type": "push", "space_id": "<space>", "accepted": <count> }
```

⇒ ⚠️ **没有 `page_id`**（判据矩阵/`l4-page-subscription-limits` §5① 逐字："**`push` 帧今天【没有 page_id】**"）
⇒ 服务端不知道"改了哪些页" ⇒ **按页路由无从谈起**（`l4-page-subscription-limits` §5① 逐字：**必须先让变更带上页**）。

**目标形状**（建议，字段名要 owner 之外的实现者一起定死；**新加的字段一律 snake_case** —— 与既有帧同风格）：

```json
{
  "type": "push",
  "space_id": "<space>",
  "accepted": <count>,
  "changes": [ { "key": "<页键>", "seq": <该变更的 seq> }, ... ]
}
```

三条未定项（⇒ §6-W2／W3）：

```text
a) **`changes` 的元素粒度**：一条变更一条（粒度高、帧大）／还是 `keys: [...], seq_max: n`（帧小、客户端只知"至少到 n"）。
   ⚠️ 它们对 L4b 的语义不同：前者能判**哪一页**跳号，后者只能判"整体跳了"。
b) **`key` 在明文空间是什么**：按 `l4-page-subscription-limits` §4 第 3 步逐字 ——
   "**未加密空间**：页键可以就是 `page_id`（无泄漏问题）；**加密空间**必须用 HMAC"。
   ⇒ 于是同一帧字段在两种空间里**语义不同**（一个是明码、一个是别名）⇒ 消费方必须知道空间是哪一档。
c) **`seq` 是空间级**（今天 `changes.seq` 是**表级** AUTOINCREMENT，见 §3.3）⇒ 帧里带的是哪个 seq，随 §3.3 的决定而变。
```

### 3.2 ② 页级**不透明键**的形状

**口径**（逐字引自 [`wps-scale-roadmap`](../plans/2026-09-29-wps-scale-roadmap.md) §4）：

```text
折中：**页级不透明键** = `HMAC(空间密钥, page_id)`
  · 服务端**不知道是哪一页**，只知道"这些订阅者关心同一个键" ✅
  · 多设备对同一页算出**同一个键**（确定性派生）✅
⇒ ⇒ **这一条是 E2E 与万级并存的唯一办法** ⇒ 要 owner 拍（触及元数据边界）。
```

**形状（本规格定的最小形态）**：

```text
page_key(space_key, page_id) = hex( HMAC-SHA256( key = space_key, msg = "ent-page:" || page_id ) )

· `space_key` = 该空间的 32 字节**空间密钥**（客户端已有：`keyring.rs:149` `random_space_key()` ⇒ 32 字节）
· 域分隔前缀 `"ent-page:"` **必须有** —— 否则同一个密钥下的两类派生会撞（本仓已有的先例是
  `keyring.rs:153-155` `seal_plaintext` 的"长度前缀让绑定空间这件事可判"）
· 输出用**定长十六进制**（长度一旦定了就是协议的一部分，不许各端各截）
```

⚠️ **三个未定项**（§6-W2，**都不是我能拍的**）：

```text
a) **截断长度**：不截断（64 hex）最省心、路由表键最长；截断（如 16 字节 = 32 hex）省内存、但引入碰撞。
   ⇒ 依据文档**没有给数**，本规格**不编**。
b) **是否掺 epoch／是否随空间密钥轮换而变**：掺 ⇒ 轮换时**全部键同时换**（在途帧与路由表要一起处理）；
   不掺 ⇒ 轮换后旧键仍可路由 ⇒ 与 E4"轮换"的语义对不上。⇒ 这是 §6-W5（加密空间的密钥轮换）的一部分。
c) **是否防"频率推断"**：`ten-thousand-scale` 关二末逐字："⚠️ 还要防'服务端通过键的出现频率推断'
   （那属于另一层，要单独评估）" ⇒ 本规格**如实标"未评估"**。
```

### 3.3 ③ `seq` 改**空间级**之后的形状

**今天**（逐字，服务端 `shuyonote-sync-server/src/db.rs:18-20`）：

```sql
CREATE TABLE IF NOT EXISTS changes (
    seq         INTEGER PRIMARY KEY AUTOINCREMENT,   -- ← 表级全局单调
    ...
```

⇒ 客户端把它当**空间水位**用（`last_pulled_seq` 存在 `sync_profiles` 里，per ws_id）
⇒ ⇒ **同一个空间的数据必须在一张表里** ⇒ 这是"按空间分片"今天被挡住的那一处（容量压测 附二 §3 逐字）。

**目标形状**（[`horizontal-scale-limit-single-space`](../plans/2026-09-29-horizontal-scale-limit-single-space.md) §6 逐字给的形态）：

```sql
-- 序号按空间分配：MAX(seq)+1 WHERE space_id=?
-- ⇒ 一个空间一条独立序列 ⇒ 空间与空间之间可以分到不同数据节点
```

四条**连带**（不许漏，逐条有出处）：

```text
① 客户端水位语义：仍按"空间水位"（`last_pulled_seq` per ws_id）—— 因为序列**已经是空间级**，
   语义**不变**；⚠️ 但一旦以后做成"每页一个序列"（D 阶段），水位要变"每分区水位"，L4b 的补漏逻辑随之调整
   （horizontal §4① 逐字）。
② **跨分区的顺序**：分区之后**跨页的先后关系不再全局有序** ⇒ 要**显式确认**它对我们没关系
   （页级 LWW ⇒ 页之间本来就独立；horizontal §4② 逐字）⇒ 这是 §6-W4（**待查，且是采用按页分片的前提**）。
③ 迁移：⚠️ 动**存储模型**；「**无真实用户 ⇒ 可重建库**」（迭代计划 迭代 4 ⑧ 逐字）。
④ 并发写抢序列：空间级分配引入"同空间并发写抢序列"（容量压测 附二 §3① 逐字）⇒ 要与"单写者"的关系一起定。
```

- ❌ **不许在 `push` 帧里加对端名／设备名**：那会把"附近设备"那张表变成第二份来源（`INV-RT-single-source` 同族；`realtime-body-spec` §3.7 逐字）。

## 4. 协议：L4 的路由／退订／跳号补漏

### 4.1 今天 vs L4 的**订阅粒度**

```text
今天：`changes_stream` 是**每空间一条** SSE（服务端 `collab.rs:338-362`）；
      广播是**每空间一个** `broadcast::channel(64)`（`collab.rs:327-335` 的 `publish_space_change`）
      ⇒ 订阅关系 = "订这个空间" ⇒ 1 次写 ⇒ **每个订阅者各自 pull** ⇒ 扇出 **O(N²)**
L4  ：订阅关系 = "订这个**页键**" ⇒ 1 次写 ⇒ **只发给同页的人（k 个）** ⇒ 扇出 **O(k)**
      ⇒ ⇒ 每客户端帧率 = 同页写者数 × r（**与 N 无关**）
```

**四道极限**（逐条引自 [`l4-page-subscription-limits`](../plans/2026-09-29-l4-page-subscription-limits.md) §2，**本规格不重算**）：

| # | 极限 | 今天的读数／推算 |
|---|---|---|
| ① | **同页人数 k** | 反推 **同页写者 ≤ 200 人**（客户端实测能吃 **~500 帧/秒** ÷ 每人 2.5 改动/秒）；与 WPS 官方"单文档 200 人"**同量级**，而**我们没有单进程硬顶** |
| ② | **路由表规模** | 内存 ∝ **活跃页数 × 每页订阅者**（**不是总页数**）⇒ 不成问题，**前提是退订纪律**（`INV-ENT-subscription-lifecycle`） |
| ③ | **网关连接数** | 10000 连接 ≈ **500 MB**；网关**无状态** ⇒ 加机器就加（S3） |
| ④ | ⚠️ **写** | L4 **没有降"写"** ⇒ N=10000 时 **2500 写/秒**（推算）打在单写者（今天 **2000~5000 事务/秒**）的边上 ⇒ **瓶颈从读的扇出换到写的吞吐** |

### 4.2 订阅／退订的**消息形状**（要立的那条协议）

```text
· 客户端上报：**当前页的页键**（§3.2）＋ 订阅它；离开页面 ⇒ **退订**
· 服务端维护：`页键 → 订阅者集合`
· ⚠️ **退订的三个触发点一个都不许漏**：① 离开页面；② 断开连接；③ 空间切换。
  （②③ 是"进程被杀"那条路 —— 客户端根本没机会发退订，服务端**必须**在连接关掉时清）
· ⚠️ **路由必须"等价路由"**：服务端只能用页键判"这些订阅者关心同一个键"，
  **不许**试图把键还原成页（`INV-ENT-dumb-relay-not-understanding` 的同一条精神）
```

### 4.3 跳号补漏（**L4b**）

```text
· 帧里带 `seq`（L4a）⇒ 客户端**只记录**，不改取数行为；
· 客户端发现**跳号**（收到的 seq 不连续）⇒ **回退 `pull` 补漏** ⇒ 数据不漏；
· ⚠️ **应用路径唯一**：推来的 payload 与拉回的 payload 必须走**同一个** `apply_pulled_changes`
  （⚠️ 它在**客户端**：本仓 `src-tauri/src/sync.rs`（`97d1eb24` 上 `apply_pulled_changes` 在 `:2354`、`apply_upsert` 在 `:305`；
  [`l4-forward-deltas-deep-dive`](../plans/2026-09-29-l4-forward-deltas-deep-dive.md) 在它自己钉的提交上引的是 `:2626`／`:2776`
  ⇒ **行号随提交漂，引用时以当次读数为准**）；它**不在服务端**（服务端只存/转发 changes）。
  `l4-forward-deltas-deep-dive` §判据 逐字："**应用路径唯一**：推来的 payload 与拉回的 payload 走**同一个** `apply_pulled_changes`"）。
  ⇒ 变异：新写一条"收到就应用"的路径 ⇒ 必须红（那会绕过 outbox/水位与合并口径）
· ⚠️ **拉取的语义一行不改**：L4 之后 pull 从"唯一取数方式"变成"**补漏的兜底**"，
  但 **by seq ＋ 幂等**这条语义不变（`l4-forward-deltas-deep-dive` § 逐字）
```

### 4.4 路由的四条**边界**（写死在协议里）

1. **明文空间**：页键可以是 `page_id` 本身（无泄漏问题）；
2. **加密空间**：**必须**用 §3.2 的页级不透明键；
3. **没有 opt-in 的空间**：退回**全空间广播** ⇒ ⚠️ 那类空间**到不了万级**（`ten-thousand-scale` 关二逐字）—— 如实写进部署文档；
4. **同一空间两种订阅粒度不许并存成两套真相源**：路由表只有一处（页键 → 订阅者），**不许**再留一份"空间 → 订阅者"的旁路做同样的事。

## 5. 边界（**写死在规格里** —— 这几句是"不许说错话"的那一类）

### 5.1 ⚠️ **单空间上限由"写"决定**（数字带出处）

```text
今天（实测）：M2 舒适区 ≈100 台 ／ M3 ≈200 台（容量压测 §4）
降阶后（推算）：按页订阅 ⇒ ≈10000 台（帧率与 N 脱钩）
写的墙（推算）：单写者 2000~5000 事务/秒 ⇒ N≈8000~20000；批量写后 1~2 万事务/秒 ⇒ N≈4万~8万
⇒ ⇒ 需求 P4 的 **5 万**落在"批量写后"那条推算带内；而**加机器对这一格无效**。
```

### 5.2 加机器扩的是 **【空间数／连接数】**，不是"单空间更大"

三句话（[`horizontal-scale-limit-single-space`](../plans/2026-09-29-horizontal-scale-limit-single-space.md) §5 逐字）：

```text
① 加机器扩的是【空间数】与【连接数】⇒ 客户/团队变多 ⇒ 加机器就够 ✅
② ⚠️ 单个空间的上限**不由机器数量决定** —— 它卡在"一个空间一个写者 + 一个序号"
   ⇒ 按页订阅后**读**不是问题；**写**才是（今天 ≈8000~20000，批量写后 ≈4万~8万）
③ ⭐ 要到 20 万+ ⇒ 必须把"空间内部的写"也分片（seq 按页/分区）⇒ **那是架构改动，不是加机器**
```

### 5.3 加密空间**只到元数据级治理**

| 档 | 服务端知道什么 | 治理能到哪 |
|---|---|---|
| **明文团队空间**（默认，待 owner 拍） | 能读内容 | **全能**：水印／密级／DLP／全文检索（G3 全量） |
| **加密团队空间** | **只知元数据** | **元数据级**：成员/角色/审计/…；**内容级治理不承诺** |

⇒ ⚠️ **这条不是缺陷，是"用户在保密 ⇄ 治理之间自己选"**（[`strongest-enterprise-benchmark`](2026-09-29-strongest-enterprise-benchmark.md) §4 逐字）。
⇒ **让出一档只发生在加密空间里**；明文空间与竞品**持平**。

### 5.4 **"能不能推内容" ≠ "懂不懂内容"**

```text
服务端**从不解析 payload** ⇒ 转发增量/密文都不需要看懂它
⇒ 所以「服务端转发内容」与「服务端懂内容」是**两件事**：
  前者 L4 必做（否则到不了万级），后者一旦做了就同时破 E2E 与许可边界。
⇒ 判据：`INV-ENT-dumb-relay-not-understanding`。
```

### 5.5 **不做**（逐字引用需求 §2 WON'T，**本文件不重写**）

```text
❌ 不做"单空间 20 万+"（除非把 seq 按页分片 —— D 阶段，不在本需求内）
❌ 不做设备直连（团队版不提供）
❌ 不做"服务端读内容"以外的治理（加密空间只到元数据级）
❌ 不做 Office 保真
❌ 不做 IM/日历/审批一体
❌ 不做强制加密
```

### 5.6 ⚠️ **要 owner 拍的**（逐条 ＋ 为什么卡在它上面 —— 详见任务单 §4）

```text
① **撤防抖**（P2 ≤50ms 发出的前置）—— 卡在它上面的是：P2 的整条判据（今天 400ms/600ms 两层防抖）
② **页级不透明键**（元数据边界）—— 卡在它上面的是：§3.2/§4.2 的形状、E5 的判据、以及"加密档能不能上万级"
③ **部署形态**（网关 ＋ 数据节点）—— 卡在它上面的是：S2/S3 的两个部署实验、以及 D1"单文件起"与分片共存的形状
④ **两档默认**（默认明文还是加密？怎么提示代价）—— 卡在它上面的是：E1 的判据（"可选**非默认**"那句要有一个确定的默认）
```
