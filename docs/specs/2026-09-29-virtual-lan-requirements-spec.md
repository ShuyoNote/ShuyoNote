# 第一部分 · 需求

## R1 场景
```text
一个人在两处（办公室 / 家）各有设备，想同步自己的笔记，但**不想让我们的服务器接触内容**。
⇒ 他自建（或用）一个虚拟局域网（WireGuard / Tailscale / ZeroTier…），
  把两处设备放进**同一个虚拟网段** ⇒ 我们的【设备直连】就能跨地点工作。
```
## R2 目标（可验收）
```text
① 两处设备在**同一虚拟网段**里 ⇒ 能互相发现（或经清单被认识）⇒ 能同步
② **我们不接触内容**（走隧道，不经我们的服务器）
③ 界面**如实**说明"这是虚拟网络下的直连"（不让人以为"和同一个 Wi-Fi 一样自动"）
④ **零新增承诺**：我们**不承诺**跨网段 / NAT 穿透 / 中继（那是 VPN 的事）
```
## R3 本轮**不做**（显式留白）
```text
❌ 不内置任何一种 VPN，也不代用户装
❌ 不做"自动检测你装了哪个 VPN"（那要读各家的 CLI/进程 ⇒ 侵入且不可移植）
❌ 不承诺穿透 / 中继 / 跨网段（沿用既有非承诺）
❌ 不做"跨虚拟网段的多跳路由"（只认"能直连的对端"）
❌ 不动服务端（这条路的服务端全程不参与）
❌ 不在本轮做"移动端的 VPN 适配"（Android 的后台/权限另有一套）
```
## R4 与既有档位的关系
```text
① 默认 = **设备直连 / 局域网**（零配置、UDP 广播自动发现）
② 进阶 = **设备直连 / 虚拟网段**（用户自带 VPN；靠**对端清单**）
③ 可选 = **服务器同步**（加密后传；零 VPN 门槛）
⇒ 三者**共用同一条网格路**（`GET /mesh/pull`）；差别只在"怎么认识对端"与"报哪个地址"。
```

# 第二部分 · 规格

## S1 不变式（每条自带判据思路）
```text
INV-VLAN-core-knows-only-a-list
  核心**只认"对端清单"这个抽象**，**不认任何一家 VPN**。
  判据：`src-tauri/src/` 里出现 `tailscale|zerotier|wireguard` 等厂商名 ⇒ 红（文本级扫描）。
  退化会怎样：把某一家写进核心 ⇒ 换一家就要改核心；且等于替用户选边。

INV-VLAN-no-new-promise
  不新增"跨网段 / NAT 穿透 / 中继"的承诺。
  判据：用户可见文案里不许出现"自动穿透/NAT/中继"这类承诺（文本级）。
  退化会怎样：用户以为"开了这个就能连上任何地方" ⇒ 连不上时投诉"你们说能穿透"。

INV-VLAN-bind-must-be-reachable
  报出去的地址（`announced_base`）必须是**对端真能连上的那个**。
  判据：绑了"不可达的地址"时，界面必须给出**可操作的提示**（而不是静默失败）。
  退化会怎样：**这是这条路最常见的失败** —— 用户装了 VPN、填了物理网卡 IP、
             报出去的是物理地址 ⇒ VPN 里的对端连不上 ⇒ **沉默地不工作**。

INV-VLAN-discovery-mode-visible
  "**靠什么发现的对端**"必须**上抛**（广播 / 清单 / 两者）。
  判据：`LanStatus` 上抛里有该字段；且**0 台时两种处境的文案不同**（见 S3）。
  退化会怎样：两种 0 台**同形**（都是"0 台"），但行动指引相反 ——
             广播模式该"等"，清单模式该"去填" ⇒ 用户卡在原地不知道该干什么。

INV-VLAN-address-field-explains-itself
  监听地址那一栏**必须说明**：在虚拟网络里要填**虚拟网卡的地址**。
  判据：文案存在且**可被搜索到**（文本级）。
  退化会怎样：与 `INV-VLAN-bind-must-be-reachable` 同一后果（用户不知道填哪个）。
```

## S2 数据形状
```text
① **对端清单**（新设置，每个空间一份，与 `mesh_bind` 同层）
   · 形状：一组 `host:port`（或 `host`，端口取默认）
   · 语义：**"这些地址上可能有我的对端"** —— 我们只往这些地址发公告/拉取
   · ⚠️ 与广播**并存**（不是二选一）：广播能用就用，清单是补充 ⇒ 两者结果取并集
② **`LanStatus` 新增字段**（上抛，供界面区分处境）
   · `discovery`：`"broadcast"` ／ `"list"` ／ `"both"` ／ `"none"`
   ⚠️ 照既有纪律：**界面只显示它，不许自己按形状再判一次**（与 `kind` 同一条口径）
③ **清单的来源**（owner 定"通用"）
   · **核心**：用户手工填（最小、最通用、零依赖）
   · **可选适配层**：从各家 VPN 的 CLI/API 读（`tailscale status --json` / `zerocier-cli`…）
     ⇒ 每家一个**独立的小适配器**，**核心不认厂商名**（INV-VLAN-core-knows-only-a-list）
     ⇒ 适配层**失败不影响手工清单**（降级）
```

## S3 面板三处调整（口径）
```text
① **监听地址那一栏加指引**（小，可立刻做）
   · 现在：`placeholder="监听地址，如 192.168.1.5:8788"`
   · 加一句：虚拟网络下要填**虚拟网卡上的地址**（否则对端连不上）
   ⚠️ 这一处**不依赖本文其余部分** ⇒ 可以单独先做。

② **「对端清单」新增一块**（真缺口）
   · 位置：与「监听地址 / 口令」同一块内（同属"这条路怎么走"）
   · 形态：可折叠行（与面板其它行一致）＋ 摘要显示条数
   · 摘要四态（照既有「附近设备」的写法）：
       没开局域网直连     ⇒ 不出现
       开着但清单为空      ⇒ 「未添加」
       有 N 条             ⇒ 「N 个地址」
       清单无效（解析不了）⇒ 「N 条无效」＋ 点开逐条说哪条坏了（**不许静默丢弃**）

③ **状态措辞分处境**（依赖 S2-② 的上抛）
   · 广播模式发现 0 台 ⇒ 「正在找…」（**该等**）
   · 清单模式 0 台     ⇒ 「还没添加过地址」（**该去填**）
   · 两者都有但 0 台   ⇒ 「正在找…（也可以手动添加地址）」（给两条出路）
   ⚠️ 判据：**同形不同话** —— 两处 0 台的文案必须不同（INV-VLAN-discovery-mode-visible）
```

## S4 验收场景（能照着演）
```text
① 两台设备在同一虚拟网段、清单为空 ⇒ 靠广播**仍然互相发现**（广播与清单并存）✅
② 广播不通（模拟：关掉广播目标）＋ 填了清单 ⇒ 靠清单**能互相发现**并同步 ✅
③ 清单里填一个**不存在**的地址 ⇒ 界面**如实说**（不静默）且**不影响别的对端** ✅
④ 绑了物理网卡地址 ⇒ 界面给出**可操作提示**（`INV-VLAN-bind-must-be-reachable`）✅
⑤ 0 台时：广播模式与清单模式**文案不同** ✅
⑥ `src-tauri/` 里搜 VPN 厂商名 ⇒ **0 命中**（`INV-VLAN-core-knows-only-a-list`）✅
⑦ 用户可见文案里搜"穿透/NAT/中继" ⇒ **0 命中**（`INV-VLAN-no-new-promise`）✅
```

# ⭐ owner 重申（2026-09-29 晚）：**同步服务器不提供个人版**

> owner 原话：「**重申：同步服务器不提供个人版；**」
> ⇒ 这条**改变了本文 §R4 与"进阶路径"的定位**，并**消掉一大片复杂度**。逐条记。

## 1. 裁定的直接含义
```text
**个人版 ⇒ 只走【设备直连】**（同一个网段 ／ 虚拟网段）；**没有"服务器同步"这一档**。
**服务器那条路 ⇒ 只服务【团队空间】**（而团队空间的**默认档**是明文；**加密档由用户按空间选** —— 见 §2 末追改）。

⇒ ⇒ 换句话说：**"个人空间 + 加密 + 绑服务器"这个组合【不存在了】。**
```

## 2. ⭐ 因此消掉的一整片复杂度（逐条，都是前面几轮反复算过的账）
```text
① **按页订阅的"不透明键"**（`HMAC(空间密钥, page_id)`）⇒ **不需要**
   因为服务器上**没有个人空间** ⇒ 不存在"要按页路由又不想泄漏页标识"的处境。
② **光标的分层论证** ⇒ **不需要**
   ~~团队空间明文~~ **明文档** ⇒ 光标直接做 ✅（⚠️ 加密档另说）；个人版走设备直连 ⇒ 光标也直接做 ✅
   ⇒ ⇒ **两边都有光标**，不再有"加密空间不能有光标"这个分层。
③ **密文冷启动**（服务端留一份密文全量）⇒ **不需要**
   ~~团队空间~~ **明文档**在服务端留明文全量**不改变任何既有承诺**（⚠️ 加密档留什么另说）。
④ **闸门（`sync_bind_gate`）的三档** ⇒ **收成一档**
   今天：「个人空间要先加密才能绑同步 ／ ~~团队空间免检~~ **明文档**免检 ／ 未分类放行」
   ⇒ 之后：**只有团队空间会绑服务器** ⇒ "先加密"那一档**没有存在意义**。
   ⇒ ⚠️ 但**代码与文案里那一档还在** ⇒ 属"待清理"，不是"现在删"（见 §4）。
⑤ **"服务端不留存内容"这个承诺** ⇒ **从"加密后不留存"变成"个人内容根本不来"**
   ⇒ **承诺更强了**（不是弱化）。
```

> ⚠️ **保住的那半（本节的结论都仍成立，只是作用域收窄）**：

> ③ 「闸门三档收成一档」**方向不变**：收的是"个人空间那一档"，「**免检**」机制照旧存在

## 3. ⚠️ 而它把「虚拟局域网」从【进阶】推成了【个人版唯一的远程路径】
```text
既然个人版没有服务器 ⇒ 个人版要"跨地点多端同步"，**只剩一条路**：
  · 局域网直连（同一物理网段）—— 只在屋子内
  · **虚拟局域网（跨地点）** ← ⭐ **变成必需，而不只是"进阶选项"**
⇒ ⇒ ⚠️ **这与我先前记的裁定「① 定位＝进阶路径」需要重新对齐**：
   · 若"个人版必须能跨地点同步" ⇒ 虚拟局域网是【**个人版的唯一答案**】⇒ 它就不是"进阶"了
   · 若"个人版可以只在局域网内用" ⇒ 它仍可当进阶
⇒ **这一条要 owner 再明确一句**（见 §5-①）。
```

## 4. ⚠️ 最要紧的执行问题：**既有个人用户怎么办**
```text
今天已经存在【个人空间 + 加密 + 绑着服务器】的用户（这是既有产品的默认路径）。
⇒ 这条裁定之后，那条路径**不再被提供** ⇒ 他们的既有同步会怎样？
三条路（都要 owner 拍，我不替选）：
  甲 **保持可用**（老路径不删，只是不再作为默认/不再宣传）—— 代价：两套并存（本仓最忌）
  乙 **迁移到团队空间**（~~明文~~ ⇒ **默认档是明文**，加密档由用户选但**今天还没有**）—— 代价：**隐私倒退**（用户当初就是为隐私才用个人空间）
  丙 **迁移到设备直连 + 虚拟局域网** —— 代价：用户要装 VPN（门槛）
⇒ ⚠️ 而"两套并存"是最需要小心的那条：它会让"个人空间到底能不能绑服务器"在本仓
   长期有两个答案 ⇒ 正是本仓反复要消灭的那种状态。
```

## 5. 待 owner 明确的（两条）
```text
① **虚拟局域网的定位要不要从"进阶"改成"个人版的远程路径（主路径）"？**
   （取决于"个人版是否必须能跨地点同步"——若必须，则它是唯一答案 ⇒ 不该叫"进阶"）
② **既有"个人空间 + 加密 + 绑服务器"的用户怎么处置**（甲保持／乙迁团队／丙迁虚拟局域网）
```

## 6. 而它让"加密"这件事的结论变得更简单了
```text
前面几轮算过的那笔账（"个人版不加密能省多少"）⇒ 现在**有了更好的答案**：
  **不是"个人版不加密"，而是"个人版根本不经过服务器"** ⇒
  · 隐私：**比加密更强**（数据不出本机/局域网/VPN 隧道）
  · 复杂度：**比"放弃加密"更低**（那一整片不用做）
  · 承诺：**更强**（从"加密后不留存"变成"根本不接触"）
⇒ ⇒ 这是一个**双赢**的形状 —— 前提是 §4 那个既有用户的账能算清。
```
