## 二、Android 为什么"能但不靠谱"✗（逐条）

```
· 接口：`AudioPlaybackCapture`（**Android 10 / API 29** 起 ✓）
· 权限：`RECORD_AUDIO` ✓ ＋ 经 `MediaProjectionManager` 由**用户弹窗授权** ✓
· ⛔ **最硬的一条**：被录的那个 app 必须**允许被捕获** ✗
  （manifest 里 `android:allowAudioPlaybackCapture="true"` 或捕获策略 `ALLOW_CAPTURE_BY_ALL` ✓）
  ⇒ ⭐ 音乐/播客类 app 出于**版权**绝大多数**关掉** ✗ ⇒ ⭐ 抓不到就是抓不到 ✓
· 只抓 `USAGE_MEDIA` / `USAGE_GAME` / `USAGE_UNKNOWN` ✓（话务/提示音等抓不到 ✓）
· 捕获 app 与被捕获 app 必须在**同一用户配置**下 ✓（工作资料 vs 个人 ✗）
⇒ ⭐ 产品上必须做成「**试一下就告诉你行不行**」✗ —— ⛔ 不能承诺"一定能抓" ✓
```

## 三、iOS 为什么"基本不可行"✗

```
· 苹果**没有**给普通 app 开放"独立抓系统音频"的接口 ✗
· 唯一路径：用户在**控制中心开「屏幕录制」** ✓ ⇒ 系统声音作为**录屏流的一部分**给到 app ✓
· ⚠️ 不能单独开关 ✗：录屏开它才开、录屏关它就关；也**不能单独静音系统声** ✗
⇒ ⭐ 对"听书做笔记"这种场景，要求用户**一边录屏**✗ —— 体验不可接受 ✓ ⇒ ⛔ 不做 ✗
```

## 四、所以产品怎么走（决策 ✓）

1. ⭐ **主路径：用户选一个音频文件** ✓（mp3 / m4a / wav ✓）—— ⭐ **全平台一致、唯一可靠** ✓，⛔ 不看任何第三方 app 的脸色 ✗。
2. ⭐ **Android 版**：可以放一个「**试试抓当前播放**」✓ —— ⚠️ 抓到就用 ✓、抓不到**明确告诉用户是那个 app 不允许** ✓（⛔ 不许假装成功 ✗）。
3. ⛔ **iOS 版**：不提供抓取 ✓。
4. ⭐ **桌面版**（macOS/Windows）：以后再加"抓系统声" ✓ —— 它需要**系统权限**（macOS 要人点「屏幕录制」✓），属于**加分项** ✓。
