## 1. 本规格要解决的**一个口径问题**（比五条不变式更根本）

```text
今天界面上能拿到的关于"网段里的别人"的东西 = lanStatus.peers : number   （src-tauri/src/sync.rs:3489）
今天发现层手上有的关于"网段里的别人"的东西 = Vec<lan::Peer>             （src-tauri/src/lan.rs:403 live()）
```

⇒ **两边不是"信息量不同"，是【同一件事在两个地方各有一份表述】**。
⇒ 一旦界面开始"自己数对端 / 自己判断某台设备服务哪些空间"，就会出现**第二份真相源**：
状态行里的「本网段发现 N 台」（`lan.rs:350`）与列表里的行数**会漂**，
而这类漂**不炸、不报错、测试全绿**（正是 `INVARIANTS.md` 头部那条"本仓花了最多代价去消灭的东西"）。

**⇒ 所以本规格的第一条不变式不是"加一个列表"，是"列表只能有一处来源"。**

## 3. 数据形状（**新增读数长什么样**）

> 这一节是**契约**：字段名、类型、谁产生、谁消费。三处必须逐字段一致（`check-web-commands` 管"命令存在性"那一维，**字段一致性靠人＋契约注释**）。

### 3.1 Rust（改 `src-tauri/src/sync.rs`，`LanStatus` 旁边）

```rust
/// 同网段里的一台**别的设备**（给人看的列表用；**不含**任何密钥材料）。
///
/// ⚠️ 它**不是**新发现的数据：每一个字段都来自既有那块砖
/// （`lan::Peer { announce: LanAnnounce { .. }, addr, seen_at_ms }`，`lan.rs:133-139`）。
/// 本结构只做一件事：**把对端表上抛**（需求 §3.2）。
#[derive(Serialize)]
pub struct NearbyPeer {
    /// 设备身份（**排障与去重用**；不许插进用户可见的句子，见 §4）。
    pub device_id: String,
    /// 设备名 —— **可能是空串**（`LanAnnounce.device_name` 是 `#[serde(default)]`，`lan.rs:71-72`；
    /// 本机名来自 `host_name()`，拿不到就留空，`lan_state.rs:371` 用它、`:454` 是定义）⇒ 界面**如实说没报名字**，
    /// **不许**回落成 `device_id` 前几位（那是 `2026-09-28-user-facing-copy-spec` 的
    /// `INV-UI-copy-no-internal-ids` 管的事，`SyncPanel.tsx:1003` 已有先例、`:1660` 是同一条纪律）。
    pub device_name: String,
    /// 收到它公告的来源地址（ip，不含端口 —— `lan_state.rs:123`）。
    /// ⚠️ 默认**不显示**，只用于同一个地址去重与排障（见 §4 的交互口径）。
    pub addr: String,
    /// **它自己声明**在服务哪些空间（`LanAnnounce.hub_spaces`，远端 `space_id`，`lan.rs:76`）。
    /// 这是"这台设备跟我有没有共同空间"的唯一依据；**界面不许自己算**这条交集。
    pub spaces: Vec<String>,
    /// 这条列表项与**当前这个空间**相不相关（由 Rust 判定，界面直接显示）。
    /// 口径：`spaces` 里含当前空间的**去空白字面量相等**（与 `mesh::mesh_peers` 同一把尺，`mesh.rs:227` 那一关 `lan::serves_space`）。
    pub serves_current: bool,
    /// ★ **只有这一台能被直接拉**（＝它就是网格对端）：与 `mesh::mesh_peers` 同一套过滤
    /// （不是我自己 · 服务这个空间 · `hub_base` 是局域网地址，`mesh.rs:221-235`）。
    /// ⇒ 界面据它决定那一行**有没有**「邀请」这个动作。
    pub invitable: bool,
}

/// `LanStatus` 的**新增字段**（其余字段一个字不动）。
pub struct LanStatus {
    // …（既有五字段原样，见 sync.rs:3483-3502）…
    /// ★ 本轮新增：**同网段里我听得见的每一台别的设备**（含不服务当前空间的）。
    ///
    /// ⚠️ 口径三条：
    /// 1. **它和 `peers`（数量）来自同一次 `state.peers(now)` 读数**（`sync.rs:3417`）——
    ///    所以 `peers == nearby.len()` 恒成立（`INV-NEARBY-one-source`）；
    /// 2. **未启用发现层 ⇒ 空**（`LanState::peers` 在未启用时一律返回空，
    ///    `lan_state.rs:192` 口径 3「关掉＝看不见」）；这里**不另判一次**；
    /// 3. **它不按当前空间过滤** —— "附近有哪几台设备"与"哪几台服务我这个空间"是两件事，
    ///    后者由每条的 `serves_current` 表达（过滤留给界面显示，判定留在 Rust）。
    pub nearby: Vec<NearbyPeer>,
}
```

**产生者**：`lan_status` 一处（`sync.rs:3385`），复用已有的 `let peers = state.peers(now);`（`sync.rs:3417`）。
**消费者**：`SyncPanel.tsx` 的「同网段的设备」块（新建）；`src/lib/platform/web.ts` 的 `lan_status` 如实回空。

### 3.2 TypeScript（改 `src/lib/platform/commands.ts`，`LanStatus` 旁）

```ts
/** 同网段里的一台**别的设备**（与 Rust `sync::NearbyPeer` 逐字段相同）。 */

  deviceName: string;

  spaces: string[];
  /** 它跟我**当前这个空间**相不相关（Rust 判的，界面直接显示）。 */
  servesCurrent: boolean;
  /** ★ 它能不能被直接拉（＝可以邀请）：与 `mesh::mesh_peers` 同一套过滤。 */
  invitable: boolean;
}

export interface LanStatus {
  // …（既有五字段原样）…
  /** ★ 本轮新增：同网段里听得见的每一台别的设备；`peers` 是它的长度（同一次读数）。 */
```

⚠️ **两个名字的映射不是自动的**：Rust 侧 `LanStatus` **没有** `#[serde(rename_all = "camelCase")]`
（`sync.rs:3482` 只有 `#[derive(Serialize)]`）⇒ 现在发出去的就是 `snake_case`。
`PeerPullReport` / `MeshRoundReport` / `MeshConfigState` 都**带** `rename_all = "camelCase"`（`mesh.rs:296`、`:313`、`:594`）。
⇒ **本轮选 snake_case（与 `LanStatus` 其余字段一致）**：新字段写 `device_id` / `device_name` /
`serves_current`，TS 侧就写 `device_id` …。**不许**只给新字段加 `rename_all`（一个结构体两种风格）。
⚠️ 这条要落在**契约注释**里（`commands.ts:175` 的注释已经写着"与 `sync.rs::LanStatus` 逐字段相同"）。

### 3.4 **数据形状的边界**（写下来免得后人"顺手"扩张）

- ❌ **不加 `seen_at_ms` / 存活剩余时间**：那会让界面能自己算 TTL，"活着"的判定就有了第二处。
- ❌ **不加 `fp`**：它**就是** `device_id`（`lan.rs:79-83`），加一个就是两个字段说同一件事。
- ❌ **不加 `hub_base`**：它就是网格那一路的地址，而"能不能被拉"已经收进 `invitable` 一个布尔。
  ⚠️ 若将来邀请**要指到具体地址**，那属**邀请协议**的载荷，不属"列表读数"（两张表不该混）。

## 4. 交互（各态显示什么字 —— 照本仓"用户可见文案"口径）

**口径来源**：`../specs/2026-09-28-user-facing-copy-spec.md`（三条不变式：不得插值内部标识裸值 / 行内 Markdown 要在边界渲染 / 相邻 inline 要有分隔）。
⚠️ 那份现在在**另一条分支**上（`spec/user-facing-copy`），主线工作树里没有这份文件 —— 见 §6 待查 R2。

| 态 | 判据（从数据怎么得出这一态） | 显示什么字 | 不许显示 |
|---|---|---|---|
| **不可用**（Web / 发现层没起） | `!enabled` | 「同网段的设备：这台机器上看不到这一层」＋（若在 Web）沿用既有的「Web 版不支持」口径 | ❌ 不许显示"还没发现设备"（那与"这一层不可用"是两种处境） |
| **发现中** | `enabled && nearby.length === 0` | 「同网段的设备」＋「还没发现别的设备… 正在找」 | ❌ 不许说"网段里没有设备"（`lan.rs:472-473` 的代价 ⇒ "看不见"不等于"不存在"，需求 §4.3） |
| **有设备** | `nearby.length > 0` | 每行：**设备名**（空 ⇒ 「这台设备没报名字」）＋ 第二列（见下）＋ 右侧动作（见下） | ❌ 不许把 `device_id` / `space_id` / 裸 IP 插进句子（`INV-UI-copy-no-internal-ids`） |
| **可邀请** | `invitable === true` | 右侧按钮：「邀请加入「<空间名>」」——**空间名**取本地 `meta.workspaces.name`（`workspaces.rs:109` 就有一处取名字的写法），取不到才回落「这个空间」 | ❌ 不许显示"邀请"而没有空间名（用户不知道邀请什么） |
| **不可邀请**（看得见但拉不到） | `invitable === false` | 右侧**不给按钮**，第二列如实说：「它没报可以直连的地址」（对应 `mesh.rs:221-235` 那三条过滤没过） | ❌ 不许给一个点了会失败的按钮 |
| **已邀请** | 本地记着对这台设备的邀请（§5.3） | 该行：「已发出邀请 · 等对方接受」 | ❌ 不许说"已连接"/"对方已接受"（本地**观测不到**，见 §6 待查 R3） |
| **对方接受**（若可观测，见 R3） | 有"对方来拉过我"的证据 | 该行：「对方已经来过」（**只说观测到的事实**，不推断它的意图） | ❌ 不许说"同步完成"（那是另一件事的读数） |
| **失败** | 邀请这一步的 `Err` | 原样显示 Rust 给的那句人话（本仓口径：错误文本必须**可操作**，例 `space_crypto.rs:319-325`） | ❌ 不许只说"失败" |

**两条文案纪律（照本仓先例）**：

## 5. 协议：邀请怎么走（**本轮就做还是先只做"看得见"？**）

### 5.1 明确取舍（**这就是本规格的那个决定**）

> **取舍：本轮【就做邀请】，但把"看得见"与"发邀请"切成两片，分片可各自落地、各有承重判据。**
> 理由三条（都是既有事实，不是偏好）：
>
> 1. **"看得见"单独落地时它没有用户的下一步** —— 列表里三台设备而**没有一个动作**，
>    用户能做的最多是把名字念给同事听。需求 §2 的痛点是"三样字符串"，"看得见"一个都没消掉。
> 2. **邀请的载荷不需要新协议栈**：`space_id` 与口令都是**一行 KV**
>    （`sync_profiles` ＋ `mesh_token:<空间>`，`mesh.rs:406`）⇒ 而发现层**已经**把
>    "谁在线、从哪个地址来"给了我（`lan.rs:133-139`）⇒ 邀请只是**一条 unicast 消息**，
>    不需要新端口、不需要新进程、不需要账本。
> 3. **分开落地的代价已经付过一次**：分片表把 ③-b-2a（控制面）/③-b-2b-1（被发现）/③-b-2b-2（界面）
>    拆成三片，结果是「链路 ＋ 入口都齐了，只差真机复验」（`../plans/2026-09-24-lan-p2p-topology-decision.md` §13 末尾）。
>    ⇒ 本轮**沿用这个切法**，别把一件能拆的事一次做完。

**⇒ 所以本规格给的是两片（方案 §2 展开）：**
- **甲片「看得见」**：§3 的数据形状 ＋ §4 的前四态。**零协议**，改的是读数与渲染。
- **乙片「发邀请 / 接受」**：§5.2 的邀请线 ＋ 接受侧的写入。**新一条线版本**，但**复用**UDP 发现通道的地址与端口。

### 5.2 邀请线（乙片；**不是** `LanAnnounce` 的扩张）

```text
载体    既有那条 UDP 通道（`lan::LAN_PORT = 47821`，`lan.rs:46`），**不新开端口**
寻址    发给**对端那一条的 `addr`**（单播）—— 与 `announce_targets` 补单播那一条同一思路（`lan.rs:476-491`）
方向    **发起侧 → 接受侧**（邀请）；接受侧**回不回**由 §5.3 决定
```

**载荷**（新增一个结构，**独立线版本**，理由：`decode_announce` 对 `v != WIRE_VERSION` 一律**丢弃且不猜**
（`lan.rs:122-124`，"不认识 ⇒ 不猜"）⇒ 把邀请塞进 `LanAnnounce` 会逼着两件事共用一个版本号）：

```rust
/// 邀请一条**空间同步关系**（给同事的）。★ **不含任何密钥材料**（INV-NEARBY-invite-has-no-keyring）。
#[derive(Debug, Clone, PartialEq, Eq, Serialize, Deserialize)]
#[serde(deny_unknown_fields)]                    // 同 pairing.rs:42 的口径：字段就是协议
pub struct NearbyInvite {
    /// 邀请**自己的**线版本（与 `lan::WIRE_VERSION` 分开：两者的演化节奏不同）。
    pub v: u32,
    /// 发起方设备身份（人核对"这是不是刚才那台"）。
    pub from_device_id: String,
    #[serde(default)]
    pub from_device_name: String,
    /// **远端空间 id**（对暗号用）—— 就是 `sync_profiles.space_id`（sync.rs:3322 那颗 ★★ 的左半边）。
    pub space_id: String,
    /// 这个空间的**口令**（`mesh_token:<空间>`，mesh.rs:406）。
    /// ⚠️ 它是"能连上这个地址的人都能拉走该空间的**密文**记录"那道闸门的钥匙（mesh.rs:805-810 的警告）。
    /// ⇒ 见 §5.4 的"别人拿到码能干什么"。
    pub token: String,
    /// 一句给人看的话（发起方写、接受方原样显示；本仓先例：`mesh::config_state` 的 `note`）。
    pub note: String,
}
```

**为什么口令要在邀请里**（这是取舍，不是默认）：
网格窗口的 `authorized` 在**没设口令时一律放行**（`mesh.rs:985-988`：`None` ⇒ `return true`），
而设了口令则**逐字节比较**（`mesh.rs:989-992`）。⇒ 如果邀请不带口令，接受侧要么开一个**无口令**窗口
（等于"同网段谁都能拉密文"），要么让用户再抄一次口令（＝需求 §2 第 4 条那条痛点还在）。
**⇒ 所以口令必须随邀请走**，而它的**代价**必须写在 §5.4 里说清。

### 5.3 接受侧回不回？（**给结论**）

> **不在本轮做"接受侧回执"。** 接受侧的消息**只写本地**（写 `sync_profiles` ＋ `mesh_token`），
> 发起侧不等待、不重传、不确认。

理由：
- 做回执就要**发起侧持久化一条待确认状态 ＋ 超时重试** ⇒ 那是**一条可靠性协议**（重传/去重/超时），
  而丙档整个定义是"**删**东西、不要账本"（`../plans/2026-09-24-lan-p2p-topology-decision.md` §4）。
- 用户**不需要**回执也能完成这件事：接受侧一旦接受，**它下一轮就会来拉**
  ⇒ 发起侧的观测点已经在手上（对端水位 / 它来拉过我），见 §6 待查 R3。
- ⚠️ **不对称是如实写出来的**：状态只写"已发出邀请"，**不写"对方已接受"**（我们没观测到）。

### 5.4 安全分析（**给同事的邀请码里有什么、没有什么**）

| | 邀请载荷里有 | 没有 |
|---|---|---|
| 空间身份 | `space_id`（远端组织空间 id，**32 位十六进制**，本就不是秘密：它在 URL/文件名/日志里流通过） | ❌ 本地空间 id（`ws_id`）—— **绝不外发**（那是本机文件名，`sync.rs:3331`） |
| 连接 | `token`（网格口令）＋ 隐含的"我在哪个 IP" | ❌ 任何监听的**端口号**（对端从公告里自己知道；邀请里不报） |
| 密钥 | ❌ **什么都没有** —— 载荷里**没有** `PairingPayload.material`（`pairing.rs:46`），没有钥匙袋，没有口令原文 | ❌ 按空间密钥材料 / 主口令 / 会话密钥 / 任何能解开盒子的东西 |

**别人拿到邀请码能干什么 / 不能干什么**：

| 能做 | 为什么 | 不能做 | 为什么 |
|---|---|---|---|
| 用 `space_id` ＋ `token` **连上发起方的网格窗口**、拉走**该空间的密文记录** | 窗口的闸门就是口令（`mesh.rs:985-992`），而记录是**密文**（网格只搬记录，不搬钥匙） | ❌ **解开**拉到的记录 | 密钥材料**不在**载荷里；解盒子要主口令（`keyring` 的口径：主口令仍由人输，见 `sync.rs:2295-2297` 注释「**主口令仍然由人来输**」） |
| 把密文**再抄给别人** | 密文可以被复制 | ❌ 冒充**发起方**去改数据 | 窗口**只服务它自己产生的记录**（`../plans/2026-09-24-lan-p2p-topology-decision.md` §13 表内 ③-b-1；判据 `the_window_serves_only_its_own_records_so_it_needs_no_ledger`）⇒ 拿到密文不等于能写进去 |
| 用它**污染**接受侧的本机档案（把某个本地空间绑到一个陌生 space_id 上） | 接受侧**必须自己点接受**；且写入走**同一道闸门**（§5.5） | ❌ 绕过加密闸门 | 见 §5.5 |

### 5.5 加密的个人空间怎么办（**明确回答**）

> **答案：不适用 —— 邀请这条路对【个人加密空间】是"直接被拦"，不是"要额外一步"。**

- 闸门是**绑同步那一刻**过的：`set_sync_profile` → `sync_bind_gate`（`sync.rs:1136-1160`）。
  接受邀请**也写这条档案** ⇒ **必须走同一个闸门**（`Err` ＝ 拦住，`Ok(Some(提示))` ＝ 放行但留痕）。
- 闸门口径逐字（`space_crypto.rs:312-325`）：**团队空间免检** · **个人空间**：库是密的**或**袋里有它的盒子 ⇒ 放行，
  否则拦（"先给它设一句口令（按空间加密），再绑定同步"）· **未分类**：放行但把"没管到"报出去。
- ⇒ **所以"给同事的邀请"只在【团队空间（免检）】上是顺的**；个人加密空间**对方没钥匙，拉到也打不开**
  —— 这与需求 §5 场景 C 是同一条。
- ⚠️ **团队空间的内容对服务端是明文**（那是"免检"换来的东西，`space_crypto.rs:318`）；
  ⚠️ 而网格这条路**不经服务端**（对等直连）—— 这两句话**不矛盾但要一起说**：
  团队空间的密文/明文取决于它的存储形态，而网格只负责搬记录。

### 5.6 邀请的**落点**（写下来，免得实现时自由发挥）

- 接受侧把 `space_id` / `token` 写到**哪一个本地空间**？
  ⇒ **不猜**：接受时**要求当前面板上选中的那个空间**（`activeRow.ws_id`）—— 也就是
  "**我把我这个空间接到他那个空间上**"。⚠️ 这是一个**产品决定**（用户可能在错的当前空间上点接受），
  所以 §4 的接受态文案必须**写出两个名字**：「把本地的「<我的空间名>」接到对方的「<对方空间名/id>」」。
  ⇒ 见 §6 待查 R4（对方那个空间的**名字**从哪来：邀请里现在只有一个 id）。
- `db_space` 与 `space_id` 的分离**照旧**：写入 `sync_profiles(space_id = 邀请里的, ws_id = 当前空间)`
  ⇒ **这一条就是 INV-NEARBY-space-id-not-db-space 的落点**。

### 9.2 总闸「同步方式 = 关闭」时：**服务器行【不灰】**，设备直连行【灰】

```text
· 设备直连      ⇒ **灰掉**（disabled）。它是开关；总闸关了它不可能生效。
· 服务器          ⇒ **不灰**。owner 原话「服务器不灰」。
   理由：那一行装的是【配置入口】（服务器地址／账号登录／组织空间绑定／成员管理），
         不是开关。灰掉它 ⇒ 用户**没法准备配置**，而他往往正是"先把配置备好、再开总闸"。
   ⚠️ 但要在值旁边**标明**「当前不自动同步」—— 不许让用户以为它已经在跑。
· 拉取间隔        ⇒ 这一行**不出现**（父项「设备直连」已灰 ⇒ 子项不显示，见 §9.3）。
· 【立即同步】     ⇒ **不灰**。既有口径原话（`syncMode.ts` 的 `syncModeHint("off")`）：
                「不自动同步：只有点「同步」时才同步（网格也跟着那一次走）。」
⇒ 一句话：**灰的是【自动】，不是【手动】。手动的路永远留着。**
```

### 9.3 「设备直连 = 关」时：**「拉取间隔」这一行不出现**（不是灰掉）

```text
同理：不显示「附近设备」区 —— **没开就不会去发现**（本仓口径：不做"看着像在工作其实没工作"的界面）。
```

## §10 新增不变式：**许可边界**（INV-LIC-no-server-in-client）

> 由来：owner 2026-09-29 问「服务器实时同步要考虑许可证问题对吧？」—— 答案是**对**，
> 且仓里本来就有明文（`docs/plans/2026-09-24-lan-p2p-topology-decision.md:31` 的 **F6**）。
> ⚠️ **这一条退化时【不会有任何判据变红】** ⇒ 只能靠白纸黑字钉住（这正是要写它的理由）。

### 10.1 事实（两边各自是什么）
```text
· 客户端 `repos/ShuyoNote`            ⇒ `LICENSE` = **GNU AFFERO GPL v3**（免费公开）
· 服务端 `repos/shuyonote-sync-server` ⇒ `LICENSE-COMMERCIAL`（**独立商业组件、私有仓**）
F6 原话：「★ 许可约束：客户端 AGPL-3.0 开源，`shuyonote-sync-server` 是私有商业授权组件
          ⇒ **不许**把服务端内嵌进客户端（否则被迫开源，或需一份例外授权）」
```

### 10.2 不变式
```text
INV-LIC-no-server-in-client：
  客户端与服务端之间**只许通过协议对接**（发网络请求、解帧），
  **不许**出现下列任何一件：
    ① 把服务端的实现（哪怕一段）搬进客户端或本仓
    ② 让客户端内嵌 / 自带一个服务端（含"只在局域网的准服务端"）
    ③ 两侧共享同一个 crate / module（等于把边界缝掉）
⇒ 退化了会怎样：**不会有任何判据变红** —— 它表现出来是"代码能跑、功能也对"，
   代价在法律面（AGPL 传染 ⇒ 服务端被迫开源，或需另取例外授权）。
⇒ 所以本条的判据只能是**审阅级的**：改到"客户端 ↔ 服务端"交界处时，人必须过一遍这三条。
```

### 10.3 ⭐ 它解释了"甲-2 被冻结"这件事
```text
owner 2026-09-25 冻结的 **甲-2（局域网里长出一个"准服务端"，热点那台当裁定者）**，
正是 10.2-②「让客户端自带一个服务端」——**许可上本来也不该做**。
⇒ 所以本档（丙档）走「**真 P2P、谁都不当中枢**」不只是技术选择，
   也是 F6 之下**唯一安全的那条**。
```

### 10.4 防呆（本档要落的一行）
```text
在客户端里那段 SSE 客户端代码（`src-tauri/src/sync_stream.rs`）的头注里加一句：
  「这里**只是协议客户端**：只发 HTTP、只解帧，**不含任何服务端实现**。
    把服务端代码抄进来 = 破 F6 ⇒ 须先取一份例外授权。」
理由：这类越界几乎总是以「先抄一段跑起来」的样子发生，且**不会让任何检查变红** ——
      只有这行字能在现场拦住人。
```

### 10.5 一条对外口径（服务端仓自己定的，本仓照办）
```text
`repos/shuyonote-sync-server/AGENTS.md:174`（红线）：
  ⚠️ 对外内容（社区 / 内容稿）**不提 AGPL / 商业许可**
⇒ 谈"服务器实时同步"可以；**别把许可话题带进对外内容**。
```

## §11 局域网光标（awareness）的**不变式**（对应需求 §8）

> ⚠️ 这一组有一个共同特点：**退化时【大多不会让任何既有判据变红】**
> （它们坏掉的样子是"跨版本组网断了""网段里全是噪音""加密空间泄了位置"）。
> 所以每条都要**自己有判据**，不能靠"既有断言还绿着"来兜。

### INV-AWARE-no-wire-version-bump —— 加光标**不许升 `WIRE_VERSION`**
```text
判据（文本级，可自动跑）：`src-tauri/src/lan.rs` 里 `WIRE_VERSION` 的值仍为 `1`，
  且新增的光标字段带 `#[serde(default)]`。
退化会怎样：升到 2 ⇒ `if a.v != WIRE_VERSION {拒收，不猜}`（lan.rs:122）
  ⇒ **新旧版本在同一网段里互相完全看不见**（连公告都拒）
  ⇒ 表现成"升级一台之后，另一台突然找不到了" —— 而没有任何东西会报错。
变异证据：把 `WIRE_VERSION` 改成 2 跑那条文本判据 ⇒ 必须变红。
```

### INV-AWARE-idle-zero-traffic —— **没人动光标时，网段里没有光标帧**
```text
判据（行为级）：造"两台互认 + 都打开同一页 + 都不动"的场景 ⇒ 统计一个窗口内
  收到的光标帧数 = **0**（公告帧不算）。
退化会怎样：变成定时广播 ⇒ 网段里每 100ms × N 台 帧 ⇒
  把"噪音可控"（公告 30 秒那条口径）直接推翻；且耗电。
变异证据：把发送侧从"光标动了才发"改成"定时发" ⇒ 该判据必须变红。
```

### INV-AWARE-e2ee-not-applicable —— 加密的个人空间**不发也不收**
```text
判据（行为级）：在【个人空间（已加密）】上打开编辑器、移动光标 ⇒ 发出的帧数 = 0；
  且该空间的界面上【不出现】光标（不是灰掉）。
退化会怎样：**光标位置泄漏内容位置**（"他在改第 3 段"）——
  那是 E2E 承诺之外的信息，且不会让任何加密判据变红（那些判的是"内容出不出网"）。
口径来源：沿用 `collab.rs` 既有的 presence 口径
  「Personal (E2E) spaces are not meant to opt into presence」。
变异证据：把闸门去掉（所有空间都发）⇒ 该判据必须变红。
```

### INV-AWARE-no-second-truth —— 光标**不进任何持久层**
```text
判据（文本级 + 结构级）：光标状态只出现在内存结构里；
  不许出现在 `page_crdt` / `pages` / 任何 db 表 / 任何 CRDT update 里。
退化会怎样：光标变成"第二份真相"（同一件事有了两个来源）⇒ 本仓最忌；
  且它会随同步跑到别的设备上去（一个"上一次谁在这"的幽灵）。
变异证据：故意把光标写进一张表 ⇒ 文本判据必须变红。
```

### INV-AWARE-identity-required —— 每条帧**必须可归因**
```text
判据（纯函数级）：解析时 `device_id` 为空 ⇒ **丢弃**（照既有
  `AnnounceReject::NoDeviceId` 的口径："没有身份的公告无法归因"）。
退化会怎样：匿名帧 ⇒ 界面上出现"不知道是谁的光标" ⇒ 无法追责、也可能是伪造。
变异证据：喂一条 `device_id: ""` 的帧 ⇒ 解析结果必须是"丢弃"而不是"接受"。
```

### INV-AWARE-expiry-on-receiver —— **过期由接收侧自己判**
```text
判据（纯函数级）：给一条 `at` 比现在早 6 秒的帧 ⇒ 判定为"人已离开"（阈值成常量、有判据钉）。
退化会怎样：UDP 会丢、也可能**没有"我走了"的告别帧** ⇒ 依赖告别帧的实现
  会留下**永久幽灵光标**（对方早就关了，你屏幕上还挂着一个）。
变异证据：把阈值改成"只在收到告别帧才消失" ⇒ 该判据必须变红。
```

## §13 设备直连的**两种情况** ＋ 「配对一次」到底是什么

> owner 2026-09-29：「**设备直连有单人多设备和多人多设备两种情况**」
> ＋「**配对一次，永远可用吗，就像蓝牙那样？**」
> ⇒ 这一节回答这两问，并**顺手解开 §B-1 那个矛盾**（闸门长在设备直连路径上）。

### 13.1 两种情况**必须分开**（它们的动作、空间、隐私全不同）
| | **单人多设备** | **多人多设备** |
|---|---|---|
| 谁的数据 | **都是你自己的** | 你的 ＋ 别人的 |
| 第二台/第二个人怎么进来 | **配对**（认领：这是我的另一台设备） | **邀请**（请他加入） |
| 空间 | **个人空间** | **团队空间** |
| 要不要成员/权限 | 不要 | **要** |
| 隐私性质 | 数据只在我自己的设备间 | 数据要给别人 |
| 局域网内 | **配对后全自动**（发现 ＋ 5 秒节拍） | 邀请后自动 |

```text
⚠️ 而今天【没有"配对进设备直连"这条路】—— 单人第二台设备只能**借"邀请"**，
   而"邀请自己"这**话术本身就不对**。已有的零件是 `pairing_export` / `pairing_import`
   （`sync.rs:2026` / `:2095`，**不经服务器**的换设备），但它今天接的是"静态加密＋换设备"，
   **没有接到设备直连上** ⇒ 这是缺口。
```

### 13.2 ⭐ 「配对一次」在我们这里 ＝ **把配置弄过去一次**（**不是**蓝牙那种"关系"）
```text
【蓝牙】配对 = 双方**存下一条关系**（link key）⇒ 关系在就能连；可以**逐台解除**。

【我们】设备直连靠**三样配置对上**（**无状态**）：
  ① 监听地址（`mesh_bind`）  ② 口令  ③ 空间身份（`space_id`）
  ⇒ ⇒ **配置在 ⇒ 就一直能连** —— 我们根本不需要"关系"这个东西。
  ⇒ ⇒ 所以"配对一次" ＝ 把这三样弄到第二台设备上一次；之后**每次开机自动发现 ＋ 自动同步**
     （比蓝牙还省：它偶尔还要重配，我们只要配置不变就不用再碰）。
```

### 13.3 ⚠️ 但「永远」会被三件事破
```text
① **换 IP**（换网段 / 路由器重分配）—— 而报出去的地址是「窗口**实际绑上的地址**」
   ⇒ **绑具体 IP ⇒ 换网就失效**；绑"自动选"（如 `0.0.0.0`）⇒ 基本不怕换网
   ⇒ ⇒ **所以"永远"取决于"绑什么"** ⇒ 见 `INV-NS-address-survives-network-change`。
② **空间身份变了**（重装 / 重置 / 换库）⇒ 对不上。
③ **改口令**（一次性的全局动作 —— 见 13.4，它不只是"改个密码"）。
```

### 13.4 ⚠️⚠️ 「共享口令」**无法逐台撤销** ⇒ 这是"多人不能用设备直连"的**结构原因**
```text
蓝牙：可以**逐台解除**（我删掉这台设备的配对）。
我们：**不能逐台撤销** —— 因为"认"的依据是【口令】
  ⇒ 要踢掉**一台设备或一个人** ⇒ **只能整体改口令** ⇒ **所有设备都得跟着改**！
⇒ ⇒ 因此：
   · **单人多设备**：没问题（都是我自己的设备）✅
   · **多人多设备**：**硬伤** —— 共享口令天生做不了成员管理
   ⇒ ⇒ ⇒ **多人必须有"成员"概念 ⇒ 那是团队空间（＝服务器那条路）。**
⇒ ⭐ 这条把一个原本像"产品偏好"的取舍（"多人为什么不用设备直连"）
   变成了**结构原因**（口令这个机制**做不到**成员管理）。
```

### 13.5 ⭐ 它**解开了 B-1**：闸门拦"个人空间被邀请"是**对的**
```text
`sync_bind_gate` 长在设备直连的【接受邀请】路上（`sync.rs:3273`），会拦住"未加密的个人空间"。
先前我把它报成"与 owner 裁定冲突"（因为个人版唯一远程路径就是设备直连）。

⇒ 但按 13.1 的区分：
   · **单人多设备**：**不走邀请** ⇒ **根本不经过那道闸门** ⇒ **矛盾不存在** ✅
   · **多人多设备**：走邀请 ⇒ 而这时【"个人空间"这个概念本身就不对】（多人＝团队空间）
⇒ ⇒ **它拦的不是合法用法，拦的是语义错误：「用个人空间去邀请别人」。**

★ 所以要改的只是**文案**（不是删闸门）：
   · ❌ 旧口径：「个人空间要先加密才能绑同步」⇒ **会让人以为"加密了就能邀请"**
   · ✅ 新口径：「**要跟别人共享，请用团队空间**」（个人空间是**你自己的设备之间**用的）
```

### 13.6 新增不变式
```text
**INV-NS-personal-is-single-person**
  个人空间**不提供"邀请别人"这个动作**；要协作 ⇒ 用团队空间。
  判据：① 界面在个人空间下**不出现**邀请入口；
        ② 邀请命令对个人空间**拒**，且理由文案是「要跟别人共享，请用团队空间」
           （**不许**是"请先加密"）。
  退化会怎样：用户以为"加密了就能邀请" ⇒ 拿个人空间当团队空间用 ⇒ 权限与隐私都失控。

**INV-NS-address-survives-network-change**
  报出去的地址要**经得起换网**：优先"自动选"而非写死具体 IP。
  判据：文案/默认值明确"换网后如何"；且换网时界面**如实提示**（而不是静默失效）。
  退化会怎样：**这是"配对一次永远可用"这句话的破绽** —— 换个网就悄悄不通了，
             而用户不知道要改地址（表现与"设备关了"无法区分）。

**INV-NS-shared-secret-cannot-evict-one**
  **共享口令无法逐台撤销** —— 要踢掉一台/一个人只能**整体改口令**。
  ⇒ 因此它**只适用于单人多设备**；多人场景**必须**有成员概念（团队空间）。
  判据：文案/规格里**不许**把"共享口令"当成"多人权限管理"来用；
        且这条要在"多人"相关文案里**说清**。
  退化会怎样：把共享口令当权限用 ⇒ 走一个人就得全员重配 ⇒ 且**无法审计谁还能拉**。
```

### 13.8 ⭐⭐ 「怎么知道是不是自己的设备？」——**系统判不出来**，以及真判据是什么

> owner：「**怎么知道是不是自己的设备？配对还是邀请？**」
> ⇒ 这一节回答它，并把 §13.1 的"配对 vs 邀请"从**话术差别**提升到**授权模型的差别**。

#### 13.8.1 ❌ 为什么判不出来
```text
设备直连的"认"依据是三样配置：**监听地址 ＋ 口令 ＋ 空间身份**（§13.2）。
⇒ 这三样**都是可以抄的** ⇒ 抄过去就能连。
⇒ ⇒ **技术上看不出**"这是我的另一台设备"还是"别人的设备" ——
   它们在机制上**完全一样**：能连上 ＋ 有口令 ＋ 空间身份对上 ⇒ 就能拉。
```

#### 13.8.2 ✅ 但有一条**真判据**：**它有没有"这个空间的密钥"**
```text
· **有** ⇒ 它是"我的设备"（同一个空间身份，密钥是从我这儿带过去的）⇒ 直接接上（**配对**）
· **没有** ⇒ 它是"别人的设备" ⇒ 要走**邀请**（加入你的空间）
⇒ 零件已有：`space_crypto` 的**钥匙袋**（`pairing_*` 搬的就是它的公开材料）。
⚠️ **但它只在空间【开了静态加密】时成立**（`space_crypto` 是可选的）
⇒ ⇒ **未加密的个人空间，技术上仍然区分不出**"我的设备"与"别人的设备"。
```

#### 13.8.3 ⭐⭐ 所以真正的判据不是"是不是我的设备" —— 而是**授权模型**
| | **配对**（单人多设备） | **邀请**（多人多设备） |
|---|---|---|
| 用户的意思 | 「这是我的**另一台**设备」 | 「请**他**加入」 |
| ★ **授权模型** | **单向** —— **我授权我自己**，**不需要对方同意** | **双向** —— **对方必须同意** |
| 为什么 | 那台设备本来就是我的 | 要把**别人的设备**纳进我的空间 |
| 谁发起 | 在**我自己的设备上**发起 | 我发给别人 |
| **要不要"接受"这个动作** | ❌ **不用** | ✅ **要** |
| 空间 | 个人空间 | 团队空间 |

```text
⇒ ⇒ 这解释了为什么"单人场景下邀请自己会别扭"：
   **不是话术不好听，是【授权模型不对】** ——
   邀请的语义里包含"**对方同意**"，而单人的第二台设备**不存在"对方"**。
```

#### 13.8.4 系统能可靠拿到的只有两件（都不足以判"是不是我的"）
```text
① **发起方是不是这个空间的既有设备**（`device_id` ＋ 空间身份 —— 我们有）
② **对方有没有这个空间的密钥**（只有加密空间才有 ⇒ 可选信号）
⇒ ⇒ 两件都不足以判"是不是我的设备" ⇒ **用户声明是必需的**；
   系统的责任是：**把两个动作分开、把话术说准、把授权模型做对**
   （尤其"**配对不需要接受**"这一点 —— 它是最容易做错的地方）。
```

#### 13.8.5 ⚠️ 一个安全后果：**未加密空间的"口令"就是全部防线**
```text
既然"是不是我的设备"判不出来，那**保护只能靠口令**。
⇒ ⇒ **未加密的个人空间 ＋ 弱口令 ＝ 同网段任何人都能拉**（抄配置就能连）。
⇒ ⇒ 所以：
   · **单人多设备**：口令强度**就是**全部防线 ⇒ **必须给强度要求**
     （否则这条路形同虚设：办公室网段里谁都能拉）
   · **加密空间**：多一层（没有钥匙就解不开）⇒ **更稳**
⇒ ⭐ ⇒ 这也是为什么 **C-1（`space_crypto` 保留）是对的**：
   **静态加密在设备直连这条路上是"第二道门"，不是冗余。**
```

#### 13.8.6 新增不变式
```text
**INV-NS-pairing-needs-no-acceptance**
  配对是**单向授权**（我授权我自己）⇒ **不许要求对方"接受"**。
  判据：配对路径上**没有** `accept` 这一步；而邀请路径上**必须有**。
  退化会怎样：把配对做成"要对方确认" ⇒ 单人多设备的第一步就卡住
             （用户在自己两台设备之间要"互相接受"，荒谬且易被当成 bug）。

**INV-NS-unencrypted-needs-strong-secret**
  **未加密**的个人空间走设备直连时，口令就是**唯一**防线 ⇒ 必须有**强度要求**，
  且界面要如实说明"这是这条路唯一的一道门"。
  判据：弱口令（如短/纯数字）⇒ **拒**并给可操作理由；文案里说清这一点。
  退化会怎样：弱口令 ⇒ **同网段任何人可拉**（抄三样配置即可）
             ⇒ 而用户**不会知道**自己其实是公开的。

**INV-NS-own-device-cannot-be-proven**
  **不许**在界面/文档里声称系统"能识别这是不是你的设备"（它做不到，见 13.8.1）。
  判据：文案里不许出现"已验证/已确认是您的设备"这类**做不到的承诺**；
        只许说"已配对/已加入"（描述**动作**，不描述**判定**）。
  退化会怎样：给了做不到的安全承诺 ⇒ 用户按"它认得出"来决策 ⇒ 出事时责任在承诺上。
```

#### 13.8.7 与既有文档的关系
```text
· 13.8.3 的"授权模型差别"是 §13.1 那张表的**根据**（原先只有"动作名"的差别）。
· 13.8.5 给 C-1（`space_crypto` 保留）补了一条**功能理由**（"第二道门"），
  而不只是"owner 说保留"—— 这让它在清理时**更难被误删**。
· 13.8.6 的三条把"配对/邀请/口令强度/不许过度承诺"都变成了**可立的判据**。
```

### 13.9 ⭐ 单人多设备的**三个技术前提**（"配对一次、之后全自动"缺的就是这三件）

> owner 2026-09-29：「设备直连时，设备地址换网是会变的，所以应该**自动填写**对吧？
> `space_id` 建立后**不变**对吧？**同步多个空间**呢？」
> ⇒ 三问都对，而今天的代码**有两件做不到**。逐条核过。

#### 前提一 · 地址必须**自动**（换网不该要人改）✅ 直觉对，❌ 今天做不到
```text
【今天的实况（核过）】
  `mesh.rs:653 announced_base(addr)`：
      if addr.port() == 0 || addr.ip().is_loopback() || !is_lan_only(addr.ip()) { return None }
  而 `mesh.rs:723 is_lan_only`：`v4.is_loopback() || v4.is_private() || v4.is_link_local()`
  ⇒ **`is_lan_only(0.0.0.0)` 是 false**（0.0.0.0 不是 loopback / 不是 private / 不是 link-local）
  ⇒ ⇒ **绑通配 ⇒ 报不出去** ⇒ 对端发现不到你
  ✅ 而且有测试**钉着**：`mesh.rs:1916  set_mesh_bind("0.0.0.0:8788") ⇒ **Err**
  ⇒ ⇒ ⚠️ **所以今天用户【必须】填一个具体内网 IP** ⇒ 换网就变 ⇒ 要手动改
     ⇒ ⇒ ⇒ **这正是"配对一次永远可用"的破绽**（§13.3-①）

【要改成】
  · **允许绑通配**（`0.0.0.0:<port>`）⇒ 听所有网卡（含虚拟网卡）
  · **报出去的地址由系统选**：枚举本机内网 IP ⇒ 报「对端可能用到的那些」
    ⇒ 零件已有：`announced_base` 就是"按绑上的地址算报出地址"那一处 ⇒ 扩成多值
  · ⭐ 它**同时解决虚拟局域网那条**（VPN 网卡地址也不用用户填）
```

#### 前提二 · `space_id` 建立后**不变** ✅ 对
```text
· 它是档案里的一个值（`sync_profiles.space_id`）⇒ **换网不改它** ✅
· ⚠️ 但两个**主动动作会改它**：① **接受邀请**（写入邀请带来的那个）
  ② 重新绑定 / 换服务器 ⇒ 而这是**有意的**（那一步就是"接线"）
⇒ ⇒ 规格要写清：**"建立了就不变"成立；变的是"你主动接线"那一步**。
```

#### 前提三 · **多空间**：今天"每空间一套"，要改成"一个窗口服务多空间"
```text
【今天的实况（核过）】
  · `mesh.rs:522 windows()` = `HashMap<space_id, MeshHandle>` ⇒ **每空间一个窗口**
  · `mesh.rs:393 bind: read_setting(c, "mesh_bind", space_id)` ⇒ `mesh_bind` 也是 **per-space**
  ⇒ ⇒ **N 个空间 ＝ N 次配置 ＋ N 个端口**
  ⚠️ 对"单人多设备 × 多空间"是**很重的负担**：我两台设备、三个空间 ⇒ 要配 6 次；
     而每个地址换网都会变 ⇒ 又都要改。

【要改成】
  · **一个窗口服务多个空间**（一个端口，按 `space_id` 路由）
  · ⚠️ 连带一个设计变化：**"每空间一个口令" ⇒ "窗口级口令 ＋ 空间级授权"**
    ⇒ 而这就撞上 §13.4（**共享口令无法逐台撤销**）
    ⇒ ⇒ 所以**窗口级口令只适合单人多设备**（自己的设备共用一个口令）✅
       —— 多人场景本来就走团队空间（服务器那条路）⇒ **不冲突**。
```

#### 13.9.1 三件合起来 ＝ 「配对一次、之后全自动」的**全部技术前提**
```text
① **地址自动**（换网不用管）  ② **空间身份一次配对**（不用重配）  ③ **多空间一个窗口**（不用配 N 次）
⇒ ⇒ 三件都做完，"配对一次永远可用"才**真的是永远**；
   今天只是【到下次换网为止】（§13.3-① 已记这条破绽）。
```

#### 13.9.2 新增不变式
```text
**INV-NS-bind-survives-network-change**
  绑定的写法**必须经得起换网**：允许通配绑定，且报出地址由系统按当前网卡枚举
  （**不许**要求用户填一个"当下这个内网 IP"）。
  判据：① 通配绑定**不再被拒**（今天 `mesh.rs:1916` 那条判据要**反过来**）；
        ② 换网后（模拟：换一张网卡的枚举结果）**仍能报出可达地址**。
  退化会怎样：用户填死 IP ⇒ 换个网就"别人找不到我"，而表现与"设备关了"**无法区分**。

**INV-NS-one-window-many-spaces**
  一个监听窗口**可以服务多个空间**（端口数不许随空间数线性增长）。
  判据：三个空间 ⇒ **一个**窗口/端口；且每空间的拉取**各自独立**（不串）。
  退化会怎样：空间数一多 ⇒ 端口数、配置次数、口令数**全部线性增长**
             ⇒ 单人多设备变成"配置地狱"，与"零配置"的定位相反。
```

#### 13.9.3 验收场景
```text
① 绑 `0.0.0.0:<port>` ⇒ **不再被拒**，且报出的是"本机可达的内网地址"（不是 0.0.0.0）
② 模拟换网（换一张网卡）⇒ **对端仍能发现我**（不需要用户改任何设置）
③ 三个空间 ⇒ **一个端口**；对每个空间的拉取**互不影响**（各自独立收敛）
④ 会话末：**换网 ＋ 多空间**两件同时发生 ⇒ **仍不需要用户干预**
```

#### 13.9.4 与既有文档的关系
```text
· 补上了 §13.3-①（"永远"的破绽）与 §13.8.5（未加密空间靠口令）的**具体手段**：
  前者靠"通配绑定 ＋ 自动枚举"，后者靠"口令强度要求"。
· 前提三（一个窗口多空间）**连带**要定"窗口级口令"⇒ 而它只适用单人多设备 ⇒ 与 §13.4 自洽。
· `mesh.rs:1916` 那条判据（`0.0.0.0 ⇒ Err`）**要按 INV-NS-bind-survives-network-change 反过来**
  ⇒ ⚠️ 这是一条**既有判据要被推翻**的地方，属"显式决定"，不是清理的副产品。
```
