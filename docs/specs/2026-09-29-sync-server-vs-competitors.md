# 同步服务器 vs 竞品 —— 详细对比

> 由来：owner 2026-09-29「**同步服务器和竞品做个详细对比**」
> 依据：`team-edition-capability-and-limits` ／ `server-capacity-loadtest`（实测）
> ／ `edition-boundary` ／ `virtual-lan-requirements-spec`（§2 许可边界）
> ⚠️ **我们的数据全部实测**；**竞品的数据全部来自它们的官方公开口径**（我没读过它们的代码，
> 凡是我推断的都会标「推断」，**不把推断写成事实**）。

---

## 0. 一句话：**它们不是同一类东西**
```text
**我们 = 一个【可自建、可私有】的同步组件**（客户端 AGPL ＋ 服务端独立商业授权）
**它们 = 一个【SaaS 服务】**（你租用，不能自建，内容在它们云上）
⇒ ⇒ 所以下面的对比里，很多"我们弱"的地方其实是【定位不同】，不是【技术不行】；
   而"我们强"的地方（可自建／不过云／E2E）**正是 SaaS 结构上做不到的**。
```

## 1. 逐维度对比
| 维度 | **我们（shuyonote-sync-server）** | **WPS / 腾讯文档 / 飞书** | 说明 |
|---|---|---|---|
| **交付形态** | **可自建组件**（单文件 SQLite、零依赖） | **SaaS**（不能自建） | 定位差异 |
| **权威在哪** | 服务端（团队版）／**设备自己**（个人版设备直连） | **服务端唯一权威** | 我们有两条路 |
| **服务端懂不懂内容** | ❌ **从不解析 payload**（哑中转，`sync.rs:129` 原话） | ✅ **懂**（能渲染/导出/搜索/OCR） | 这是最大差别 |
| **传输模型** | **通知（SSE）＋ 各自拉（pull by seq）** | **推送内容**（服务端直接发） | 见 §2 |
| **扇出** | ⚠️ **O(N²)**（1 次写 ⇒ N 个订阅者各拉一次） | **O(N)**（服务端路由） | **我们的瓶颈根在这** |
| **单空间容量** | **≈100 台**（实测 M2；只读不订阅 ≈200） | 单文档 **200 人**（WPS 官方）；多端同步受**配额**限 | 见 §3 |
| **延迟** | 双向 **0.4~1 秒**（下载侧实测 16ms ＋ 上传防抖 400ms） | **100~300ms** | 见 §4 |
| **协同单元** | **一个空间** | **一个文档** | 我们现在没"文档"这个服务端单元 |
| **权限** | viewer / editor（`require_space` 查 `space_members`） | 完整（企业版更多：水印/审计/密级…） | 它们更成熟 |
| **审计** | ✅ 有（`audit_log`） | ✅ 有（企业版更强） | 基本持平 |
| **成员管理** | ✅ 有 | ✅ 有 | 持平 |
| **隐私** | ✅ **个人版可不过服务器**（设备直连）／⚠️ 团队版明文 | ❌ **全明文在云** | **我们的结构性优势** |
| **离线** | ✅ 本地优先（离线可用） | ⚠️ 弱（文档在云） | **我们的优势** |
| **可迁移/可退出** | ✅ 自建即可带走 | ❌ 绑定厂商 | **我们的优势** |
| **许可** | 客户端 **AGPL-3.0**；服务端 **独立商业授权**（`INV-LIC`：两边不许互相内嵌） | 专有 | 我们开源客户端 |
| **规模上限的形态** | **设备数**（扇出 N²） | **配额 + 单文档并发** | 见 §3 |
| **成熟度** | 新（今天刚补完上传侧触发） | **多年运维** | 不可比 |

## 2. ⭐ 最本质的差别：**"通知+拉" vs "推内容"**
```text
**我们**：1 次写 ⇒ 服务端发**通知**（帧里没有内容）⇒ 每个订阅者**各自来拉**
  ⇒ 好处：服务端**不懂内容** ⇒ 支持 E2E、可自建、实现简单
  ⇒ 代价：**N² 扇出** ＋ **多一跳**（通知 → 拉）

**它们**：1 次写 ⇒ 服务端**把内容直接推给该收到的人**（按文档/按页路由）
  ⇒ 好处：**O(N)** 扇出、延迟少一跳
  ⇒ 代价：**服务端必须懂内容** ⇒ 明文在云、不能 E2E

⇒ ⇒ **这一条解释了后面所有的"谁强谁弱"**：
   我们的隐私/可自建/离线，是用"服务端不懂内容"换的；
   它们的速度/规模，是用"服务端懂内容"换的。
```

## 3. 容量：**为什么"上限"这个词对两家含义不同**
```text
**我们**：上限 = **一个空间的设备数**（扇出 N² ⇒ 实测 ≈100 台）
**它们**：上限 = ① **配额**（容量/文件数 —— 产品策略，不是性能）
          ② **单文档并发**（WPS 官方：200 人/进程）
          ⇒ 而"一个账号多少台设备"这类数【没有公开】——
            因为**架构上不按设备数设限**（客户端不互拉 ⇒ 加一台只是加一个客户端）
⇒ ⇒ 所以"多端同步极限"这个问法，**对它们来说可能不存在那个数**。
```

## 4. 延迟：**差距的分解**
```text
它们 ≈ 100~300ms（服务端直接推）
我们 ≈ 400ms~1s ｜ 分解：
  · 编辑器去抖（~600ms，今天之前）＋ 上传防抖（400ms）  ← **今天刚补上"立刻上传"**
  · 上传往返（公网 50~200ms）
  · 服务端广播（实测 16ms）
  · 对方拉取往返（50~200ms）
⇒ ⇒ **差距主要在两处**：① 那两层防抖（要"先发后落库"撤掉）
                        ② "通知 → 拉"多一跳（L4 转发能省掉）
```

## 5. 我们**比它们强**的地方（结构性的，不是努力能追平的）
```text
① **可自建 / 可私有**（单文件、零依赖）⇒ 数据不出自己机房
② **个人版根本不经过服务器**（设备直连）⇒ 隐私强于任何云文档
③ **离线可用**（本地优先）
④ **客户端开源（AGPL）** ＋ 服务端独立商业授权 ⇒ 可审计、可退出
⑤ **不做"服务端懂内容"的事** ⇒ 不需要为"能不能搜内容"做取舍
```

## 6. 我们**比它们弱**的地方（诚实）
```text
① **扇出 N²** ⇒ 单空间容量小一个量级（≈100 vs 它们的量级）
② **延迟慢半拍**（0.4~1s vs 100~300ms）
③ **没有"文档"这个服务端单元** ⇒ 不能做文档级的路由/渲染/导出
④ **企业功能面窄**（水印、密级、DLP、跨空间检索… 这些要求服务端读内容）
⑤ **成熟度**：它们多年运维，我们是新的
```

## 7. 而**我们的差距都能追**（今天的分析已经算清了）
```text
① 延迟：**增量 ＋ 先发后落库 ＋ L4c 转发** ⇒ 接近 100~300ms （见 `wps-scale-roadmap` A 阶段）
② 容量：**L1 只读不订阅（10 倍）** ⇒ **按页订阅（降阶，到万级）**（B 阶段）
③ 横向：**连接与数据分离 ＋ 按空间分片**（C 阶段）
⇒ ⚠️ 而每一步都要**不破 E2E/可自建**这条底线 ⇒
   所以"按页订阅"必须用**页级不透明键**（那是 E2E 与万级并存的唯一办法）。
```

## 8. 一句话
```text
**我们和它们不是同一类东西：**
  · 它们是**SaaS**（服务端懂内容 ⇒ 快、能扩、功能多；代价是明文在云、不能自建）
  · 我们是**可私有组件**（服务端不懂内容 ⇒ 隐私强、可自建、离线好；代价是 N² 扇出 ＋ 慢半拍）
⇒ 而**我们的差距是可追的**（增量／先发后落库／L4c／按页订阅），
  代价是**必须用不透明键这类手段**（不能靠"让服务端读内容"抄近路 —— 那会破 E2E 与许可边界）。
```
