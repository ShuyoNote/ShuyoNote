# ShuyoNote 产品评价（全面）

> 基于对 ShuyoNote 的深度接触（架构、同步、多端、打磨、一系列 bug 与修复）给出的诚实评估。
> 结论不吹不黑：**架构相当出色、功能密度很高，但「稳定与打磨」仍在爬坡**。

## 一句话定位

一个**本地优先的桌面级生产力工具**：Tauri 2 + Lexical + SQLite，全平台（桌面 / 浏览器 / 鸿蒙 ArkWeb），数据在本机、离线可用。底子、理念、技术选型都是同级里很能打的一档；短板集中在**健壮性 / 一致性**与**自托管同步的工程细节**上。

## 一、亮点（强项）

1. **本地优先，数据归你**：数据完全在本机、离线可用；与 Notion / Obsidian 差异化清晰。
2. **功能密度高**：块编辑器、数据库（表格/看板/日历/画廊/目录/时间线/甘特图）、原生甘特图、PDF 批注（双引擎 + OCR + AI 帮读 + 目录生成）、公式、绘图、模板、多工作空间、文件夹=网盘、属性、双链/反链、AI 助手 + 语义检索——做到「桌面级工具链」而非「单编辑器」。
3. **架构分层干净**：平台无关 core + 可插拔 driver（桌面 Rust / 浏览器 Web）；命令契约层（`CommandMap` 编译期校验）；读写分离 + 只读连接池 + 流式附件。设计是「能长大的那种」。
4. **加密与隐私**：个人空间 E2E、附件静置加密、内容寻址去重；安全审计文档详实。
5. **产品化意识好**：帮助系统、免费出口（静态站）、竞品对比、设计系统、UX 流程文档齐全——很多小产品没有。

## 二、短板（诚实说）

1. **同步健壮性是最大痛点**（历史暴露的一串）：
   - 早期 `device_seq` 全 0 → 变更被去重合并；
   - Web 端旧附件 **FNV(16 位) 与 SHA-256(64 位) 不一致** → 上传 400，需靠「一次性迁移 + 上传自愈」兜底；
   - 桌面 `sync.rs` 把 **`.part` 临时文件当附件上传** → 哈希不匹配 400；
   - `/attachment` 单数缺 hash 的旧 URL、413 体积上限、FK 顺序、并发幂等。
   - 这些不是功能 bug，而是**一致性边界没堵严**。多设备同步的可信度还没到「写完就放心」。
2. **自托管同步精度**：单写者在 `Mutex` 下（读靠只读池）；**无 CORS** → 浏览器只能同源；附件按空间隔离但缺「增量断点/校验和」（下载中断整块重下）。
3. **Web 平台的内存天花板**：Web 用 sql.js（整库进内存）+ IndexedDB Blob；附件读写虽已流式化，但**整库快照**在大工作区仍是瓶颈——**桌面才是「完整体」**。
4. **迭代节奏**：v1.82.x 更新频繁；bug 靠用户触发 + 逐个修，**缺一个「回归测试 / 升级自检」关口**（`smoke-web.mjs` 等部分补强）。

## 三、技术选型判断

- **Lexical**（vs ProseMirror/Tiptap）：做块编辑器正确且性能好，但生态小、表格/协同要自己写；对「桌面笔记」够用，对「在线协同」偏吃力。
- **Tauri 2**：体积 / 性能 / 安全边界优于 Electron，是「全平台」关键。
- **自研同步协议**（push/pull + content-addressed 附件）：方向对（简单、去重、离线友好），但缺心跳 / 冲突展示 / 增量校验；近实时仍在规划。

## 四、总体建议（按优先级）

1. **先稳同步**：把 device_seq / 哈希一致性 / `.part` / 断点整理成一套「迁移 + 幂等 + 校验」程序，加一个跨设备回归脚本，避免单点补丁。
2. **文档化自托管**：把 2TB 上限、`--max-body-mb`、增量 / 去重、常见 400 / 413 排查写成部署手册。
3. **打磨节奏**：统一历史遗留的 z-index / 弹窗 / 图标 / 层级（已做一部分），减少「看起来差一点」的观感。
4. **明确定位**：**桌面是主线**，Web 是「可看可轻度编辑」；别拿 Web 当同步主力。

## 五、一句话结论

**作为「本地优先的桌面级生产力工具」，ShuyoNote 已完成度很高、架构扎实、值得用**；但**作为「要放心的多设备同步工具」，还有一段一致性 / 稳定性要补**。它上限很高，当下最值得投资的是**同步的可信度与回归**，而非再堆新功能。
