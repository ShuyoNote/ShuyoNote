# 基于 Web 版开发鸿蒙桌面应用：能力边界（天花板）分析

> 关于把 ShuyoNote 的 **Web 版** 套进 **鸿蒙 ArkWeb 壳** 的能力上限。
> 关键认知：**任何 WebView 壳都不改变内核是浏览器**。

## 一句话结论

**用 Web 版做鸿蒙桌面应用，天花板 =「浏览器沙箱」本身**。ArkWeb（鸿蒙 WebView，类似 Tauri 的 WebView2）只是把 Web 应用包进容器，**不能突破 Web 版固有限制**——拿到的是「浏览器级」应用，不是桌面级。真正决定天花板的是**有没有一座「原生桥」**。

## 能拿到的（Web 能力都能用）

编辑、数据库视图、AI、语义检索、PDF（pdf.js）／OCR（tesseract WASM）、公式、绘图、预览、多工作区、自托管同步（**前提：同源或服务端加 CORS**）——这些纯 JS/WASM 能力在 ArkWeb 里都能跑。

## 天花板具体在哪（浏览器沙箱的硬约束）

| 维度 | 桌面（Tauri native） | Web / 鸿蒙 ArkWeb 壳 | 说明 |
|---|---|---|---|
| **数据库** | 原生 SQLite（rusqlite） | **sql.js（WASM 内存 SQLite）+ IndexedDB** | 整库快照进内存，**大工作区内存天花板**；查询性能远不如原生 |
| **文件系统** | 真实磁盘文件、原生保存对话框 | **沙箱内 IndexedDB Blob、无真实路径** | 不能存任意路径、不能读系统文件；`dialog.save` 只是拿个默认名 |
| **原生引擎** | 原生 **mupdf**（PDF）+ 原生 tesseract | pdf.js + tesseract **WASM** | 大 PDF/OCR 更慢、更吃内存 |
| **加密 / 密钥** | OS 安全存储 + 归档静置加密（Rust） | 仅 JS 层 | 拿不到 OS Keychain |
| **系统集成** | 协议 `asset://`/`attachment://`、通知、托盘、关联文件、拖放、菜单、更新器 | **无** | ArkWeb 里都没有 |
| **同步** | reqwest 直连任意服务器 | **fetch，服务端无 CORS → 只能同源** | 鸿蒙 App 若从别的源加载 web，跨源同步被拦；要么加 CORS，要么用同源代理 |
| **插件 / 薄 agent** | 原生插件宿主 + 受限 Agent | 基本缺 | — |

## 两条路线（决定天花板）

- **路线 A：纯 Web 套壳（无原生桥）** = 相当于一个**高质量 PWA**。内容能力强，但卡在沙箱：内存 DB、无真实文件 / 原生对话框 / 原生 PDF OCR / 系统集成、同步受 CORS 限制。**最低天花板**。
- **路线 B：加一座「鸿蒙原生桥」**（ArkTS ↔ JS invoke，类似 Tauri 的 `invoke`）——把 Web 应用想要的原生能力（原生 SQLite、文件系统、对话框、通知、OS 密钥）用 ArkTS/NDK 暴露给 JS。能**逼近桌面能力**，但本质是**把 Tauri 的 Rust 命令用 ArkTS 重写一遍**，是**显著的原生开发投入**，不是「套壳」能到的。

> 关键认知：**任何 WebView 壳都不改变内核是浏览器**。Tauri 桌面之所以强，靠的不是 WebView，而是**那层 Rust↔JS 的桥**。把 Web 塞进 ArkWeb 而没有对应的 ArkTS 桥，就只继承了浏览器的约束。

## 对 ShuyoNote 的具体建议

- **适合 Web / 鸿蒙壳做的事**：查看、轻度编辑、读 PDF、用 AI、当「移动 / 轻量端」。**值得做**（低门槛、复用现有 Web 前端）。
- **不适合用 Web / 鸿蒙壳做的事**：当**大工作区 / 大附件 / 重型 PDF 批注**主力（内存 + 原生引擎天花板），以及需要真实文件系统 / 系统集成的场景（导出到磁盘、文件关联、托盘）。
- **若鸿蒙桌面要当「正式桌面端」**：走**路线 B**，把最常缺的原生能力（SQLite、文件对话框、导出）做成 ArkTS bridge，否则它始终是「浏览器里的笔记」，不是「桌面笔记」。

## 值不值得？

- **只是想在鸿蒙上用** → 路线 A 足够（已在本地用 nginx 同源代理解决 web 同步）。
- **想在鸿蒙上给「原生桌面体验」** → 有，但要为**原生桥**投入；对个人产品，先确认鸿蒙用户的量级，再决定要不要把 Tauri 的命令做到 ArkTS。
