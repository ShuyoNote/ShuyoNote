# Web 版为什么不提供多设备同步（平台能力边界）

> 结论先行：**Web 版不提供多设备同步是「产品决定」（2026-09-15 裁定），不是「没有实现」。**
> 恰恰相反——`src/lib/platform/web.ts` 里**已经有一套 TypeScript 版同步引擎**（见 §1、§2.2）。
> 不提供的原因有三层真实约束：服务端**默认不开 CORS**（§2.1，同源反代可绕过）、
> **浏览器存储会被系统回收**（不适合当唯一副本）、以及**凭证与密钥的信任边界**（§2.4）。
>
> ⚠️ **2026-09-15 按代码修订**：本文原文写"**不是『关掉了』，是 Web 侧根本没有实现同步引擎**"、
> "这些**没有一行跑在 Web driver 上**"——**与代码相反**，已改正。产品决定同时明确：
> **现有 web 同步代码保持、不要删**（删了平台层不完整，口径也会退回错的）。
> 相关：[系统架构](architecture.md) · [Web 补齐清单](plans/2026-08-24-web-polish-backlog-plan.md) · 团队版方案（私有仓库 `shuyonote-sync-server`） · [身份与隐私模型](identity-privacy-model.md)

## 1. 用户可见的表现（与代码的实际状态）

| 入口 | 现象 |
|---|---|
| 同步面板（`SyncPanel`） | 在**非 Tauri 平台**（含桌面浏览器与手机浏览器）配置区整体**置灰、不可交互**（`SyncPanel.tsx:523` + `App.css:1222-1227` 的 `pointer-events: none`），并提示「**建议使用桌面版以获得稳定多设备同步；Web 版同步受浏览器环境限制**」（`SyncPanel.tsx:502`） |
| 同步 / 团队命令 | **不是桩**：`web.ts` 的 `list_sync_profiles`(:2539) / `set_sync_profile`(:2540，含登出清 token) / `sync_now`(:2447) / `sync_workspace`(:2559，带进度上报) / `team_*`(:2464+，真的打 `/auth/register` 等) **全是真实现** |
| 实际能不能连上 | **默认连不上**——服务端不挂 CORS 层（见 §2.1），浏览器里的 `fetch` 连 `OPTIONS` 预检都过不去；除非把服务端反代到同源路径 |
| 唯一真会抛错的桩 | **聚合邮箱**（`web.ts:1119-1122`：「聚合邮箱仅桌面版支持」）——那是桌面专属能力，**与同步无关** |

> ⚠️ **为什么"有实现"却"不提供"**：这是**产品决定**（2026-09-15：Web 版不开多设备同步、
> **现有 web 同步代码保持**）。所以口径是「**不提供**」，而**不是**「是 stub / 没实现」——
> 后者与代码相反，还会诱使下一个人把真实存在的实现当死代码删掉。
> 代码侧的完整说明见 `web.ts` 里 `sync_now`(:2447) 上方那段注释。

## 2. 四层原因

### 2.1 同步服务端刻意不带 CORS 层（配置层，可绕过）

`shuyonote-sync-server/src/main.rs:477-478` 在路由组装处写明：不挂 CORS layer，因为桌面客户端走
Rust `reqwest`（没有浏览器 origin 概念），**默认拒绝跨源是安全基线**。

⚠️ **该注释的理由有半句已过时**：它写的是 "the Web build's sync is a stub"，而 Web 侧**是有实现的**
（§1、§2.2）——**但它导出的决定仍然成立**：Web 版不提供多设备同步（产品决定），跨源默认拒绝照旧；
理由应表述为「产品上不提供 Web 同步 + 默认拒绝跨源是安全基线」。

结果是浏览器里任何指向同步服务端的 `fetch` 连预检 `OPTIONS` 都过不去——
**这是"即使绕过置灰的 UI 也同步不了"的那道真实闸门**。
（团队版 M27 客户端把登录 / 空间 / 成员做成 **Rust 代理命令**（`team_login` / `team_list_spaces` / …）
是同一层原因的另一面：桌面 WebView2 同样受同源策略约束，必须由 Rust 侧发 HTTP 绕开，与 `ai.rs` 同一模式。）

> 这一层可以不靠放开跨源来解决：把同步服务端反代到 Web 站点的**同源路径**（如 `/sync/` → `127.0.0.1:8787`），浏览器眼里就是同源请求。**属于建议，尚未实施。**

### 2.2 同步引擎有**两份**实现（Rust 与 TypeScript），不是"只有 Rust"

桌面同步的全部逻辑在 `src-tauri/src/sync.rs`：`do_push` / `do_pull`（`change_log.seq` 游标 +
`sync_profiles` 的 `last_pushed_seq` / `last_pulled_seq`）；`sync_attachments`（按内容寻址双向补齐、
`.part` 临时文件、hash 合法性校验防路径穿越、可选落盘加解密）；页级 LWW + 墓碑。

**但 Web 侧也有一套等价实现**（`src/lib/platform/web.ts`，同为 outbox + 游标模型）：
`doPush`(:827)、`doPull`(:844)、`syncAttachments`(:896)——把远端缺失的字节拉进
**IndexedDB blob store**（内容寻址、按 hash 校验），并有独立的进度上报（`useSyncStatus`）。

> ⚠️ **（2026-09-15 修订）** 本节原文写"这些**没有一行跑在 Web driver 上**……Web 要同步不是
> 『打开开关』，而是用 TypeScript 重写一份等价引擎"——**与代码相反**。
> 现在真正要注意的不再是"有没有实现"，而是**两份实现的语义差异**（游标推进、附件范围、
> 错误处理是否对称），那才是将来若要开放 Web 同步时必须先对齐的东西。

### 2.3 存储模型不同，协议无法直接搬（实现层）

| | 桌面 | Web |
|---|---|---|
| 数据库 | rusqlite 真事务，每空间一个 SQLite 文件 | sql.js 整库镜像持久化进 IndexedDB |
| 多空间 | 物理隔离（`spaces/<ws_id>/`） | 每空间一份 DB 快照 + restore 切换 |
| 附件字节 | 内容寻址文件目录，跨空间去重 | IndexedDB blob store |
| 大文件 | 无硬上限 | 单文件 50MB 以上直接拒绝（内存约束） |

同步协议按「增量 change_log + 按 hash 传附件」设计，落到 Web 需要解决：IndexedDB 事务里的增量应用与回滚、快照切换与同步游标的关系、blob 分片/流式上传、断点续传、以及大文件在整库快照模型下的内存峰值。**这些不是"待实现"，而是"已有实现里需要复核与对齐的部分"**——`web.ts` 的 TS 引擎已经把这些走过一遍（§2.2）；将来若要开放 Web 同步，重点是与桌面语义**逐条对齐并验证**，不是从零写。

### 2.4 凭证与加密的信任边界不同（安全层）

- 桌面：会话 token 存在 meta 库的 `auth_sessions` 表（按服务器一条），渲染层拿不到持久副本；at-rest 加密密钥同样由 Rust 侧持有。
- Web：只能放 IndexedDB / localStorage，**一次 XSS 即等于长期团队凭证失窃**。

个人空间的 E2E 加密同理——密钥留在浏览器里，与「本地优先、数据不出本机」的定位是两个风险档次。团队版本身已明确放弃零知识（口径以[数据可见边界](sync-server-data-boundary.md) §0.5 为准；服务端侧详见私有仓库 `shuyonote-sync-server` 的 `docs/plans/2026-08-30-team-edition-plan.md`），但那是**在桌面的前提下**做的取舍，不等于可以直接平移到浏览器。★ 另有一条**待定**：加密的**个人空间**在 Web 上应表现为「**不可同步、不可编辑**」（见[加密作用域决策稿](plans/2026-09-23-encryption-scope-decision.md) §3 第 4 步与 §7.1），**不许**悄悄降级成明文上传。

## 3. 现状不是缺陷，是声明过的边界

[Web 补齐清单](plans/2026-08-24-web-polish-backlog-plan.md) 已把**加密 / 同步 / 插件**三项归为「平台能力边界」，不在功能补齐范围内；[结构性改进立项](plans/2026-09-01-structural-backlog-plan.md)顺带完成了这三处入口的**显式降级提示**（SyncPanel / ThemeSettings / PluginManager）。

**2026-09-15 产品裁定（本节的正式依据）**：**Web 版不开多设备同步；现有 web 同步代码保持。**

⇒ 三条口径：① 对外用「**不提供**」；② **不许**写"是 stub / 没实现"（与代码相反，
`web.ts` 的引擎是完整的）；③ **代码按决定保留**——不要因为"Web 不提供同步"就把那套引擎当死代码删掉。

Web 版当前的定位是：**同一份前端、真实 SQLite 能力、离线可用的单设备笔记环境**。跨设备的数据交换走**备份 / 导出 zip**（`export_backup` / `import_backup`，与桌面格式互认），而不是实时同步。

## 4. 如果将来要开放，还缺什么

**先说结论：W1–W3 那类"引擎本身"的工作，`web.ts` 里已经做过一遍**（§2.2）。
所以缺的不再是"写引擎"，而是下面四件事：

| # | 缺什么 | 判据 / 说明 |
|---|---|---|
| ① | **改产品决定** | 置灰是当前唯一的入口闸门（`SyncPanel.tsx:523` + `App.css:1222-1227`）；放开它 = 改决定本身（2026-09-15 已裁定：不开） |
| ② | **同源反代**（配置层，可绕过） | 服务端默认不开 CORS（§2.1）⇒ 浏览器里连不上。把同步服务端反代到 Web 站点的同源路径即可，**不需要为浏览器放开跨源白名单** |
| ③ | **短时凭证**（安全层） | 短 TTL token + 刷新，或同源 `HttpOnly` Cookie 会话——**不要把长期 bearer 落在 IndexedDB** |
| ④ | **两份实现语义对齐**（最容易被低估） | 游标推进、附件范围、错误处理是否对称——Rust 与 TS 两套要逐条比对并验证 |

**唯一仍属"要新做"的是 W4（冲突与并发）**：页级 LWW 对齐桌面语义；再谈是否升级 CRDT。

明确**不做**的：为 Web 单独设计一套协议（必须与桌面同协议，否则两端各写一套语义）；把团队长期凭证常驻浏览器；为绕过存储/内存限制做整库常驻内存的大附件方案。

## 5. 一句话版本

> Web 版不提供多设备同步，是**产品决定**，**不是"没实现"**——`web.ts` 里那套 TypeScript 同步引擎是完整的
> （outbox + 游标 + IndexedDB 附件字节）。真正挡住它的是三件事：**服务端默认不开 CORS**（浏览器里连不上）、
> **浏览器存储会被系统回收**（不适合当唯一副本）、**凭证与密钥放浏览器是另一个风险档次**。
> 要真开放，先把服务端反代到同源，再把两份实现的语义逐条对齐。
