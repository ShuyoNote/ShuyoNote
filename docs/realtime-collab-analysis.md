# 实时协同（Real-time Collaboration）利弊分析

> 定位：评估 ShuyoNote 是否 / 何时引入「多人同页实时协作编辑」。为团队版后续「实时协同（P2 后置项）」提供决策依据。
> 关联：[团队版方案](plans/2026-08-30-team-edition-plan.md) · [身份与隐私模型](identity-privacy-model.md) · [同步服务端](SYNC.md)

---

## 1. 背景与现状基线

ShuyoNote 目前的多设备同步是**离线优先、可容忍延迟**模型：

| 维度 | 当前实现 |
|---|---|
| 同步机制 | outbox 变更日志 + push/pull；**页级 LWW（最后写者胜）** |
| 频率 | 手动「同步」+ 自动轮询（用户可配 10s ~ 5min） |
| 冲突策略 | 页级 LWW —— 后到覆盖，**非字段/块级合并** |
| 附件 | 内容寻址（SHA-256），字节走 `/spaces/{space}/attachments/{hash}` |
| 客户端 | 本地 SQLite（每空间独立库），离线可读写 |
| 隐私 | 个人空间端到端加密；团队空间服务端可见明文（已定：放弃零知识） |

这个模型的好处是**离线可用、自建简单、网络差也稳**；代价是**多人同改同一页会互相覆盖**，且改动最多等一轮轮询才可见。

「实时协同」就是要解决这两个短板：**实时可见** + **同页不互相覆盖**。

---

## 2. 先区分两种档次（成本差一个数量级）

- **A. 近实时（低成本，推荐近期做）**
  看到「谁在编辑 / 在线状态」，改动即时可见，评论/@ 触达，同页冲突时给**提示**而非静默覆盖。
  复用现有 push/pull，只把轮询间隔调小 + 加在线状态/提示即可，拿回大部分协作价值。

- **B. 块级实时协作编辑（高成本）**
  两人**同页同块实时合并**（块级 CRDT 或 OT），光标/选区/操作流实时同步，WebSocket 长连接。
  这是「再写一个协作引擎」，和现有 LWW + changes 序列是**两套不同的同步模型**。

---

## 3. 好处（Pros）

1. **对标一线竞品**：Notion 团队版 / 语雀 / 飞书知识库都是实时协同；没有它，团队版在演示与客户预期上明显弱一档。
2. **不再丢内容**：块级合并解决「两人同改一页互相覆盖」；当前页级 LWW 只能后者覆盖前者，真实团队场景会丢改动。
3. **实时感知**：在线状态、正在编辑提示、光标/评论触达，协同体验顺很多。
4. **即时可用**：改动立刻出现在别人屏幕，不用等一轮轮询。

---

## 4. 代价与风险（Cons）

### 4.1 工程量极高，富块更难
ShuyoNote 是**自由块编辑器**，且有多种自定义/富块：数据库视图、看板/甘特图、图表、PDF 批注、公式、双链/块嵌入。
CRDT 对**纯文本段落**尚可；对这些富块做块级合并，几乎是再做一个协作引擎，成本陡增。

### 4.2 服务端负担 + 自建成本
块级实时需要 **WebSocket 长连接 + 协作状态机 + 断线重连/重同步 + 横向扩展**。
当前 sync-server 是**单机 SQLite + 短请求**（push/pull/附件），要新增一套长连接层，私有化部署与运维成本明显上升。

### 4.3 离线优先 × 实时并存，两套机制打架
ShuyoNote 核心是**本地优先、可离线编辑**。
- 在线看到别人 → WebSocket；
- 离线本地改 → CRDT 合并 + 本地操作日志。
**离线 CRDT 与实时状态机两套引擎并存**，断线、并发、合并的正确性验证是已知最难的区间。

### 4.4 与端到端加密矛盾
块级合并需要服务端**看到操作明文**才能协调多端。
团队空间已放弃零知识（明文 OK）；但**个人空间保留 E2E**——若个人空间也要实时协同，则与 E2E 冲突。这是比「功能」更深的取舍（见 [身份与隐私模型](identity-privacy-model.md)）。

### 4.5 非团队购买点核心
项目已明确：团队版核心是**共享 + 权限 + 评论 + 通知 + 私有化部署**（见 [团队版方案](plans/2026-08-30-team-edition-plan.md)）。
实时协同被定为「**看起来该有、实际高成本低频**」的后置项（P2）。客户真正付费的是**数据不出去 + 权限审计 + 能自建**，而非「同页实时打架」。

### 4.6 迁移与兼容
现架构围绕 LWW + changes 序列设计；引入 CRDT 是新的写入模型，要么与 LWW 共存（两套冲突逻辑），要么替换（破坏既有同步数据与客户端升级路径）。

---

## 5. 技术方案与成本估算（简述）

| 方案 | 技术 | 成本 | 说明 |
|---|---|---|---|
| 近实时 | 缩短轮询 + 在线状态/冲突提示 | 低（半天~2 天） | 复用现有 push/pull |
| 页级 LWW + 冲突提示 | 保留 LWW，加「两人同改」检测/提示 | 低 | 不合并，但不再静默丢 |
| 块级 CRDT（最小） | Yjs/Automerge + WebSocket | 高（数周~数月） | 只对纯文本段落做 |
| 富块 CRDT | 逐类块定制合并 | 极高 | 数据库视图/看板/图表/PDF/公式等 |

---

## 6. 与现状架构 / 隐私的冲突点（小结）

1. **LWW ↔ CRDT**：两套冲突模型需并存或替换。
2. **离线优先 ↔ 实时在线**：两套引擎并存，验证难。
3. **E2E（个人空间）↔ 服务端明文协作**：块级合并需明文，个人空间冲突。
4. **富块 ↔ 块级合并**：非文本块难以通用合并。
5. **单机自建 ↔ WebSocket 横向扩展**：部署/运维复杂度上升。

---

## 7. 结论与建议（分阶段，别一把梭）

- **近期（推荐）**：不做块级 CRDT。先把 **A（近实时）** 做扎实：
  自动同步间隔可选更小 + **在线状态/「正在编辑」提示 + 评论/@ 触达 + 同页冲突提示**。低成本拿回大部分团队协作价值。
- **中期**：若确有「多人在同一页实时写」需求，先做**页级 LWW + 冲突提示/手动保留**，验证真实需求，再评估是否值得上 CRDT。
- **长期（有条件才做）**：只有当「实时同页编辑」成为明确购买点，再上**纯文本块的最小 CRDT（Yjs/Automerge）+ WebSocket 层**；富块/自定义块用「锁或最后写者胜」降复杂度。且**只对团队空间开放**，个人空间维持 E2E，避免隐私冲突。

### 一句话
- 定位「**私有化自建团队知识库**」→ 实时协同是**加分项不是门槛**，近实时 + 评论/通知/权限已能打；不建议现在上块级 CRDT。
- 定位对标 Notion/语雀/飞书 → 实时协同是竞争力一部分，但**成本极高、与离线优先 + E2E 冲突**，应在付费信号明确后再投入（P2）。

## 8. 决策记录 / 待定项

| 项 | 状态 |
|---|---|
| 是否上块级 CRDT | ❌ 现阶段不做（P2 后置，需付费信号） |
| 是否先做近实时 | ✅ 建议近期做（在线状态/冲突提示/评论触达） |
| 个人空间是否参与实时协同 | 不；个人空间保留 E2E |
| 富块合并策略 | 用「锁 / 最后写者胜」，不做块级 CRDT |
