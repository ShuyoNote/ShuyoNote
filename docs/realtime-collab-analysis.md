# 实时协同（Real-time Collaboration）利弊分析

> 定位：评估 ShuyoNote 是否 / 何时引入「多人同页实时协作编辑」。为团队版后续「实时协同（P2 后置项）」提供决策依据。
> 关联：团队版方案（已移入私有仓库 `shuyonote-sync-server` 的 `docs/plans/2026-08-30-team-edition-plan.md`） · [身份与隐私模型](identity-privacy-model.md) · [同步服务端](SYNC.md)

---

## 1. 背景与现状基线

ShuyoNote 目前的多设备同步是**离线优先、可容忍延迟**模型：

| 维度 | 当前实现 |
|---|---|
| 同步机制 | outbox 变更日志 + push/pull；**服务端 `seq` 为权威序 + dirty 优先本地**（v1.84.3） |
| 频率 | 手动「同步」+ 自动轮询（用户可配 10s ~ 5min） |
| 冲突策略 | **服务端 seq 基准 + dirty 优先本地** —— 本地有未同步改动（dirty）优先保留，不再静默被覆盖；无 dirty 时按服务端 seq LWW。**非字段/块级合并**（见 [seq-LWW 方案](plans/2026-09-09-sync-seq-lww.md)） |
| 附件 | 内容寻址（SHA-256），字节走 `/spaces/{space}/attachments/{hash}` |
| 客户端 | 本地 SQLite（每空间独立库），离线可读写 |
| 隐私 | 个人空间端到端加密；团队空间服务端可见明文（已定：放弃零知识） |

这个模型的好处是**离线可用、自建简单、网络差也稳**；代价是**多人同改同一页仍会覆盖（只是 dirty 优先保护了"未同步"的那份）**，且改动最多等一轮轮询才可见。

「实时协同」就是要解决这两个短板：**实时可见** + **同页不互相覆盖**。

---

## 2. 先区分两种档次（成本差一个数量级）

- **A. 近实时（低成本，推荐近期做）**
  看到「谁在编辑 / 在线状态」，改动即时可见，评论/@ 触达，同页冲突时给**提示**而非静默覆盖。
  复用现有 push/pull，只把轮询间隔调小 + 加在线状态/提示即可，拿回大部分协作价值。

- **B. 块级实时协作编辑（高成本）**
  两人**同页同块实时合并**（块级 CRDT 或 OT），光标/选区/操作流实时同步，WebSocket 长连接。
  这是「再写一个协作引擎」，和现有 LWW + changes 序列是**两套不同的同步模型**。

---

## 3. 好处（Pros）

1. **对标一线竞品**：Notion 团队版 / 语雀 / 飞书知识库都是实时协同；没有它，团队版在演示与客户预期上明显弱一档。
2. **不再丢内容**：块级合并解决「两人同改一页互相覆盖」；当前页级 LWW 只能后者覆盖前者，真实团队场景会丢改动。
3. **实时感知**：在线状态、正在编辑提示、光标/评论触达，协同体验顺很多。
4. **即时可用**：改动立刻出现在别人屏幕，不用等一轮轮询。

---

## 4. 代价与风险（Cons）

### 4.1 工程量极高，富块更难
ShuyoNote 是**自由块编辑器**，且有多种自定义/富块：数据库视图、看板/甘特图、图表、PDF 批注、公式、双链/块嵌入。
CRDT 对**纯文本段落**尚可；对这些富块做块级合并，几乎是再做一个协作引擎，成本陡增。

### 4.2 服务端负担 + 自建成本
块级实时需要 **WebSocket 长连接 + 协作状态机 + 断线重连/重同步 + 横向扩展**。
当前 sync-server 是**单机 SQLite + 短请求**（push/pull/附件），要新增一套长连接层，私有化部署与运维成本明显上升。

### 4.3 离线优先 × 实时并存，两套机制打架
ShuyoNote 核心是**本地优先、可离线编辑**。
- 在线看到别人 → WebSocket；
- 离线本地改 → CRDT 合并 + 本地操作日志。
**离线 CRDT 与实时状态机两套引擎并存**，断线、并发、合并的正确性验证是已知最难的区间。

### 4.4 与端到端加密矛盾
块级合并需要服务端**看到操作明文**才能协调多端。
团队空间已放弃零知识（明文 OK）；但**个人空间保留 E2E**——若个人空间也要实时协同，则与 E2E 冲突。这是比「功能」更深的取舍（见 [身份与隐私模型](identity-privacy-model.md)）。

### 4.5 非团队购买点核心
项目已明确：团队版核心是**共享 + 权限 + 评论 + 通知 + 私有化部署**（见私有仓库 `shuyonote-sync-server` 的 `docs/plans/2026-08-30-team-edition-plan.md`）。
实时协同被定为「**看起来该有、实际高成本低频**」的后置项（P2）。客户真正付费的是**数据不出去 + 权限审计 + 能自建**，而非「同页实时打架」。

### 4.6 迁移与兼容
现架构围绕 LWW + changes 序列设计；引入 CRDT 是新的写入模型，要么与 LWW 共存（两套冲突逻辑），要么替换（破坏既有同步数据与客户端升级路径）。

---

## 5. 技术方案与成本估算（简述）

| 方案 | 技术 | 成本 | 说明 |
|---|---|---|---|
| 近实时 | 缩短轮询 + 在线状态/冲突提示 | 低（半天~2 天） | 复用现有 push/pull |
| 现有 seq-LWW + dirty 优先 + 冲突提示 | 保留当前 seq-LWW/dirty 语义，加「两人同改」检测/提示 | 低 | 不合并，但不再静默丢（dirty 已保护未同步） |
| 块级 CRDT（最小） | Yjs/Automerge + WebSocket | 高（数周~数月） | 只对纯文本段落做 |
| 富块 CRDT | 逐类块定制合并 | 极高 | 数据库视图/看板/图表/PDF/公式等 |

---

## 6. 与现状架构 / 隐私的冲突点（小结）

1. **LWW ↔ CRDT**：两套冲突模型需并存或替换。
2. **离线优先 ↔ 实时在线**：两套引擎并存，验证难。
3. **E2E（个人空间）↔ 服务端明文协作**：块级合并需明文，个人空间冲突。
4. **富块 ↔ 块级合并**：非文本块难以通用合并。
5. **单机自建 ↔ WebSocket 横向扩展**：部署/运维复杂度上升。

---

## 7. 结论与建议（分阶段，别一把梭）

- **近期（推荐）**：不做块级 CRDT。先把 **A（近实时）** 做扎实：
  自动同步间隔可选更小 + **在线状态/「正在编辑」提示 + 评论/@ 触达 + 同页冲突提示**。低成本拿回大部分团队协作价值。
- **中期**：若确有「多人在同一页实时写」需求，先做**页级 LWW + 冲突提示/手动保留**，验证真实需求，再评估是否值得上 CRDT。
- **长期（有条件才做）**：只有当「实时同页编辑」成为明确购买点，再上**纯文本块的最小 CRDT（Yjs/Automerge）+ WebSocket 层**；富块/自定义块用「锁或最后写者胜」降复杂度。且**只对团队空间开放**，个人空间维持 E2E，避免隐私冲突。

### 一句话
- 定位「**私有化自建团队知识库**」→ 实时协同是**加分项不是门槛**，近实时 + 评论/通知/权限已能打；~~不建议现在上块级 CRDT~~（⚠️ **这半句已被 §9 取代**）。
- 定位对标 Notion/语雀/飞书 → 实时协同是竞争力一部分，但**成本极高、与离线优先 + E2E 冲突**，应在付费信号明确后再投入（P2）。

### 9.1 已经变了的事实（都可在仓里复核）

| 当时的判断 | 现在 |
|---|---|
| 块级 CRDT「高成本（数周~数月），P2 后置」 | **客户端两侧已落地**：每页状态落盘（`page_crdt`）＋ 编辑器绑定 ＋ 推/收两侧都消费 `crdt_state`（桌面亦然）。见[全上线冲刺](plans/2026-09-23-crdt-full-launch-sprint.md) §11–§14 |
| 「服务端要看得懂明文」是主要障碍 | 障碍**未消失**，但代价已量化：服务端开算的**格式层**已由 [yrs 对拍尖刺](plans/2026-09-23-yrs-interop-spike-conclusions.md) 证明可行（JS `yjs` ↔ Rust `yrs` 投影逐字节相同），**状态体积**也测了（线性 ~158 B/块、比同页 JSON 更小）；**建议暂缓**的**唯一硬理由**是与面 5（E2EE 快照）冲突 ⇒ 两者必须同批设计（见 [S5 决策稿](plans/2026-09-23-s5-server-merge-decision.md)） |
| 近实时「拿回大部分协作价值」（低成本替代） | 它**已经落地**，但**定位要改**：它不再承担"避免同页覆盖"（那是 CRDT 的活），而是**感知与讨论层** ＋ **CRDT 体验的延迟环节** |

### 9.2 近实时四件的**新定位**（这才是本文最该被人读到的部分）

| 件 | 旧定位 | **新定位** |
|---|---|---|
| 同页冲突提示（P0.1） | 止损：别静默覆盖 | ⬇️ **辅助信息**（块级合并已接手"不覆盖"；页级 LWW 残余路径仍靠它） |
| presence（P0.2） | 协同体验 | ➡️ 不变，**且更有意义**：以前"两人同页"意味着有人要被覆盖（止损场景），现在会收敛 ⇒ 它是"感知 + 讨论" |
| 评论 / @ / 通知（P1） | 触达 | ➡️ 不变：这就是团队版的付费主线（共享/权限/评论/通知） |
| **SSE 推送（P1.5）** | 锦上添花 | ⬆️ **升级**：CRDT 是**最终一致**，"改动多久可见"**就等于这个拉取延迟** |

### 9.3 两条**如实记的缺口**（2026-09-23 核对代码）

1. **桌面没有推送通道**：`src/hooks/useSyncStream.ts` 首句就是 `if (isDesktopPlatform()) return;`
   ⇒ 桌面的"近实时"实际由**轮询间隔**（用户可配 10s~5min，见 [SYNC](SYNC.md)）决定，
   而它同时就是 CRDT 合并的可见延迟。
2. **SSE 曾经订错空间**（已修）：原先挑"第一个绑定过的档案"，多工作空间用户会订到别的空间上 ——
   与 claim 那条（把本地工作空间 id 当远端 space id）是**同一类**错；现在两处共用
   `src/lib/crdt/claimScope.ts` 的 `resolveWorkspaceSyncScope` 唯一解析，并有文本级接线判据防复发。
